# Libevra · 运维上手教程（零基础）

> **这份文档假设你从来没管过服务器。**
> 它不给你一堆命令让你背，而是每一步都讲清四件事：
> **为什么做、在哪里做、成功时会看到什么、失败怎么办。**
>
> **⚠️ 想知道权威的技术事实，看 [`生产环境与运维手册.md`](生产环境与运维手册.md)。**
> 本文是"怎么上手"，那一份是"到底是什么"。
>
> 最后更新：2026-10-16。

---

## 0. 先搞懂四件事，剩下都好办

### 0.1 你的电脑和服务器是两台完全不同的电脑

| | 你的 Windows 电脑 | 云服务器 |
|---|---|---|
| 在哪 | 你桌上 | 腾讯云的机房里 |
| 关机了会怎样 | — | **网站照常运行** |
| 上面有什么 | 代码、编辑器、浏览器 | 跑着网站的四个容器 |
| 你怎么操作它 | 直接点 | **通过 SSH 隔着网络操作** |

**⚠️ 最常见的误解**：以为"我电脑关了网站就停了"。**不会。** 服务器 24 小时开着。

### 0.2 SSH 是什么

**你可以把 SSH 想成"一条通到服务器的加密电话线"。** 拨通之后，
你在自己窗口里敲的命令，实际上是在**服务器上**执行。

**怎么知道自己在哪台机器上？** 看提示符：

```
PS C:\Users\ZhuanZ（无密码）>        ← 你的 Windows
ubuntu@VM-0-15-ubuntu:~$             ← 服务器（Linux）
```

**⚠️ 这一条极其重要**：下面所有命令，**没标"服务器"的都在 Windows 上跑，
标了的必须先 SSH 进去**。搞混了会得到"命令不存在"之类的怪错。

### 0.3 容器（Docker）是什么

**把容器想成"一个装好了应用和它所有依赖的盒子"。**

Libevra 用了四个盒子：

| 盒子 | 里面是什么 | 打个比方 |
|---|---|---|
| `db` | PostgreSQL 数据库 | **账本的柜子** |
| `api` | 后端程序 | **记账的会计** |
| `web` | 网页文件 + HTTPS | **前台和门** |
| `migrate` | 建表的程序 | **装修队，干完就走** |

**⚠️ 为什么 `migrate` 干完就走是正常的**：它的工作只是"把数据库结构改成最新"，
改完就该退出。所以看到它 `Exited (0)` **不要紧张**——`0` 表示成功。

### 0.4 域名、DNS、证书

| 名词 | 是什么 | 比方 |
|---|---|---|
| **域名** | `libevra.com`，人记得住的名字 | 你家的门牌号 |
| **DNS** | 把域名翻译成 IP 地址的系统 | **电话簿**：查"libevra.com"得到 `43.161.227.152` |
| **IP** | 服务器的真实地址 | 经纬度 |
| **HTTPS 证书** | 证明"这个网站真的是 libevra.com"的东西 | **营业执照** |

**⚠️ 证书会自动续期**（Caddy 负责），你**不需要**每年手动做什么。
但目前**没填邮箱**，所以你收不到"快到期了但我续不上"的提醒。

## 1. 第一次连上服务器

### 1.1 为什么

后面所有"在服务器上"的操作，都要先连上去。

### 1.2 在哪里做

**Windows PowerShell**（开始菜单搜 PowerShell，**不需要管理员**）。

### 1.3 怎么做

```powershell
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152
```

拆开看：

| 部分 | 意思 |
|---|---|
| `ssh` | 拨号 |
| `-i ...libevra_server` | **用这把钥匙**（私钥文件） |
| `ubuntu@` | 用 `ubuntu` 这个用户登录 |
| `43.161.227.152` | 服务器的 IP |

### 1.4 成功会看到什么

```
Welcome to Ubuntu 24.04.4 LTS (GNU/Linux 6.8.0-138-generic x86_64)
...
Last login: ...
ubuntu@VM-0-15-ubuntu:~$
```

**看到 `ubuntu@VM-0-15-ubuntu:~$` 就成功了**——你现在"在"服务器上。

顺手确认一下没连错机器：
```bash
hostname && curl -s https://api.ipify.org
```
应该输出 `VM-0-15-ubuntu` 和 `43.161.227.152`。

### 1.5 失败怎么办

**先看错误信息长什么样**：

| 错误 | 意思 | 怎么办 |
|---|---|---|
| `Permission denied (publickey,password)` | 钥匙不对 / 没被服务器接受 | 见下 |
| `Connection timed out` | 连不上 | 服务器可能关机了；或安全组没放行 22 |
| `Host key verification failed` | 服务器的"指纹"变了 | 只在**你确实重装过服务器**时才 `ssh-keygen -R 43.161.227.152` |
| `No such file or directory` | 找不到钥匙文件 | 检查路径拼写；用 `Test-Path` 确认 |

**`Permission denied` 有两种完全不同的原因，用这条命令区分**：

```powershell
ssh -vv -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152 "echo ok" 2>&1 |
  Select-String 'Server accepts key|Permission denied'
```

- **有 `Server accepts key` 但后面还是 `Permission denied`**
  → 公钥装好了，问题在**你本地这把钥匙用不了**（多半是私钥有密码短语但没解锁）
  → 见 §1.6
- **完全没有 `Server accepts key`**
  → 公钥可能真的没装到服务器上

### 1.6 关于"密码短语"（passphrase）

**密码短语是给钥匙本身加的密码。** 私钥文件被人拷走了，没有密码短语也用不了。

**部署当天真实遇到过**：私钥设了密码短语，而自动登录不给它输入的机会，
于是服务器**接受了公钥却又拒绝登录**——**看起来像"公钥没装"，其实是"钥匙没解锁"**。

**两个解法，选一个**：

**解法 A：每次手动输**（适合偶尔用）
**解法 B：让 ssh-agent 帮你记着**（适合经常用）

```powershell
# 启动记账的小程序（重启电脑后要重做）
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent

# 把钥匙交给它（**只需要输一次密码短语**）
ssh-add "$env:USERPROFILE\.ssh\libevra_server"

# 之后就不用 -i 了
ssh ubuntu@43.161.227.152
```

```powershell
ssh-add -l     # 看它记着哪些钥匙
ssh-add -D     # 全部忘掉（离开共用电脑前做一次）
```

### 1.7 下次还要重复吗

**要——每次想操作服务器都要先 SSH。** 想少打几个字，可以在
`C:\Users\ZhuanZ（无密码）\.ssh\config` 里加一段：

```
Host libevra
    HostName 43.161.227.152
    User ubuntu
    IdentityFile C:\Users\ZhuanZ（无密码）\.ssh\libevra_server
```

之后 `ssh libevra` 就够了。（**这个文件现在还不存在，是我建议加的。**）

**⚠️ 退出服务器**：输入 `exit` 或按 `Ctrl+D`。

## 2. 看看网站现在活着没有

### 2.1 为什么

**接手第一件事永远是这个。** 在改任何东西之前，先知道现在的状态——
否则出了问题分不清"是我弄坏的"还是"本来就是坏的"。

### 2.2 在哪里做

**Windows 就可以**（访问的是公开网址）：

```powershell
curl.exe -s -o NUL -w "网页: %{http_code}`n" https://libevra.com/
curl.exe -s https://libevra.com/api/v1/health
```

### 2.3 成功会看到什么

```
网页: 200
{"ok":true,"service":"libellum-api","version":"0.1.0","database":"up","timestamp":"..."}
```

**关键看两个词**：
- `200` = 网页正常
- `"database":"up"` = **后端连得上数据库**（这个比 200 更重要，
  网页可能缓存着，但 `database` 是实时查的）

**⚠️ `"service":"libellum-api"` 里的 `libellum` 是历史遗留，不是拼写错误**——
那是内部标识，改了会牵动代码，收益为零。

### 2.4 失败怎么办

| 现象 | 意思 | 下一步 |
|---|---|---|
| 网页不是 200 | 网站有问题 | SSH 上去看容器（§3） |
| `database` 不是 `up` | 后端连不上数据库 | SSH 上去 `docker compose ps` 看 `db` |
| 命令直接报错连不上 | 可能你自己的网络问题 | 换个网络或用手机热点试试 |

### 2.5 下次还要重复吗

**每次接手都做一次**，10 秒的事。

## 3. 看四个容器活着没有

### 3.1 为什么

网站打不开时，**第一件事是分清"哪个盒子坏了"**。这一步就能看出来。

### 3.2 在哪里做

**服务器上**（先 §1 连上去）：

```bash
cd /srv/libevra/deploy
sudo docker compose -f docker-compose.prod.yml ps
```

**⚠️ 这两行可以合成一个快捷方式**，先设一次变量：

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"
$DC ps                      # 之后就短了
```

（**这个变量只在当前这个 SSH 会话里有效**，退出再进来要重设。）

### 3.3 成功会看到什么

```
SERVICE   STATUS                      PORTS
api       Up 28 minutes (healthy)     3000/tcp
db        Up 28 minutes (healthy)     5432/tcp
migrate   Exited (0) 24 minutes ago
web       Up 24 minutes (healthy)     0.0.0.0:80->80/tcp, ...:443->443/tcp
```

**逐行怎么读**：

| 看到 | 意思 |
|---|---|
| `api`/`db`/`web` 是 `(healthy)` | ✅ 正常 |
| `(health: starting)` | 刚启动，**等 40 秒再看** |
| `(unhealthy)` | 容器活着但健康检查不过——**看 §9** |
| `migrate` 是 `Exited (0)` | ✅ **正常**，它就是干完就走的 |
| `migrate` 是 `Exited (1)` 或别的非 0 | ❌ 迁移失败了，看它的日志 |
| `PORTS` 列里 **只有 `web`** 有 `0.0.0.0:` | ✅ 正确。**如果 `db` 或 `api` 也出现端口，说明配置被改坏了** |

**⚠️ 最容易被误判的一行**：`migrate` 显示 `Exited`。**它本来就该是 Exited。**

### 3.4 失败怎么办

**哪个不正常就看哪个的日志**：

```bash
$DC logs api --tail 50        # 把 api 换成 db / web / migrate
```

日志是**从上往下按时间**的，**看最后 20 行**通常就够了。

### 3.5 下次还要重复吗

**每次接手、每次改动后都做一次。**

## 4. 看日志

### 4.1 为什么

容器"活着"不等于"工作正常"。日志是唯一能看到它在想什么的地方。

### 4.2 在哪里做

**服务器上**。

```bash
$DC logs api --tail 50        # 最近 50 行
$DC logs -f api               # 实时跟随（Ctrl+C 退出）
$DC logs web --tail 50        # Caddy 的日志（证书信息在这里）
$DC logs api --since 10m      # 最近 10 分钟
```

### 4.3 成功会看到什么

正常的 api 日志大概长这样（很安静）：

```
api-1  | {"level":30,"time":...,"msg":"Server listening at http://0.0.0.0:3000"}
```

**⚠️ 日志区分的诀窍**：先看有没有 `"level":50`（错误）或 `"level":40`（警告）。

一键只看错误：
```bash
$DC logs api --tail 200 2>&1 | grep -iE '"level":(40|50)|error|fatal'
```

### 4.4 失败怎么办

日志里出现看不懂的英文，**把那一行复制去搜**，或者对照
[`生产环境与运维手册.md`](生产环境与运维手册.md) §11 的故障表。

### 4.5 下次还要重复吗

**出问题时才做。** 平时不用盯着。

## 5. 改完配置怎么让它生效

### 5.1 为什么

**这一节很容易搞错**：Libevra 的 Caddy 配置**不是直接读的，是启动时生成的**
（因为 Caddy 的 `email` 指令不能接受空值，会拒绝整个配置让你网站起不来）。

所以**改完必须重启容器，`reload` 不够**。

### 5.2 在哪里做

**服务器上**。

```bash
cd /srv/libevra/deploy
$DC up -d --force-recreate web
```

### 5.3 成功会看到什么

```
Container deploy-web-1  Recreated
Container deploy-web-1  Started
```

然后看它有没有渲染对：

```bash
$DC logs web --tail 10
```

正常会看到两行说明，例如：
```
web-1  | libevra: no ACME account email configured - certificates will still be issued
web-1  | libevra: www.libevra.com does not resolve - no www block added
```

**⚠️ 第二行现在是正常的**——因为 `www` 的 DNS 有个拼写错误还没修（见手册 §12.9）。
**修好 DNS 之后再重启，那一行会变成 "added a redirect"。**

### 5.4 失败怎么办

```bash
$DC ps web                      # 起来了没有
$DC logs web --tail 30          # 为什么没起来
```

如果是 Caddyfile 语法错，日志里会有 `adapting config using caddyfile` 之类的字眼。
**先改回上一版**：

```bash
cd /srv/libevra && git diff deploy/Caddyfile    # 看改了什么
git checkout deploy/Caddyfile                   # 撤销（⚠️ 会丢掉未提交的改动）
```

### 5.5 下次还要重复吗

**每次改 `Caddyfile` 或 `web-entrypoint.sh` 之后都要做。**

## 6. 备份（**最该养成习惯的一件事**）

### 6.1 为什么

**账目数据不可再生。** 手机丢了、浏览器缓存清了，服务器上的那份就是唯一副本。
备份是你唯一的退路。

**⚠️ 而且"有备份文件"不等于"备份能用"**——它可能在写的时候被截断、
可能漏了某张表、可能恢复到一半报错，**而这些只有真的恢复一次才知道**。
所以这个脚本**默认就做恢复演练**。

### 6.2 在哪里做

**服务器上**。

```bash
cd /srv/libevra/deploy
./backup.sh
```

### 6.3 成功会看到什么

```
=== Libevra 生产备份 ===
库：libevra_prod    文件：/srv/libevra/deploy/backups/libevra_prod-20261016-102804.dump

→ 导出…
✅ 备份写完：68K
→ 校验归档可解析…
✅ 归档可解析：167 个条目
→ 恢复演练：建临时库 libevra_verify_...
✅ 已恢复到临时库
✅ 行数一致（逐表比对）
🎉 这份备份验证通过，可以拿去救命。
```

**看到 `🎉` 那行才算真的成功。**
中间它会临时建一个库来演练，**练完会自动删掉**。

### 6.4 失败怎么办

| 现象 | 意思 | 怎么办 |
|---|---|---|
| `找不到 deploy/.env` | 你在错误的目录 | `cd /srv/libevra/deploy` |
| `❌ 归档条目只有 N 个` | 备份文件是空的或被截断 | 看磁盘是不是满了：`df -h /` |
| `❌ 行数不一致` | **这份备份不能拿去救命** | 别删旧的备份；查为什么（可能有写入在进行） |
| `pg_dump: error: connection failed` | 数据库容器没起 | `$DC ps db` |

### 6.5 ⚠️ 最重要的一条：本地备份不是备份策略

**同一台服务器上的备份，会和服务器一起消失。**
（服务器被删、磁盘坏、机房出事——备份跟着一起没。）

**目前还没有异地备份**（手册 §13）。等它做好之前，**要知道你现在的保护是有限的**。

### 6.6 下次还要重复吗

**要，而且要定期。** 建议配成每天自动跑（**目前还没配**）：

```bash
crontab -e
```
加一行（**记得改成你自己的时间**）：
```
17 3 * * * cd /srv/libevra/deploy && ./backup.sh >> backups/cron.log 2>&1
```
（凌晨 3:17，避开整点，免得和别人撞。）

## 7. 发布一个新版本

### 7.1 为什么

**改完代码、测试通过、推送到 GitHub——网站还是旧的。** 这是**故意的**。

**⚠️⚠️ 这一条必须记牢：GitHub 更新 ≠ 生产更新。**

中间隔着一个**人的决定**。理由不是流程洁癖：**一台服务器、一个人维护，
跟着 main 自动上线的服务意味着每一次推送都是一次没有验收的发布。**

### 7.2 在哪里做

**先在 Windows 上准备，再在服务器上发布。**

**第一步（Windows）**：确认要发布的版本已经推送且 CI 通过

```powershell
cd "C:\Users\ZhuanZ（无密码）\Desktop\工作\记账程序\记账程序v1"
git status                       # 应该干净
git log --oneline -3             # 看最近的提交
git push origin main             # 如果还没推
gh run list --limit 3            # 看 CI 结果，要 success
```

**第二步（服务器）**：让服务器上的源码变成那个版本

⚠️ **这一步现在需要小心**——服务器上的代码比仓库新（手册 §12.7）。
**推荐做法是从本机 `git archive` 打包传过去**（手册 §7.2）。

**第三步（服务器）**：发布

```bash
cd /srv/libevra/deploy
./deploy.sh --version 1.10.24
```

**⚠️ `--version` 是必填的**，不打会被拒绝执行。这是有意的：
**发布一个说不清编号的版本，等于放弃"这是哪一版"这个问题的答案。**

### 7.3 成功会看到什么

`deploy.sh` 会依次：**备份 → 构建 → 迁移 → 起服务 → 健康检查**

```
→ 发布前备份…
🎉 这份备份验证通过，可以拿去救命。
→ 构建镜像…
→ 应用迁移并启动…
→ 健康检查…
✅ 发布成功：1.10.24
   API 健康（数据库 up）、Web 健康。

⚠️ 还有两件手工确认的事：
   1. 用浏览器打开 https://libevra.com，走一遍登录与记一笔；
   2. 确认「账户 → 软件更新」显示的版本号就是 1.10.24。
```

**⚠️ 看到 ✅ 只代表"容器健康"，不代表"能用"。** 请务必做完那两件手工确认。

### 7.4 失败怎么办

**脚本会自己停下，并打印回滚路径。它不会自动回滚**——因为回滚是个判断，不是个动作。

```
❌ 健康检查未通过（API=0 Web=1）。

⚠️ 回滚应用不会回滚数据库。……
   * 只改代码的版本：切回上一个 commit，重新构建即可
   * 改了 schema 的版本：先读该迁移，判断旧代码能否在新 schema 上跑；
     不能就跑 ./restore.sh <备份文件> 把整个库恢复到发布前那一刻
```

**⚠️⚠️ 最关键的一句：回滚应用不会回滚数据库。**
迁移是只向前的，`prisma migrate deploy` **没有 `down`**。
一个删列的迁移，退回旧镜像也换不回那一列。

**这就是"发布前先备份"是第一步而不是可选项的原因。**

### 7.5 下次还要重复吗

**每次发布都要走一遍。** 没有"自动部署"——**这是有意的，不要开启。**

## 8. 从备份恢复（**危险操作**）

### 8.1 为什么

只在**数据被误删、误改，或发布回滚需要**时做。

### 8.2 ⚠️ 先想清楚

**恢复会覆盖整个数据库，丢掉备份之后产生的所有数据。**
做之前问自己：
- 真的需要**整个库**回退吗？还是只需要找回**几笔账**？
- 我知道备份文件对应的是**哪个时刻**吗？

### 8.3 在哪里做

**服务器上**。

```bash
cd /srv/libevra/deploy
ls -lh backups/                 # 先看有哪些备份、什么时候的
./restore.sh backups/libevra_prod-20261016-102804.dump
```

### 8.4 成功会看到什么

它会**要求你手打 `yes`**（因为危险），然后：

```
→ 安全副本：先把当前库导出…
✅ 当前状态已存到 backups/pre-restore-20261016-120000.dump
   （如果恢复错了，这就是回去的路。）
→ 停 API…
→ 重建数据库…
→ 恢复…
✅ 已恢复
→ 重启 API…
✅ 恢复完成，API 健康。
```

**⚠️ `pre-restore-*.dump` 是"我恢复错了，想回去"的唯一出路。不要删它。**

### 8.5 失败怎么办

脚本会打印回退命令。**最关键的是别慌**：
当前状态在恢复前已经被存成 `pre-restore-*.dump`，**用它再恢复一次就回到原样**。

如果连 API 都起不来：
```bash
$DC logs api --tail 50
$DC ps
```

### 8.6 恢复之后**必须**做的三件事

1. **确认账目数量是对的**——"恢复成功"和"恢复对"是两件事
2. **立刻跑一次 `./backup.sh`**——现在的库还没有被验证过的备份
3. **检查管理员名单**——`$DC exec -T api pnpm admin:list`
   （库回到了旧状态，**授权记录也是旧的**）

### 8.7 下次还要重复吗

**希望永远不用。** 但**要知道它在哪、怎么用**——出事时才现学太晚了。

## 9. 看到 `unhealthy` 怎么办

### 9.1 为什么

**`unhealthy` 不等于"网站坏了"。** 部署当天就遇到过一次：
**web 显示 unhealthy，而网站完全正常**——是健康检查问错了问题。

### 9.2 在哪里做

**服务器上**。

```bash
$DC ps
$DC logs web --tail 30
```

看健康检查到底在抱怨什么（**这一步最关键**）：

```bash
sudo docker inspect deploy-web-1 --format '{{json .State.Health}}' | python3 -m json.tool | tail -20
```

### 9.3 怎么读结果

| 看到 | 意思 |
|---|---|
| `ssl3_read_bytes:tlsv1 alert internal error` | **健康检查被跳转带进了没有证书的 `https://127.0.0.1`** —— 见手册 §12.6 |
| `Connection refused` | 容器里的服务真的没在监听 |
| `wget: not found` | 镜像里没有 wget（检查写错了） |

### 9.4 判断"网站其实是不是好的"

**别只看 unhealthy，直接问网站**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://libevra.com/
curl -s https://libevra.com/api/v1/health
```

**⚠️ 如果这两条都正常，而容器显示 unhealthy，那问题在"检查"上，不在"服务"上。**
这种情况**不要急着重启或改配置**——先搞清检查为什么问错问题。

### 9.5 下次还要重复吗

出问题时做。

## 10. 关于管理员（**现在还没有管理员**）

### 10.1 为什么

管理员身份是**唯一**能做平台级操作的东西。**在建立之前，谁都做不了。**

### 10.2 现状（2026-10-16）

| 项 | 值 |
|---|---|
| 生产库里的账号 | **0 个** |
| `admin_grants`（授权） | **0** |
| `admin_allowlist`（允许名单） | **0** |
| 待用的邀请码 | **1 个**（预留编号 10000002，永不过期） |

### 10.3 成为管理员需要**两步**，缺一不可

**⚠️ 这是最容易搞错的地方。**

```bash
cd /srv/libevra/deploy
$DC exec -T api pnpm admin:grant <你的UUID> --by "owner"    # 第一步：授权
$DC exec -T api pnpm admin:allow <你的UUID> --by "owner"    # 第二步：列入允许名单
```

**⚠️ 只做第一步，你还不是管理员。**
`pnpm admin:list` 会把你显示在「⚠️ 只满足一半（不会通过校验）」一栏里，
而那个账号**确实不能通过校验**。**这是设计在工作，不是故障。**

**为什么要两步**：授权（"这个账号被授予过管理员角色吗"）与允许名单
（"这个账号是当前允许行使管理员身份的之一吗"）是**两件不同的事**，
分别撤销。详见 [`管理员与权限边界-设计决定.md`](管理员与权限边界-设计决定.md) §4。

### 10.4 怎么查当前状态

```bash
$DC exec -T api pnpm admin:list
```

它会分四栏显示：**真正的管理员** / **只满足一半** / **有资格但未授权** / **已撤销**。

### 10.5 邀请码在哪

**⚠️ 邀请码不写在任何文档里**——**这个仓库是公开的，而邀请码是唯一能注册账号的东西。**
写进文档就等于把注册开放给所有能读到仓库的人。

在服务器上查：
```bash
$DC exec -T db psql -U libevra -d libevra_prod -c \
  "select code, note, account_number from registration_invites where used_at is null;"
```

### 10.6 下次还要重复吗

**建立管理员是一次性的**（除非要换人）。查状态可以随时做。

## 11. 三个最该记住的观念

### 11.1 GitHub 更新 ≠ 生产更新

**改代码 → 推送 → CI 通过……网站还是旧的。** 要发布，得有人在服务器上跑 `deploy.sh`。

**⚠️ 不要开启自动部署。** 这是所有者定的规则（`DEVLOG.md` ADR-037），
理由是一台服务器一个人维护，**没有验收的发布不算发布**。

### 11.2 容器健康 ≠ 能用

`deploy.sh` 说成功，只代表"四个盒子都活着"。
**能不能登录、能不能记账、离线同步对不对**——这些只有人走一遍才知道。

### 11.3 备份 ≠ 备份能用

**一个没被恢复过的备份，只是一份让人安心的文件。**
所以 `backup.sh` 默认就做恢复演练——**看到 `🎉` 才算数**。

## 13. 出事了找谁

**⚠️ 一个人维护的项目，没有"运维团队"可以打。** 所以：

1. **先别慌、别乱试。** 大多数"网站挂了"是某个容器停了，重启就好。
2. **先看状态**（§3），**再看日志**（§4），**再对照手册 §11 的故障表**。
3. **不确定的操作不要做**——尤其 §10.1 那十条禁止项。
4. **数据相关的操作之前，先备份**。
5. **把现象、时间、你看过的日志记下来。** 这是唯一能让下一次更快的东西。

**⚠️ 如果拿不准，停下来问所有者，而不是"试一下看看"。**
生产环境的"试一下"代价可能是真实账目。
