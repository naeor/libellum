## 1. ⚠️ 先学会查状态，而不是背状态

**本文里的"当前状态"只在写作那一刻成立。** 生产环境会变，所以每一节都给出**查询命令**。
**接手时的第一件事是查一遍，不是相信本文的数字。**

### 1.1 一条命令看全部

```bash
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152   # Windows PowerShell
```
```bash
cd /srv/libevra/deploy && sudo docker compose -f docker-compose.prod.yml ps
```

`docker compose ps` 是**最该先看的一条**。健康时的样子：

```
SERVICE   STATUS                      PORTS
api       Up N minutes (healthy)      3000/tcp
db        Up N minutes (healthy)      5432/tcp
migrate   Exited (0) N minutes ago
web       Up N minutes (healthy)      0.0.0.0:80->80/tcp, ...:443->443/tcp
```

**⚠️ 读这张表的三个要点**：
- `migrate` **本来就该是 `Exited (0)`**——它跑完迁移就退出，**不是故障**。
  只有在它是 `Exited (非0)` 时才是问题。
- `api`/`db`/`web` 必须是 `(healthy)`。`(health: starting)` 是启动中，等 40 秒。
- **只有 `web` 该有 `0.0.0.0:` 开头的端口**。若 `db` 或 `api` 出现端口，**说明配置被改坏了**，见 §10。

### 1.2 服务器上跑的是哪个 commit

```bash
cat /srv/libevra/.deployed-commit        # 部署时记录的提交
grep -o 'APP_VERSION = "[^"]*"' /srv/libevra/apps/web/src/lib/version.ts   # 应用版本号
```

⚠️ **`.deployed-commit` 只由 `deploy.sh` 写入。** 如果你手工改了服务器的文件（**别这么做，见 §10**），
它就会过时。**想知道文件真实内容，用 `git` 比对或直接看文件，不要只信这个文件。**

### 2.1 ⚠️ 两件与"常见预期"不同的事

**① 内存是 7.5 GiB，不是 2 GB。**
`deploy/README.md` §3 写了四档"2 GB 机器上的降级方案"，**在这台机器上一档都不需要**：
语音模型直接用 `small`（约 488 MB），OCR 与语音可以同时常驻。
**那四档方案留在 `deploy/README.md` 里对别的机器仍有效，但对这台不适用。**

**② `ufw` 是关闭的，这是有意的。**
入口过滤由**腾讯云安全组**负责（§4.4）。**⚠️ 不要贸然打开 ufw**：
两层防火墙规则不一致时，最容易的结果是**把自己锁在 SSH 外面**。
如果确实要开，**先用 `ufw allow 22` 再加 `enable`**，并且**另开一个 SSH 会话验证能连上再关闭原会话**。

### 3.1 ⚠️ 为什么 OCR 和语音不是独立容器

`apps/api/src/ocr/client.ts` 与 `voice/client.ts` 各自 `spawn` 一个 Python 进程，
用 **stdin/stdout JSON** 通信——**故意的，这样识别服务不开任何端口**。

把它们拆进独立容器会**强迫它们开放网络端口**，而那正是这个设计特意避开的东西。
所以 API 与两个 Python 环境**同一个镜像**。代码一个字没改，靠两个环境变量告诉它解释器在哪：

```
LIBELLUM_OCR_PYTHON=/opt/libevra/python/bin/python
LIBELLUM_VOICE_PYTHON=/opt/libevra/python/bin/python
```

**⚠️ 这两个变量名里的 `LIBELLUM` 是历史遗留，不是拼写错误。**
改名会牵动代码与文档，收益为零——见 [`Libevra品牌迁移记录.md`](Libevra品牌迁移记录.md) §5。

### 3.2 四个容器各自的职责

| 服务 | 镜像 | 职责 | 公网端口 |
|---|---|---|---|
| `web` | `deploy/Dockerfile.web` | 静态前端 + TLS + 反代 `/api` | **80、443** |
| `api` | `deploy/Dockerfile.api` | Fastify 接口 + 两个 Python sidecar | 无 |
| `migrate` | 同 `api` | 跑 `prisma migrate deploy` 然后**退出** | 无 |
| `db` | `postgres:17` | 数据 | 无 |

**⚠️ `api` 和 `migrate` 是同一个镜像的两个不同命令**，所以**改 `Dockerfile.api` 要同时重建这两个**：

```bash
sudo docker compose -f docker-compose.prod.yml build api migrate
```

**只重建 `api` 会让 `migrate` 继续用旧镜像**——这是部署当天真的踩过的坑（§12.3）。

### 3.3 数据存在哪：命名卷

| 卷 | 内容 | 丢了会怎样 |
|---|---|---|
| `db-data` | **全部账目** | **灾难**。只能从 `backup.sh` 的备份恢复 |
| `api-data` | 语音模型（约 488 MB）、上传临时区 | 无损失，下次用时重新下载 |
| `caddy-data` | **证书 + ACME 账号密钥** | 重新签发证书（**Let's Encrypt 有签发频率限制**） |
| `caddy-config` | Caddy 运行状态 | 无损失 |

**⚠️ 备份脚本只备份 `db-data` 的内容，不备份卷本身。** 恢复靠 `restore.sh`（§9.3）。

## 4. 域名、证书、反向代理、防火墙

### 4.1 DNS（在 Namecheap 管理）

| 记录 | 值 | 状态 |
|---|---|---|
| `libevra.com` A | **43.161.227.152** | ✅ 正确 |
| `www` CNAME | ⚠️ **曾经指向 `libvera.com`（拼写错误，v/e 颠倒）** | **待所有者修正为 `libevra.com`** |

怎么看当前解析：
```powershell
Resolve-DnsName libevra.com -Type A
Resolve-DnsName www.libevra.com
```
```bash
# 或从服务器上
getent hosts libevra.com www.libevra.com
```

**⚠️ `www` 修好之后要重启一次 web 容器**（原因见 §4.3）：
```bash
cd /srv/libevra/deploy && sudo docker compose -f docker-compose.prod.yml up -d --force-recreate web
```

### 4.2 HTTPS 证书

**由 Caddy 自动向 Let's Encrypt 申请与续期**，不需要任何手工操作。

```bash
# 看证书
echo | openssl s_client -connect 127.0.0.1:443 -servername libevra.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -enddates
```

**⚠️ 当前 `ACME_EMAIL` 是空的**：证书照发照续，**但你收不到到期提醒**。
填地址：改 `/srv/libevra/deploy/.env` 里的 `ACME_EMAIL`，再 `up -d --force-recreate web`。

### 4.3 ⚠️ Caddyfile 是"生成"的，不是直接读的

```
deploy/Caddyfile            （模板，挂载为 /etc/caddy/Caddyfile.template，只读）
        │
        │  deploy/web-entrypoint.sh 在容器启动时渲染
        ▼
/etc/caddy/Caddyfile        （容器内部，Caddy 真正读的文件）
```

**为什么要有这一步**：Caddy 的 `email` 指令**不接受空值**——
`email {$ACME_EMAIL}` 在变量为空时会让 Caddy **拒绝整个配置**，
于是**站点根本起不来**（不是"少了提醒"）。Caddyfile 格式没有条件语句，
所以用一个脚本按需生成那一行。

**⚠️ 因此改完 Caddyfile 必须重启容器，`reload` 不够**（生成步骤在启动脚本里）：

```bash
sudo docker compose -f docker-compose.prod.yml up -d --force-recreate web
```

同一个脚本还会**探测** `www.$LIBEVRA_DOMAIN` 是否解析，解析成功才加 `www → apex` 的跳转。
**⚠️ 探测是有意的**：给一个 DNS 不指向本机的域名申请证书会失败，
而 Let's Encrypt 对失败**按注册域名限流**。

### 4.4 防火墙：两层，各管一段

| 层 | 位置 | 状态 | 管什么 |
|---|---|---|---|
| **腾讯云安全组** | 腾讯云控制台 | 放行 **22、80、443** | **入口过滤（真正的防线）** |
| **ufw** | 服务器内 | **inactive**（有意） | 未启用 |

**⚠️ 只能由所有者在腾讯云控制台改安全组**，在服务器上改不了。
**⚠️ 不要为了"更安全"随手开 ufw**——见 §2.1 ②。

### 4.5 安全响应头（已实测下发）

`Caddyfile` 里的 `header` 块会下发：CSP、HSTS、`X-Frame-Options: DENY`、
`X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Permissions-Policy`。

```bash
curl -sI https://libevra.com/ | grep -iE 'content-security|x-frame|strict-transport'
```

**⚠️ CSP 里的 `style-src 'unsafe-inline'` 是必需的，不要删**：
React 为了淡入动画每帧写 `--p` 到 DOM 的 `style` 属性（见 `detail-motion.css`），
去掉它整个过渡系统会停。

## 5. Windows 开发电脑如何管理服务器

### 5.1 现在是怎么连的

```powershell
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152
```

| 文件 | 作用 |
|---|---|
| `C:\Users\ZhuanZ（无密码）\.ssh\libevra_server` | **私钥**（464 字节），ED25519 |
| `…\.ssh\libevra_server.pub` | **公钥**，已装到服务器的 `~/.ssh/authorized_keys` |

**公钥指纹**：`SHA256:Y0gfnk6XMEX++Nt457QuZk3fFKrLlvF3qfYrPGSDOMU`，注释 `libevra-deploy`。

```powershell
# 核对用的是不是这把钥匙
ssh-keygen -l -f "$env:USERPROFILE\.ssh\libevra_server.pub"
```

### 5.2 ⚠️ 公钥、私钥、密码短语、ssh-agent 分别是什么

| 概念 | 是什么 | 打个比方 |
|---|---|---|
| **公钥** | 可以随便给任何人的那一半。装在服务器上，表示"持有对应私钥的人可以进来" | **门锁** |
| **私钥** | **绝不能给任何人**的那一半。**不要复制、不要上传、不要粘贴到对话里** | **钥匙** |
| **密码短语（passphrase）** | 给私钥本身加的密码。**私钥文件被偷了，没有它也用不了** | **保险箱密码** |
| **SSH Agent** | 一个在后台记着"已解锁私钥"的小程序。**解锁一次，之后不用每次输密码短语** | **把钥匙插在锁上不拔** |

**⚠️ 部署当天真实遇到过的问题**：`libevra_server` 这枚私钥**当时设了密码短语**，
而非交互式登录（`BatchMode`）不给它输入的机会，于是服务器**接受了公钥却又拒绝登录**
（`Permission denied (publickey,password)`）——**看起来像"公钥没装"，其实是"私钥没解锁"**。

**⚠️ 这两种失败长得几乎一样，区分方法**：
```powershell
ssh -vv -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152 "echo ok" 2>&1 |
  Select-String 'Offering public key|Server accepts key|Permission denied'
```
- 有 `Server accepts key` 但随后 `Permission denied` → **公钥装了，是本地解锁/匹配问题**
- **没有** `Server accepts key` → 公钥可能真的没装

### 5.3 用 ssh-agent 免得每次输密码短语（可选）

```powershell
# 1. 启动 agent 服务（只需一次；重启电脑后要重做，或设为自动启动）
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent

# 2. 把私钥加进去（会提示输入一次密码短语）
ssh-add "$env:USERPROFILE\.ssh\libevra_server"

# 3. 之后就不需要 -i 了
ssh ubuntu@43.161.227.152
```

```powershell
ssh-add -l          # 看 agent 里有哪些钥匙
ssh-add -D          # 全部清掉（离开电脑前用）
```

**⚠️ ssh-agent 让"解锁的私钥"留在内存里。** 在共用电脑上离开前用 `ssh-add -D` 清掉。

### 5.4 ⚠️ 本机其它 AI 会话的注意事项

**私钥和密码短语都不应该出现在对话、日志、文档或仓库里。**
本项目的做法是：**密钥只在服务器上生成、只在服务器上使用**，
需要跑一次性脚本时**用 `ssh` 把脚本内容传过去执行**，而不是把密钥搬来搬去。

**从 Windows 传脚本时的一个实际坑**：Write/Set-Content 默认写 CRLF，
而 bash 会因为行尾的 `\r` 报 `$'\r': command not found` 之类的怪错。
**稳妥做法是把脚本 base64 编码后传过去再解码**：

```powershell
$script = (Get-Content .\x.sh -Raw) -replace "`r`n","`n"
$b64 = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($script.TrimEnd()))
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152 `
  "echo $b64 | base64 -d > /tmp/x.sh && bash /tmp/x.sh; rm -f /tmp/x.sh"
```

### 6.3 ⚠️ 环境变量：在哪、有什么、绝不放哪

**位置**：`/srv/libevra/deploy/.env`，权限 `600`，**被 `.gitignore` 排除**。

## 7. 本地开发 → GitHub → CI → 生产：四个地方的关系

```
① Windows 开发电脑                    ② GitHub 仓库
   C:\Users\ZhuanZ（无密码）\Desktop\    https://github.com/naeor/libevra
   工作\记账程序\记账程序v1               │
   │                                    │  ③ GitHub Actions（CI）
   │  pnpm typecheck                    │     干净库跑迁移 → 类型检查
   │  pnpm -r test                      │     → 全量测试 → 真实构建
   │  pnpm check:build                  │     ⚠️ CI 不部署，只证明"这个 commit 是好的"
   │  pnpm check:docs                   │
   │  pnpm check:db                     │
   │                                    │
   └── git push ────────────────────────┘
                                        │
                                        │  ⚠️⚠️ 到这里就停了。main 更新 ≠ 生产更新。
                                        │     中间必须有人做决定。
                                        ▼
                              ④ 生产服务器 43.161.227.152
                                 /srv/libevra
                                 git checkout <commit>（或人工传源码）
                                 ./deploy/deploy.sh --version X.Y.Z
                                        │
                                        ▼
                                 用户访问 https://libevra.com
```

### 7.1 ⚠️⚠️ 最重要的一条：**GitHub 更新不等于生产更新**

**这是有意的设计，不是还没做。**

- **CI 只检查，不部署。** `.github/workflows/ci.yml` 里**没有**任何部署步骤。
- **发布必须人工执行**，而且 `deploy.sh` **要求你打出具体版本号**：
  ```bash
  ./deploy/deploy.sh --version 1.10.24      # ✅
  ./deploy/deploy.sh                        # ❌ 拒绝执行
  ```
- **决策记录见 `DEVLOG.md` 的 ADR-037**。

**⚠️ 不要擅自开启 main 自动部署。** 理由不是流程洁癖，而是这个项目的实际情况：
**一台服务器、一个人维护**。一个跟着 main 自动上线的服务，
**意味着任何一次推送都是一次没有验收的发布**——而"没验收"和"没发布"在复盘时是完全不同的两件事。

**⚠️ 如果你（AI）认为需要自动部署，那是要向所有者提议的事，不是自己改 CI 的事。**

### 7.2 代码是怎么上服务器的

**推荐做法**（保持"服务器运行的就是仓库里验证过的那个 commit"）：

```powershell
# 在 Windows 上，从已提交的 commit 打包（不含未提交改动）
git -C <仓库> rev-parse HEAD                      # 记下这个 commit
git -C <仓库> archive --format=tar.gz -o out.tar.gz HEAD
```
把它传到服务器解到 `/srv/libevra`，并更新 `.deployed-commit`。

**⚠️ 部署当天为了方便，直接在服务器上改了 `deploy/` 里的文件再补回仓库**，
于是出现"服务器比仓库新"的状态（§12.6）。
**下次请反过来：先在本地改、提交、推送，再从服务器拉取。**

## 8. 发布、验证、回滚

### 8.1 发布一个指定版本

```bash
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152
cd /srv/libevra
# 1. 让源码变成你要发布的那个 commit（见 §7.2）
# 2. 发布
cd deploy && ./deploy.sh --version 1.10.24
```

`deploy.sh` 会依次做：**备份 → 构建 → 迁移 → 起服务 → 健康检查（API + Web）**。
**健康检查不过就停下、不写版本号、并打印回滚路径。**

### 8.2 发布后必须人工验证

**⚠️ 脚本只证明"容器健康"，不证明"能用"。** 脚本跑完后请自己走一遍：

1. 浏览器打开 <https://libevra.com>，**登录**
2. **记一笔**，看它出现在明细里
3. **开飞行模式**，记一笔，恢复网络，看是否同步上来
4. 打开「账户 → 软件更新」，**确认显示的版本号就是刚发布的那个**
5. `curl -s https://libevra.com/api/v1/health` → `{"ok":true,...,"database":"up"}`

### 8.3 回滚

| 情况 | 做法 |
|---|---|
| **只改了代码** | `git checkout <上一个 commit>`（或重新传源码）→ `./deploy.sh --version <上一个版本>` |
| **改了数据库 schema** | ⚠️ **回滚应用不会回滚数据库**，见下 |

**⚠️⚠️ 迁移是只向前的。** `prisma migrate deploy` **没有 `down`**。
一个删列的迁移，退回旧镜像也换不回那一列。

所以**改 schema 的版本要这样想**：
1. 那个迁移能不能被旧代码容忍？（加列、加表通常可以——旧代码用不到而已）
2. **能容忍** → 只回滚应用即可
3. **不能容忍** → 用 `./restore.sh <发布前的备份>` **恢复整个数据库**，
   代价是**丢掉发布之后产生的所有数据**

**这就是"发布前先备份"是 `deploy.sh` 的第一步而不是可选项的原因。**

### 8.4 看日志

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"
$DC logs -f api              # 实时
$DC logs api --tail 100      # 最近 100 行
$DC logs web --tail 50       # Caddy（证书信息在这里）
$DC logs api --since 10m     # 最近 10 分钟
```

## 9. 数据库：迁移、备份、恢复

### 9.1 迁移

**正常情况不用手动做**：`docker-compose.prod.yml` 里的 `migrate` 服务会在
`api` 启动之前自动跑完，**跑完退出（`Exited (0)` 是正常的）**。

手动跑（例如排查问题）：
```bash
cd /srv/libevra/deploy
sudo docker compose -f docker-compose.prod.yml run --rm migrate pnpm db:deploy
```

**⚠️ 只用 `prisma migrate deploy`。**
**`migrate dev` 会在生产库上试图创建新迁移**，
**`migrate reset` 会删掉整个数据库**——**这两个词永远不该出现在生产命令里。**

### 9.2 备份

```bash
cd /srv/libevra/deploy && ./backup.sh
```

它会：导出 → **校验归档可解析** → **恢复进一个临时库、逐表比对行数、再删掉临时库** → 轮转。

**⚠️ 一个没被恢复过的备份不是备份，只是一份让人安心的文件。**
所以这个脚本**默认就做恢复演练**；`--no-restore-drill` 可以关掉，**不推荐**。

**⚠️ 本地备份不是备份策略。** 同一台服务器上的备份会和服务器一起消失。
**⚠️ 目前还没有异地备份**（见 §12.5）。

建议加每日 cron（**尚未配置**）：
```bash
crontab -e
17 3 * * * cd /srv/libevra/deploy && ./backup.sh >> backups/cron.log 2>&1
```

### 9.3 恢复

```bash
cd /srv/libevra/deploy
./restore.sh backups/libevra_prod-YYYYMMDD-HHMMSS.dump
```

**⚠️⚠️ 这是本仓库最危险的脚本——它会覆盖整个生产数据库。**
它会先做一份"安全副本"到 `backups/pre-restore-*.dump`，
**那是"我恢复错了，想回去"的唯一出路**。

恢复之后一定要：
1. **确认账目数量是对的**（"恢复成功"和"恢复对"是两件事）
2. **立刻跑一次 `./backup.sh`**（现在的库还没有被验证过的备份）
3. **检查管理员名单**（`pnpm admin:list`）——库回到了旧状态，授权记录也是旧的

## 10. ⚠️ 禁止与谨慎操作

### 10.1 绝对禁止（会造成不可逆损失）

## 12. S12-B 实际做了什么、遇到什么故障

### 12.1 部署流程（六步）

1. **只读 SSH 检查**：确认能登录、看系统/资源/Docker/防火墙/现有服务
2. **装 Docker**（官方源；**不动其它包**）
3. **传源码**：本机 `git archive` 出 `d2c7a67`，base64 过 SSH 解到 `/srv/libevra`
4. **生成密钥**：在服务器上用 `openssl rand` 生成，**直接写入 `deploy/.env`（600）**，**从未经过对话或仓库**
5. **`caddy validate`** → 立刻发现一个会让站点起不来的 bug（§12.5）
6. **`compose up`** → 又发现三个只在真机才暴露的 bug（§12.2–§12.4）

### 12.2 ⚠️ `prisma.config.ts` 与 `prisma/` 没进镜像

```
schema.prisma: file not found
prisma/schema.prisma: file not found
```

Prisma 7 从 `prisma.config.ts` 读 schema 位置，而 `Dockerfile.api` **没有 COPY 它**。

**⚠️ 更危险的是迁移目录也没进去**：`prisma migrate deploy` 找不到迁移时
**会报"没有待应用的迁移"并退出 0** —— 于是 api 在**空 schema** 上启动、接口全 500。
**一个退出码为 0 的假成功，比一个失败更难查。**

**已修**：构建阶段与运行阶段都 COPY 两者。

### 12.3 ⚠️ `node_modules` 属于 root，容器跑 uid 10001

```
Can't write to /repo/node_modules/.pnpm/@prisma+engines@7.10.0/...
```

Prisma 首次使用要把查询引擎写进自己的包目录。**已修**：`chown` 到 10001。

### 12.4 ⚠️ pnpm 每次跑脚本前重装依赖 → `migrate` 退出 127

```
Packages: +308
Error: ERR_PNPM_CMD_SHIM_CHMOD ... Operation not permitted
[WARN] The install that runs before scripts failed, so your node_modules may be out of sync
$ prisma migrate deploy
sh: 1: prisma: not found
[ELIFECYCLE] Command failed with exit code 127.
```

**⚠️ 这个 bug 教了三件事：**

1. **pnpm 11+ 默认在 `pnpm run` / `pnpm exec` 前检查依赖，发现"不同步"就自己跑一次安装。**
   默认值是 `install`，而且那句警告的意思是**"安装失败但我还是继续跑了命令"**——
   于是 `node_modules` 被它自己搞坏，命令再去找 `prisma` 就找不到了。
   **退出码 127 读起来像"镜像坏了"，完全不像"依赖检查刚把依赖删了"。**

2. **⚠️ 关掉它的开关只能写在 `pnpm-workspace.yaml` 里。** 按直觉试了两次，**两次都完全无效**：
   - `ENV verifyDepsBeforeRun=false` 写在 Dockerfile 里 → 无效
   - 运行镜像里放 `.npmrc` 写 `verify-deps-before-run=false` → 无效，
     且 `pnpm config get verify-deps-before-run` 仍回答 `undefined`

   **查 pnpm 官方文档才确认：pnpm 12 只从 `.npmrc` 读认证与 registry 设置，
   其他所有设置都来自 `pnpm-workspace.yaml` 或全局配置文件。**
   正确写法是 `pnpm-workspace.yaml` 里的 **`verifyDepsBeforeRun: false`**。

   **⚠️ 两个无效的尝试都已删除**，没有留在仓库里假装有效——
   **一条不起作用的配置行比没有更糟，因为下一个人会信它。**

3. **为什么生产镜像里必须关掉**：镜像的 `node_modules` 是 CI 验证过的锁定图层，
   运行时的"依赖检查"**不可能改善它，只能让容器偏离被验证过的产物**。
   而它偏偏在**运维命令**（`invite:create`、`admin:grant`、`admin:allow`、`db:deploy`）上触发——
   **也就是出事时最需要它们好用的那些命令**。

### 12.5 ⚠️ `Caddyfile` 的 `email` 空值会让整个站点起不来

```
parsing caddyfile tokens for 'email': wrong argument count
```

**实测确认 Caddy 的两种行为**（关键，因为两者看起来一样）：

| `ACME_EMAIL` | 结果 |
|---|---|
| **未设置** | `{$ACME_EMAIL:默认}` 的默认值生效 → **有效** |
| **设置但为空** | 展开成什么都没有 → `email` 没有参数 → **拒绝整个配置** |

**⚠️ 而 Compose 传的 `${ACME_EMAIL:-}` 正是"设置了但为空"。**
所以"还没填邮箱"会让**账本站不起来**，不只是少了提醒。
**已修**：`web-entrypoint.sh` 按需生成那一行。

**⚠️ 这正是 `caddy validate` 存在的理由**——配置写好后一直"看起来没问题"，
因为**从没被真正的 Caddy 解析过**。**首次部署前 validate 一步都不能省。**

### 12.6 ⚠️ web 一直 unhealthy，而站点完全正常

Caddy 对 Host 不是配置站点的请求回 308 跳转到 `https://127.0.0.1/healthz`；
wget 跟过去、容器递出 `libevra.com` 的证书、握手失败。

**⚠️ 危险的不是检查失败，而是它传达的信息**："web 不健康"正是会让运维
**去查一个并不存在的故障**的信号。**已修**：健康检查带真实 `Host` 头，修复后 8 秒内 healthy。

### 12.7 ⚠️ "服务器上的代码比仓库新"（遗留状态，下次发布会收敛）

部署时为修 bug，**直接在服务器上改了 `deploy/` 的文件并重建镜像**，当时仓库里还没有这些修复。

| | 提交 |
|---|---|
| 服务器实际运行 | `d2c7a67` **+ 就地修复** |
| 仓库 HEAD | 把那些修复补回仓库后的提交 |

**功能等价，但不是同一个提交**；`/srv/libevra/.deployed-commit` 仍写着 `d2c7a67`（当时的事实）。
**下次用 `deploy.sh` 发布会自动收敛。**
**⚠️ 在那之前，要改服务器上的部署代码请先在本地改、提交、推送，再从服务器取**——
否则会再次分叉。

### 12.8 ⚠️ 差点把注册邀请码发到公开仓库

写部署记录时，为了"让所有者方便"，把**生产邀请码明文写进了文档**。
**提交前的秘密扫描抓到了它，在推送之前移除**，改成用查询命令获取。

**为什么值得单独记下来**：邀请码是**唯一**能注册账号的东西，而**仓库是公开的**。
写进文档就等于把注册开放给所有能读到仓库的人。`.gitignore` 里 `docs/邀请码.md` 那条规则
正是防这个的，而那次**绕过了它——形状是"为了让你方便"**。
**⚠️ 方便正是这一类泄露的入口。**

### 12.9 DNS 的 `www` 拼写错误（待所有者修）

```
实测：www.libevra.com  CNAME → libvera.com      （v 和 e 写反了，该域名不存在）
正确应为：                    → libevra.com
```

`www.libevra.com` 因此完全无法解析。Caddy 侧已写好**探测式**的跳转（§4.3），
**DNS 一改就自动生效**（改完记得重启 web 容器）。
