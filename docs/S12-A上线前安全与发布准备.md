## 3. Git 历史的处置建议

**⚠️ 现状**：`3f72f4e` 里的旧口令**已失效**。历史里留着它，是一个"整洁问题"。

| 方案 | 说明 | 建议 |
|---|---|---|
| **A. 什么都不做** | 字符串已无价值；GitHub 会一直保留它 | ✅ **推荐**（见下） |
| **B. 请 GitHub 清除缓存** | Support → *Sensitive data removal*；**不改历史**，但清理其缓存 | 可选，成本低 |
| **C. `git filter-repo` 重写历史** | 会改写全部 commit hash、需要强推、任何克隆都必须重新克隆 | ❌ **不建议** |
| **D. 删除并重建仓库** | 会丢掉 116 次 CI 记录与全部历史 | ❌ **不建议** |

**⚠️ 为什么推荐 A（+可选 B）：**

1. **凭据已失效**——这是安全问题的实质，而它已经解决；
2. **本仓库 0 fork / 0 star**，志愿者副本存在的可能性很低（但**无法证明**）；
3. 方案 C 的代价是**真实的**：改写历史会让每一个已克隆的副本失效，
   而收益只是"一个不能用的字符串不再出现"。**为一个失效字符串重写历史，是用真实代价换虚构的安全感。**
4. 本项目自己写过这条纪律：**"不要为了追求字符串归零而破坏 Git 历史。"**

**如果将来要做**，正确顺序是：① 先确认口令已失效（已完成）→ ② 确认没有其他**有效**秘密
→ ③ `git filter-repo --path docs/交接.md --replace-text` → ④ **通知所有克隆者重新克隆**
→ ⑤ 强推。**本轮不执行任何一条。**

## 4. 管理员双重检查：本轮的核心修正

### 4.1 ⚠️ 核实确认：此前**不是**真正独立

`isOnAdminAllowList()` 在 1.10.22 里的判定是：

> *"账号在资格区间内 **且** 持有有效 `admin_grants`"*

**它是从 `admin_grants` 派生的。** 两个函数、两个开关、两个调用点——
**但只有一个数据来源**，所以一次授权同时满足两半，两道检查**永远不可能不一致**。

**所有者指出的正是这一点：**

> *"授权记录和允许名单并没有完全分离……如果未来误将另一个合格账号加入 `admin_grants`，
> 在默认的 first-batch 范围下，它可能同时通过所谓的两重检查。"*

**⚠️ 今天的可利用率**：不能直接利用（`admin_grants` 里只有 `naeor`）。
**但"今天不能利用"不是"不是问题"**——一次打错 UUID 的 `admin:grant` 就会造出一个
**看起来通过了两道检查**的管理员。

### 4.2 修正后的数据来源

| | 第一重：授权 | 第二重：允许名单 |
|---|---|---|
| **表** | `admin_grants` | **`admin_allowlist`**（本轮新增） |
| **问题** | "这个账号被授予过管理员角色吗？" | "这个账号是当前允许行使管理员身份的那几个之一吗？" |
| **写入** | `pnpm admin:grant` | `pnpm admin:allow` |
| **撤销** | `pnpm admin:revoke` | `pnpm admin:disallow` |
| **能单独存在吗** | ✅ 能——**然后 guard 拒绝** | ✅ 能——**然后 guard 拒绝** |

**⚠️ 两个命令都不写对方的表。** 所以运维必须**两次都表态**——
而这正是"问两次"的全部意义。

### 4.3 完整判定链

```
有效会话  AND  有效授权(admin_grants)  AND  在允许名单(admin_allowlist)
          AND  前 100 资格(10000000–10000099)  AND  账户可用(存在、非演示)
```

- **身份只从已验证会话取**——请求头 / 体 / 查询参数里的 `isAdmin`、`role`、
  `username`、账号编号、自定义管理员头，**一个都不读**；
- **不缓存**——撤销在下一次请求生效；
- **所有拒绝都是同一个 403 同一句话**，不透露卡在哪一关；
- **未登录是 401**（"你是谁"），已登录无权是 403（"不是你"）。

### 4.4 实现细节（两处值得记住）

**① 允许名单是"表"而不是"环境变量"。**
理由：本项目所有状态都在 PostgreSQL（不引入第二套配置机制）；
可审计（谁、何时、为何）；多实例天然一致；改名单不需要重启容器。
环境变量方案的优势是"API 根本碰不到"，代价是每改一次要重启、多实例要同步、
Windows 开发与 Linux 生产两套格式容易漂。**取舍见 `管理员与权限边界-设计决定.md` §4.2。**

**② 判定顺序是刻意的。**
账号层面的三个事实（存在、非演示、资格）**先判**，两道独立检查**后判**。
否则一个既不合格又不在名单上的账号会被报成"不在名单"，
**而下一个人会以为资格规则不可达、把它删掉**。

### 7.1 新增：`pnpm check:db`（开发库与测试库迁移一致性）

**⚠️ 为什么加它**：本轮之前，`ledger_test` 曾**落后 `ledger_dev` 9 个迁移**
（停在 `20261011140000`，开发库已在 `20261013190000`）。成因很平常——
**测试库需要单独跑一次 `prisma migrate deploy`**，而一个需要"记得做"的步骤迟早会被忘记。
后果不只是"测试跑不起来"：**在那之前，跑在测试库上的集成测试可能一直在测一个旧 schema。**

| 它做什么 | 比较两个库 `_prisma_migrations` 里 `finished_at` 非空的行，不一致时指出差在哪 |
| 它不做什么 | **不重置、不应用迁移、不碰业务数据**——"发现不一致"和"改掉它"是两件事 |
| 额外守卫 | 两个变量指向同一个库时**直接报错**（那不是"一致"，是"没在比较"） |
| 秘密 | **不打印任何连接串或口令**，只打印库名与迁移名 |
| 位置 | `apps/api/src/scripts/check-db-parity.ts`（需要 Prisma 客户端，根目录的 `tools/` 用不了 `pg`） |

**实测**：正常情况报"一致"；把两个变量指向同一个库时报"没有可比性"。
**它没有跑过真正的"不一致"场景**（当前两个库一致）——这一点如实说明。

**⚠️ 文档里没有服务器规格。** 需要你提供（**不要给密码或密钥**）：

| 项 | 状态 |
|---|---|

| 地区 | 待确认 |

| CPU / 内存 / 磁盘 | **待确认**（计划 2 核 / 2 GB） |
| 域名 | **待选定**（品牌已定，域名未定） |
| DNS 服务商 | 待确认 |

**内存估算与降级建议**见 `deploy/README.md` §3。结论：
**2 GB 跑全套是紧的**，两个模型（语音约 500 MB–1 GB、OCR 约 300–600 MB）先后常驻后容易 OOM，
而 OOM 在容器里表现为**静默重启**（"用着用着 502 一下"，很难查）。

**建议顺序**：① `LIBELLUM_WHISPER_MODEL=base` → ② 加 2 GB swap →
③ 只跑记账主路径（不调用 OCR/语音）→ ④ 才考虑升级内存。
**⚠️ 不建议在实测内存之前买更贵的服务器。**

## 11. 长期开发与发布流程

```
Windows 开发机                    GitHub                     服务器
─────────────                    ──────                     ──────
pnpm typecheck                   CI：干净库跑迁移
pnpm -r test               →     → 类型检查            →     git checkout <commit>
pnpm check:build                 → 全量测试                  ./deploy.sh --version X.Y.Z
pnpm check:docs                  → 真实构建                  健康检查不过 → 报告 + 回滚路径
pnpm check:db                    （**不部署**）
git push ──────────────────▶
```

| 问题 | 答案 |
|---|---|
| SSH 密钥 | 生成 ed25519 密钥对，公钥放服务器 `~/.ssh/authorized_keys`；私钥只在本机 |
| 独立运维账号 | 建议建一个 `deploy` 用户（不用 root 直接登录），加入 `docker` 组 |
| **`docker` 组的权限** | ⚠️ **等价于 root**——能用 docker 的人可以挂载宿主机 `/`。**当 root 对待** |
| 是否用 Actions 自动部署 | ❌ **不用**（所有者要求发布需人工确认） |
| 如何避免 main 更新就上线 | **CI 不部署**；上线只能由人在服务器上跑 `deploy.sh` |
| 如何发布指定版本 | `./deploy.sh --version 1.10.24`（不打版本号会拒绝执行） |
| 如何回滚 | 只改代码 → 切 commit 重新部署；改了 schema → 读迁移后决定，必要时 `restore.sh` |
| 如何跑迁移 | **自动**：compose 里的 `migrate` 服务，`api` 等它成功后才启动 |
| 如何检查版本 | 站点「账户 → 软件更新」；或 `deploy/.last-deployed` |
| 如何备份 | `./backup.sh`（含恢复演练）；建议 cron 每日 |
| 如何恢复 | `./restore.sh backups/<文件>.dump`（会先做安全副本） |

**⚠️ 不需要 Kubernetes，也不需要多环境集群。** 一台服务器、一个人维护。
