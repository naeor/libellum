# S8 第 2 轮：离线记账 / 改 / 删（同步队列）

> **状态**：⏳ 进行中（2026-10-11 开始）
> **前置**：第 1/1.5 轮（离线**读**）✅ 已完成并双真机确认。
> **本轮的验收标准**：**飞行模式下能记账、能改、能删，恢复网络后不重复、不丢。**

---

## 1. 服务端**已经**准备好了什么

**这一轮不是从零开始**——`prisma/schema.prisma` 的注释就是为它写的：

| 已有 | 原话 | 它解决什么 |
|---|---|---|
| **`idempotency_key`**（`@unique`，客户端生成） | **"makes a retried upload harmless — the same key can only ever produce one row"** | **重放不重复**。网络抖动导致的重试、离线队列的重复投递，都只会产生一行 |
| **`version` + `deleted_at`**（软删除） | **"a tombstone, never a hard delete — let a device that was offline learn what changed without resurrecting data"** | **冲突检测**（服务端已有 `version_conflict`）+ **删除不会复活** |
| `POST /transactions` | 已有两段幂等处理（先查 key、再处理竞态） | 创建 |
| `PATCH /transactions/:id` | **要求带 `version`**，不符即 `409 version_conflict` | 修改 |
| `DELETE /transactions/:id` + `POST /:id/restore` | 软删除 | 删除 |

**⚠️ 所以本轮要写的是"客户端怎么排、怎么重放"，而不是"服务端怎么支持"。**

---

## 2. 三个基本决定

### 2.1 ⚠️ 队列存"每个实体的**最终意图**"，不存操作流水

**两种做法**：

| 存操作流水 | 存最终意图 ✅ |
|---|---|
| 离线期间改同一笔三次 → 三条记录，重放时发三次 | **一行，只发最后一次** |
| 需要按顺序重放 | **顺序无关** |
| 中间状态会成为"用户其实没想要的结果" | **存的正是用户想要的结果** |

**决定**：**一行一个实体**（用实体 id 做主键），保存**它的目标状态**。

**⚠️ 为什么这是对的**：用户在离线时改三次，**他想要的是最终那一版**。
把中间两版也发给服务器，是把"过程"当成"意图"——**而过程是实现的细节。**

### 2.2 ⚠️ 本地立即生效，服务器稍后跟上

**做法**：一次离线写入＝**同时**做两件事：

1. **改本地存储**（`ledger-months`，见 `离线与同步-设计决定.md` §1b）→ **界面立刻变**；
2. **写队列**（outbox）→ 联网后投递。

**⚠️ 两条路各自独立**：
**本地那份是"给用户看的"，队列那份是"给服务器看的"。**
**任何一条失败都不能让另一条不动**——**否则一次写入失败会让界面看起来没反应。**

### 2.3 ⚠️ 不在本轮做冲突**解决**，但要能**发现**并**留住**

**服务端用 `version` 做乐观锁**：客户端提交时带它"看到的版本"；
若服务器上已经是更新的版本，返回 `409 version_conflict`。

**本轮的处理**：

| 情况 | 做法 |
|---|---|
| 服务端版本 == 客户端所见版本 | ✅ 正常提交 |
| 服务端版本 ≠ 客户端所见版本 | ⚠️ **把这条移进"冲突"状态，保留双方的版本**，界面显示"有 N 笔需要处理" |

**⚠️ 冲突的对比与选择界面是第 3 轮**（所有者已定：**默认自动合并不冲突的字段，
只问冲突的字段，并且"自动合了哪些"必须显示出来**）。

**⚠️ 但本轮必须把冲突的原始材料留住**——否则第 3 轮无从做起：
**要留下"我方这一版"、"服务端那一版"、以及"我离线时看到的那个版本"三个快照。**

## 3. 存储结构

### 3.1 队列（`outbox`）

| 字段 | 说明 |
|---|---|
| `id` | 实体 id（**本身就是主键**——保证"一行一个实体"） |
| `op` | `create` / `update` / `delete` |
| `payload` | **目标状态**（`create` 与 `update` 用；`delete` 为空） |
| `baseVersion` | **离线时看到的版本**——提交时带上去做乐观锁 |
| `queuedAt` | 入队时间（**只用于显示"最久的一条等了多久"**，不用于排序） |
| `attempts` | 重试次数 |
| `lastError` | 上次失败原因 |
| `conflict` | 服务端**当前**那一版（仅冲突时存在） |

**⚠️ `baseVersion` 是这一轮的关键字段**：
**没有它就无法区分"我在改一笔没人动过的账"和"我在改一笔别人已经改过的账"**，
而这两种情况的正确处理完全不同。

### 3.2 本地账目上的标记

| 字段 | 说明 |
|---|---|
| `pending` | 是否还没同步（界面显示"待同步"） |
| `deletedLocally` | 本地已删（**软删，保留原始数据以便冲突对比**） |

## 4. 重放协议

**触发时机**：① 网络恢复；② 应用回到前台；③ 用户手动点"立即同步"；④ 每次写入后尝试一次。

**每一步**：

```
取出最久未成功的一条
  ├── create  → POST /transactions     （带 idempotencyKey = 实体 id）
  ├── update  → PATCH /transactions/:id（带 version = baseVersion）
  └── delete  → DELETE /transactions/:id
        │
        ├── 2xx  → 从队列移除，把本地标记为已同步
        ├── 409  → 移入"冲突"状态，保留双方快照（本轮的终点）
        ├── 4xx  → 这条是**永久失败**（例如分类被删了）→ 标记出来，不再重试
        └── 5xx / 网络 → 留在队列里，退避后重试
```

**⚠️ 三条纪律**：

| 纪律 | 理由 |
|---|---|
| **一次只投一条，按 `queuedAt` 从旧到新** | 并发投递会让"顺序"变成不可预测的；而用户能感知的是"最早那笔还没上去" |
| **4xx 与 5xx 分开处理** | **5xx 是"稍后再试"，4xx 是"再试一万次也一样"**——**把 4xx 当可重试，会让队列永远卡在第一条** |
| **重试有退避、有上限** | 无限重试等于无限耗电；上限之后标记为"需要你处理" |

|---|---|

## 7. 验收（所有者要在场）

> 🔴 **需要所有者开飞行模式真机实测。**

| # | 场景 | 期望 |
|---|---|---|
| 1 | 飞行模式 → 记一笔 | **立刻出现在明细里**，带"待同步"标记 |
| 2 | 飞行模式 → 改一笔 | 同上 |
| 3 | 飞行模式 → 删一笔 | 从明细里消失，带"待同步"标记 |
| 4 | 恢复网络 | **N 笔全部上去，且服务器上不多不少** |
| 5 | 恢复网络后刷新 | **记录与离线时看到的一致**（不重复、不复活） |
| 6 | 飞行模式记账 → **杀掉应用** → 重新打开 | **那笔还在**（队列是持久的，不是内存里的） |
| 7 | 同一笔在**另一台设备**上改过 → 本机离线改它 → 恢复 | **不静默覆盖**，出现"有 1 笔需要处理" |

**⚠️ 第 6 条最容易漏，也最重要**：
**"杀掉应用后还在"是"真的存在本地"和"只是记在内存里"的分界线。**
