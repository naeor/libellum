## 0. 这份文档的定位

开篇原话式的定位：

- 开发过程中提出过很多"先不做，但别忘了"的想法，之前散落在对话、技术方案和开发日志里，**没有完整整合**。这份文档把它们**全部集中到一处**，并写清楚做判断所需的信息。
- **开发顺序由项目所有者决定**，文档只负责把信息整理齐，**不替所有者排序**。

### 0.1 怎么读这份文档（§1）

每一项包含**六列**：

| 列 | 含义 |
|---|---|
| **编号** | 便于讨论时引用，例如"先做 B2" |
| **想法** | 一句话说清是什么 |
| **为什么想要** | 提出时的意图（这决定了它值不值得做） |
| **前置条件** | 做它之前必须先有什么；没有前置的可以随时开工 |
| **规模** | 小＝半天内／中＝1–2 天／大＝3 天以上 |
| **表结构余地** | 文档自称"**最容易被忽略的一列**" |

**"表结构余地"分两级，别被它吓到：**

| 级别 | 含义 | 以后改的代价 |
|---|---|---|
| **需要** | 改的是**已存数据的含义**，或必须是**记账当时**才能记录的信息 | 迁移真实数据；**可能产生歧义、无法回填** |
| **不需要／不必现在加** | 加一张新表、或加一个带默认值的列就能解决 | **零迁移**，随时可加 |

> **重要态度修正**：文档明确承认早期把一切都标成"需要留余地"，**那是过度紧张**。"加一张新表、或加一个带默认值的列，对已有数据没有任何影响，**完全不需要现在决定**。"
> 真正需要提前拍板的只有第一级，而**到目前只出现过一条——金额小数位，且已毕业（见 §2.1 B1）**。

### 1.5 §2.0.1 邀请码有效期与撤销（**已实现** 2026-10-10）

| 类型 | 有效期 | 可撤销 |
|---|---|---|
| **普通邀请码**（`pnpm invite:create`） | **7 天** | ✅ |
| **预留编号的码**（`pnpm invite:batch`、首批那批） | **永不过期** | ❌ |

**为什么分两种**：码是**在聊天窗口里传递的凭据**。普通码的用途是"现在给某人注册"——七天足够送达、被看到、被使用，而且**发错了能收回**；而预留编号那批是**写在卡片上、几个月里陆续发出去**的，**七天寿命会让它根本发不出去**。

**三种失效原因分开报**：`invite_used` / `invite_revoked` / `invite_expired`。理由：**"邀请码无效"这句话告诉不了对方任何可行动的信息**——这条规则来自"暂无分类"那次教训。

> ⚠️ **界面还没做**：撤销目前走数据库或脚本。邀请列表与撤销按钮排在协作阶段（S9）。

#### C2 · 汇率折算（详细）

**已决定的口径**：按**记账当时的汇率**折算，**不是**用今天的汇率去算过去的账。

> 理由原话：用当前汇率折算历史账目，**等于每次看报表金额都在变**，而且**反映的不是当时真实的购买力**。

**数据源调研（2026-10-09）**

| 候选 | 权威性 | 是否免费可抓 | 历史数据 | 结论 |
|---|---|---|---|---|
| **[Frankfurter](https://frankfurter.dev/)** | **104 家央行与官方机构**，含欧洲央行与**中国人民银行（CFETS）**，覆盖 **223 种货币** | ✅ **无需 API Key、无调用配额** | ✅ **可回溯到 1948 年** | **首选** |
| ECB 官方每日参考汇率 | 欧洲央行本体 | ✅ 公开 XML | ✅ | 备选（Frankfurter 的上游之一） |
| 中国人民银行 / 国家外汇管理局中间价 | 对人民币最权威 | ⚠️ 抓取形式不如 API 规整 | ✅ | 将来若需精确到人民币中间价再单独接 |

**选 Frankfurter 的理由**：它是唯一**同时满足四个条件**的——**权威（央行数据）**、**免费可抓（无 key、无配额）**、**有完整历史（能按当时汇率折算）**、**可按来源过滤**（`?providers=ecb` 只用单一官方来源，官方说明这适用于合规场景）。项目开源，**也可自建（Docker）以免依赖第三方可用性**。

**设计草案（6 条）**

1. **新表 `exchange_rates`**：`base` / `quote` / `rate`（高精度 numeric）/ `rate_date` / `source` / `fetched_at`
2. **每天抓取两次**：**00:01** 与 **12:01**（用户建议，实现上只是定时任务多一个时间点，成本几乎为零）
   - ⚠️ **但要先认清一件事**：**上游本身就只每天更新一次**——欧洲央行在每个工作日约 **16:00（中欧时间）** 发布当日参考汇率，Frankfurter 只是转发。**所以第二次抓到的通常和第一次完全一样，"精度更高"这个预期并不成立。**
   - **因此抓取时间应该对齐上游的发布时刻**，否则抓到的永远是"昨天"的数据。建议：
     - **一次放在上游发布之后**（ECB 16:00 CET ≈ 北京时间 22:00–23:00，所以定 **23:30** 比较稳），保证拿到当日汇率
     - **一次放在 12:01 做兜底**，覆盖"某天抓取失败"的情况
   - 用户原意是"两次、间隔不超过 12 小时"，**两次没问题，只是别期待数据会更新两次**。
3. **记账时把"当时汇率"写进流水本身**——这正是"按当时汇率"能成立的关键
4. **取不到最新数据时**：使用**已记录的最近一期**，并在界面标明用的是哪一天的数据
5. **免责提示（必须，措辞要防御性）**：界面需同时说明三件事——
   - **按哪一天的汇率折算**（例如"按 2026-10-09 汇率折算"）
   - **不保证汇率准确**（明确写出，而不是含糊的"仅供参考"）
   - **请用户自行核实**，实际结算以银行成交价为准
   > 用户明确要求措辞更有防御性。**只说"仅供参考"太软**——它没有划清责任边界。不告诉用户这个数字有多旧，免责声明本身也就失去了意义。
6. **协议注意**：Frankfurter 明确说明汇率数据本身遵循**各提供方的条款**，对外发布时需注明来源

**表结构余地**：**不必现在加。** 与"金额小数位"（B1）不同，这一条**可以事后回填**——Frankfurter 提供历史汇率，将来能按每条流水的日期逐条查出当时的汇率。**但现在加成本最低**，而且能摆脱"依赖第三方历史数据长期可用"的隐忧。**决定权在所有者。**

## 3. 【重点】I8 详述：「浏览器其它」是什么

### 3.1 问题来源（所有者 2026-10-11 原话）

> **"我一直想知道这个浏览器及其他到底是啥——一直占我空间还删不掉！"**

**要求**：**加一条待办，在正式上服务器之前查一下这是什么东西以及怎么删除，希望前人有充分的经验。**

### 3.2 结论：它是浏览器的 HTTP 缓存，而网页无法用代码清除它

| 问题 | 答案 |
|---|---|
| **它是什么** | **浏览器自己的 HTTP 缓存**（存原始响应），**不属于** IndexedDB，也**不属于** Cache Storage |
| **为什么删不掉** | **Web 平台没有任何 API 能清 HTTP 缓存。** `caches.delete()` 只清 **Cache Storage**（Service Worker 那一套）——**而应用已经在"清除本应用的全部本地数据"里清光了它**，所以那个按钮对这部分**天然无能为力** |
| **它为什么这么大** | **开发模式**：Vite 按需提供**未打包的模块**，每个模块一个请求、每个都进 HTTP 缓存；**而且没有关 sourcemap**，每个模块还带一份源码映射 |
| **它为什么涨** | 每次刷新都要重新拉一整套模块（**开发服务器不复用浏览器缓存**），旧的条目仍按源记账 |

### 3.3 实测数字（2026-10-11，本机）

| 项 | 开发模式 | 生产构建 |
|---|---|---|
| **一次加载要拉的量** | **142 个源文件 + 约 309 个依赖包，逐个请求** | **1 个 JS（610 KB）+ 1 个 CSS（37 KB）+ HTML/SW（9 KB）** |
| **产物总体积** | `node_modules/.vite` 预打包 **6.26 MB**（还会被 sourcemap 放大） | **655 KB** |

> ⚠️ **所以那个 68.9 MB 里，真正"属于账本"的可能只有几百 KB**——**其余是开发模式自己制造的，而且它在浏览器眼里是"页面缓存"，不是"我们的数据"。**

### 3.4 怎么清除（分两种，各有前提）

| 场景 | 做法 |
|---|---|
| **只想清缓存，不动账本**（推荐先试这个） | **Chrome / Edge**：`F12` → **Network** → 勾 **Disable cache**（开发时）；或 **Application → Storage → Clear site data** 里**只勾"Cache storage / 缓存的图片和文件"**。<br>**Safari（iOS）**：**设置 → Safari → 清除历史记录与网站数据**——⚠️ **但这一个会连 IndexedDB 一起清掉，见下方警告** |
| **彻底清（含账本）** | 用应用里的**「清除本应用的全部本地数据」**，或浏览器的"清除网站数据" |

> ### ⚠️ 动手之前必须先确认一件事
>
> **HTTP 缓存、IndexedDB、Cookie 是按"源"（origin）算的，很多浏览器把它们放在同一个"网站数据"里**——
> **"清除网站数据"会连我们的离线账本一起删掉。**
>
> **所以清除之前**：**确保账本已经全部同步到服务器**（**明细页没有淡绿/淡红的行**），
> **否则那些只在本机的改动会一起没掉。**
> **这与 `归档/离线与同步-设计决定.md` 的立场一致**：**"缓存是用户唯一的离线副本"**——
> 所以**任何"小心起见清掉缓存"的做法都是错的**，除非用户明确知道自己要清什么。

### 3.5 根治办法：日常用生产构建，而不是开发服务器

- **开发模式（`pnpm dev`）本来只是"我改代码时看的"，不是"给人用的"。**
- 所有者日常在手机上用时，**应该用生产构建**——那时每次加载只拉 **3 个小文件**，HTTP 缓存自然几乎不增长。
- **这件事归到 S10（可上线）**：那时有真正的域名与 HTTPS，手机上用的是构建产物。

> ⚠️ **顺带一条可以直接减负的**：`vite.config.ts` **没有关 sourcemap**，开发模式下每个模块都带源码映射。**关掉它（或只在需要时打开）能立刻让开发模式的缓存占用小一大截**——但**这属于代码改动，要按规矩升版本 + 写版本记录**，所以**留到有明确需要时再做**。

### 3.6 ✅ 已排期：上线时关掉开发服务器（所有者 2026-10-11 点名加的一项）

**所有者原话**：

> **"关于开发者缓存：现在还是开发状态，所以肯定没办法做。但是你可以在待办名单里加一项。
> 程序在上线前关掉开发服务器。这样一来，用户应该不会再出现这样的问题了吧。"**

**已写入 `ROADMAP.md` 的 S10（可上线）任务与验收标准**：域名指向 `apps/web/dist` 的静态产物，`pnpm dev` 只留在开发机上；**顺手关掉开发模式的 sourcemap**。

**⚠️ 而"这样一来就不会再出现"这句话，要答得准确一点：**

| 问题 | 上线后会怎样 |
|---|---|
| **开发模式那几十万个模块请求** | ✅ **消失**——家人访问的是构建产物，一次加载只拉 3 个文件 |
| **sourcemap 放大** | ✅ **消失**（前提是关掉它） |
| **Service Worker 的外壳缓存** | ⚠️ **仍然会有，但它是有限的**：3 个文件、约 655 KB，而且**只在版本变化时才更新**——**不会再持续增长** |
| **`storage.estimate()` 报的数** | ⚠️ **仍然会略高于真实数据**——它包含浏览器还没落盘的部分。这是浏览器的记账方式，**不是我们的泄漏**，也**无法由程序消除** |

**结论**：**"每刷新一次就涨"这个现象会消失**，占用会稳定在一个小而固定的量级（预计**几百 KB 到 1–2 MB**，不再是无上限增长）。**但 `estimate()` 那个数字本身永远会比真实数据大一点**——**这不是 bug，是浏览器的记账口径**，所以文档明确**不承诺"这个数字会变成账本的真实大小"**。

**⚠️ 一条现在仍然成立的警告**（上线前后都一样）：**HTTP 缓存、IndexedDB、Cookie 同属"网站数据"**，**很多浏览器"清除网站数据"会连离线账本一起删**——所以清之前必须确认**明细页没有淡绿/淡红的行**。

**⚠️ 还有一件事要分开看**：**开发服务器不能"完全删掉"**——真机调试仍然需要它（手机通过局域网 https 访问，见 `docs/README.md`；而且 **Service Worker 只在生产模式下注册**，所以**离线功能只能在构建产物上测**，见 `worker.ts`）。**要分的是"谁在用它"**：**开发服务器给开发机，构建产物给家人。**

**参考**：`docs/归档/离线与同步-设计决定.md` §4.5d（**52.5MB 与 127KB 的差**）。

## 4. 【重点】I9 详述：`idempotencyKey` 与 `id` 不同源（**独立缺陷，仍然真实存在**）

### 4.1 条目原文要点

- **标题**：⚠️ 拍照页 / 语音复核页的 `idempotencyKey` 与 `id` 不同源
- **代码事实**：
  - **`ScanPage.tsx:339-340`** 与 **`VoiceReviewPage.tsx:278-279`** **各自生成两个 `uuidV7()`**（即 `id` 一个、`idempotencyKey` 另一个，两者互不相同）。
  - **其余所有写入路径统一 `idempotencyKey = id`**：
    - `AddEntryPage.tsx:192-195`
    - `sync.ts:371`
- **后果**：**这两条路径的请求被重发时，服务端基于 `idempotency_key` 的去重保护不生效，会产生第二笔记账。**
- **重要限定**：**与"离线拍照"无关，是独立缺陷**——"离线不做，但**这个仍然真实存在**"。
- **规模**：小
- **状态**：**待定**

### 4.2 为什么这条重要

1. **这是一条"看起来像离线遗留、其实不是"的缺陷**。S8 第 4 轮（离线拍照排队）被取消后，文档特意把"拍照页/语音页改走离线写路径"顺带要补的这两个问题**单独拎出来编成 I9 / I10**，明确"I9 需要时再单独决定"。
2. **它的触发条件是"请求被重发"**——不需要离线。任何网络重试、用户重复提交、客户端重放都可能触发。
3. **服务端的幂等保护机制本身是有的**（基于 `idempotency_key` 去重），**只是这两条路径没有把 key 和 id 对齐，导致保护空转**。
4. **修复面很小**（规模"小"）：把两处双重 `uuidV7()` 改成 `idempotencyKey = id`，与其它写入路径一致即可；**但状态是"待定"而非"待做"**——说明所有者尚未拍板是否现在改。

### 4.3 涉及的精确位置清单（供后续修）

| 位置 | 行为 | 是否合规 |
|---|---|---|
| `apps/web/src/pages/ScanPage.tsx:339-340` | 生成两个 `uuidV7()`（id 与 idempotencyKey 不同源） | ❌ **缺陷** |
| `apps/web/src/pages/VoiceReviewPage.tsx:278-279` | 同上 | ❌ **缺陷** |
| `apps/web/src/pages/AddEntryPage.tsx:192-195` | `idempotencyKey = id` | ✅ 正确 |
| `sync.ts:371` | `idempotencyKey = id` | ✅ 正确（离线写路径） |

# 第二部分：`docs/COLORS.md` —— 颜色清单（COLORS）

## 1. 文档定位与由来

**这份文档回答一个问题：某个位置用的是哪个颜色，它是"可以动的主题"还是"不能动的数据"。**

- 最后更新：**2026-10-11**（补上冲突态新增的琥珀色警告令牌；更正 `#3f7a5f` 的出处）。
- **配套的两个"唯一处"**：
  - `apps/web/src/index.css` —— **唯一的令牌定义处**
  - `apps/web/src/lib/chart/theme.ts` —— **唯一的图表调色板定义处**

**用户（项目所有者）原话**：

> "把颜色全写成硬编码可是最蠢的设计了。但说到这个，界面当前使用的绿也不是同一种绿吧？
> 回头单独整理出来哪些页面用了哪样的绿色，有哪些用的是相同的绿色，这样到时候做主题色的时候，
> 只要找到几种不同的绿色或者几种不同的红色就可以一键替换了。"

> ⚠️ **写这份文档时发现的一个事实**：界面里**只有一种绿**（`#55997a` 及其深浅两档）。看起来"好几种绿"其实来自两个不同的地方：**热力图的一条五档色阶**，以及**图表调色板的第一格**——而后者当时**正好等于主题绿**，**这是真问题**（见 §4.1）。

**查证结果：一共有 27 种颜色** = **15 个语义令牌** + **8 个分类色** + **5 个热力色**（`#b8574f` 同时出现在令牌与调色板里，**只算一次**）。秩序是好的，但**混了两套**。文档把它们分开，并给出每一处的归属。

> ⚠️ **这个数字在 2026-10-11 由 26 改成 27**：S8 第 3 轮（冲突）新增了**琥珀色警告令牌** `--color-warn` 三件套。
> **一个"清点结果"是有保质期的**——它记的是清点那天的代码，不是永远。

## 2. 核心概念：**两套积木，相乘而非相加**

界面的美术逻辑是**两套独立的积木**：

```
  基准套装（明暗轴）        ×        强调积木（色相轴）
  ────────────────                  ──────────────
  画布 / 卡片底色                     那一个主色
  正文色 / 次要文字                   它的深、浅两档
  分隔线                             它自己可读的深色
```

| 积木 | 换什么 | 将来"深色模式"换的是它 | 将来"主题色"换的是它 |
|---|---|---|---|
| **基准套装** `--color-canvas / --color-surface / --color-ink / --color-muted / --color-line` | **明暗** | ✅ | ❌ |
| **强调积木** `--color-brand / --color-brand-dark / --color-brand-soft / --color-accent-ink` | **色相** | ❌ | ✅ |
| **状态积木** `--color-danger*`（+ `--color-warn*`） | **含义**（红=出错） | ❌ | ❌ **永远不跟着换** |

### ⚠️ 为什么必须一起做（这也是所有者要求"深色和主题色一起做"的原因）

**同一个绿色，在浅色底和深色底上不该是同一个值。**

| | 浅色底（现在） | 深色底 |
|---|---|---|
| 主题绿需要 | **深一点**（`#55997a`）——对比近白底才有足够对比度 | **浅一点、去饱和**——深绿放在近黑底上会糊成一团 |
| 文字色需要 | 深墨绿 `#24312b` | 接近白 |

所以**基准套装决定强调积木的明度档位**：不是"深色模式下把绿色原样搬过去"，而是"**深色模式需要另一档绿色**"。这也是为什么主题色与深色模式**不能分两次做**——第一次做完，第二次还要把所有颜色再过一遍。

## 3. 语义令牌清单（定义处：`apps/web/src/index.css`）

**命名原则**：**令牌名说的是"它去哪儿（职责）"，不是"它长什么样"。**

`--color-brand` 之所以看起来像"外观"，是**因为历史原因**：
- **2026-10-10 清点为 467 处类名引用它**；
- **2026-10-11 复数为 169 处**——**数字本身会变，别拿它当工作量估算的依据**；
- 它的职责其实是"**那一个强调色**"。

### 3.1 基准套装 —— 明暗轴（5 个令牌）

| 令牌 | 当前值 | 职责 | 用在哪 |
|---|---|---|---|
| `--color-canvas` | `#fafcfb` | **页面底色**（卡片之外的一切） | `body` 背景、列表页背景、卡片之间的缝隙 |
| `--color-surface` | `#ffffff` | **卡片/面板底色**（浮在画布上的东西） | 所有 `bg-surface`：列表容器、输入框、弹窗、图表 tooltip |
| `--color-ink` | `#24312b` | **正文与标题**（最高对比度） | 金额、标题、正文 |
| `--color-muted` | `#6b7f76` | **次要文字**（说明、标签、时间） | 分组标题、辅助说明、未选中的 Tab |
| `--color-line` | `#e3ede7` | **分隔线与描边** | 列表分隔、卡片边框、图表边框、输入框描边 |

### 3.2 强调积木 —— 色相轴（4 个令牌）

| 令牌 | 当前值 | 职责 | 用在哪 |
|---|---|---|---|
| `--color-brand` | `#55997a` | **主强调色**（可点、可选中、品牌） | 主按钮底、顶栏底、Tab 高亮、图形品牌区、默认头像花瓣 |
| `--color-brand-dark` | `#447d63` | **主强调色的按下态 / 深色文字** | 按钮 hover、`text-brand-dark` |
| `--color-brand-soft` | `#edf5f0` | **主强调色的浅底**（次级按钮、提示条） | 次级按钮、记账小卡片、提示块、默认头像花心 |
| `--color-accent-ink` | `#8fa39a` | **强调色系的"小字灰"** | **图表**坐标轴与图例文字、环形图中心"合计"、卡片 tooltip 内小字 |

> **`--color-accent-ink` 为什么单独一个令牌**：它以前是写死的 `#8fa39a`，和 `--color-muted` 很像但**职责不同**——正文的次要文字要满足"**长句子可读**"，图表上的小字要满足"**10px 下仍能分辨**"。**两者的对比度要求不一样**，所以哪怕现在颜色接近，**也不该合并成一个**。

### 3.3 状态积木 —— 含义轴（6 个令牌，两组三件套）

| 令牌 | 当前值 | 职责 | 用在哪 |
|---|---|---|---|
| `--color-danger` | `#b8574f` | **错误 / 破坏性操作** | 错误提示、删除文字、危险确认按钮 |
| `--color-danger-dark` | `#9c4740` | 危险色的按下态 | 危险按钮 hover |
| `--color-danger-soft` | `#fbefee` | 危险色的浅底 | 错误提示条背景 |
| `--color-warn` | `#b07d2b` | **需要人做决定的状态**（当前就是"冲突待选"） | 冲突行的琥珀色底、冲突提示文字 |
| `--color-warn-dark` | `#8f6420` | 警告色的按下态 / 深色文字 | 警告按钮 hover、`text-warn-dark` |
| `--color-warn-soft` | `#fdf6e7` | 警告色的浅底 | 冲突行背景（`bg-warn-soft`） |

> **⚠️ 为什么"警告"是第三种状态，而不是借用红或绿**（`index.css` 里的原话）：
> **冲突既不是"出错"，也不是"只是在等"**——**没有任何东西失败，也没有东西仅仅在等待**。
> **红色**会对一个"需要做决定"的情况说"**出问题了**"；**绿色**会对一个"**用户不回答就永远不会发出**"的行说"**等着发送**"。
> **它是"未同步"（绿）和"出错"（红）之外的第三种，所以它有自己的颜色。**
>
> **⚠️ 而这个令牌是 2026-10-11 补上的**：**删账当初借用了错误色**，当时的记录写着
> **"如果以后要区分'未同步'和'出错'，加一个琥珀色警告令牌才是诚实的做法"**——**冲突这一轮兑现了它**。
> **本节此前只列了 `danger` 三色，是遗漏。**

> **状态色不参与主题化。** 换成蓝色主题时"错误"仍然是红的、"警告"仍然是琥珀的——**它表示含义，不表示品牌**。它只跟**明暗**一起调整（深色底上的 `#b8574f` 偏暗，**需要提亮**）。

## 4. ⚠️ 图表调色板：**值，不是令牌**（定义处：`apps/web/src/lib/chart/theme.ts`）

`theme.ts` 里的颜色**故意不写成 `var(--…)`**，原因有三条，都很实际：

1. **要交给 SVG 当字符串用**，还要**被测试断言**（`expect(pie).toContain(color)`）；
2. **它是"数据"不是"主题"**：一张图里 **8 个分类各要一个互相可分辨的颜色**，这是"**可区分性问题**"，与"品牌色是什么"无关；
3. **深色模式需要另做一条色阶**，而不是把这条重新上色（**浅色底可分辨的一组色，放到深色底上未必还可分辨**）。

### 4.1 分类调色板 `CATEGORICAL_COLORS`（8 色）

| 序号 | 值 | 说明 |
|---|---|---|
| 1 | `#3f7a5f` | ⚠️ **2026-10-10 换过**：原来是 `#55997a`，**与主题绿完全相同** |
| 2 | `#4a7fb5` | 蓝 |
| 3 | `#c08a3e` | 橙 |
| 4 | `#b8574f` | 红（与 `--color-danger` **同值，但用途无关**） |
| 5 | `#7a6bb0` | 紫 |
| 6 | `#5d8c8c` | 青 |
| 7 | `#8a8f5c` | 橄榄 |
| 8 | `#a86f9a` | 洋红 |

**为什么要换第 1 个色**：主题绿同时是"品牌色"和"数据系列第 1 色"，导致**每一张环形图的第一块，和它上面的按钮是同一个绿**——**读者分不清"这块颜色是主题还是数据"**。换成 `#3f7a5f`（**更深、更灰**）后，**主题归主题、数据归数据**。

### 4.2 热力图色阶 `HEAT_COLORS`（5 档）

| 档 | 值 | 含义 |
|---|---|---|
| 0 | `#eef1ef` | **当天无记录**（中性灰，**故意不是绿**——"**没记**"和"**花得少**"**是两件事**） |
| 1 | `#d7e8dd` | 最少 |
| 2 | `#a9d0ba` | 较少 |
| 3 | `#79b596` | 较多 |
| 4 | `#4b8a6d` | 最多 |

> 这是**一条色阶**（**同一色相的五档**），不是"五个碰巧不同的绿"。**不要合并成一个令牌**，也**不要因为"深色模式"就删掉档位**。

### 4.3 标签色板

`ManagePages.tsx` 里创建标签时提供的色块**直接复用 `CATEGORICAL_COLORS`**。

理由：**标签颜色和图表系列色是同一类东西**——**用户挑的、需要彼此可分辨的值**。以前两者各写一份，于是同一批颜色**在两处慢慢分叉**（旧列表里也含主题绿）。

## 6. 将来怎么做主题（照这个顺序，**五步**）

1. **第一步：把"基准套装"抽出来**
   把第 3.1 节的五个令牌变成**两组值（浅色一组、深色一组）**，用 `:root[data-theme="dark"]` 切换。
   **这一步不需要动任何组件**——**467 处类名已经在用语义令牌了**。
2. **第二步：给强调积木定"每档明度"**
   不是"深色模式下也用 `#55997a`"，而是**为深底挑一档更浅、更去饱和的绿**，并**同步调整 `--color-accent-ink`**（深底上它要**变亮**）。
3. **第三步：状态积木跟着明暗调**
   **只调明度，不调色相**。
4. **第四步：图表单独走一遍**
   `CATEGORICAL_COLORS` 与 `HEAT_COLORS` **各自需要一条深色版色阶**，并**在深色底上重新验证可分辨性**。
5. **第五步：主题色自选**
   **只换「强调积木」三个值（+ `--color-accent-ink`）**，**基准与状态一律不动**。

> ⚠️ **顺序不能反**：**先定明暗、再定色相**。反过来会得到"**深色底上放浅色主题绿**"这种需要**全部重做一遍**的结果。

## 7. 维护规则（写进纪律，四条）

1. **组件里禁止硬编码颜色**——加颜色先问"**它属于哪套积木**"，属于就**加令牌**，不属于（数据）就**放 `theme.ts`**；
2. **改令牌只改 `index.css`**；**改图表色只改 `theme.ts`**；
3. **新增颜色必须同时更新本文档的第 3 或第 4 节**；
4. **主题色与深色模式要一起做**（§2 的乘法关系）。

## 2. 需要最优先记住的几条

1. **唯一真正"必须现在决定"的表结构问题只有 B1（金额小数位按币种），且已于 2026-10-09 毕业。** 其余几乎全是"零迁移、随时可加"，文档明确批评过早期"一律留余地"的过度紧张。

4. **"离线优先"的准确含义**＝**记账主路径（记/改/删/看）离线可用**；**拍照、语音、导出/导入、组织器管理都不离线**（OCR 与 whisper 都在服务器上）。所有者已定稿"不要再问"。
