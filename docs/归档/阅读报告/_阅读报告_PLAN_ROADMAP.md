## 1. 项目定义

### 1.1 已确认功能（v1 范围）

**账号与安全**：用户名+密码登录（argon2id、服务端会话 + httpOnly Cookie、支持"退出所有设备"）；邀请码注册（开源但不开注册）；**一次性恢复码**（注册时生成、用户自存，忘记密码用它重置，**不依赖邮件服务**）；登录限流；**会话策略已推翻**（原文"同时只允许一个账号登录且必须在线"→ **2026-10-11 起一个账号可多设备同时在线**，离线写入与冲突合并按"多设备会分叉"设计）；公开只读演示账号（预置示例数据给招聘方）。

**账本、货币与支付方式**：每账号一本独立账本（注册即自动创建、可改名、账号间完全隔离）；**多币种混记**（同一账本可分别记人民币/美元等，**v1 各币种独立统计，不做汇率折算**）；汇率折算开关预留设置项（**v2 实现**）；**支付方式**（微信/支付宝/现金/其他，可自定义可排序，**v1 不追踪余额**）。

**记账**：记一笔（金额、收/支、分类、支付方式、币种、**记账时刻**、备注）；**收入也记**（明细页直接呈现"这个月花了多少、分了几笔、赚了多少、结余多少"）；截图识别记账（**S5 实现**，图片不落盘）；
- **记账时刻与时区**：默认读手机当前时间（**精确到秒**），同时记录手机所在时区；**统计一律按"记账时的本地日期"**，服务器只存数据。
- **日期绝不沿用**：新建、连续记账、截图识别入账都取**当前时刻**；只有**编辑已有账目**用这笔账**自己的**时刻；**截图识别若读到付款时间，以识别结果为准**。
- **连续记账**：保存后可接着记下一笔，**分类/支付方式/币种全部沿用上一笔，日期绝不沿用**，金额与备注清空。
- **常用金额快捷键**：**不足 10 条记录时**用默认 10/20/100；**达到 10 条后**取最近 30 天出现最多的 **5 个金额**。
- **复制上一笔**：一键复制**全局最近一笔**的结构；**备注自动补全**（联想历史写法，**S12 实现**）。

**分类与标签**：**预设分类注册即生成**（支出 9 类 + 收入 6 类，**纯文字不用图标**）；收支各一套（`categories.kind` 区分）；**分类界面永远有值**（首次记账默认"无分类"，之后沿用上一笔）；自定义分类（增删改、排序）；**归档而非删除**（① 选择器不再出现 ② 历史流水分类名照常显示、颜色淡一点 ③ 随时可恢复）；**标签**（一笔最多 10 个；**v1 不做二级分类**）。⚠️ **列表页显示标签尚未实现**（"显示前 5 个"的规则还没落地，流水列表不显示标签），详情页显示全部。

**预设分类清单（2026-10-09 定稿，所有者确认）**
- 支出 9 类：餐饮（日常用餐与饮品）、娱乐（游戏、影音与休闲）、服务（通信、会员及其他服务费）、购物（日用品与商品采购）、教育（学费、课程与培训）、转账（转给他人的款项）、生活缴费（房租、水电、物业等固定支出）、交通（通勤、加油与出行）、其他。
- 收入 6 类：转账（他人转入）、工资（薪资与劳务报酬）、奖金（年终奖及各类奖励）、理财（投资、利息与分红）、退款（退货及费用返还）、其他。

> **"无分类"怎么表示（已按实现更新）**：实现上不是空值，而是 `categories` 里一个**真实的系统分类行「暂无分类」**（`is_system = true`）：**不出现在选择器**、**不能改名/归档/删除**，因此 `transactions.category_id` 可以**保持 NOT NULL**，统计、外键、约束三处都不必为"空"写特例。（初稿"可为空"方案已被取代，见 §5.1 差异表。）

**查看与统计**：**明细页（登录后主页）**——顶部主题色底 + 白字显示**该月支出/入账/结余**（**按币种分组，每币种一行**）；中部"支出/收入"两个切换（**默认支出**）；下部白底流水预览，**最新在最上面**，向下滚动加载更早。**多币种展示规则**：按**记账总数额**（支出与收入绝对值之和，不折算）从大到小排序，**只显示前 2 种**，其余收进"其它币种（N）"可展开——**不静默隐藏，避免用户以为钱不见了**（⚠️ 实际实现已改为"币种卡片横条"，见 §7 注）。**流水筛选**：分类/支付方式/标签/币种 + 关键字搜索 + 按日分组。**默认月份**：当月；**若当月无任何记录，自动跳到最近有记录的那个月**。**删除**：软删除 + 底部"已删除·撤销"提示条，**5 秒内可撤回**。**统计（全部要做，S4 实现）**：月度收支趋势折线 · 分类占比饼图 · 环比/同比 · 年度总览 · 每日花销日历热力图 · 另加若干专业向分析；布局"常用的放前面，其余可折叠"。

**数据与体验**：导出 CSV/XLSX（按时间范围）；**CSV 导入历史账**（提供模板，逐行校验 + 错误报告）；**中英双语可切换**；浅色主题（白底 + 单一主题色，后期支持主题色自选）；手机优先（响应式、可加主屏）；**离线可用 ✅ 已交付**（S8，2026-10-11 双真机确认：离线记账/改/删/看历史/看统计/冲突处理；**离线拍照与离线录音已由所有者取消**）。

> **账本模型的取舍（重要）**：v1 做成"一个账号 → 一本自己的账本"；**多人共享账本放 v2**（共享会牵出成员管理、权限矩阵、邀请码、并发冲突一整套界面与接口）。
> **但数据库从第一天就按「可共享」设计**：`books` + `book_members` 两张表照建，v1 每个账本只有一行 owner 记录 → v2 做共享**只写界面和接口，不用改表、不用数据迁移**。这是本方案里**最关键的一处"为未来留门"**。

### 1.3 非功能约束

终端（安卓手机浏览器为主：Chrome/国产厂商/微信内置可看，布局**从 360px 宽度起**自适应）；**大陆可访问性是硬要求**（服务器选香港，不用 Cloudflare/Vercel 默认域名；**延迟目标 < 100ms**）；性能（**首屏 4G 下 3 秒内可用**；列表分页 **20–50 条/页**）；安全（密码不可逆、全程 HTTPS、账号间严格隔离）；成本（**月支出 ≤ ¥100**）；开发条件（**无安卓真机**、有基础编程能力、**主要编码由 AI 协作完成，所有者负责验收/提问/决策**）。

### 1.4 「开源 + 简历」双重目标带来的硬性要求

GitHub 公开托管（仓库干净、README、LICENSE、**密钥绝不进仓库**、`.env.example`）；招聘方点开就能试（稳定公网域名 + **只读演示账号**）；**要能讲出技术深度 → 不推荐纯 BaaS（如 Supabase 一栈到底）**；工程规范（迁移、类型安全、CI、测试、备份、错误处理）；可读性（**英文 README**、提交信息规范、目录清晰、注释适量）；免费=可信（不接第三方统计/广告 SDK，README 写明不收集/不出售数据）。
> 结论：**自建后端 + 认真做开源规范**，比最省事做法多花约 2 个工作日。

### 1.5 ⚠️ 界面内容的第一原则：**这是客户端，不是管理后台**（2026-10-10 所有者定，**高于任何单个页面的设计偏好**）

> 原话大意：**这个网站本质上是一个客户端，所有用户都能看见它上面的东西。** 设计任何界面只问一个问题：**这个用户是否必须要看到它？** 后台数据（如"所有用户的导出记录"）**绝对不能显示在界面上，也不要把这些数据发到前端**。

| 判断 | 结论 |
|---|---|
| 用户自己的数据（账目、资料） | ✅ 可以显示，而且应该显示 |
| **用户自己的操作历史**（如"我导出过哪些文件"） | ✅ 可以显示 |
| **其他用户的数据 / 跨用户汇总** | ❌ **不显示；更关键的是不要发给前端** |
| 服务端审计与运维数据（谁做了什么、错误日志、统计计数器） | ❌ 同上：它是**服务端的记录**，不是客户端的内容 |
| 调试用内部信息（阶段编号、路线图、技术细节） | ❌ 界面文案不得夹带项目内部语境（见 ADR-020） |

**"不要发给前端"比"不要显示"更重要**，三层理由：① 看不见 ≠ 拿不到（开发者工具可读，CSS 隐藏/不渲染拦不住）；② 不发就不会漏（接口存在后，将来某页面/调试开关/重构可能把它显示出来，**最可靠的"不显示"是根本不发送**）；③ 它让权限边界变简单（每个接口只回答"这**一个**用户能看到什么"）。

**落地做法**：审计类接口（如 `GET /api/v1/export-log`）**必须按调用者自己的账本过滤**；**界面不主动调用**这类接口，除非有明确面向用户自己的用途；新增接口先问"**这个响应里有没有一行是别人不该看到的？**"
> 来源：导出页曾显示"导出记录"列表，接口已按账本过滤但**界面本身不该承载审计信息**——所有者指出后列表被删除，客户端也不再请求该接口。

### 1.6 记账入口的设计目的：**任何页面都能直接开始记账**（2026-10-10 所有者明确，并纠正过一次实现）

背景（所有者原话）：底部中央记账键**最初只是一个按钮**（点一下进手动记账页）；后来加了**拍照记账**与**计划中的语音记账**，**没有合适的地方再放两个新按钮**，于是改成"点一下展开一个小界面"，三种方式都在里面。

| 规则 | 理由 |
|---|---|
| **任何情况下点击记账键只做一件事：展开三个选项** | 记账键是**唯一记账入口**；若某些页面变成"直接跳手动记账"，想拍照/语音的人必须先绕一圈；相机与语音**本来就无处安放** |
| **切换到任何其它界面时把三个选项收回（默认关闭）** | 新页面应以**自己的内容**开场，而不是带着上一页打开的菜单 |
| **唯一例外是明细页** | 明细页展示态里三张卡片**是布局的一部分**（占真实空间、不遮盖内容），保持自己的开合；**向下滑进入明细态时收回**（那一刻汇总区刚让出空间） |
| **开合状态全局共享**（不是每页各自一份） | 否则"切页面就收回"无法表达：每个 Tab 不知道别的 Tab 开着菜单 |

> ⚠️ **一次被纠正的实现（值得留下）**：为给分析页与账户页腾空间，曾把记账键在非明细页改成"直接跳转手动记账"。所有者指出这**违背设计目的**（会让拍照与语音更难触达）。**正确做法是"可以展开，但默认收起"**，而不是"不能展开"。这条也修正了 §7 里"记账 = 跳转 `/add`"的旧描述：**中央按钮是开关，不是目的地**；手动记账是开关里的三个选项之一。

## 2. 形态选型：为什么是「Web，APK 备用」

### 2.1 四种形态对比（原生安卓 Kotlin / **Web·PWA（选定）** / 微信小程序 / 混合 Capacitor）

按维度对比：无安卓真机时的开发体验（Web 极好 / 原生极差）、多用户账号（Web 天然支持）、家人加人换机成本（Web 发个链接）、迭代速度（Web 最快）、截图识别记账（Web 好）、断网通知提醒（原生/混合最好，Web 弱）、桌面小组件（原生/混合支持）、导出 Excel/CSV（Web 最容易）、简历可讲度（Web 高）、分发阻力（Web 零阻力，原生要开"未知来源"）、开源友好度（**Web 最好：clone + 两条命令就能跑**）。

### 2.2 定案与理由

**做网页**，四条决定性理由：① **账号系统已经决定必须要有服务端**，所以"APK 不用服务器、数据存本机"的优势不存在；② **没有安卓真机**（纯 APK 路线下一个界面 bug 的成本是"改代码→Gradle 打包→签名→导出→传文件→家人卸载重装"，且无法在他们手机上调试；网页是"我改完，他们下拉刷新"）；③ 家人分居两地，网页天然跨设备跨系统；④ 开源项目要让陌生人能跑起来（网页 = `git clone` + 两条命令）。

**APK 的定位：v2 可选项**——若家人真需要"断网准时提醒"或"桌面小组件"，用 **Capacitor** 把现有网页原样打进安卓壳，加一个本地通知插件，**前端代码零重写**。**不是二选一，而是"先把本体做好，外壳随时能加"**。
> 版本参考（2026-10 核实）：Capacitor 稳定版 **8.5**；官方本地通知插件 `@capacitor/local-notifications` **8.3.1** 仍在维护。8.5 是 breaking minor（改了 iOS UIScene 生命周期），真要套壳时直接上 8.5 并跑一次 `npx cap migrate`。

### 3.1 架构图

三种终端（大陆家人手机 / 境外所有者手机电脑 / 公开访客演示站）→ HTTPS（跨境公网、香港节点）→ **香港轻量服务器 2 核 2G（免 ICP）**：**Caddy 反向代理**（自动申请续期 HTTPS 证书 · 静态资源托管 · `/api` 转发 · 安全头）→ **Node + Fastify API（TypeScript）**（会话鉴权 · 账本权限校验 · Zod 入参校验 · 统计聚合 · CSV/XLSX 导出 · 图片处理）→ Prisma ORM → **PostgreSQL 17**（用户/账本/流水）+ **OCR/语音 sidecar**（首次使用时才拉起）；每日 `pg_dump` 备份，异地保留 7/30 天。前端是 React SPA/PWA，由 Caddy 直接托管静态产物。

### 3.3 离线优先（local-first）架构

> 关键决策：**不做"纯离线"，做"离线优先 + 服务器权威"**。

**为什么不能做纯离线**：纯离线数据只在浏览器 IndexedDB → **清缓存/换手机/手机丢失就全没、无法找回**，且无跨设备、无演示站。记账数据**不可再生**——家人记了三个月，清一次缓存全丢，风险不可接受。

**数据流**：① 界面操作**立即写本地（IndexedDB）**→ 立刻响应不等网络 → ② 变更进入同步队列（带幂等键）→ ③ 联网时按顺序上传 → ④ 服务器（权威副本 + 每日备份）回执确认后，本地记录标记"已同步"。

**四条关键设计（必须在第一批就写进表结构与接口，后补代价很大）**

| # | 设计 | 解决什么问题 |
|---|---|---|
| 1 | **客户端生成 ID（UUID v7）** | 离线记账不必等服务器分配 ID，同步天然幂等 |
| 2 | **幂等键**（每次变更一个唯一 ID，服务端记录已处理集合） | 网络重试**不会重复记账** |
| 3 | **软删除**（打标记而非真删） | 否则离线设备会把已删除的账"复活" |
| 4 | **`updated_at` + 版本号** | 判断新旧；必要时"最后写入者获胜"并保留冲突副本 |

**会话策略 —— ⚠️ 这一条已被推翻（2026-10-11）**：原文（当初定的）"**同时只允许一个账号登录，且必须在线才能登录**"，理由是这样"直接把'两台设备同时离线改同一笔账'这个最难的问题消掉了，不需要做复杂的冲突合并"。**而实际情况相反**：**一个账号可以同时登录多台设备**（手机 + iPad 是日常），**因此"两台设备改同一笔"必须正面解决**——**冲突检测与冲突选择界面就是为它做的（S8 第 3 轮，双真机确认）**。
> **这个反转值得记住**：**用一个策略"消掉"一个难题，等于把风险藏起来**——真实需求（多设备）出现时，那个难题会**带着利息回来**，**而它确实回来了，还成了 S8 最贵的一轮**。

**离线时的界面提示**（✅ 已实现，**文案以代码为准**）：实际文案（`apps/web/src/components/OfflineStatus.tsx`）为 **"连不上服务器，现在显示的是本机保存的数据。本机共有 N 条记录……联网后会自动同步"**。
> ⚠️ 原先那句"待同步 3 笔 · 请勿清除浏览器数据"是**设计稿不是实现**；**"未同步 N 笔"的条数提示仍在待办**——现在**靠行颜色表达**（**浅绿 = 还没备份，浅红 = 还没删掉**），所有者已确认颜色正确。

**关于"本地计算是否安全"**：统计与金额计算放本地**完全没问题而且更快**（金额用整数"分"，是纯函数）；真正要防的是 ① 数据只存一份会丢 ② 只靠前端判断权限会被绕过（**服务端仍对每一次读写做鉴权与校验**）。一句话：**前端负责快，服务端负责对和安全。**

**分批交付 —— ⚠️ 已被推翻（2026-10-11）**：原计划"第一批（在线版）+ 第二批（离线写入）"。实际：第一批的四条离线设计**确实在第一批就进了表结构**（这一步做对了）；**但"批次"不存在了**——离线被**提前到上线之前**，与协作一起排 S8/S9。

**⚠️ 两处与设计稿不同，以代码为准**：① **没有"同步队列"**——**印记就是队列**（`localLedger.ts` 的 `EntryMark`），工作清单**从印记推导、从不落盘**（原因见 `教训.md` §8.8：两份状态迟早不一致）；② **"待同步计数"仍未做**——现在靠行颜色。

### 3.4 协作与共同记账（**S9** · 设计已定稿，尚未开发）

> **状态：定稿于 2026-10-09 08:05**，五个关键问题已由所有者确认。本节只描述设计，不写任何代码。
> （⚠️ 注意：PLAN 这里还写着"尚未开发"，但 ROADMAP §2 显示 **S9 已于 1.09.01–1.09.35 完成**——PLAN 未同步。）

**目标**：让两个人能**互相找到**，然后**一起记账**（共享同一个账本）。
**为什么能成立**：账号有一个**可公开的纯数字编号**（8 位，如 `86818383`），可以随便告诉别人 →"找到某个人"变成"输入这串数字"。

**已定下来的五个问题**

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 登录用什么标识 | **用户名（保持唯一）**，编号只作社交标识 | 唯一登录名 + 可重复显示名是通行做法（微信、Telegram、GitHub）；用户名好记好输，对长辈友好；**已完成的登录逻辑不动** |
| 2 | 用户名能否重复 | **不能** | 用户名是登录凭据 |
| 3 | 模块叫什么 | **协作**；每个人叫**协作者** | 中性、正式、不暗示社交关系 |
| 4 | 如何添加 | **搜索编号 → 发送申请 → 对方同意** | 看别人账目是敏感操作；代价是需要申请表与待处理提示 |
| 5 | 能否互相看见账目 | **必须加入同一账本才可见** | 分享的最小单位是**账本**而非账号；"协作者"身份本身不授予任何账目权限 |

**术语表**：**用户名**＝登录凭据、全站唯一、等同"微信号"、可被搜索（任何人可见）；**昵称**＝应用内显示名、可重复、等同"微信昵称"；**账号编号**＝8 位纯数字随机生成、公开可分享；**协作**＝整个功能模块；**协作者**＝与我互相添加成功的人（单向申请不算，双方可见昵称/用户名/编号）；**账本成员**＝协作者中被授权访问**某一个具体账本**的人；**恢复码/密码**＝凭据，**永不对外**。

**搜索用什么（2026-10-09 补充决定）**：**搜索框同时接受「用户名」与「账号编号」**（实现上只是一次 `OR` 查询）。用户名好处是好记好念好分享、缺点是可被字典枚举；编号好处是**不可枚举**（8 位随机、1 亿空间）、缺点是需要记或存。**对策：搜索接口必须限流**（否则用户名枚举与编号遍历会变得廉价）；登录本身仍由 argon2id 与失败锁定兜底。

**不会变的边界**：编号公开、密码与恢复码保密（编号只是"找到你"的入口，不是凭据）；**不用协作功能也能记账**；**看见账目 ≠ 看见账号**（分享最小单位是账本）；**任何单向动作都可撤销**（能拒绝申请、能删除协作者、能退出账本）；**编号搜索必须限流**。

**技术预判**：新表 `collaborations`（状态：待同意/已接受/已屏蔽，由申请方一侧发起）；复用 `books` / `book_members`（**共同记账 = 往同一个账本里加成员**，表结构第一批就按可共享建好，**不需要迁移数据**）；服务端仍对每次读写鉴权，**账本成员关系是唯一判据**。

**明确暂缓**：**二维码扫码添加**（把编号编码成二维码，扫码即发起申请，省去手输 8 位数字）——方向记录在此，**当前不做**；协作相关的**站内消息通知**暂不做，先用"**待处理申请**"列表代替。

**users — 用户**：`id` uuid PK；`username` text UNIQUE（登录名）；`password_hash` text（argon2id，**永不可逆**）；`display_name` text（"谁记的这笔账"）；`is_demo` bool（演示账号标记，只读、可定期重置）；**`recovery_code_hash`** text（一次性恢复码的哈希，注册时生成让用户自存，用于找回密码，不依赖邮件）；**`recovery_code_used_at`** timestamptz（用过即失效）；`created_at` / `updated_at` timestamptz。
（+ 实际另有 `account_number`、`is_admin`、`default_currency`、`last_book_id`——见差异表。）

**sessions — 登录会话**：`id` uuid PK；`user_id` uuid FK→users；`token_hash` text UNIQUE（**只存 token 哈希，泄库也无法直接冒用**）；`expires_at` timestamptz；`user_agent` / `ip` text（便于查看与踢下线；实际列名 `ip_address`，另有 `last_seen_at`）；`created_at`。

**books — 账本**（v1 每账号一本；v2 共享的载体）：`id` uuid PK；`name` text（如"家庭账""我们俩"）；`owner_id` uuid FK→users（**实现里叫 `created_by`**）；`currency` char(3) 默认 CNY（**实际不存在**）；`created_at` / `deleted_at`（软删除防误删；**实际不存在 `deleted_at`**）。

**book_members — 账本成员与角色**（**权限的唯一依据**）：`book_id` uuid FK→books；`user_id` uuid FK→users；**`role` enum(owner, editor, viewer)**（决定能做什么）；`joined_at` timestamptz；**PK(book_id, user_id)**（同一人同一账本只能有一条）。
> **v1 说明**：v1 里每用户只有一本账，`book_members` 每位用户一行（role = owner）。这张表在 v1 界面上**不可见，但必须存在**——否则 v2 做共享要改表并迁数据。预设分类同理，注册时按 `book_id` 生成一套。
> （实际：v1 **取消了 owner**，改为 editor/viewer；`role` 默认值 `viewer`，现有 owner → editor，见 ROADMAP S9 与 `版本记录.md`。）

**categories — 分类**：`id` uuid PK；`book_id` uuid FK→books（**按账本隔离**）；`name` text；`kind` enum(income, expense)；`icon` text（**v1 不用图标**）；`sort_order` int；`is_archived` bool（归档而不删除，历史流水仍可读）。
（+ 实际有 `is_system`，用于「暂无分类」。）

**payment_methods — 支付方式**：`id`；`book_id`；`name`（用户可自定义）；`icon`；`sort_order`；`is_archived`。→ **v1 只记"这笔从哪付的"，不追踪余额**。

**tags — 标签**：`id`；`book_id`；`name`（同一账本内唯一）；`color`；`created_at`。

**transactions — 流水**：`id` uuid PK（**客户端生成 UUID v7**——离线也能立刻记账）；`book_id`；`user_id`（记账人）；`category_id`（**实际 NOT NULL**，指向系统分类「暂无分类」）；**`payment_method_id`**（可空，兼容历史数据）；`kind` enum(income, expense)（冗余存储，便于统计并防止分类被改后语义漂移）；**`amount_cents` bigint**（**金额以"分"存整数，绝不用浮点数**）；**`currency` char(3)**（每条流水自带币种，统计按币种分开算）；**`occurred_at` timestamptz**（**记账时刻，精确到秒**，默认取手机当前时间，用户可改）；**`occurred_local_date` date**（**记账时手机的本地日期**；分组、筛选、"本月"统计一律用它——**服务器不做任何时区推断**）；**`occurred_tz` text**（记账时手机的 IANA 时区，如 `Asia/Shanghai`）；`note` text；**`version` int**（乐观锁/同步版本号，每次修改 +1）；**`idempotency_key` uuid UNIQUE**（**同步幂等键**，网络重试不会重复记账）；`created_at` / `updated_at` / `deleted_at`（**软删除 tombstone**，否则离线设备会把已删的账"复活"）。
（+ 实际另有 `source_ref`、`import_ref`、`value_history`。）

**transaction_tags — 多对多**：`transaction_id` uuid FK→transactions；`tag_id` uuid FK→tags；**PK(transaction_id, tag_id)**。

**attachments — 小票图片**（⚠️ **实际未建表**，S5 改"付款截图 + 图片不落盘"后不再需要，本节仅作设计记录）：`id`；`transaction_id`；`book_id`（冗余，便于批量权限校验）；`storage_key` text（服务器上的随机文件名，**不是原始文件名**）；`mime`/`size_bytes`；`thumb_key`；`sha256`；`created_at`。

**invites — 邀请成员**（v1 建表预留，v2 启用；⚠️ **实际未建表**。v1 用的注册邀请码是另一张表 `registration_invites`）：`id`；`book_id`；`code` text UNIQUE；`role` enum(editor, viewer)；`expires_at`；`created_by`；`used_at`/`used_by`（一次性使用）。

### 5.2 五个关键设计决策（面试会被问）
1. **金额用整数"分"存（bigint），不用 float/double**——浮点无法精确表示 0.1，累加漂移（`0.1+0.2≠0.3`），记账软件出现 0.01 元误差就是致命 bug；所有加减在整数域完成，只在展示层格式化成 `12.34`。
2. **权限只在 `book_members` 判断，业务表全部带 `book_id`**——任何查询必须先过"当前用户是不是这个账本的成员"，杜绝"改 URL 里的 id 就能看别人账本"。
3. **记账日期用 `date`、系统时间用 `timestamptz`，两者分开**——"这笔钱是 10 月 3 日花的"与"这行记录是 10 月 5 日 14:22 创建的"是两件事，混用会导致跨时区/补记账时数据错乱。
4. **主键由客户端生成（UUID v7）+ 幂等键**——离线记账不能等服务器分配 ID；同步时带 `idempotency_key`，服务端见过就跳过，**"请求超时后重试"不会变成两笔账**（离线优先架构能成立的前提）。
5. **删除一律软删除（tombstone），永不做物理删除**——硬删除会让离线设备下次同步把已删数据"复活"；软删除 + 墓碑标记才能让删除正确传播到所有副本。

### 5.3 索引与约束（**已按实现更新**）
- `transactions`：主索引 **`(book_id, deleted_at, occurred_local_date DESC, created_at DESC)`**（列表页核心查询"某账本未删除行按记账日期倒序"，**游标分页直接走索引，不需要额外排序**）；另有 `(book_id, kind, occurred_local_date DESC)`、`(category_id)`、`(payment_method_id)`、`(book_id, import_ref)`；**`idempotency_key` 唯一索引**；**`(book_id, source_ref)` 唯一索引**（S6 判重，**作用域＝账本**）。
- `transaction_tags`：`(tag_id)`（按标签反查流水）。
- `tags`：`(book_id, name)` 唯一。
- `categories`：`(book_id, kind, name)` 唯一 + `(book_id, kind, is_archived)`。
- `book_members`：`(user_id)`（首页要列"我参与的所有账本"）。
- `export_logs` / `import_logs`：`(book_id, created_at)`，各自的 `file_ref` 唯一。
- 约束：`amount_cents > 0`（**上限 1e12 分由 Zod 校验**）；`book_members` 主键防重复加入；外键均设级联策略；**可追溯编号的格式由 CHECK 约束保证**（`In-`/`Out-` 前缀与日期时分范围）。
- **所有列表查询强制带 `book_id` 且分页，禁止全表扫描式查询。**

### 5.4 预留扩展（v2 及以后）
多账户与余额、预算与超支提醒、按汇率折算统计、定期账单（房租/订阅）、AA 结算、二级分类——都能通过**新增表 + 一次 Prisma 迁移**加上，**不需要改动现有表结构**（这正是选关系型数据库 + ORM 迁移的原因）。
> **标签（tags）已从本清单移出**：按所有者决定，它进入 v1。

### 6.5 鉴权与防护要点
- 会话 Cookie：**`HttpOnly` + `Secure` + `SameSite=Lax`**；写操作校验 **CSRF 令牌（双提交）**。
- 登录失败：同一用户名/IP **递增延迟 + 限流**。
- 所有写接口限流（Fastify rate-limit）。
- 上传：只允许 jpg/png/webp，**真实内容嗅探**（不信任扩展名），≤10MB，**图片只在内存中存在，识别后立即释放**。

## 8. 安全与隐私
- **8.1 密码泄露**：argon2id + 每用户独立盐；库泄露也无法还原明文；日志绝不打印密码。
- **8.2 会话被盗**：httpOnly Cookie 存 token，库里只存 token 哈希；支持"退出所有设备"。
- **8.3 中间人窃听**：Caddy 自动 HTTPS、强制跳转、HSTS 与安全响应头。
- **8.4 越权访问他人账本**：每个读/写接口先校验 `book_members`；**前端传的 `user_id` 一律忽略，以会话为准**。
- **8.5 恶意上传**：白名单类型 + 内容嗅探 + 大小限制 + **不落盘**（没有文件就没有可执行、可遍历、可泄露的文件）。
- **8.6 陌生人注册滥用**：**开源不等于开放注册**——注册**必须邀请码**；对外只放**只读演示账号**（`is_demo=true`，写操作被服务端拦截，数据每日重置）。
- **8.7 暴力破解**：登录限流 + 失败递增延迟。
- **8.8 数据丢失**：每日自动备份，本地 7 天 + 异地 30 天；上线前做一次**恢复演练**。
- **8.9 隐私**：不接入任何第三方统计/广告 SDK；日志不记录金额、备注、图片路径；README 写明隐私立场。
- **8.10 服务器被入侵**：只开放 22/80/443；SSH 密钥登录并禁用密码；系统与镜像定期更新；数据库不对公网暴露端口。
- **8.11 密钥入库（开源项目高发事故）**：`.gitignore` 从一开始排除 `.env`；仓库只放 `.env.example`；上线前 `git log -p` 复查。
- **8.12 把不该给用户看的数据发到了前端**：见 §1.5——**不发送**，而不是"发送了但不显示"。
> 一句话总结给面试官：**"钱的数据，宁可少一个功能，也不能多一个越权。"**

### 10.4 备案问题：我们走了哪条路（已核实）
**结论：不申报 ICP 备案，改为办一次「公安联网备案」。**

| 问题 | 核实结论 |
|---|---|
| 个人能做 ICP 备案吗？ | 能做（满 16 周岁、证件住所在本省、域名持有人=主办人）。但官方文档明确：因国务院取消"互联网电子公告服务专项审批"，BBS 前置审批已停止办理，**"论坛网站已无法办理 ICP 备案"**——交互式站点在审核中容易被驳回 |
| 备案的前提 | 必须有**中国内地服务器**；顶级域须已批复、注册商为已批复境内机构、已实名、持有人与备案主体一致。**香港服务器不能也不需 ICP 备案** |
| 那香港就"什么都不用办"？ | ❌ **不是**。依据《计算机信息网络国际联网安全保护管理办法》，**服务器在境外但为中国内地提供服务**的，须在开通起 **30 日内**到[全国互联网安全管理服务平台](https://beian.mps.gov.cn)办理**公安联网备案**；个人可选"个人用户登录" + APP 扫码实名，主体审核约 2–3 个工作日；**备案号须展示在网页底部** |
| 还有别的风险吗？ | ⚠️ 有公开案例称**未备案域名可能被腾讯网址安全判为风险域名，在微信内被拦截**（可申诉）。这条**没有官方明文规则**，但值得预防 |

**因此本项目要落实三件事**：① **上线（S10）后 30 天内完成公安联网备案**，备案号放网站底部（**⚠️ 页面位置目前还没预留**——`apps/web/src` 里没有相关代码，S10 要补）；② **不要把链接在微信群/朋友圈传播**（给家人发链接时附一句"用手机浏览器打开"，或让其复制到 Chrome/系统浏览器）；③ **域名注册信息用本人真实信息**，日后真要备案时不用返工。

## 13. 项目命名

### 13.1 筛选标准（先说一个踩过的坑）
一开始把"GitHub 用户名是否空闲"当硬指标，后来发现**所有短且可发音的英文单词，GitHub 用户名几乎 100% 被占用**（用随机字符串做对照确认检测方法没问题——是标准本身不适用）。**真正要紧的只有三条**：**域名可用**（.app/.dev/.com）、**没有同名产品或公司**、npm 包名空闲（次要）。仓库挂在自己账号下（`用户名/项目名`），**不必抢同名用户名**；但 **GitHub 组织名**值得占（干净、免费、以后能当项目门面）。

### 13.2 英文自造词方向：实测结果（2026-10-08，两套独立 RDAP 通道交叉验证）
Naelo（2 音节/5 字母，npm 与 GitHub 组织空闲，.app/.dev 未注册，.com 已注册，仅一家法国小公司与一个情绪记录 App 同名）；Yinda（谐音"银达/赢达"，但撞新加坡一家 IT 外包上市公司）；Cendo / Ranzo / Zenno（.app/.dev 均已被注册）；Tallyn / Nummo / Moneti / Markka / Fenly（仅 .dev 可用）。

### 13.3 拉丁语方向：你的想法验证结果
`liber rationum` 是"账本"吗？→ **成立**（Lewis & Short 中 `ratio` 首义即"清算、账目"，复数指"账目"；`liber` 亦有"登记簿、名录"义）。但**不能说"古罗马人就这么说"**——该确切短语用例主要来自 **16–17 世纪罗马法/教会法文献**，未见古典拉丁用例；古罗马人实际说 `codex accepti et expensi`、`tabulae`、`adversaria`（草账）。`liber`"书/自由"双关**成立但要说清**：**同形异音**（书 = 短 i `lĭber`，自由 = 长 i `līber`，还有第三义"孩子 liberi"），属**拼写双关**而非读音双关。
**`liberum` 必须放弃（两条硬伤）**：① 语法上它是形容词"自由"的变格形式（中性主格/宾格），不是词典形；② **五个域名后缀全被注册**，且 **Panmure Liberum 是英国受监管的投资银行**（原 Liberum Capital），金融领域直接撞名。
**顺带排掉**：Libri（德国 Libri GmbH 持含"计算机软件"类别的英国商标 + 同名 iOS App）；Rationum（应用商店已有同名记账 App）；Libero（Microchip Libero SoC FPGA 工具链知名度高）；Ratio（已有记账 App "Ratio Money – Finance Tracker"）。
**拉丁方向唯一活下来的：Libellus / Libellum**（`liber` 的指小词，意为"小簿子、备忘账、日记账"）——**没有任何金融/记账类撞名**。`Libellum`：`libellum.app` 未注册（.dev/.io 也空），npm 与 GitHub 组织已被占；`Libellus`：仅 `libellus.dev` 可用，词典形更正统但 .app 已被占。
> ⚠️ 一个需要知道的英语联想：英语 **libel**（诽谤）正是从拉丁 `libellus` 演变而来（小册子 → 诉状 → 诽谤文书）。美国招聘方不一定会联想，但这是这个词的阴影面。

### 13.4 定名结论：Libellum（已定）
选定 **Libellum** / `libellum.app`（已核实未注册）：拉丁"小簿子/备忘账"与记账语义最贴、无金融类撞名、有可讲的故事（liber = 书/自由）；缺点：npm 与 GitHub 组织名已被占（不影响用自己账号建仓库）、libel 的英语联想。
备选：Naelo（`naelo.app`，短、国际范、全空闲、零争议；缺点是自造词无含义）；Yinda（`yinda.app`，家人一眼记住；缺点国际观感弱、撞一家新加坡 IT 公司）。
**定名理由（面试可直接讲）**：拉丁语 `liber` 同时是"书"和"自由"，指小词 `libellus / libellum` 意为"小簿子、日记账"——**一个免费的、开源的小账簿，名字本身就把项目说完了**；而在 Liberum / Libri / Rationum 之间取舍时，是**商标与同名产品排查**淘汰了另外三个。
**品牌用法**：正式名 **Libellum**；副标题 `Libellum — the free, open ledger`；域名 `libellum.app`；仓库 `github.com/<用户名>/libellum`。

### 13.5 核实的边界（务必知道）
`npm 404` 只代表包名当前未被占用，不代表一定能注册；域名能否购买以注册商结账页为准；同名产品排查基于公开检索，**不构成商标检索**（日后商业化需另做，可用 TMview）；拉丁语词义核对自 Lewis & Short（Perseus 数字版），`liber rationum` 的语料证据来自 16–17 世纪法律文献，**不是古典拉丁常用表达**；GitHub 组织名 404 已用随机字符串对照验证有效；**正式定名前建议再复查三处**：GitHub、App Store / Google Play、TMview。

### S5 · 截图识别记账（**已重新定义**，原估 0.5 天 → **2–3 天**）
> **2026-10-09 重大修正**：所有者更正场景——**不是"小票拍照"，而是"付款截图识别"**（微信付款截图、支付宝收款截图、银行转账截图），这个区别极大。
**为什么"截图"比"小票拍照"容易得多**：几何形变（拍照有透视畸变/纸卷，截图**完全没有、像素完全对齐**）；光照（拍照有阴影反光色偏，截图**无、屏幕自发光**）；对比度（截图**极高，通常黑字白底**）；版式（截图**字段固定、措辞固定**）；**OCR 难度：高 → 低**。
> 所有者对 OCR 持怀疑态度（此前的自动化测试项目里 OCR 表现很差）——**那个经验很可能来自"拍照/复杂界面"，而付款截图恰好是 OCR 最擅长的一类输入**。
**实测数据（2026-10-09，本机 CPU，未做任何图像预处理）**：用 **`RapidOCR`**（PaddleOCR 模型的 ONNX 轻量版，`pip install rapidocr-onnxruntime`）对三张仿真付款截图实测——微信支付 19 行 / 置信度 0.975 / 1.12s / 金额·类型·渠道·日期·时间·对方·单号全部 ✅；支付宝收款 17 行 / 0.997 / 0.50s / 全部 ✅；银行转账 17 行 / 0.996 / 1.01s / 全部 ✅。**平均 0.88 秒/张（不含模型加载），三张全部字段正确。**
> **过程中的关键教训（最有价值）**：第一版提取规则**只有 1/3 能取到金额**——因为它要求 `¥` **紧挨着**数字，而识别器把 `¥` 单独成行，在一张里甚至认成了「夫」（置信度 0.966）。**问题不在识别，在提取规则。** 改用"**金额是屏幕上最大的数字**"（用识别返回的文字框**高度**判断）后立刻变成 3/3；随后又发现"对方"取错了方向（支出取到了付款方自己的账号），修正后完全正确。**结论：OCR 只负责"把像素变成文字"，"把文字变成结构化数据"是我们自己的活——而那一层可以调到对为止。**
**产品流程**：记账页点相机图标 → 选图（最多 5 张）+ 选模式（单笔消费多张凭证 → 金额相加 → 一个弹窗；多笔消费批量上传 → 每张一个弹窗）→ 上传 → 服务端 OCR → 字段提取 → 返回结构化数据 → **【图片在此刻被丢弃，从未写入磁盘】** → 弹窗展示识别结果（一屏以内、可编辑）→ 用户核对 → 确认 → 保存为账目。
**已定方案**：**图片不落盘**（比"存了再删"更彻底：没有可泄露的副本，也没有要清理的垃圾）；**不调用第三方云 OCR**（付款截图含账户、余额、交易号，不应发给任何第三方）；试运行期**样本保存开关**（默认关，调试可开）；**数量上限 5 张**；**单笔多凭证暂限同一币种**（金额相加；不同币种一次上传 → 已记入待办）；入口 = **记账页的相机图标**；弹窗**一屏以内、可编辑**（目标是"核对"不是"重填"）；**识别不准时字段留空 + 明确提示，不猜**（**猜错比留空更糟**——留空用户会填，猜错用户可能直接确认）。
**任务清单**：`apps/ocr` Python 服务（常驻进程、模型只加载一次）；与 Node API 通信走 **stdin/stdout JSON 行**，不开端口、不增加攻击面；提取规则（金额按字号、日期时间、收支方向、渠道、对方、单号、备注）；上传接口（内存接收、类型白名单、**内容嗅探**、≤10MB、**不落盘**）；多图模式；弹窗组件；记账页相机图标入口；识别耗时提示（**超过 1.5 秒显示进度**）；样本保存开关。
**验收标准**：三类截图各上传一张，字段识别正确、**总耗时 2 秒以内**；上传后**检查服务器磁盘，确认没有任何图片残留**；上传改名为 `.png` 的文本文件 → 被拒；识别失败字段**留空并提示**，不填猜测值；弹窗**手机上一屏内显示完**，无需滚动即可点到确认。

## ⚠️ S11 详细规格（所有者 2026-10-13 新增）—— **这是当前要做的阶段**
### 为什么它在 S12「可上线」之前
因为它改的是**所有界面共用的东西**（文字、颜色、层级风格）。**上线后再做，意味着两个版本之间整站的观感会变一次**，而 S12 要做的是部署、演示账号与备案——那些都需要界面已经稳定。
### 一、文字语义化
**现状**（所有者原话）："部分的文字是标题，部分的文字是按钮，部分的文字是说明"——同样的角色在不同页面由不同的人手写，于是同一类文字的字号、颜色、措辞不一致。
**目标**：① **同一功能的按钮，文案始终相同**（例如"保存"不会在某处叫"确定"、另一处叫"提交"）；② **所有说明性文字风格统一**（字号、颜色、行距一套）；③ **有一个地方能看到全部文本**——便于通读与校对，而不是靠 grep 各个页面去猜哪些是用户可见的。
### 二、颜色语义化
**所有者给的真实例子**："现在账本空间开始页面最深的那个海浪颜色跟其他的页面导航栏是不一样的——平时可能看不出什么，但是当用户从账本跳转到账本空间/开始时，他就会明显的感觉到导航栏的颜色自然不一样。"
**这一点已核实**：品牌色令牌 `--color-brand` = **`#55997a`**（用于一级页面标题区、导航高亮）；**海浪最深一层 = `#3f7059`**（`OceanBackdrop.tsx` 里的**硬编码字面量**）。
**根因**：`colors.test.ts` 有一条"颜色只能来自令牌"的规则，而 `OceanBackdrop.tsx` 被列进了**豁免名单**（理由是"它是一幅画，不是主题"）。**这个豁免是错的**——海浪是整个应用里面积最大的一块颜色，**它恰恰是最需要与品牌色一致的地方，而不是最不需要的地方。**
**目标**：所有**导航**同一个颜色；所有**按钮**同一个颜色；**危险操作**（删除等）同一个颜色；**海浪的层次由令牌的明度变化导出**，而不是四个独立的字面量。
### 三、三类界面风格统一
所有者用的类比：**"就像微信里面的通讯录和聊天一样"**——不用看标题，**一看就知道这两个是同级页面**。

| 类别 | 包含 | 应有的一致特征 |
|---|---|---|
| **一级界面** | 明细、分析、账本／协作、账户 | 品牌绿标题区 + 固定底部导航；四页美术与设计思路统一 |
| **设置／二级页** | 个人资料、软件更新等 | 左上角返回 → 功能名 → **灰色说明文字** → 内容 |
| **功能页** | 再往下的操作页 | **灰底** + **灰框圈出的白底内容块** |

**目标**：每类内部**结构、间距、字号层级、颜色用法**都一致；**跨类之间要有可辨认的差异**（让人知道"我进到更深一层了"）。
