> 服务器更多是数据备份。"** 这份文档记录的是**把它变成真的**的过程。

## 1. 一句话概括现状

> ### ✅ **离线"看"这条线已经打通（2026-10-11，手机与 iPad 双真机确认）。**
>
> **代价是十二轮修改**，而其中**只有最后一轮修的是用户看到的那个问题**——
> 前面十一轮修的都是真缺陷（详见 §4 与 `版本记录.md`）。
> **完整教训见 `教训.md`。**

| 能力 | 状态 | 说明 |
|---|---|---|
| 离线**看**明细（任意月份） | ✅ **可用** | 手机与 iPad 都确认；**无需等待** |
| 离线**看**某一条的详情 | ✅ 从本机已存数据里查，不请求服务器 |
| 离线**看**分析/统计 | ✅ 在本机按与服务端相同的规则算出 |
| 离线**切换**支出/收入/分类筛选 | ✅ 在本地副本上筛选 |
| 离线**记**账 / 改 / 删 | ✅ **可用**（第 2 轮，所有者真机确认 2026-10-11）：**印记就是队列**，未同步的新建浅绿、待删除浅红 |
| 离线**拍照**识别 | ⛔ **不做**（第 4 轮已由所有者取消，2026-10-11） |
| 冲突对比界面 | ✅ **可用**（第 3 轮，所有者双真机确认 2026-10-11）：先自动合并不冲突字段，只问冲突字段，**并显示自动合了哪些** |
| 离线**首次打开应用** | ✅ Service Worker 缓存外壳 |

### ⚠️ 真正的原因，一句话

**数据早就读到了（诊断日志里写着 `本机存储 138 条`），而界面一直在加载——
因为一次 `setState` 被调用了，组件却没有重渲染。**

> **我修了十一轮"数据怎么拿到"，而问题是"界面收得到吗"。**
> **这两件事可以同时是"是"和"否"，而我长时间只检查了第一个。**

**修法**：**把值放在 React 之外，渲染时同步读**（`useSyncExternalStore`）——
**没有"排队的更新"这回事，也就没有可丢的更新。**

## 1b. 数据到底存在哪里（最终结构）

**⚠️ 先澄清"存储"这个词**：IndexedDB 数据库名 `libellum`（`storage.ts`），**只有一个 object store 叫 `kv`**；
**`ledger-months` / `ledger-marks` / `query-cache` / `offline-log` / `auth-user` 都是这个 store 里的键**，
**不是各自独立的 store**——**下表第一列因此是"键"，不是"存储"。**

| 键（同一个 `kv` object store 下） | 内容 | 谁写 | 信任级别 |
|---|---|---|---|
| **`ledger-months`** | **按月为键的账目映射** `{ "2026-10": [...] }` | **下载时直接写**（`storeMonth`） | ⭐ **唯一的权威副本**——只增不减，谁也不删 |
| `query-cache` | TanStack 的持久化查询缓存 | 库的 persister | ⚠️ **内存的视图**，会被整份重写；**不承担保存责任** |
| 内存中的查询缓存 | 同上，运行时 | 库 | ⚠️ 同上 |
| `offline-log` | 诊断记录（上限 200 条） | 我们 | 诊断用 |
| `auth-user` | 记住的登录状态 | 我们 | —— |

**⚠️ 为什么最终要自己存一份**（所有者的原话就是设计说明）：

> **"数据保存到本地，然后它就可以直接拿这些本地的数据去计算去显示，
> 毕竟我用电脑直接调一个本地的文件可没出现过这么多问题。"**

**而"查询缓存"不适合承担这个责任**：它是**内存的视图**，
而持久化**把这个视图整份写出去**——**任何离开内存的东西，都会被一起写掉。**
下载的六十个月一度变成六个，就是这个原因。

> **一个职责就是"遗忘"的结构，不该用来保存用户唯一的那份数据。**

## 2. 四个基本决定

### 2.1 缓存"查询响应"，不缓存"表结构"

**决定**：用 TanStack Query 的持久化把**查询缓存**存进 IndexedDB。

**为什么不是手写一套与服务器同构的表**：

| 手写表结构 | 持久化查询缓存 ✅ |
|---|---|
| **是 schema 的第二份定义**，加一列就开始漂移 | **是"响应"的副本**，只依赖缓存语义 |
| 每个页面都要写一遍查询 | 页面**已经在用了** |
| —— | **离线可读范围 = 已成功请求过的范围**，正是想要的 |

**底层是一个键值存储**（`storage.ts`），不是"每张表一个 store"：
**缓存不需要查询能力**——"十月有哪些账"由**已经会做的内存代码**回答。

### 2.2 数据真的在本机，不是"只是缓存"

**所有者问过**："网页只有缓存，没办法真的把数据下到用户本机里。实在不行我看看打包成 APK。"

**这句话是那个词最常见的误解，而事实相反**：

| 直觉 | 实际 |
|---|---|
| "网页只有缓存" | **IndexedDB 是真实数据库**，就在浏览器数据目录里，**和原生 App 存文件是同一件事** |
| "打包成 APK 就能离线" | **APK 里的 WebView 用的是同一套 IndexedDB**，机制完全一样 |

> **Web 在这里不是"原生应用的薄版本"，而是"同一套安排换了安装方式"。**
> **打包能换来图标、推送、应用商店——不是离线能力。**

**⚠️ 但"缓存会被清掉"是真事**，而且这才是那个词真正的危险：
浏览器存储**默认是 best-effort**，空间紧张时可能被回收；**Safari 对七天未访问的站点会清除**。

**修法**：`navigator.storage.persist()`（`persistence.ts`）。
**浏览器拒绝时，在下载管理页明确告知**——**这件事该在家里知道，不是在飞机上发现。**

### 2.3 提醒"有新闻才出现"，不做常驻

**所有者的意见**：**"不仅不太美观，用户平时也可能看不见"** —— 第二条是更要紧的：

> **一条永远在那里的提示，就没人再读了**——于是它唯一该起作用的那次，它是隐形的。

| 时机 | 行为 |
|---|---|
| 下载中 | **所有页面顶部**常驻 + 进度 |
| 刚下载完 | **再留 10 秒** |
| 之后 | **自动收回，不再出现**（直到下一次下载） |
| 每次都提示 | **"可以在「账户 → 下载管理」里查看和调整"** |

**⚠️ 倒计时属于"下载"，不属于"看它的人"**（见 §3.4）。

**唯一的例外不自动消失**：**"浏览器未承诺保留"**——它不是会过期的新闻。

### 2.4 警告放在"它是主题"的界面

**所有者的意见**：**"把这个弹窗挪到下载管理界面以及下载管理的每个子界面"**。

**理由和 §2.3 相同**：**跟着用户到处走的警告，就没人读了**。
持久化警告因此只出现在「下载管理」和「月份下载管理」两页——**而这两页是用户主动打开的**。

## 3. 被证明是错的四个做法（教训）

> ⚠️ **这一节是本文档最重要的部分。**
> 这四条都"看起来对、写起来也顺"，**而且都是靠真机反馈才推翻的**。

### 3.1 ⚠️ 用"比例"定位，永远落不到中线上

**问题**：核对页的日期框与时间框重叠。**所有者报了三次**：

| 版本 | 定位方式 | 结果 |
|---|---|---|
| 一 | 行 `w-3/5`，内部 3:2 分 | 时间框在 **42%**——偏左一个字 |
| 二 | 两列各 `basis-1/2`（撑满屏幕） | 时间框在 **50% + 半个 gap**——偏右一个字 |
| 三 | 行 = 屏幕左半 + `justify-between`，**但规则写在 `min-[360px]:` 断点里** | 手机上断点**没命中**，`min-w-0` 也一起失效 → **日期框撑爆、时间框被挤出屏幕** |
| **四** | **两行，一行一个框**（所有者拍的板） | ✅ 整类问题消失 |

**教训**：

1. **"窄一点"是感觉，"中线"是约束。** 可验证的约束一次到位，凭感觉的要来回三次；
2. **同一个地方被报多次，说明要换方案而不是继续调参数**；
3. **⚠️ 一条"必须成立"的规则，绝不能写进"可能不成立"的条件里。**
   响应式断点只能放锦上添花；**断点没命中时页面会坏得很难看，而不是优雅降级**；
4. **浏览器的视口逻辑宽度 ≠ 屏幕物理宽度**。用宽度断点控制布局的正确性，是在赌一个
   自己不完全掌握的输入。

### 3.2 ⚠️ "请求失败"和"服务器拒绝了"是两件事

**问题**：离线时应用表现得像**已登出**。

```ts
catch { setUser(null); }     // ← 任何失败都当作"未登录"
```

**连锁后果，而且正好在最需要它的时候发生**：

1. 离线时 `GET /auth/me` 请求不出去 → 被当作已登出；
2. **缓存好的账本被登录页挡住**；
3. **而且过不去**——**登录也需要网络**。

> **这个应用在最需要它的场景下完全不可用。**

**修法**：只有**服务器明确说 `401`** 才结束会话；够不着服务器时**沿用上次记住的用户**。

**⚠️ `403` 也算"不变"**：这个项目用 403 表示"你无权动这本账"，不是会话失效——
**一个 403 就把人登出会是另一个 bug**。

**教训**：

1. **`catch { setUser(null) }` 这种写法本身就该被怀疑**——它把"我们不知道"写成了"答案是没有"；
2. **只有服务器有权结束会话**。够不着它的时候，正确答案是**沿用已知的**。

### 3.3 ⚠️ "有数据"和"数据全了"是两件事

**问题**：所有者报告下载了数据，离线却看不到。

**根因**：`fetchInfiniteQuery` **只取第一页就 resolve**，
而翻页是**页面**调 `fetchNextPage()` 触发的——**`QueryClient` 上根本没有这个方法**。

所以"下载了一个月"实际只取了**第一页**。**更糟的是第二半**：
**"已缓存"不等于"缓存全了"**——只要键下有**任何**数据它立刻返回，
**所以曾经只缓存一页的月份，永远补不全**。

**修法**：自己写翻页循环；**"取完了"定义为"最后一页不再给 cursor"**。

**并且顺带发现一个同类问题**：**查询 key 由对象生成，而 `JSON.stringify` 会丢掉
`undefined` 的值**——所以 `{month, kind, categoryId}` 和
`{month, kind, categoryId, currency: undefined}` 是**不同的缓存条目**。
**填充写四个字段、页面写三个**，于是**下载好的月份存在页面从不查询的键下面**。

**教训**：

1. **"有数据"和"数据全了"在缓存这一层长得一样**，必须显式判断完整性；
2. **凡是 key 由对象生成的地方，都要有一个唯一的构造函数**（`transactionFilters()`）；
3. **`JSON.stringify` 丢 `undefined`** 是个容易忘的语言事实；
4. **"缓存未命中"和"没下载"在界面上完全一样**——这类缺陷**必须靠测试**；
5. **测试要断言"请求次数"**，不只是"条数"。**条数对但请求次数不对，说明分页仍然可疑。**

### 3.4 ⚠️ 倒计时属于"事件"，不属于"订阅者"

**问题**：下载完成弹窗**每打开一个页面就重新出现一次**。

**根因**：**十秒是"组件"拥有的**——每次挂载都重新开始倒计时。

**修法**：把"刚下载完"记成**时间戳**，每个页面**从同一个事实算出同一个答案**：

> **"不到十秒前"在所有页面同时为真、同时为假。**

**⚠️ 并且"是否还在显示"改成派生值，不再是状态**：
存一个 `lingering` 布尔值就是同一事实的第二份拷贝，**而它正是会过期的那一份**。

**教训**：

1. **凡是"某件事之后 N 秒内显示"，时间点要记在事件上**；
2. **能从既有事实算出来的，不要另存一份**。

### 3.5 ⚠️ "没有反馈"和"没有生效"是同一件事

**问题**：所有者三次报告"下载点了没反应"。

**其中一次的真实情况**：下载**成功了**，但**进度条在完成的瞬间消失**——
**看起来就像闪了一下**。

**判断**：

> **在按按钮的人看来，"没有反馈"和"没有生效"没有区别。**

**修法**：完成后**保留 10 秒**，并且**在所有页面显示**；按钮下方常驻一句说明。

**教训**：**"它工作了吗"这个问题，界面必须自己回答**，
而不是靠用户去猜、也不是靠开发者读代码。

## 4. ⚠️ 当前未解决的问题

> **这一节是为了不把未解决的事写成已解决。**

### 4.1 ✅ 已解决：下载按钮"没有反应"（2026-10-11 定位）

**所有者的诊断记录一次就定位了它**（见 DEVLOG §9.1）。日志长这样：

```
手动下载 — 月份：2026-10
开始 — 计划 1 个月
跳过（已完整） — 2026-10
```

**没有一行"取回"**——说明**它从来没去取过**。而**空间却在涨**。

**根因**：**缓存有两份，而删除只删了其中一份。**

| 副本 | 谁在写 |
|---|---|
| **内存中的 query cache** | 应用运行时用这个 |
| **IndexedDB 里的持久化 blob** | **TanStack 的持久化是单向的**：内存一变化就覆盖 blob |

**`forgetMonth` 与 `storedMonths` 读写的都是持久化 blob**，而**内存里的月份还在**。于是：

1. 用户删除十月 → **blob 里删了，内存里还在**；
2. 内存一有任何变化 → **把十月整月重新写回 blob**；
3. 再点下载 → 程序看到"已完整" → **"跳过（已完整）"**；
4. **而内存中的条目仍在按 staleTime 重取并写回** → **占用持续变大**。

> **一个用户删不掉的月份，和一个永远不会再发生的下载，是同一个 bug 的两个面。**

**修法**：

| 改动 | 说明 |
|---|---|
| **`storedMonthsIn(queryClient)`** | 改问**活着的 query client**——**只有它知道现在实际存了什么** |
| **`forgetMonth(queryClient, month)`** | 走 `removeQueries`，**内存与持久化一起清** |
| **手动下载 = 强制重取** | 见 §4.2 |

**教训**：

1. **⚠️ 有两份数据时，必须问清"哪一份是真的"。**
   持久化副本是**历史的快照**，内存才是**当前状态**——而**写入方向决定了谁覆盖谁**；
2. **"删除不生效"和"下载不工作"可能是一个原因**，不要当成两个问题查；
3. **诊断记录里"缺了某一行"和"多了某一行"一样有用**——
   这次的关键正是**没有"取回"这一行**。

### 4.2 ✅ 已解决：手动下载被"已完整"挡住

**顺带发现**：即使删除正常了，"下载全部"在数据已存在时**也只会跳过**——
因为"跳过已完整的"是**自动填充的正确行为**，却被用在了**用户主动点击**上。

**判断**：**两种行为都对，但属于不同的调用者**：

| 调用者 | 行为 | 理由 |
|---|---|---|
| **自动** | 跳过已有的 | 这才让第二次启动几乎免费，也是它能无人值守的前提 |
| **手动** | **真的去取** | **按了按钮的人要的是"下载"，不是"状态报告"**；这也是**修复一个缓存错了的月份**的唯一办法 |

**修法**：`start(months, force)`，两个按钮都传 `force: true`。

**教训**：**"聪明地跳过"要用在没人看着的时候。** 有人按了按钮，就照他说的做。

### 4.3 ✅ 已解决：占用持续增长（16 → 24 → 30MB）

**一半是正常的**：下载确实在发生，数据确实在进设备。

**一半是真问题**：**查询键的形状变过**（见 §3.3），
**旧键下的条目永远不会被再读到，却一直占着空间**。

**修法**：下载管理页现在显示**存储明细**：

```
存储明细：缓存 1.2 MB，其中 61/180 条是当前版本会读的
[清理 119 条无效记录]
```

**教训**：**只增不减的存储，一定有一部分"谁也不再读它"。**
要能看见它，而不是等用户发现手机满了。

### 4.3b ⚠️ 我引入过的一个破坏性缺陷（已修）

**所有者的反馈**：**"更新之后所有下载的具体数据都变成了 0 笔账单 0B，
看起来似乎是把真正有用的数据删了而留下了一堆冗余数据。"**

**他没看错，是我干的。** 我加的"清理无效记录"用**内存中的 query cache** 判断"哪些是活的"，
而**持久化缓存是异步恢复的**——**在恢复完成之前按按钮，内存是空的，
六十个月全部被判为垃圾删掉**，而任何地方都没有备份。

> **⚠️ 破坏性操作，绝不能依赖"可能还没加载完"的东西。**

**修法**：把"什么算无效"改成**只看存储就能判断**的性质——
条目是旧的，当且仅当它的 key 形状不是当前版本会写的形状。
**不需要内存、不需要等恢复、不需要计时——而"不需要等待"正是它安全的原因。**

并且加了一道拒绝：**一条都没删掉时什么都不写**——
**一次没有理由的重写，就是一次没有理由的数据损失机会。**

**教训**：

1. **"清理"这类功能，第一版必须假设自己的判据是错的**：
   问一句"如果这个判据失效，它会删掉什么"；
2. **异步恢复的缓存，在恢复完成前是空的，而"空"和"没有"长得一样**；
3. **任何删除都要有一个"我不能删"的兜底条件。**

### 4.3c 📌 44.5MB：已归因于浏览器，不再追查

### 4.5b ✅ 已解决：离线读不到数据——**判据错了**

**所有者自己给出了正确的规则**：**"先去读网络数据，被拒绝/超过两秒没有收到数据然后直接改成用
本地数据就可以了吧？"**

**修法前**：`if (isOffline()) 用本地`——**只在浏览器自报离线时才回退**。

**而手机在四种日常场景里都会报"在线"**：

| 场景 | `navigator.onLine` | 实际 |
|---|---|---|
| 电梯里 / 地铁里 | **true** | 请求不通 |
| 需要登录的 Wi-Fi（captive portal） | **true** | 请求被劫持 |
| 路由器停止转发的 Wi-Fi | **true** | 请求不通 |

**这四种情况下应用都会等、失败、什么都不显示——而设备上躺着一份完好的账本。**

> **要问的不是"浏览器以为我们在不在线"，而是"答案到了没有"。**

**修法**：`withLocalFallback()` —— **先试网络，任何失败（被拒 / 超时 / 服务器出错）都改用本地**；
**2 秒上限**，因为**等待是用户的，回退是廉价的**（数据已经在设备上）。

**教训**：

1. **"环境告诉我可以"不等于"操作成功了"**。
   任何"先用 A，不行再用 B"的逻辑，**判据必须是 A 的结果，而不是 A 的前提**；
2. **`navigator.onLine` 只能用来"快速失败"，不能用来"决定是否尝试"**；
3. **用户描述的规则往往比代码里的更准**——这一次他直接说出了正确的算法。

**下载一直是成功的；问题在读，不在下载**（他的直觉是对的）。

### 4.5d 📌 52.5MB 与 127KB 的差：已解释，不再追查

**截图**：本机共占用 **52.5 MB**，而查询缓存只有 **127 KB**（**72/72 条全部有效**）。

**判断**：`navigator.storage.estimate()` 报的是**整个源**的数字，
包含**浏览器替我们持有的东西**；而且 **Chrome 会把它可能还没落盘的数据也算进去**，
所以这个数字可能跑在数据前面。

**修法**：下载管理页显示**占用构成**：

```
占用构成：账本数据 127 KB · 应用本体 X MB · 运行记录 X KB · 浏览器其它 X MB
```

**"其余是浏览器的账"必须说出来**——否则**账本会背上 52MB 的锅，而它只占 127KB**。

**教训**：**一个总数如果不拆开，就会被归因给最显眼的那个东西。**

## 5. 已经做对、值得保持的做法

| 做法 | 为什么 |
|---|---|
| **存储层的每个操作报告失败而不抛错** | 隐私模式、被阻止的源、磁盘满都会让 IndexedDB 失败。应用**退化成"和这个文件不存在时一样"**——**一个会把程序弄坏的缓存，比没有缓存更糟** |
| **`maxAge` 设为 `Infinity`** | 缓存的**是用户自己的账本**，不存在哪一种"你自己的记录过期了"对他们有帮助。**"陈旧"该被说出来，不是删掉** |
| **`/api` 绝不在 Service Worker 里缓存** | 查询缓存已经拥有那些数据，懂陈旧语义，且登出时会清——**第二份副本既会分歧、又会在登出后存活**（隐私问题） |
| **登出先删本地、再打服务器** | **只在有网络时才能登出，那不叫登出**。而且**只删查询缓存、不删整个库**——**队列在同一个库里，删库会丢掉还没送到服务器的记账** |
| **本地统计与服务端算法逐条对齐，并共用 `fillSeriesGaps`** | 两份实现只要差一笔，用户就会**在线看一个数、离线看另一个数，且无从判断** |
| **通知只在有内容时显示** | 见 §2.3 |
| **界面的"取完没有"以数据为准**（最后一页无 cursor） | 见 §3.3 |
| ⭐ **用户要求"存在本地"的数据，有它自己的、只增不减的存储键**（`ledger-months`） | **一个把内存视图整份写出去的持久化机制，会连带删掉它没提到的数据**（§1b） |
| ⭐ **界面读的值放在 React 之外，渲染时同步读**（`useSyncExternalStore`） | **没有排队的更新，就没有可丢的更新**（§1） |
| ⭐ **"存了的数"和"读到的数"分开报告** | **合并后的总数会掩盖要查的那个分歧** |
| ⭐ **破坏性操作串行化整个"读-改-写"，而不是只串行化写** | 只串行化写，两次读仍会基于同一份旧快照做决定 |

### 7.1 ⚠️ 关于第 2 轮那一列"同步队列"的说法

**⚠️ 而这不只是措辞差别**：**所有者报告的"钉子户"**

**一份记得要删、另一份已经空了，于是那一行永远在等一件没人排队的活。**

**幂等重放仍然在**：`idempotency_key` 就位，**新建的键就是那条账目自己的 id**，
