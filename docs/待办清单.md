# Libevra · 后期待办与想法池

> **这份文档是做什么的**
>
> 开发过程中提出过很多"先不做，但别忘了"的想法。它们之前散落在对话、技术方案和开发日志里，
> 没有一个完整的整合。这份文档把它们**全部集中到一处**，并写清楚做判断所需的信息。
>
> **开发顺序由项目所有者决定**，这里只负责把信息整理齐，不替你做排序。
>
> 最后更新：**2026-10-16**（新增 §2.0.4 的 P1/P2 两项）

## 1. 怎么读这份文档

每一项都包含六列，回答"要不要现在做、先做哪个"时需要的全部信息：

| 列 | 含义 |
|---|---|
| **编号** | 便于讨论时引用，例如"先做 B2" |
| **想法** | 一句话说清是什么 |
| **为什么想要** | 提出时的意图（这决定了它值不值得做） |
| **前置条件** | 做它之前必须先有什么；没有前置的可以随时开工 |
| **规模** | 小＝半天内 / 中＝1–2 天 / 大＝3 天以上 |
| **表结构余地** | **最容易被忽略的一列**。分两级，见下 |

> **关于最后一列：分两级，别被它吓到。**
>
> | 级别 | 含义 | 以后改的代价 |
> |---|---|---|
> | **需要** | 改的是**已存数据的含义**，或必须是**记账当时**才能记录的信息 | 迁移真实数据；**可能产生歧义、无法回填** |
> | **不需要 / 不必现在加** | 加一张新表、或加一个带默认值的列就能解决 | **零迁移**，随时可加 |
>
> 早期我把它一律标成"需要留余地"，**那是过度紧张**：加一张新表、或加一个带默认值的列，
> 对已有数据没有任何影响，**完全不需要现在决定**。
>
> 真正需要提前拍板的只有第一级，而到目前**只出现过一条**——金额小数位，且已毕业（见 §2.1）。

### 2.0.3 ⚠️ 通知配额与前一百个账号的豁免（**已实现** 2026-10-13，1.10.04）

**通知有两个上限，都是所有者定的**：

| 上限 | 值 | 防的是什么 |
|---|---|---|
| 对**同一个**账号 | **5 条 / 天** | 反复骚扰同一个人 |
| 对**所有**账号合计 | **20 条 / 天** | 群发骚扰 |

**⚠️ 而账号编号在 `10000000`–`10000099` 之间的（"头一百个"）不受这两个上限约束。**
所有者 2026-10-13：*"对于编号前一百（一直到 1000099）的用户取消限制，只跳过限制仍然计数。
注意其他所有账号都保持不变"*。

| | |
|---|---|
| **谁** | 编号 `10000000`–`10000099`：所有者、家人、**以及 98 个预留编号的邀请码**（`10000002`–`10000099`） |
| **豁免什么** | **两个上限都不再拦截** |
| **不豁免什么** | **计数照旧**——诊断面板仍说得出实际发过多少 |
| **其他账号** | **完全不变** |
| **实现** | `apps/api/src/collab/quota.ts` 的 `isQuotaExempt()` |

> **⚠️ 两条改这里之前必须知道的事**（都写在代码注释里）：
> 1. **不要把它简化成 `users.is_admin`。** 今天两者恰好重合，但规则是**编号区间**——
>    否则以后把某人提为管理员，会顺手取消他的通知上限。
> 2. **测试夹具的账号编号必须落在区间之外。** 原来用随机数生成，**约 1/10 会落进豁免区间**，
>    让上限测试随机空过或莫名失败。**一条上限测试必须跑在受上限约束的账号上。**

### 2.0.1 邀请码有效期与撤销（**已实现** 2026-10-10）

| 类型 | 有效期 | 可撤销 |
|---|---|---|
| **普通邀请码**（`pnpm invite:create`） | **7 天** | ✅ |
| **预留编号的码**（`pnpm invite:batch`、首批那批） | **永不过期** | ❌ |

**为什么要分两种**：码是**在聊天窗口里传递的凭据**。普通码的用途是"现在给某人注册"——
七天足够送达、被看到、被使用，而且**发错了能收回**；而预留编号的那批是
**写在卡片上、几个月里陆续发出去**的，**七天寿命会让它根本发不出去**。

**三种失效原因分开报**（`invite_used` / `invite_revoked` / `invite_expired`），
因为"邀请码无效"这句话**告诉不了对方任何可行动的信息**——这条规则来自"暂无分类"那次教训。

> ⚠️ **界面还没做**：撤销目前走数据库或脚本。邀请列表与撤销按钮排在协作阶段（S9）。

> ⚠️ **本表早期版本把 S5 写成"小票拍照与上传"、S6 写成"导出 CSV / Excel"，编号还停留在旧方案。**
> 已按 2026-10-09 重新定义的场景与当前阶段表改正。

### 2.0.4 ⚠️ 2026-10-16 所有者点名记录、**明确只记录不实施**的两项

**这两项是在 S12-B 部署当天提出的。所有者明确要求：只记进待办，不要在部署过程中顺手做。**
**开工前先与所有者确认优先级。**

| # | 任务 | 为什么想要 | 前置 | 规模 | 表结构余地 |
|---|---|---|---|---|---|
| **P1** | **首次进入逻辑**：新账号**首次**进入时展示**展开的账本空间**；**第二次及以后**直接进入该账号**上次使用账本**的明细页 | 新账号第一次进来还没有"上次的账本"，展开态才是正确的第一印象；老账号每天最想直接看到明细 | 无 | 中 | ⚠️ **需要**——"上次使用的账本"必须被记住 |
| **P2** | **全站用户可见中文文案优化**：检查按钮、提示、错误、权限与危险操作说明 | 文案是攒着长的，前后语气与详略不一致；危险操作的说明尤其要清楚 | 无 | 中 | 不需要 |

#### P1 的详细口径（**所有者逐字要求，不要自行扩大或缩小**）

1. **首次进入** → 展示**展开的**账本空间；
2. **第二次及以后** → 直接进入**该账号上次使用的账本**的明细页；
3. **跨设备保持一致**——"上次使用的账本"是**账号级**的，不是设备级的；
4. **账本失效时安全回退**——上次那本被删了 / 没权限了 / 不存在了，
   要**优雅退回**到一个仍可用的状态，而不是报错或空白；
5. **⚠️ 不重新制作海浪动画**——展开态与收缩态**已有**实现（S10，规格见
   [`海浪效果要求.md`](开发过程记录/海浪效果要求.md)），这一项只动"进哪个状态"的判断，
   **不要碰海浪本身**。

**⚠️ 表结构余地说"需要"的理由**：要记住"某账号上次用的是哪本账"，
就必须有一处存这个事实（账号上的一个字段，或一张小表）。
**这属于"改的是已存数据的含义"那一级**——账号一多、设备一多，
**事后无法从行为反推出每个人当时用的是哪本**。
所以**动手前要先定这个字段放哪**（见 `教训.md` §8.7：不要留同一件事的第二份记录）。

**⚠️ 一个必须先想清楚的问题**：跨设备一致意味着这个偏好**存在服务器上**，
但应用是**离线优先**的——**没网的时候"上次用的账本"从哪来？**
（可能答案：本地也缓存一份，服务器是权威；本地的那份用于离线时的即时判断。）
**这个取舍要在动手前定，不要写完才发现离线路径没考虑。**

#### P2 的详细口径

**范围**：**全站用户可见的中文文案**——按钮、提示、错误信息、权限说明、危险操作说明。

**要求**（所有者原话）：**保持简洁自然、清晰一致的产品语言**。

**⚠️ 边界**：
- **不改变现有业务语义**——只改措辞，不改行为的含义；
- **不要碰 `应用内文案一律用产品语气` 这条既有纪律**（`开发日志.md` ADR-020）：
  面向用户的提示必须严谨、礼貌、中性，**不夹带项目内部语境**；
- 危险操作（删除账本、撤销授权、恢复数据库等）的说明**要更清楚，不是更短**；
- 内部路线图信息**留在文档里，不进界面**。

**⚠️ 已有的检查器**：`apps/web/src/lib/copy.test.ts` 会拦一些退场文案
（例如 `协作者`、`/collaborators`）。改文案前先读它，别把护栏拆了。

#### C2 · 汇率折算（**口径已定，待开发**）

**已决定的口径**：按**记账当时的汇率**折算，而不是用今天的汇率去算过去的账。

> 这个区别很关键：用当前汇率折算历史账目，等于每次看报表金额都在变，而且**反映的不是当时真实的购买力**。

**数据源调研（2026-10-09）**

| 候选 | 权威性 | 是否免费可抓 | 历史数据 | 结论 |
|---|---|---|---|---|
| **[Frankfurter](https://frankfurter.dev/)** | **104 家央行与官方机构**，含欧洲央行与**中国人民银行（CFETS）**，覆盖 223 种货币 | ✅ **无需 API Key、无调用配额** | ✅ **可回溯到 1948 年** | **首选** |
| ECB 官方每日参考汇率 | 欧洲央行本体 | ✅ 公开 XML | ✅ | 备选（Frankfurter 的上游之一） |
| 中国人民银行 / 国家外汇管理局中间价 | 对人民币最权威 | ⚠️ 抓取形式不如 API 规整 | ✅ | 将来若需精确到人民币中间价再单独接 |

选择 Frankfurter 的理由：它是唯一**同时满足四个条件**的——**权威（央行数据）**、**免费可抓（无 key、无配额）**、**有完整历史（能按当时汇率折算）**、**可按来源过滤**（`?providers=ecb` 只用单一官方来源，官方说明这适用于合规场景）。项目开源，也可自建（Docker）以免依赖第三方可用性。

**设计草案**

1. **新表 `exchange_rates`**：`base` / `quote` / `rate`（高精度 numeric）/ `rate_date` / `source` / `fetched_at`
2. **每天抓取两次**：**00:01** 与 **12:01**（用户建议，实现上只是定时任务多一个时间点，成本几乎为零）
   - ⚠️ **但要先认清一件事**：**上游本身就只每天更新一次**——欧洲央行在每个工作日约 16:00（中欧时间）发布当日参考汇率，Frankfurter 只是转发。**所以第二次抓到的通常和第一次完全一样，"精度更高"这个预期并不成立。**
   - **因此抓取时间应该对齐上游的发布时刻**，否则你抓到的永远是"昨天"的数据。建议：
     - **一次放在上游发布之后**（ECB 16:00 CET ≈ 北京时间 22:00–23:00，所以定 **23:30** 比较稳），保证拿到的是当日汇率
     - **一次放在 12:01 做兜底**，覆盖"某天抓取失败"的情况
   - 用户原意是"两次、间隔不超过 12 小时"，**两次没问题，只是别期待数据会更新两次**。
3. **记账时把"当时汇率"写进流水本身**——这正是"按当时汇率"能成立的关键
4. **取不到最新数据时**：使用**已记录的最近一期**，并在界面标明用的是哪一天的数据
5. **免责提示（必须，措辞要防御性）**：界面需同时说明三件事——
   - **按哪一天的汇率折算**（例如"按 2026-10-09 汇率折算"）
   - **不保证汇率准确**（明确写出，而不是含糊的"仅供参考"）
   - **请用户自行核实**，实际结算以银行成交价为准
   > 用户明确要求措辞更有防御性。**只说"仅供参考"太软**——它没有划清责任边界。不告诉用户这个数字有多旧，免责声明本身也就失去了意义。
6. **协议注意**：Frankfurter 明确说明汇率数据本身遵循**各提供方的条款**，对外发布时需注明来源

**表结构余地**：**不必现在加。** 与"金额小数位"不同，这一条**可以事后回填**——Frankfurter 提供历史汇率，将来能按每条流水的日期逐条查出当时的汇率。**但现在加成本最低**，而且能摆脱"依赖第三方历史数据长期可用"的隐忧。**决定权在你。**

> **⚠️ 所以"离线优先"这句话要读准确**：**它指的是记账主路径（记 / 改 / 删 / 看）离线可用**，

> 所以它们离线不可用是设计的一部分。
> **写进这里是为了不再重复讨论**（见 §5 维护要求第 3 条：理由比结论更重要）。

#### I8 详述：「浏览器其它」是什么 —— **✅ 已查清（2026-10-11）**

**所有者的问题（2026-10-11，原话）**：

> **"我一直想知道这个浏览器及其他到底是啥——一直占我空间还删不掉！"**

**要求**：**加一条待办，在正式上服务器之前查一下这是什么东西以及怎么删除，
希望前人有充分的经验。**

##### 结论：**它是浏览器的 HTTP 缓存**，而**网页无法用代码清除它**

| 问题 | 答案 |
|---|---|
| **它是什么** | **浏览器自己的 HTTP 缓存**（存原始响应），**不属于** IndexedDB，也**不属于** Cache Storage |
| **为什么删不掉** | **Web 平台没有任何 API 能清 HTTP 缓存。** `caches.delete()` 只清 **Cache Storage**（Service Worker 那一套）——**而我们已经在"清除本应用的全部本地数据"里清光了它**，所以那个按钮对这部分**天然无能为力** |
| **它为什么这么大** | **开发模式**：Vite 按需提供**未打包的模块**，每个模块一个请求、每个都进 HTTP 缓存；**而且没有关 sourcemap**，每个模块还带一份源码映射 |
| **它为什么涨** | 每次刷新都要重新拉一整套模块（开发服务器不复用浏览器缓存），旧的条目仍按源记账 |

**实测数字（2026-10-11，本机）**：

| 项 | 开发模式 | 生产构建 |
|---|---|---|
| **一次加载要拉的量** | 142 个源文件 + 约 309 个依赖包，**逐个请求** | **1 个 JS（610 KB）+ 1 个 CSS（37 KB）+ HTML/SW（9 KB）** |
| **产物总体积** | `node_modules/.vite` 预打包 **6.26 MB**（还会被 sourcemap 放大） | **655 KB** |

**⚠️ 所以那个 68.9 MB 里，真正"属于账本"的可能只有几百 KB**——
**其余是开发模式自己制造的，而且它在浏览器眼里是"页面缓存"，不是"我们的数据"。**

##### 怎么清除（**分两种，各有前提**）

| 场景 | 做法 |
|---|---|
| **只想清缓存，不动账本**（推荐先试这个） | **Chrome / Edge**：`F12` → **Network** → 勾 **Disable cache**（开发时）；或 **Application → Storage → Clear site data** 里**只勾"Cache storage / 缓存的图片和文件"**。<br>**Safari**（iOS）：**设置 → Safari → 清除历史记录与网站数据**——⚠️ **但这一个会连 IndexedDB 一起清掉，见下方警告。** |
| **彻底清（含账本）** | 用应用里的**「清除本应用的全部本地数据」**，或浏览器的"清除网站数据" |

> ### ⚠️ 动手之前必须先确认一件事
>
> **HTTP 缓存、IndexedDB、Cookie 是按"源"（origin）算的，很多浏览器把它们放在同一个"网站数据"里**——
> **"清除网站数据"会连我们的离线账本一起删掉。**
>
> **所以清除之前**：**确保账本已经全部同步到服务器**（明细页没有淡绿/淡红的行），
> **否则那些只在本机的改动会一起没掉。**
> **这与 `归档/离线与同步-设计决定.md` 的立场一致**：**"缓存是用户唯一的离线副本"——
> 所以任何"小心起见清掉缓存"的做法都是错的，除非用户明确知道自己要清什么。**

##### 根治办法：**日常用生产构建，而不是开发服务器**

**开发模式（`pnpm dev`）本来只是"我改代码时看的"，不是"给人用的"。**
**所有者日常在手机上用的时候，应该用的是生产构建**——那时每次加载只拉 **3 个小文件**，
HTTP 缓存自然几乎不增长。**这件事归到 S12（可上线）**：那时有真正的域名与 HTTPS，手机上用的是构建产物。

**⚠️ 顺带一条可以直接减负的**：`vite.config.ts` **没有关 sourcemap**，
开发模式下每个模块都带源码映射。**关掉它（或只在需要时打开）能立刻让开发模式的缓存占用小一大截**——
但**这属于代码改动**，要按规矩升版本 + 写版本记录，所以留到有明确需要时再做。

##### ✅ 已排期：**上线时关掉开发服务器**（所有者 2026-10-11 点名加的一项）

**所有者原话**：

> **"关于开发者缓存：现在还是开发状态，所以肯定没办法做。但是你可以在待办名单里加一项。
> 程序在上线前关掉开发服务器。这样一来，用户应该不会再出现这样的问题了吧。"**

**已写入 `开发计划.md` 的 S12（可上线）任务与验收标准**：域名指向 `apps/web/dist` 的静态产物，
`pnpm dev` 只留在开发机上；**顺手关掉开发模式的 sourcemap**。

**⚠️ 而"这样一来就不会再出现"这句话，要答得准确一点**：

| 问题 | 上线后会怎样 |
|---|---|
| **开发模式那几十万个模块请求** | ✅ **消失**——家人访问的是构建产物，一次加载只拉 3 个文件 |
| **sourcemap 放大** | ✅ **消失**（前提是关掉它） |
| **Service Worker 的外壳缓存** | ⚠️ **仍然会有，但它是有限的**：3 个文件、约 655 KB，而且**只在版本变化时才更新**——**不会再持续增长** |
| **`storage.estimate()` 报的数** | ⚠️ **仍然会略高于真实数据**——它包含浏览器还没落盘的部分。这是浏览器的记账方式，**不是我们的泄漏**，也**无法由程序消除** |

**结论**：**"每刷新一次就涨"这个现象会消失**，占用会稳定在一个小而固定的量级（预计**几百 KB 到 1–2 MB**，
不再是无上限增长）。**但 `estimate()` 那个数字本身永远会比真实数据大一点**——
**这不是 bug，是浏览器的记账口径**，所以我们**不承诺"这个数字会变成账本的真实大小"**。

**⚠️ 一条现在仍然成立的警告**（上线前后都一样）：**HTTP 缓存、IndexedDB、Cookie 同属"网站数据"**，
**很多浏览器"清除网站数据"会连离线账本一起删**——所以清之前必须确认**明细页没有淡绿/淡红的行**。

**⚠️ 还有一件事要分开看**：**开发服务器不能"完全删掉"**——真机调试仍然需要它
（手机通过局域网 https 访问，见 `docs/README.md`；而且 **Service Worker 只在生产模式下注册**，
所以**离线功能只能在构建产物上测**，见 `worker.ts`）。
**要分的是"谁在用它"**：开发服务器给开发机，构建产物给家人。

**参考**：`docs/归档/离线与同步-设计决定.md` §4.5d（52.5MB 与 127KB 的差）。
