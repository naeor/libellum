## 2. 怎么把它跑起来

### 2.1 前置

| 需要 | 说明 |
|---|---|
| **Node + pnpm** | 见根 `package.json`；pnpm workspace |
| **PostgreSQL 17** | 测试库与开发库**是分开的** |
| **`.env`** | **不进 git**（`DATABASE_URL` 等） |

**数据库连接串**（本机开发环境）——**格式如下，口令看你自己机器上的 `.env`**：

```
DATABASE_URL=postgresql://ledger:CHANGE_ME@127.0.0.1:5432/ledger_dev?schema=public
TEST_DATABASE_URL=postgresql://ledger:CHANGE_ME@127.0.0.1:5432/ledger_test?schema=public
```

> **⚠️ 这里以前写的是真实口令，2026-10-14 已改成占位符。** 原因与处理过程见
> [`Libevra品牌迁移记录.md`](开发过程记录/Libevra品牌迁移记录.md) §13。
> **那份口令已经泄露（曾提交进公开仓库），并且已经轮换过**——所以**别再去历史里找它，它已经不能用了**。

**本地怎么拿到真实口令**：它在仓库根目录的 `.env` 里（**`.env` 已被 `.gitignore` 排除，永远不进 Git**）；
要新配一台机器，就把 `.env.example` 复制成 `.env` 再填你自己的口令，**不要再把口令写进任何文档**。

**⚠️ 测试库要单独跑一次 `prisma migrate deploy`**，否则 API 测试会因为缺表失败。

### 2.2 常用命令（**都在仓库根目录跑**）

| 命令 | 作用 |
|---|---|
| `pnpm typecheck` | 三个包的类型检查 |
| `pnpm -r test` | 全量测试（shared / web / api） |
| **`pnpm check:build`** | **真实构建**——**见下方警告** |
| **`pnpm check:docs`** | **文档检查**：相对链接是否有效 + 文档里的值是否与代码一致 |
| `pnpm docs:build` | 把 **27 份** markdown 生成 `.docx` / `.pdf`（生成物落在 `docs/` 根目录） |
| `node tools/check-modules.mjs` | 每个源码模块能否独立编译 |
| `pnpm db:generate` / `pnpm db:deploy` | Prisma 生成 / 应用迁移 |
| **`pnpm admin:list`** | **看谁是管理员、谁只是有资格**（只读） |
| **`pnpm admin:grant <UUID> --by "<操作者>"`** | **授权管理员**——**唯一的授权方式**，见设计决定 §7 |
| **`pnpm admin:revoke <UUID> --by "<操作者>"`** | **撤销管理员**——**立即生效**，不需要重启或重新登录 |

### 2.3 ⚠️ **`pnpm check:build` 不能省**

**类型检查和单元测试都拦不住"整个应用起不来"。**
**这个项目真的发生过一次**：一条 CSS 规则放进了 Tailwind 的 `@theme` 块
（它只允许自定义属性或 `@keyframes`），**于是 Vite 用错误浮层替换掉整个应用，
所有路由包括登录页都变成一张错误图**——**而当时 `typecheck` 全过、650 条测试全过。**

**见 `教训.md` §8.10。** **所以**：**每次提交前跑 `pnpm check:build`。**

## 3. 代码长什么样

### 3.1 目录

```
apps/api        Fastify 5 + Prisma 7 + PostgreSQL 17
apps/web        React 19 + Vite 8 + Tailwind 4 + TanStack Query 5
apps/ocr        识别服务
apps/voice      语音服务
packages/shared 前后端共用类型与校验
docs            设计文档（markdown 是源，.docx 是产物，且不进 git）
tools           证书生成、模块检查、构建检查
```

### 3.2 ⚠️ 四条会咬人的约定

| 约定 | 说明 |
|---|---|
| **金额一律是整数最小单位** | 元以"分"存（`amountCents`）。**永远不要引入浮点** |
| **`exactOptionalPropertyTypes: true`** | 可选属性写 `undefined` 会报错。**可选 prop 的类型要显式 `\| undefined`** |
| **时间要比较"瞬间"，不能比较字符串** | 家里有 UTC-7 和 UTC+8 两种记录时，**ISO 字符串排序是错的**——用 `Date.parse` |
| **`categoryName` / `version` 不参与冲突比较** | 前者是派生显示字段，后者是记账用的 |

### 3.3 离线层的核心（**改这里之前先读 `归档/S8-冲突-设计决定.md`**）

| 文件 | 作用 |
|---|---|
| `lib/offline/storage.ts` | **底层是一个键值存储**：IndexedDB 数据库 `libellum`，**只有一个 object store 叫 `kv`**（不是"每张表一个 store"） |
| `lib/offline/localLedger.ts` | **权威副本**：`ledger-months`（账目）+ `ledger-marks`（印记）——**这两个是 `kv` 里的键**，不是两个 store；键形如 `ledger-months:<userId>:<bookId>`（按账号与账本隔离）；**外部 store + `useSyncExternalStore`** |
| `lib/offline/scope.ts` | scope 键（`<account>:<ledger>`）；**必须能同步读**，因为持久化查询缓存读得很早 |
| `lib/offline/sync.ts` | `syncAll()`（从印记推导要发什么）、拉月份、拉冲突 |
| `lib/offline/write.ts` | 新建 / 修改 / 删除 / 解决冲突 |
| `lib/offline/conflictChoices.ts` | **冲突界面的候选项**（来自服务端的 `claims`） |
| `lib/offline/device.ts` | 本机标识（冲突记录要写"哪两台设备"） |
| `lib/ledgerView.ts` | 界面用的账目合并（**服务器那份优先，本机未同步的保留**） |

**⚠️ 而这一条是这一层最容易犯的错**：

> **绝不用 React state 承载"界面要读的离线数据"。**
> **必须走模块级外部 store + `useSyncExternalStore`**——

## 4.5 ⚠️ 1.10.02 修的一个真缺陷：**换账号后看到上一个账号的账本**

**所有者发现的**：登录另一个账号后，屏幕上显示的却是**他自己**的账本编号。

**不是服务端的问题、也不是数据的问题**（两样都用真实会话与真实数据库核实过）：

| 层 | 事实 |
|---|---|
| 数据 | 两个账号各一本账，流水归属完全干净，**零串账** |
| 服务端 | `mama` 带 `naeor` 的账本 → **403**；反向也 403。**权限来自 `book_members`，没破** |
| 客户端 | ⚠️ **会话失效时没有清"当前账本"** |

**根因**：`logout()` 会清 `current-book`，但**会话过期那条路没清**。于是设备上还留着上一个账号的账本 id，
登录新账号后第一个请求就声明了一本自己不是成员的账本 → 403（数据没泄露），
**但缓存里那本账的元数据还在屏幕上** → 标签显示成别人的编号。

**⚠️ 这条教训的形态值得记住**：**"登出"和"会话失效"必须做同一套清理。**
只把其中一条路写对，另一条路就会留下上一个人的痕迹——而它平时不出现，只在换账号时出现。

**修法**：抽出 `forgetLocalState()` 供三条路径共用（登出 / 会话失效 / 登录时换了账号），
并给 `currentBook.ts` 补了 5 条回归测试。详见 `版本记录（1.10-1.13）.md` 的 1.10.02。

### 4.6 ⚠️ 1.10.03：同一个形状的第二个缺陷——**建了新账本却进不去**

**所有者发现的**：用妈妈的账号新建「共享账本」，**点击"创建并进入"、或事后在开始页面点击，都进不去**，
依旧进"我的账本"。

**根因**：**"当前账本"存了两份，而激活账本时只更新了服务端那一份。**

| 份 | 谁写 | 激活时有没有更新 |
|---|---|---|
| **服务端** `users.lastBookId` | `POST /books/:id/activate` | ✅ 更新了 |
| **本机** `current-book` | `setCurrentBook()` | ❌ **没有**——它只在 `useLedger()` 里被调用 |

于是 `enterLedger` 结尾那次整页刷新读回的是**旧账本 id**，`/ledger` 遵守请求头返回旧账本，
而 `useLedger` 又 `setCurrentBook(旧账本)` **把它钉回去**——**每一次尝试都走同一条路，所以永远进不去。**

**⚠️ 还顺手修了一个真实的竞态**：`setCurrentBook` 原先 `void writeValue(...)`，
而 `storage.ts` **只在 IndexedDB put 成功之后**才更新同步镜像——
"先写、再 `location.assign`"是一次真竞速，**输了刷新就会把刚离开的账本读回来**。
现在 `onSuccess` 返回这个 Promise，**写入落地之后才跳转**。

**⚠️ 而 4.5 与 4.6 是同一个形状，这才是值得记的**：
**一个事实存了两份，而只更新了其中一份。**
1.10.02 是**账号**换了、账本没清；1.10.03 是**服务端**换了、本机没换。
`教训.md` §8.7 早就写过：**"关于同一件事的第二份记录，迟早会不一致。"**
**所以下次看到"两份记录"的结构，先问一句：两边都会更新吗？**

## 4.10 1.10.07：协作页的**容器规则**（S11 第一阶段补充）

**所有者给的规则**：*"摘要型信息保留卡片；可直接操作的功能区采用'半开放式'设计；
浏览型列表保留一个总外框，但内部不再套小卡片。"*
诊断：*"当前协作页空间利用率偏低，存在明显的'盒子套盒子'问题。"*

### 4.10.1 三层容器，写进组件而不是写在注释里

| 内容 | 容器 | 组件 |
|---|---|---|
| 摘要对象 / 概览 | **卡片** | `Section` |
| 小列表 / 复合功能区 | **一个总外框** | **`SectionFrame`**（新增） |
| 局部操作区、外框内的条目 | **直接排列，不套卡片** | 子元素自己不加边 |

**⚠️ 去框靠 `embedded` 开关，绝不复制列表。** `HistoryList` 在完整历史页仍自画框（那里它**就是**页面），
协作页传 `embedded` 就不画。**复制一份会是"同一个服务端句子有两个渲染器"**（`教训.md` §8.12）。

**⚠️ 六处次级入口统一用 `FrameAction`**（`查看全部` / `展开完整对话` / `新消息 N 条` / `账本详情` /
`切换账本` / `成员管理`）——手写六遍 class 就是六次机会让其中一处又变成实体按钮。

### 4.10.2 ⚠️ 一个我自己写出来、被测试抓到的真 bug

第一版用了 **`window.localStorage`**。**浏览器里没问题，但这个项目的 Web 测试跑在纯 Node、没有 DOM**
（`vitest.config.ts` 明确写了这条设计）。**`window` 不存在 → 整个留言板渲染不出来。**

改成**裸全局 + `typeof` 守卫**。**⚠️ 教训：只在浏览器里成立的工具函数，是对渲染器的依赖，不是对存储的依赖。**

### 4.10.3 「新消息 N 条」

| 规则 | 决定 |
|---|---|
| 存哪 | `localStorage`，**key 里带账本 id** |
| 首次进入 | **0**（否则第一次打开就是"新消息 47 条"——那是历史，不是新消息） |
| 没有新消息 | **隐藏**；`展开完整对话 ›` **始终显示** |
| 边界 | 严格 `>`：**当时正在看的那条不算新的** |

**⚠️ key 必须带账本**：共用时间戳会让 **B 账本继承 A 的已读状态**——在 B 里写的留言会被报成"已读"，
**人不会被告知**。这是最安静的一种跨账本泄漏：不是把数据给错人，而是**把通知悄悄吞掉**。

## 4.11 1.10.08：开始页精简 + 每本账的齿轮面板 + 海浪提示词

**所有者三条核心要求**：开始页回归「账本选择与管理空间」；**点齿轮不得切换当前账本**；
**不要动海浪的任何动画机制，只改提示词和箭头**。

### 4.11.1 海浪提示词：根因是**被容器裁掉**，不是淡出

```css
/* 之前 */ .space-cue-window { height: calc(20dvh * (1 - var(--p))); overflow: hidden; }
```

**提示词装在一个高度收缩到 0 且 `overflow: hidden` 的盒子里**——所以它是被物理裁掉的。
**修法**：改成**覆盖层**（脱离盒子，没法被裁）+ **`opacity: clamp(0, calc(var(--p) * 14 - 12), 1)`**。
`--p` 是海浪每帧写进 DOM 的同一个数，**所以不可能不同步**。

> **⚠️ 一般化的教训**：*"某个元素淡出得不自然"*，先看它是不是**被父容器裁剪或覆盖**，
> 而不是先去调它的 opacity——**裁剪和淡出在观感上很像，成因完全不同。**

### 4.11.2 ⚠️ 齿轮面板：`book` 是**值**，不是查询

面板**从来没拿到"当前账本"**，所以"误用当前账本"没有代码路径可走。
目标账本 id 通过**已有的 `apiFetch` 单次 header 覆盖**传递，**全局当前账本一动不动**。
→ `useBookMembers(bookId)` / `useShareLinks(bookId)` / `useChangeMemberRole(bookId)` / `useRemoveMember(bookId)`
都加了可选 bookId，**且缓存键带上账本**（否则第二本会命中第一本的缓存）。

**⚠️ 另有 `useLedgerMeta(bookId)`，不能用 `useLedger`**：后者会调 `setCurrentBook`/`setOfflineBook`
——那是"设备学会自己在哪本账里"的机制，**对一本只是点了齿轮的账本调用它，等于静默切换**（所有者明确禁止）。

### 4.11.3 新增的两样（都已获批准）

| | |
|---|---|
| **`PATCH /books/:id` 重命名** | 后端原本**没有**。权限**沿用现成的 `requireBookForWrite`**，没新造规则。**路径与请求头不一致 → 400 `book_mismatch`，什么都不改**——这是让齿轮面板安全的那条规则 |
| **迁移 `20261013190000_book_changed_event`** | `transaction_events` 有 CHECK 逐字列举事件类型，**不加就写不进去**。只放宽这一条约束，**不动数据** |

### 4.11.4 ⚠️ 顺带修的缺陷：viewer 打不开「账本信息」

`/ledger` 一直挂在**写**权限上 → **viewer 得到 403**。而规则是"查看者不应获得编辑或邀请权限"，
**读名字和账目数不是编辑**。已收窄为读权限，并补测试：**该能读的能读，不该能写的仍 403。**

### 4.11.5 ⚠️ 三个错，全是检查抓住的

1. **CSS 注释里的直引号**：Lightning CSS **在注释里也把 `"` 当字符串起始符**，奇数个就吞掉整个文件 →
   `Unterminated string`。**`pnpm check:build` 拦下的**（`教训.md` §8.10 的原样重演）。
   **⚠️ CSS 注释里一律用「」。**
2. **空状态写了「你还没有账本」**，违反既有语体规则 → **`copy.test.ts` 拦下的**。
3. **历史句子拼成 "naeor 变更了这本账 这本账"**（名词重复）。**我的单测只断言"包含这本账、不含一笔账目"，两条都过**，
   **真实接口冒烟把句子读出来才看见**。

| 现在 | **改画法**：描边（与 tab 五个图标同一套），一个外圈 + 轴心 + **八根短径向笔画当齿** |

> **⚠️ 一般化教训**：*"图标不好看"* 可能是**形状**错，也可能是**在这个尺寸下的画法**错。
> **填充图形在缩小时会糊成一团，描边不会**——所以小图标优先用描边。

### 4.12.2 ⚠️ 把真按钮放进"纯装饰"容器时，有两个不会报错的坑

`.space-ocean` 一直是 `pointer-events: none` + `aria-hidden`——**对一幅画是对的**。
放进去一个真按钮之后：

- `aria-hidden` → **读屏软件完全看不见这个按钮**；
- `pointer-events: none` → **看起来完全正常，但点不动**。

**两个都不会报错**。现在有一个显式的 `interactive` 开关，**调用方必须主动声明**。
> **⚠️ 通用问法**：往一个 `aria-hidden` / `pointer-events: none` 的容器里加可交互内容之前，
> **先回去把这两个属性处理掉**。

### 4.12.3 ⚠️ 返回绕圈：根因是**历史栈成环**，不是某个页面写错

「关于」的 `backTo` 是 `/settings`；**当它从第三处（开始页页脚）进入时，两个页面互相指向对方，按返回就是绕圈。**

**修法**：**声明的来处胜过历史** —— `location.state.from`。

**⚠️ 两条必须同时成立**：
1. `useGoBack` **先看 `from`，再看 `location.key`**（顺序就是修复本身）；
2. **每个入口都要设置 `from`**，而且**必须用 `Link` 而不是 `<a>`**——
   `<a>` 是整页加载，会重置历史，**声明送不到，兜底反而生效，bug 静悄悄回来**。

**⚠️ 改动 `useGoBack` 会影响全站每个二级页**，所以测试**同时断言读取方与设置方**——
只测一边的测试会在 bug 还在时通过。

## 8. 和所有者打交道

**这一节是给下一个 AI 的，而且它可能是最有用的。**

### 8.1 他会给出非常准确的判断，**要当真**

**这个项目里好几次是他比我先找对方向**：

| 他的原话 | 后来的结论 |
|---|---|
| **"在进入明细态时右上角的三个按钮很难被点击到，似乎是判定的问题"** | **确实是判定问题**——按钮上移 4px，升进了上方横幅 `z-index` 更高的那条带里 |
| **"至于'判定里完全不需要版本号'，这个似乎是你早期提出的一点，但被我否决之后，它隐藏在你的思路里"** | **完全正确**，而那就是冲突检测失效的根因 |
| **"我想没有哪个程序会弹出一个弹窗让人选择数字是 60 还是 60"** | **一句话定义了规则 2** |

**⚠️ 所以他说"似乎是这样"的时候，先按他说的去查，而不是先解释为什么不可能。**

### 8.2 他要的是结果，不是过程描述

- **报告要说清**：**版本号、改了什么、怎么验证的**；
- **⚠️ 而他明确要求过"略微精简诊断"**——**不重要的诊断不要写出来**；
- **而"未解决"必须写成未解决**：`版本记录（1.10-1.13）.md` §1.3 有一条：
  **"一个把'未解决'写成'已解决'的记录，比没有记录更糟。"**

### 8.3 他会用中文，而**回复也用中文**

**他的原话要求过**：**"记得用中文回复，并且思考过程也用中文。"**

### 8.4 ⚠️ 一条我给下一个 AI 的实话

**这一轮我表现不好**：**我在他已经说清楚规则之后还自己加了东西，而加的那条把主要功能弄坏了。**
**代价是四个多小时和很多次来回。**

**所以**：**当他说"我就是这个逻辑"的时候，不要再问"要不要顺便……"。**
**当他没说的，不要加。当他不确定的，问他。**

**⚠️ 而他会因为反复失败而急躁——那是正常的**，
**而这时的正确做法不是道歉更多次，是"少做、做对、把结果说清楚"。**
