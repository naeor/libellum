## 0. ⚠️ 先记住一件事：**本地和云端是两个互不相干的库**

这是你问题的根源，值得先说清楚。

```
本机开发库 ledger_dev                    云端生产库 libevra_prod
  ├─ 账号 2 个（naeor、mama）              ├─ 账号 0 个
  ├─ 邀请码 102 个                         ├─ 邀请码 1 个
  ├─ 管理员 naeor（授权 + 名单）            ├─ 管理员 0 个
  └─ 流水 279 条                           └─ 流水 0 条
        ↕                                              ↕
   两个库之间【没有任何同步机制】
```

**⚠️ 邀请码、账号、管理员、流水——全都不在两库之间流动。**
在本机 `invite:create` 生成的邀请码，**只存在于本机那个库里**，
在 `libevra.com` 上**一点用都没有**（因为服务端是去**生产库**里查这个 code）。

**⚠️ 这不是配置错误，是设计。** 两个库各自独立：
本机是开发/试验用的，云端是真正在跑的。**它们的唯一共同点是同一份代码。**

## 1. 你的邀请码会不会上传到服务器？

**不会，而且不应该会。**

| | 实际情况 |
|---|---|
| 本机那 102 个邀请码在哪 | **只在本机开发库 `ledger_dev` 的 `registration_invites` 表里** |
| 会自动同步到生产吗 | **不会**。没有同步机制 |
| 应该手动搬过去吗 | ❌ **不应该**。邀请码是**一次性凭据**，搬过去等于把开发期的凭据变成生产的凭据 |
| 那本机那批还有用吗 | ⚠️ **对 `libevra.com` 没有用**。它们对本机开发服务器（`localhost`）仍然有效 |

**⚠️ 顺带说清楚那 102 个是什么**：其中 98 个是**预留编号**码（编号 `10000002`–`10000099`），
是当初为"首批邀请码"准备的。它们**仍然是有效的邀请码**，
**但只在生成它们的那个库里有效**——也就是只在本机。

**⚠️ 而且它们现在不会产生管理员了**（1.10.22 之后的修复）：注册流程永远是 `isAdmin: false`。
这一点见 §6。

**`naeor`（编号 `10000000`）的 `admin_grants` 与 `admin_allowlist` 各有一条有效记录**。
**不需要再注册、也不需要重新授权。**

## 3. 日常掌控：所有操作都在同一个地方

### 3.1 唯一入口：SSH 上服务器

**⚠️ 已经配好了别名，最短的写法是四个字：**

```powershell
ssh libevra
```

**看到 `ubuntu@VM-0-15-ubuntu:~$` 就成功了。**

别名写在 `C:\Users\ZhuanZ（无密码）\.ssh\config` 里（2026-10-16 加），内容是：

```
Host libevra
    HostName 43.161.227.152
    User ubuntu
    IdentityFile ~/.ssh/libevra_server
    IdentitiesOnly yes
    ConnectTimeout 15
    StrictHostKeyChecking ask
```

**⚠️ 那个文件里没有任何密码或密码短语** —— 它只记录"连哪台机器、用哪个用户、拿哪把钥匙"。
**⚠️ 如果哪天想不用别名**（例如配置文件丢了），完整写法仍然有效：

```powershell
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152
```

### 3.2 进去之后，先设两个快捷变量（每个会话设一次）

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"
```

**⚠️ 这两个变量只在当前 SSH 会话有效**，退出再进来要重设。
后面所有命令都用 `$DC`。

## 4. 邀请码：怎么看、怎么生成、怎么作废

### 4.1 看当前有哪些邀请码能用

**⚠️ 邀请码不能写进任何文档或仓库**（仓库是公开的，而邀请码是唯一能注册的东西）。
所以**要看就上服务器查**：

```bash
$DC exec -T db psql -U libevra -d libevra_prod -c \
  "select code, coalesce(note,'(无)') as 备注, coalesce(account_number,'(未预留)') as 预留编号,
          case when used_at is not null then '已用'
               when revoked_at is not null then '已撤销'
               when expires_at is not null and expires_at < now() then '已过期'
               else '可用' end as 状态,
          coalesce(to_char(expires_at,'YYYY-MM-DD HH24:MI'),'永不过期') as 有效期
     from registration_invites order by created_at;"
```

**⚠️ 这条命令会把邀请码原文打在屏幕上。看完记得清屏**（`clear`），
**不要截图、不要复制到聊天里。**

**只要一个能用的**（不打印别的）：
```bash
$DC exec -T db psql -U libevra -d libevra_prod -tAc \
  "select code from registration_invites
    where used_at is null and revoked_at is null
      and (expires_at is null or expires_at > now()) limit 1;"
```

### 4.2 生成一个新邀请码

**这是你以后最常用的命令。** 在服务器上：

```bash
# ① 普通邀请码：7 天后过期，普通账号
$DC exec -T api pnpm invite:create "给妈妈"

# ② 预留编号码：永不过期，编号从计数器取（下一个），仍是普通账号
$DC exec -T api pnpm invite:create "首批" --reserved
```

**成功会看到：**

```
  邀请码已生成（只能使用一次）
  邀请码：XXXX-XXXX-XXXX
  有效期：7 天后过期（2026/10/23 14:12:10）
  权限：普通账号
  备注：给妈妈
```

**参数说明：**

| 写法 | 有效期 | 账号编号 | 会产生管理员吗 |
|---|---|---|---|
| `pnpm invite:create "备注"` | **7 天** | 注册时从直接计数器取（`10000101` 起） | ❌ 不会 |
| `pnpm invite:create "备注" --reserved` | **永不过期** | **现在就预留**（第一批区间内） | ❌ 不会 |
| `pnpm invite:create "备注" --admin` | 永不过期 | 现在预留 | ⚠️ **不会**（见 §6） |

**⚠️ 备注只是给你自己看的**，不会显示给注册的人。
建议写清楚是给谁的——**将来要作废时你得认得出是哪一个**。

**⚠️ 邀请码只显示这一次。** 命令的输出就是它唯一一次出现，
**要发就当场复制**，否则只能作废重新生成。

### 4.3 作废一个邀请码

**⚠️ 目前没有 CLI 命令做这件事**，要直接改数据库。**这是一个数据写入，做之前先想清楚。**

```bash
# 先看清楚要作废哪一个（按备注找，别凭记忆）
$DC exec -T db psql -U libevra -d libevra_prod -c \
  "select id, coalesce(note,'(无)') as 备注, coalesce(account_number,'(未预留)') as 预留编号,
          created_at, used_at, revoked_at
     from registration_invites where used_at is null order by created_at;"

# 确认无误后作废（把 <备注> 换成你要作废那条的备注）
$DC exec -T db psql -U libevra -d libevra_prod -c \
  "update registration_invites set revoked_at = now()
    where note = '<备注>' and used_at is null and revoked_at is null;"
```

**⚠️ 永远不要 `delete` 邀请码行**：`revoked_at` 时间戳保留了"什么时候作废的"，
而删除会让这段历史消失。**作废用 `update`，不用 `delete`。**

**⚠️ 预留编号的码撤销后，那个编号不会退回。** 编号一旦预留就占住了
（这是设计：编号是"发出去的卡片"，收回卡片不代表编号空出来）。

### 4.4 怎么把邀请码给家人

1. 在服务器上生成，**当场把码复制出来**
2. 用你平时的方式发给他（微信、短信、口头）
3. ⚠️ **发完从聊天记录里删掉**
4. ⚠️ **不要在对话里、文档里、仓库里留下它**

## 5. 管理员：怎么看、怎么授权、怎么撤销

### 5.1 看当前管理员状态

```bash
$DC exec -T api pnpm admin:list
```

**它会分四栏显示：**

```
真正的管理员（授权 + 名单，两者都有）      ← 只有这里的人能做管理员操作
⚠️ 只满足一半（不会通过校验）              ← 做了两步中的一步，还不能用
有资格但未授权（N 个）                     ← 编号在 10000000–10000099 内，但没有管理员身份
已撤销 / 已移出的记录                      ← 历史
```

**⚠️ 2026-10-17 只读核查：第一栏有 `naeor`（授权 + 名单都有效）。**
（2026-10-16 当天四栏全空；此后所有者已完成注册与两步授权，**旧记录已过时**。）

### 5.2 授权一个管理员（**两步，缺一不可**）

**⚠️ 这是最容易做错的地方。** 必须先拿到那个账号的 **UUID**（不是用户名）：

```bash
# 第 1 步：查 UUID（用户名、编号、UUID 都会列出来）
$DC exec -T api pnpm admin:list

# 第 2 步：授权（第一重）
$DC exec -T api pnpm admin:grant <UUID> --by "owner"

# 第 3 步：列入允许名单（第二重）—— ⚠️ 这一步不能省
$DC exec -T api pnpm admin:allow <UUID> --by "owner"

# 第 4 步：确认
$DC exec -T api pnpm admin:list
```

**⚠️ 只做第 2 步，这个账号还不是管理员。**
`admin:list` 会把它显示在「⚠️ 只满足一半（不会通过校验）」一栏，
而它**确实不能通过校验**。**这是设计在工作，不是故障。**

**为什么要两步**：授权（"这个账号被授予过管理员角色吗"）与允许名单
（"这个账号是当前允许行使管理员身份的之一吗"）是**两件不同的事**，可以分别撤销。
详见 [`管理员与权限边界-设计决定.md`](开发过程记录/管理员与权限边界-设计决定.md) §4。

**⚠️ 另外两个前提**：账号必须**编号在前 100 之内**（`10000000`–`10000099`），
且**不是演示账号**。不在区间内的账号**不能被授权**，脚本会拒绝。

### 5.3 撤销管理员（也是两步，但通常只做一步）

```bash
# 常规：撤销授权
$DC exec -T api pnpm admin:revoke <UUID> --by "owner" --why "原因"

# 出事时的第一反应：移出允许名单（不论它持有什么，立刻不许行使）
$DC exec -T api pnpm admin:disallow <UUID> --by "owner" --why "原因"
```

**⚠️ 两者都立刻生效**（下一次管理员请求就失败），**不需要重启，也不需要让人重新登录**。

**⚠️ 脚本会拒绝撤销最后一个管理员**，除非加 `--allow-empty`。
**系统不会自动补一个替补管理员。**

### 5.4 改某个账号的密码（服务器终端前）

**⚠️ 什么时候需要它**：应用里改密码的接口**要求先登录**，而恢复密码要靠**恢复码**。
当**两者都不可用**时（密码记错、恢复码也丢了），唯一剩下的路径就是**站在服务器终端前**——
那本来就是比应用管理员**更高的一层权限**。这不是后门：拿到数据库访问权的人本来就能改任何东西。

```bash
$DC exec -T api pnpm set:password <UUID> --by "owner" --password '<新密码>'
```

**⚠️ 别把密码写进 shell 历史。** 上面的写法会把密码留在 `~/.bash_history` 里。
**更干净的做法**：先 `set +o history`，改完再 `set -o history`：

```bash
set +o history
$DC exec -T api pnpm set:password <UUID> --by "owner" --password '<新密码>'
set -o history
```

**⚠️ 几点如实说明**：

| 事项 | 说明 |
|---|---|
| **不会踢掉已登录的设备** | 改密码只换哈希，`sessions` 表不动。想踢掉就自己去「我的」页登出 |
| **不会回显密码** | 脚本只报"改成功了"与账号标识 |
| **至少 8 位** | 短于此会被拒绝 |
| **哈希用项目自己的 `hashPassword`** | Argon2id，与注册/改密码接口同一套参数 —— 不另写第二套实现 |
| **改完自己测一次** | 用新密码在浏览器登一次确认。**"脚本说成功"不等于"能登"** |

**⚠️ 大小写与形近字符**：改密码时**逐字符核对**。这个项目真的发生过一次
"把用户口述的密码大小写弄错，结果**覆盖掉一个本来能用的密码**"——
而当时还反过来断言用户记错了。**口述的密码先原样记录、再逐字符确认**，不要凭印象补大小写。

### 5.5 ⚠️ 你也可以给自己一个"备用管理员"

**建议考虑**：如果你只有 `naeor` 一个管理员，而它出了问题（忘记密码、恢复码丢了），
**你就没有任何办法做管理员操作了**（没有"找回超级管理员"接口，那是故意的）。

**可行的后备方案**（按推荐顺序）：
1. **保管好恢复码**——它是你恢复访问的正常途径；
2. **注册第二个自己的账号**（编号会落在 10000000–10000099 内，所以有资格），
   但**平时不授权**；需要时再 `grant` + `allow` 它；
3. 最坏情况下：SSH 上服务器，用 `admin:grant` + `admin:allow` 从终端前授权任意合格账号——
   **这不需要管理员权限，需要的是服务器权限**，而那本来就是更高的一层。

## 6. ⚠️ 一个现在很安全、但值得知道的事

**`--admin` 参数现在的行为和你可能以为的不一样。**

| | 事实 |
|---|---|
| `pnpm invite:create "x" --admin` 会做什么 | 预留编号 + 把 `grants_admin = true` 写进那一行 |
| **注册时它会读这个标志吗** | ❌ **不会**。注册流程永远是 `isAdmin: false` |
| 所以它会造出管理员吗 | ❌ **不会** |

**⚠️ 为什么不直接删掉 `--admin`**：删它要改代码，而它现在**没有任何效果**；
留着它 + 一段说明，比删掉更能解释这里发生过什么。
**⚠️ 但你在命令行里不要用它**——用 `--reserved`，意思更清楚。

**⚠️ 相关的历史**：2026-10-14 之前**不是**这样。
当时 98 个预留编号的码带着 `grants_admin = true`，
**拿到任意一张卡的人注册即成为管理员，而那一刻没有任何人做决定**。
这是 1.10.22 修掉的安全问题，详见
[`S12-A上线前安全与发布准备.md`](开发过程记录/S12-A上线前安全与发布准备.md) §4。

**⚠️ 顺带一提**：`apps/api/src/scripts/create-invite-batch.ts` 的注释还写着
"This generator creates administrators"——**那句话已经过时**。
代码是安全的（注册端不读那个标志），但注释没跟上。属于待清理的小尾巴。

## 7. ⚠️ 绝对不能做的事（会造成不可逆损失）

| # | 禁止 | 为什么 |
|---|---|---|
| 1 | `docker compose down -v` | **`-v` 删掉所有卷，包括 `db-data`——全部账目** |
| 2 | `prisma migrate reset` | 删库重建 |
| 3 | `docker volume rm` / `docker system prune --volumes` | 同上 |
| 4 | 手工 `DELETE` 生产表里的行 | 不可逆。要停用就 `update` 一个时间戳 |
| 5 | 把邀请码、口令、私钥写进文档/仓库/聊天 | **仓库是公开的** |
| 6 | 把开发库的 `admin_grants` / `admin_allowlist` 复制到生产 | 绕过双重授权；授权必须在生产上重新决定 |
| 7 | 把开发库的邀请码搬到生产 | 它们是一次性凭据，且搬过去改变不了"哪个库有效" |
| 8 | 为了编号连号去改 `account_number` 计数器 | 会让"编号是发出去的卡片"这件事失去意义 |
| 9 | 在 CI 里加自动部署 | 发布必须由人确认（ADR-037） |
| 10 | 开着 ufw 而不先放行 22 | 会把自己锁在 SSH 外面 |

**完整清单**：[`生产环境与运维手册.md`](生产环境与运维手册.md) §10。

## 9. 一句话总结

> **本机和云端是两个互不相干的库，之间不同步任何东西**——
> 所以本机的邀请码**不会**、也**不该**出现在服务器上。
>
> **管理员没有"失效"，而是生产上还没建立**——它必须在生产上重新授权（两步）。
>
> **你掌控服务器的方式**：SSH 上去，用 `$DC exec -T api pnpm ...` 这一套命令
> 生成邀请码、看/授权管理员、备份、发布。
> **邀请码只在服务器上查，不写进任何文档。**
