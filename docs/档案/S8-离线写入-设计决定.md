> ### ⭐ 最终的简化：**印记就是队列**
>
> **所有者一句话定了这件事**：**"直接把删除标记作为某一个订单的变量，就比写下一个队列要被删掉更靠谱。"**
>
> **原来的实现有一个持久化的队列**——一个独立的"待办列表"，写着"这个 id 要被删掉"。
> **而它漂移了**：他 iPad 上出现 **`队列 0 条` 而那两条还红着**——
> **颜色看印记、投递看队列，两份数据，各说各话。**
>
> **现在没有队列**：`syncAll()` 每次**遍历所有带印记的条目**，按印记决定发什么请求。

## 1. 服务端**已经**准备好了什么

**这一轮不是从零开始**——`prisma/schema.prisma` 的注释就是为它写的：

| 已有 | 原话 | 它解决什么 |
|---|---|---|
| **`idempotency_key`**（`@unique`，客户端生成） | **"makes a retried upload harmless — the same key can only ever produce one row"** | **重放不重复**。网络抖动导致的重试、离线期间的重复投递，都只会产生一行 |
| **`version` + `deleted_at`**（软删除） | **"a tombstone, never a hard delete — let a device that was offline learn what changed without resurrecting data"** | **冲突检测**（服务端已有 `version_conflict`）+ **删除不会复活** |
| `POST /transactions` | 已有两段幂等处理（先查 key、再处理竞态） | 创建 |
| `PATCH /transactions/:id` | **要求带 `version`**，不符即 `409 version_conflict` | 修改 |
| `DELETE /transactions/:id` + `POST /:id/restore` | 软删除 | 删除 |

**⚠️ 所以本轮要写的是"客户端怎么排、怎么重放"，而不是"服务端怎么支持"。**

## 2. 三个基本决定

### 2.1 ⚠️ 存"每个实体的**最终意图**"，不存操作流水

**两种做法**：

| 存操作流水 | 存最终意图 ✅ |
|---|---|
| 离线期间改同一笔三次 → 三条记录，重放时发三次 | **一行，只发最后一次** |
| 需要按顺序重放 | **顺序无关** |
| 中间状态会成为"用户其实没想要的结果" | **存的正是用户想要的结果** |

**决定**：**一行一个实体**（用实体 id 做主键），保存**它的目标状态**。

**⚠️ 为什么这是对的**：用户在离线时改三次，**他想要的是最终那一版**。
把中间两版也发给服务器，是把"过程"当成"意图"——**而过程是实现的细节。**

**⚠️ 而那个"一行"后来变成了"印记"，不再是"队列条目"**——见 §3.1。

### 2.2 ⚠️ 本地立即生效，服务器稍后跟上

**做法**：一次离线写入＝**同时**做两件事：

1. **改本地存储**（`ledger-months`，见 `离线与同步-设计决定.md` §1b）→ **界面立刻变**；
2. **打上"待投递"的印记** → 联网后投递。

**⚠️ 两条路各自独立**：
**本地那份是"给用户看的"，印记那份是"给服务器看的"。**
**任何一条失败都不能让另一条不动**——**否则一次写入失败会让界面看起来没反应。**

### 2.3 ⚠️ 本轮不做冲突**解决**，但第 3 轮已经做了

**⚠️ 本节记录的是第 2 轮当时的范围，而第 3 轮已经完成**——
**完整的冲突设计见 `S8-冲突-设计决定.md`。** 这里保留一句历史：

**第 2 轮当时定的**：**把冲突的原始材料留住**（我方那一版、服务端那一版），
**界面显示"有 N 笔需要处理"，而对比与选择界面留到第 3 轮。**

**⚠️ 而第 3 轮做完之后，"留住两个快照"这个做法被证明不够**：
**两个快照只能表达"本机"和"服务器"两个来源**，
**而真正的候选来自服务端下发的 `claims`（每一台设备报了什么）**——
**只比较两个快照会导致"手机本地恰好等于服务器"那种情况下一个候选都生不出来**（见 `S8-冲突-设计决定.md` §6.2）。

## 3. 存储结构

### 3.1 ⚠️ **没有队列了——印记就是队列**

> **⚠️ `outbox.ts` 已被删除，`outboxSemantics.test.ts` 一并删除。**

**第 2 轮最初实现的是一个真实的队列（`outbox`，一行一个实体，见本节末尾"早期设计"）。**
**它被删掉了，因为"队列"和"印记"是两份状态，而它们会不一致——那是一整类 bug 的来源。**

**现在的工作方式**：

| 项 | 做法 |
|---|---|
| **"要发什么"** | **从印记推导**（`intents()`）：`deleted === true` → 删除；`synced === false` → 新建；否则 → 修改 |
| **"什么时候发"** | `syncAll()` **每一轮走遍所有被标记的账目** |
| **持久化** | **只有印记**（`ledger-marks`） |

**⚠️ 而这不只是简化**：**所有者报告的"钉子户"**——一行卡着删不掉、红色不退——
**正是"队列和印记是两份状态"的后果**：
**一份记得要删、另一份已经空了，于是那一行永远在等一件没人排队的活。**
（见 `教训.md` §8.8："要影响某个东西，直接把条件绑在那个东西上，而不是绑在它的位置上。"）

**⚠️ 而幂等重放仍然在**：`idempotency_key` 就位，
**新建时那个键就是账目自己的 id**，所以重发一次新建是安全的。

#### 早期设计（已废弃，保留以便读懂旧记录）

| 字段 | 说明 |
|---|---|
| `id` | 实体 id（**本身就是主键**——保证"一行一个实体"） |
| `op` | `create` / `update` / `delete` |
| `payload` | **目标状态**（`create` 与 `update` 用；`delete` 为空） |
| `baseVersion` | **离线时看到的版本**——提交时带上去做乐观锁 |
| `queuedAt` | 入队时间（**只用于显示"最久的一条等了多久"**，不用于排序） |
| `attempts` | 重试次数 |

**⚠️ 其中 `baseVersion` 那一条在第 3 轮被**推翻**：
判定**不再使用版本号**（所有者否决过它，而它藏着把冲突检测整个吞掉了）。
见 `S8-冲突-设计决定.md` §2。**这一段留着是为了说明"为什么它曾被写在这里"。**
| `lastError` | 上次失败原因 |
| `conflict` | 服务端**当前**那一版（仅冲突时存在） |

**⚠️ `baseVersion` 是这一轮的关键字段**：
**没有它就无法区分"我在改一笔没人动过的账"和"我在改一笔别人已经改过的账"**，
而这两种情况的正确处理完全不同。

### 3.2 本地账目上的标记

| 字段 | 说明 |
|---|---|
| `pending` | 是否还没同步（界面显示"待同步"） |
| `deletedLocally` | 本地已删（**软删，保留原始数据以便冲突对比**） |

## 4. 重放协议

**触发时机**：① 网络恢复；② 应用回到前台；③ 用户手动点"立即同步"；④ 每次写入后尝试一次。

**每一步**：

```
取出最久未成功的一条
  ├── create  → POST /transactions     （带 idempotencyKey = 实体 id）
  ├── update  → PATCH /transactions/:id（带 version = baseVersion）
  └── delete  → DELETE /transactions/:id
        │
        ├── 2xx  → 清掉印记，本地即为已同步
        ├── 409  → 移入"冲突"状态，保留双方快照（本轮的终点）
        ├── 4xx  → 这条是**永久失败**（例如分类被删了）→ 标记出来，不再重试
        └── 5xx / 网络 → 印记留着，退避后重试
```

**⚠️ 三条纪律**：

| 纪律 | 理由 |
|---|---|
| **一次只投一条，按 `queuedAt` 从旧到新** | 并发投递会让"顺序"变成不可预测的；而用户能感知的是"最早那笔还没上去" |
| **4xx 与 5xx 分开处理** | **5xx 是"稍后再试"，4xx 是"再试一万次也一样"**——**把 4xx 当可重试，会让那一条永远卡在同一个请求上** |
| **重试有退避、有上限** | 无限重试等于无限耗电；上限之后标记为"需要你处理" |

## 7. 验收（所有者要在场）

> 🔴 **需要所有者开飞行模式真机实测。**

| # | 场景 | 期望 |
|---|---|---|
| 1 | 飞行模式 → 记一笔 | **立刻出现在明细里**，带"待同步"标记 |
| 2 | 飞行模式 → 改一笔 | 同上 |
| 3 | 飞行模式 → 删一笔 | 从明细里消失，带"待同步"标记 |
| 4 | 恢复网络 | **N 笔全部上去，且服务器上不多不少** |
| 5 | 恢复网络后刷新 | **记录与离线时看到的一致**（不重复、不复活） |
| 6 | 飞行模式记账 → **杀掉应用** → 重新打开 | **那笔还在**（**印记是持久的，不是内存里的**） |
| 7 | 同一笔在**另一台设备**上改过 → 本机离线改它 → 恢复 | **不静默覆盖**，出现"有 1 笔需要处理" |

**⚠️ 第 6 条最容易漏，也最重要**：
**"杀掉应用后还在"是"真的存在本地"和"只是记在内存里"的分界线。**
