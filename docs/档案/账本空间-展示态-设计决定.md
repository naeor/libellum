# 账本空间的「展示态」——设计与实现决定

> **状态**：🗒 **规格已由所有者于 2026-10-13 给出（很详细）；实现未开始。**
> **本文档是它的落点**，包括我勘察到的复用基础。实现时以本文档为准。

## 1. 两种状态，同一个页面

| 状态 | 用途 | 内容 |
|---|---|---|
| **展示态**（`--p = 0`） | 第一次进入时的品牌展示 | 品牌绿 `#55997a` 的抽象海洋、层叠波面、留白呼吸感、`Libellum` 字样为主视觉文字、可少量抽象纸张意象 |
| **常规态**（`--p = 1`） | 日常选择与管理账本 | 现有实用型账本空间：账本卡片（图标/名称/个人或共享/成员）、点击进入、右侧独立「更多」、新建入口 |

**所有者原话**：*"这两种状态属于同一个页面，不是两个互相独立的页面，也不应该通过传统的页面跳转或整页覆盖实现切换."*

**⚠️ 属于第三类页面**（特殊展示／沉浸式）。所有者定的视觉原则：
**"华丽用于欢迎与展示，简约用于日常与操作。"** 这份华丽**不得扩散到日常功能界面**。

## 2. 最高优先级：退潮过渡

**所有者说这是本次优先级最高的部分。**

1. 绿色海浪整体**向上移动或收束**
2. 不同层次波面带**轻微速度差和惯性**，整体方向一致
3. 波浪退去时，下方**逐渐显露**常规内容
4. 展示态的部分**颜色、形状或曲线自然演化**为常规态顶部的视觉装饰
5. 过渡完成后账本列表**可正常操作**

**明确禁止**（所有者原话）：
- ❌ 只是"绿色画面渐隐、白色页面渐显"
- ❌ 简单把完整新页面从下面推上来覆盖旧页面

**目标**：*"原本那片海正在退去，而账本空间就是从这片海里自然显露出来的."*

**时长**：**600–850 ms**。所有者说这是"设计参考，而不是必须机械执行的固定数值"。
**不要设计成需要等好几秒的开场动画。**

## 3. 反向：常规态 → 展示态

- 在常规态**从页面顶部向下滑动**回到展示态
- ⚠️ **只在"已位于顶部"且"有明确继续下拉动作"时触发**；**不能把普通滚动或轻碰误判成切换**
- 反向动画与退潮**相互呼应**：波面重新展开
- 可以有一个**不干扰画面的辅助入口**主动重看，但不要增加界面负担

## 4. 什么时候播放展示态

| 场景 | 行为 |
|---|---|
| 新用户第一次进账本空间 | **优先展示态** |
| 上滑之后 | 进入常规态 |
| 以后从其他账本返回账本空间 | **默认直接常规态** |
| 顶部下拉 | 重新进入展示态 |
| 已有用户正常登录 | **仍走现有的"上次使用账本"恢复逻辑，不被展示动画打断** |
| 用户主动返回账本空间 | 不必重新经历完整展示 |

⚠️ **所有者原话**：*"展示态是一个欢迎体验，而不是每次进入软件都必须经过的启动广告."*

## 5. 展示态自身的动画

缓慢起伏、波面之间**轻微速度差**，接近**安静的潮汐**。

**禁止**：剧烈晃动、**高频闪烁**、音频可视化／音乐播放器风格、大量元素同时无规律运动、
**复杂 3D 场景**。**不要炫技。**

## 6. 响应式与手势

手机、iPad、桌面浏览器；iPad 横屏与竖屏；触屏上滑与下拉；
**手势与正常滚动的冲突**；Safari 与 PWA 安全区域；**动画结束后按钮必须可用**。

# 7. ⚠️ 实现基础：项目里已经有这个机制（**最重要的一节**）

**所有者规格里的每一条，`apps/web/src/lib/detailTransition.ts` 都已经解决过一次。**
明细页的「展示态 ↔ 明细态」就是同一个模式，2026-10-10 完成并调过多轮。

## 7.1 单一连续进度，而不是两套 DOM

> *"`0` is the display state — the tall green summary... `1` is the list state... Everything in between is a
> real position, not a transition between two finished layouts."*

**⚠️ 这直接满足所有者"不能是整页覆盖／突然消失"的要求**：中间态是真实位置，
所有几何都由 `--p` 用 `calc()` 推导。

## 7.2 进度存在 ref 里，每帧写 CSS 变量，**不进 React state**

> *"a phone fires scroll and touch events at 60–120 Hz, and re-rendering the ledger that often is how a
> transition starts to stutter. React is told only when the screen settles."*

**⚠️ 这条是实现流畅度的关键，不要"改进"成 `useState`。**

## 7.3 弹簧 + **速度上限**（这条最值得抄）

> *"So it is a speed limit rather than a physics fix: whatever the velocity reading says, the value moves at
> most this fast, and the whole animation therefore always plays out over at least half a second."*

`MAX_SPEED = 1 / 0.5` —— **保证任何手势都不会让过渡快于 0.5 秒**。
所有者当年为"卡顿"折腾了好几轮，最后是这个上限解决的。

**⚠️ 与本次规格的关系**：所有者要 600–850 ms，而这个上限保证**最少 500 ms**。
**两者相容**，但实现时要确认总时长落在 600–850 区间内（可能需要调 `DRAG_DISTANCE` 或弹簧常数）。

## 7.4 手势：**按落点分区**，不按方向猜

> *"deciding by direction meant guessing from the first few pixels, getting it wrong, and either killing the
> transition or blocking an ordinary scroll. Where the finger starts is not a guess."*

区域内有横向滚动条的元素标 `data-h-scroll`，落在里面的手势**完全属于它**，页面不拦。

## 7.5 手势速度：**整段平均**，不用最近采样

> *"A recent sample is the noisiest thing available: fingers slow and drift in the last few milliseconds
> before they lift... The average over the gesture cannot do that."*

## 7.6 常规态顶部的下拉：**已经实现了，而且踩过坑**

> *"The previous version checked 'at the top' but not the direction, so an upward drag there was swallowed:
> prevented from scrolling and driven into a progress that was already at its end. The list jolted and went
> nowhere."*

**⚠️ 这正是所有者规格里"不要把普通的向下滚动或轻微触碰误判成切换状态"那一条**，
**已经修好了**：`if (progress.current >= 1) { if (!atTop || dy <= 0) return; ... }`

## 7.7 桌面端：滚轮也能驱动

`WHEEL_SCALE = 2400`，并且**累积增量而不是每个事件单独应用**（触控板一次手势会发几十个事件）。

## 7.8 记忆：模块级 session

`session = { progress, month, kind, scrollTop }` 存在**模块变量**里而不是 context，
所以切换 Tab 再回来能保持；**整页刷新会重置**（这也是所有者要的）。

## 7.9 一代一主：`generation` 计数器

> *"a spring that is mid-step will schedule itself again from inside its own callback — so cancelling the
> handle and then starting a new spring could leave two of them writing progress."*

**⚠️ 每个弹簧带着自己的编号，编号不再是当前值就立即停止。**

# 8. 实现方案（待所有者确认一处结构问题后开工）

## 8.1 ⚠️ 待确认：`/start` 与 `/books` 的关系

| 页面 | 现状 |
|---|---|
| **`/start`（账本空间）** | **目前是占位页**，只有一段"这个页面还没有做"的说明 |
| **`/books`（我的账本）** | **真正的账本列表、新建、弃置、恢复、退出都在这里** |

**所有者规格说"在现有「账本空间」页面上开发"，但账本空间是空的，实用功能在另一个路由上。**

**我的建议**：把 `BooksPage` 的内容搬到 `/start`，让 `/start` 成为唯一的账本空间，
`/books` 改为重定向。**理由**：规格说"常规态就是现有的实用型账本空间"，
而**两个页面并存会让它们对"当前是哪本账"产生分歧**（项目里已有这类教训）。

**⚠️ 这会动到现有 `/books` 入口，所以等所有者确认。**（`教训.md` §8.13）

## 8.2 步骤

| # | 步骤 | 说明 |
|---|---|---|
| P1 | 常规态搬到 `/start` | 保留现有全部账本管理功能与导航关系 |
| P2 | 展示态 | 品牌绿抽象海洋、层叠波面、`Libellum` 字样、可选纸张意象 |
| P3 | 展示态自身动画 | 缓慢潮汐、波面速度差 |
| P4 | **退潮过渡** | 波浪上移收束 + 层次速度差，600–850 ms |
| P5 | 反向过渡 | 顶部下拉，按 §7.6 已有的方向判断 |
| P6 | "是否看过"的记录 | 首次展示、之后默认常规态；**不影响"上次账本"恢复** |
| P7 | 响应式与安全区域 | 横竖屏、Safari、PWA |
| P8 | 验证 | 三包 typecheck + 全量测试 + 真实构建 |

## 8.3 复用 vs 泛化

**倾向**：把 §7 的机制**泛化成通用 hook**（`useStateTransition`），
让 `detailTransition` 成为它的一层薄包装——**行为不变，测试应全部继续通过**。

**⚠️ 但不新建第二份。** 复制一份改改参数，就是让两处对"手势怎么算速度"产生分歧，
而**那种分歧的表现形态是"某一页滑起来有点怪"**，最难归因。

## 8.4 ⚠️ 我不能验收的部分

**所有者要求"不要只以页面能够编译、测试通过作为完成条件，还要检查实际显示效果"**：

- 海的观感是否"安静、广阔、有生命力"（而不是科技粒子／卡通波浪）
- **退潮是否真的像"海水退去"** —— 规格里的最高优先级
- 手势与滚动的冲突、iPad 横竖屏、Safari／PWA 安全区域
- 动画在真实设备上是否卡顿

**这些必须由所有者确认，我不会声称已验证。**
