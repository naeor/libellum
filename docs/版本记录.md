# 版本记录与发版规则

> **本文档是"每次更新改了什么"的唯一清单。**
> **规则由所有者定，代码与文档都必须遵守。**

---

## 1. 📌 发版规则（必须遵守）

### 1.1 版本号格式

```
1.08.14
│ │  └── 该阶段里的第几版：**用户看得见的行为变化就 +1**
│ └───── 正在开发的阶段，**与 `ROADMAP.md` 的阶段号一致**
└─────── 第几次整体开发：**只有"从头再做一遍"才变**
```

**来源**：所有者提出（原话见 `DEVLOG.md` §1.49.3）。

**⚠️ 中间那段与阶段号一致，是这套方案最有用的一半**：
"这个构建来自哪个阶段"写在屏幕上，而"里面是什么"离 `ROADMAP.md` 的一节只有一步。
一个 `1.4.2` 这样的版本号需要一次谁也不会去做的查表。

### 1.2 ⚠️ 每次更新都要做两件事

**所有者定的规矩（原话）**：

> **"我需要提醒一下以后你每次更新一次，就把版本号加1。"**
>
> **"在之后也加一条规则：就是每次更改都要做版本更新，并且写清楚这次版本更新做了什么，写入文档。"**

**所以每一次代码改动都必须**：

| # | 动作 | 位置 |
|---|---|---|
| 1 | **把 `APP_VERSION` 的最后一段 +1** | `apps/web/src/lib/version.ts` |
| 2 | **在本文档下面追加一条记录**，写清改了什么、为什么 | `docs/版本记录.md` |

**⚠️ 为什么这条规矩是必要的**：

> **一个不动的版本号，无法用来区分两个构建——而那是它唯一的用途。**
> **这个项目已经在"分不清你在跑哪一版"上花了三轮**（`DEVLOG.md` §1.48–1.49）。

### 1.3 一条记录要写什么

**最少三件事，缺一不可**：

1. **改了什么**——具体到文件或行为；
2. **为什么**——是哪个报告、哪条证据、哪个判断；
3. **怎么验证的**——测试数量、真机结果，或"待真机确认"。

**⚠️ 并且允许写"这一版没修好"**：

> **一个把"未解决"写成"已解决"的记录，比没有记录更糟——下一个人会从错误的地方开始。**
> （见 `离线与同步-设计决定.md` §4 的做法。）

### 1.4 版本号显示在哪里

| 位置 | 内容 |
|---|---|
| **账户 → 软件更新** | 版本号、构建时间（本机时间 + UTC）、Service Worker 状态、缓存条目数 |
| **诊断信息的第一行** | `构建：<UTC 时间戳>`——**用于确认"设备上跑的到底是哪一版"** |
| **`ROADMAP.md` 的版本号规则小节** | 现行版本号 |

### 1.08.41 —— 一个账号可以同时登录多台设备（2026-10-11 13:20）

**改了什么**

- **数据库**：`sessions.user_id` 去掉 UNIQUE，改为普通索引（迁移 `20261011133000_multi_device_sessions`）。
- **`User.session` 由一对一改为一对多**（`sessions`）。
- **登录改为 `create`**，不再 `upsert`——**每次登录新增一行会话，不碰别的设备**。
- **两条测试改写**：原来那条叫"keeps only one session per account"，**现在断言的是相反的事**。

**为什么**

**所有者在两台设备测试之后提出**：

> **"我觉得是时候删除掉每个账号只能有一台设备登录的限制了；每个账号现在都应该可以被多台设备同时登录，
> 而不会被踢掉。"**

**⚠️ 而这条限制一直在伤害它要配合的那个功能**：
`upsert({ where: { userId } })` 会覆盖已存在的会话，**于是手机上登录会让平板在下一次请求时被登出**——
**而"pad 被踢掉"正是他那次测试里出现的一环。**

**⚠️ 而两台设备共用一个账号是常规情况，不是边界情况**：
**离线设计就建立在"手机和平板各持一份账本副本"之上**，
**冲突检测之所以存在，正是因为这两份可以分叉。**
**一条把其中一台踢下线的规则，取消了使用（以及测试）它所在功能的可能。**

**⚠️ 而安全模型不依赖这条限制**：
会话由**它自己的 token 哈希**标识，那个本来就是唯一的；
**注销是按 token 删**；**改密码仍然清掉该账号的全部会话**——**那才是"所有设备一起"真正有意义的唯一场合。**

**怎么验证的**

- **两条新测试**：**多设备同时在线**（原断言反转）、**在一台注销不影响其它设备**
- 类型检查三个包通过；全量测试 **633 通过**（api **137**）
- **迁移已应用到开发库与测试库**

### 1.08.40 —— 每一次编辑都和自己冲突；以及冲突终于看得见了（2026-10-11 13:04）

**改了什么**

- **编辑时本地自增版本号**（`write.ts` 的 `updateEntry`）——**这是根因**。
- **冲突行有自己的颜色**（新增 `--color-warn-soft` 琥珀色令牌），**点它打开选择界面**。
- **`resolveConflict`**：用户选定后写回本机并立刻送上去。

**为什么**

**所有者的两台设备测试直接暴露了两个问题**：

> **"pad 先断网在 test9 上改成 48 元。手机一直联网把 test9 改成 10 元。
> 现在的结果是 pad 上 test9 显示 48 元，但是是绿色的；点击刷新也没用，手机上一直显示 test9 是 10 元。"**

**⚠️ ① 绿色 + 刷新没用 = 每一次编辑都在和自己冲突**

```ts
const next = apply(current);     // ← version 保持原样
```

**服务端的乐观锁把"版本相同"也当成冲突**——**它无法区分"我就是刚刚改它的那个人"和"我已经过期了"。**
**而同步发请求时用的是条目上记录的版本**，那个版本从来没随着本机编辑前进过：

> **提交的版本永远是旧的 → 每次都是 409 → 每次都被拒绝 → 绿色永远在、刷新永远没用。**

**修法**：**编辑时把版本 +1，与服务端一致**。
**两个副本对版本号的一致，正是"下一次编辑能基于它"的前提。**

**⚠️ ② 而绿色什么都不说——这正是我上一轮标为"待做"的第 5 项**

**绿色的含义是"等着被送上去"，而它在"反复重试一个永远被拒的请求"时长得一模一样。**
**屏幕上没有任何东西告诉用户"有一个决定在等你"，所以也没有东西可以点。**

**修法**：**冲突有自己的颜色（琥珀色）和点击行为**——
**点它打开选择界面，而不是打开编辑页**：

> **打开编辑页会让用户给一笔已经有两份的记录造出第三份，而"这两份你要哪个"这个问题就永远不会被问。**

**⚠️ 而琥珀色令牌是我两轮前就承诺过的**：
**当初删除借用错误色时我写过"如果以后要区分'未同步'和'出错'，加一个琥珀色警告令牌才是诚实的做法"**——
**现在第三种状态出现了，就该把它加上**：
**冲突既不是"出错了"，也不是"在等着"——红会把它说成"有东西坏了"，绿会把它说成"在排队"。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **632 通过**
- **已用 grep 核实五处接线**（`bg-warn-soft`、`conflicted.has`、`setSettling(waiting)`、`ConflictScreen`、`--color-warn-soft`）
- **待真机确认**——**就是他那套两台设备的流程**

### 1.08.39 —— 冲突检测与冲突界面（2026-10-11 12:54）

**改了什么**

- **客户端识别冲突并留住两份**（`sync.ts` 的 `recordConflict` + `localLedger.ts` 的 `ConflictRecord`）。
- **新增冲突界面**（`ConflictScreen.tsx`）：**先列出"已经自动合好的地方"，再列出"需要你选的地方"**。
- **7 条界面测试 + 12 条合并测试**。

**为什么**

**你说过的两半，这一版都在界面上**：

> **"先自动合并：不冲突的字段自动合，只有冲突的字段才问"**
> **"但'自动合了哪些'必须显示出来，否则用户不知道机器替他决定了什么。"**

**⚠️ 而第二半是最容易漏掉、也最贵的一半**：

> **一个只问冲突字段、对其余一句不提的界面，在用户眼里和"程序猜了一个"无法区分**——
> **他分不清"它替我合了四处"和"它丢了我三处编辑"，因为两者都渲染成"一个问题 + 一个保存按钮"。**

**⚠️ 所以自动决定是显式列出来的，并且标明每个值来自哪一边**：
**"金额 → ¥25.00"没有"用你的"三个字，用户就无法判断自己的编辑有没有活下来**——
**而那个问题正是这个列表存在的全部理由。**

**⚠️ 三个刻意的设计决定**：

| 决定 | 理由 |
|---|---|
| **冲突在"被拒绝的那一刻"就写下来** | 服务器那一版随 409 到达，而**我这一版会被紧接着的整份刷新覆盖**——**不在此刻写下来的冲突，已经把用户打进去的东西弄丢了** |
| **base 一律记为"未知"** | 存储里那份**就是**本机的编辑（待同步印记的含义），**拿它当起点会让每个字段都显示"我改的"**，于是合并会把我的值全取走、**静默覆盖另一台设备的工作**。**未知 = 每个差异都问：问得多，但从不静默覆盖** |
| **未回答的冲突保留服务器的值，并明说** | 默认选"我的"会让"快速点过去"变成静默覆盖——**而那正是这个界面存在要防止的结果** |

**⚠️ 而"稍后再处理"不会丢东西**：两份都留着，下次打开还会问。

**怎么验证的**

- 类型检查三个包通过；全量测试 **632 通过**（web **329**）
- **已用 grep 核实冲突链**（`recordConflict` / `readConflict` / `setConflict` / 四个导出）
- **待真机确认**——**需要两台设备**（手机 + iPad 正好）

### 1.08.38 —— S8 第 3 轮开工：合并判断（2026-10-11 12:39）

**改了什么**

- **新增 `merge.ts`**：**两个副本逐字段对比**，决定哪些自动合、哪些要问。
- **12 条测试**（`merge.test.ts`），覆盖自动合并、冲突、以及两种最容易出错的情况。
- **服务端 409 带上它当前持有的那一版**（`details.current`）。

**为什么**

**所有者已定的规则**：**"先自动合并：不冲突的字段自动合，只有冲突的字段才问"**——
**以及同一句话里的另一半："但'自动合了哪些'必须显示出来，否则用户不知道机器替他决定了什么。"**

**⚠️ 而这两半同等重要，因为它们各自对应一种"不会报错的错误"**：

| 错误 | 后果 |
|---|---|
| **覆盖了用户没碰过的字段** | **静默丢掉别人的编辑** |
| **隐藏了自动决定** | **看起来和"程序弄丢了我的编辑"一模一样** |

**四种情况，而只有一种要问用户**：

| 情况 | 处理 |
|---|---|
| 两边一样 | 什么都不做 |
| **只有我改了** | **用我的**（这就是普通的离线编辑） |
| **只有对方改了** | **用对方的**——**覆盖用户没碰过的字段，正是同步丢掉别人编辑的方式** |
| **两边都改了、且不同** | **✅ 只有这一种要问** |

**⚠️ 而"谁改了"是相对"两边共同的起点"判断的**——**那个 base 是整件事成立的前提**：
**没有它，"改了"无法判断，每一个差异都只能变成一个问题**，
**而那正是"让用户做程序本可以做完的事"的版本。**

**⚠️ 而 base 未知时（重装后、印记活得比条目历史更久），每一个差异都问**：
**猜错会静默丢掉一边的工作，而唯一比"问得太多"更糟的是"没问就决定了"。**

**⚠️ 而 `categoryName` / `paymentMethodName` 刻意不参与对比**：
**它们跟在 id 后面，把名字也拿去比会导致"重命名分类"被报成第二个冲突**——
**一次决定问两遍。**

**⚠️ 而服务端把当前版本放在 409 里，是我刻意选的**：
**客户端需要"双方在哪几个字段上不同"，而它拿不到服务器那一版就算不出来。**
**改用第二个请求去取会竞态**——**那一行可能在拒绝与追问之间又变了，
于是合并是按一个从未造成冲突的版本算的。**

**⚠️ 而"让服务端合并"被否掉了**：
**那样自动决定就发生在用户看不到的地方**，**而你的规则是"自动合了哪些必须显示出来"**——
**一次合并只有在客户端能展示它做了什么的时候，才是可复核的。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **625 通过**（web **322**，新增 12 条）
- **待真机确认**

### 1.08.36 —— 404 不是"删好了"（2026-10-11 12:25）

**改了什么**

- **删除遇到 404 不再当作成功**——**删除只有一种成功判据：服务器的列表里没有它了**。
- **清印记后重新发布账本**（否则印记没了、条目还画在屏幕上）。
- **「更多」页加一个「清空『待同步』印记」按钮**——**你能直接拍板的出口**。

**为什么**

**所有者的诊断给出了完整证据链，而他的判断是对的**：

```
04:22:20.650Z DIAGNOSTIC:write-failed — delete 01a128c9 — 404 找不到这笔记账。
04:22:20.652Z DIAGNOSTIC:write-already-gone — 删除 01a128c9 — 服务器上已经没有它
04:22:36.157Z DIAGNOSTIC:sync-ok — delete 01a128c9（服务器上本就没有）      ← 印记被清掉了
```

**他的原话**：**"我刷新的时候，他会直接把删除印记给去掉，东西是实际上并没删除。"**

**⚠️ 而服务端的 404 有两个含义，我把它们混为一谈了**：

| 404 的含义 | 正确处理 |
|---|---|
| 那一行已经软删除过 | 完成 |
| **这个 id 在这个账本里根本不存在** | **什么都没发生——印记必须留着** |

**⚠️ 而我把 404 当成成功，等于对第二种情况宣布"做完了"**——
**程序忘掉了删除，而那条记录还在用户眼前。**

**修法**：**删除只有一种成功判据——服务器自己的列表里没有它了**（`recordServerList`），
**而不是从一个错误码推断出来。**

**⚠️ 而清印记后必须重新发布账本**：
`setMark` 只发布印记，而**行是从账本快照画的**——
**所以印记清了、条目还留在屏幕上，正是他看到的那个现象。**

**⚠️ 而那个按钮是给他的出口**：
**自动路径在这个区域每一处都至少错过一次**（队列没排空、印记清了东西还在、合并把屏幕清空），
而**当程序无法执行一条指令时，下指令的人必须能撤回它。**
**它只做一件事：停止提醒。不发请求、不删任何东西。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **619 通过**
- **已用 grep 核实四处接线**（`cleared` 计数、`republishLedger` 调用、`clearAllMarks` 定义与按钮调用）
- **待真机确认**

### 1.08.35 —— 按所有者的模型重做：印记就是一切（2026-10-11 12:21）

**改了什么**

- **删除"队列"这个持久化概念**：新增 `sync.ts`，**待办列表在每次同步时从印记推导出来**。
- **`syncAll()`**：**从上到下走一遍所有带印记的条目**，绿的 `POST`、改的 `PATCH`、红的 `DELETE`，
  **成功就清掉印记**（颜色随之消失）。
- **`recordServerList()`**：用服务器的列表**释放"服务器已经证明完成"的印记**。
- **诊断精简**（所有者要求）：存储追踪只留最近 20 步，运行记录只留最近 60 条，空的段落不输出。

**为什么**

**所有者把他的模型讲清楚了，而它比我的实现简单且可靠**：

> **"它是红色的，也就证明它的删除印记变量为一…每次刷新时会触发一次联网核对，
> 而联网核对应该从上到下遍历所有订单，把所有绿色的订单加入到服务器中，
> 同时删在服务器和本地上删掉所有的红色订单。这一套逻辑是看起来挺清晰的。"**

**⚠️ 而他说得对。我的实现里多了一层——一个持久化的"队列"——而那一层正是所有问题的来源**：

| | 他的模型 | 我的实现 |
|---|---|---|
| 状态 | **每条自己带一个变量** | **一张印记表 + 一个独立队列** |
| 刷新时 | **遍历所有订单** | 遍历队列（另一份数据） |
| 红色 | **就是"删除印记=1"的渲染** | 期望如此，**而实际由队列决定** |

> **⚠️ 两份关于同一件事的记录，迟早会不一致。**
> 他 iPad 上出现的正是这个：**`队列 0 条`，而那两条却还红着**——
> **在我的设计里这两件事甚至不算矛盾，它们只是两份各自漂移的记录。**

**修法**：**待办列表不再持久化，而是每次从印记推导**：

> **一个从印记重建出来的列表，不可能漏掉印记提到的那一条。**

**⚠️ 而这样"颜色"和"要做的事"变成了**同一份数据的两种读法**——
**一行被画成绿色，就不可能没有东西可发**——这正是那些"钉子户"的成因。

**⚠️ 而"重试记账"也简化了**：失败记录**只存在内存里**——
**存储一份错误会让它活得比造成它的情形更久**（"永久失败"是对"那一刻那一次响应"的判断），
**在内存里它只是自然过期，下次会话再试一次**——**这正是所有者的体验所要求的：现在停止，下次重新开始。**

### 1.08.34 —— 用服务器的列表对账（2026-10-11 12:12）

**改了什么**

- **`setServerIds` + `reconcileWithServer`**：**每次拿到服务器完整列表，就和本机对一次账**——
  **"本机有、服务器列表没有"的已删除记录，重新排队删除**。
- **`queries.ts` 在 `nextCursor === null` 时把列表交给它**，然后触发一次 `refreshPending`。
- **印记改为同步读**（`readSnapshot`），不再依赖一次可能错过的磁盘读。

**为什么**

**所有者 iPad 的诊断说明了根本问题**：

```
read ledger-marks — 键不存在          ← 这台设备上"谁该被删"的信息没了
read ledger-months — 键：2025-02,…    ← 而且当前月份也不在
DIAGNOSTIC:drain — 在线判定通过，队列 0 条
```

**⚠️ 也就是说：这台设备上没有任何东西记得他删过什么。**
**而队列是空的，所以投递无事可做**——**红色是"一个没有记录支撑的动作"留下来的记忆。**
**同时那两条一直在服务器上**（他在手机上还能看到）。

> ## **设备无法只靠本地状态回答"什么应该被删"，它也不该尝试。**
> **服务器那份列表才是"什么东西存在"的记录。**

**⚠️ 而这一步我上一版就写了一半**：
`reconcileMarks`（两轮前为相邻目的写的）**同样是"只导入、从未调用"**——
**所以这次把它接进了 `refreshPending` 那条链**，也就是 `DIAGNOSTIC:drain` 每次都会走到的那条。
**一个不在那条链上的修复，不能指望它真的发生。**

**三条安全约束**（缺一条都会毁数据）：

| 约束 | 不这样会怎样 |
|---|---|
| **只在 `nextCursor === null` 时对账** | **拿半页列表对账，会把"在第二页"的记录全部标成删除**——**这是这个文件能犯的最具破坏性的错误** |
| **只对"本机自己认为已删除"的条目重发删除** | **离线新建的条目本来就不在服务器列表里**（它还没送到）——**那样会把用户刚记的账删掉** |
| **服务器列表到达之前什么都不做** | **空列表和"还没有列表"无法区分**，而当成列表就会删掉整月 |

**⚠️ 而印记改为同步读，是因为同一类问题已经发生过两次**：
**写入是不等待地发出的，所以基于 `await` 的读取可能读到写之前的值**——
**而"读不到印记"在这台设备上表现为"没有任何东西记得你删过什么"。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **619 通过**
- **已用 grep 核实六处接线落地**（`reconcileWithServer` 调用、`setServerIds` 定义与调用、
  `readSnapshot<LedgerMarks>` 两处）

### 1.08.33 —— 印记设了，而从没入队（2026-10-11 12:03）

**改了什么**

- **删除无条件入队**，不再依赖"本机找得到那一条"。
- **`repairMissingQueueRows`**：`refreshPending` 时，**凡是"有印记、无队列"的，补回队列**。
- **删除遇到 404 视为成功**（服务器上已经没有它了）。

**为什么**

**所有者的诊断直接指出矛盾**：

```
read ledger-marks — 对象，键：01a128d9-…, 01a128cf-…     ← 两条被标记为已删除
DIAGNOSTIC:drain — 在线判定通过，队列 0 条               ← 而队列是空的
```

**⚠️ 也就是说：那两条被标记为"已删除"，而"删除"这个动作从来没有进过队列。**
**所以投递永远无事可做，红色永远不会消失。**

**而他自己从另一侧确认了**：**"我在我手机上登录了一下，发现手机竟然看不到"** ——
**他判断"说明他并没有被存到服务器，只是本地还没删掉"**——**对的，服务器上确实没删。**

**根因在两行代码的不一致上**：

```ts
const current = await findStoredEntry(id);
await setMark(id, { pending: true, deleted: true });   // ← 标记：无条件
if (current !== null) { queueChange(...); }            // ← 入队：有条件
```

> **⚠️ 当本机找不到那一条时，印记照设、队列不写——
> 于是这一条卡死在"已标记、从未投递"的状态。**

**⚠️ 而这个条件本来就不需要**：**队列里的删除不携带任何内容**（就是 `DELETE /transactions/:id`），
**所以本机还有没有那一份副本，与能不能删它无关。**
**一条记录不在本机存储里有很多正常原因**（它来自查询缓存、从没被写进 `ledger-months`、那个月从没下载过），
**而没有一个能构成"拒绝删除它"的理由。**

**而"已经处于坏状态"的设备也要能自己好起来**：
**`repairMissingQueueRows` 在每次 `refreshPending` 时执行**——
**不是一个需要一次做对的迁移，而是一条持续被维持的不变式**：

> **凡是标记为待处理的，就必须有对应的队列项；没有就补上。**

**⚠️ 而补的时候是"补工作"而不是"丢掉主张"**：
**丢掉印记等于悄悄撤销用户要求的删除**——**那比一个不消失的颜色更糟。**

**⚠️ 而 404 对删除意味着"目的已达成"**：
服务器在找不到 `deletedAt: null` 的记录时返回 `404 transaction_missing`——
**其中包括"已被另一台设备删掉"**。
**把它当失败，就会留下一条永远不可能成功的行**：
**每次重试都是同一个 404，而那条记录在所有设备上都已经看不见了，
屏幕上唯一剩下的东西是一行红色，在指控用户一件他已经做完的事。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **619 通过**
- **已用 grep 核实七处接线落地**
- **待真机确认**——判据：**那两条红色在刷新后消失，并在手机上确认服务器也删掉了**

### 1.08.28 —— 字符串比较看不见时区；删掉的条目又被合并回来了（2026-10-11 11:24）

**改了什么**

- **`sortByTime` 改为按"真实时刻"比较**（`Date.parse`），不再比较字符串。
- **新增"本机已删除"的外部 store**（`deletedEntriesValue` / `subscribeDeleted` / `publishDeleted`）。
- **明细页在合并之后应用删除**——这是关键的一步。
- **4 条新测试**（共 9 条），其中一条**如实记录旧比较法的错误结果**。

**为什么**

**① 排序：所有者说"理论上说，按照我设计的那个排序走的话，他们应该就在最前面"——他是对的，
而实现里有一个经典错误**：

```ts
return left.occurredAt < right.occurredAt ? 1 : -1;   // ← 比较字符串，不是比较时刻
```

**字符串比较只在"所有条目偏移相同"时才对——而这本账里有两种偏移**：
**他在加州（UTC-7），而另一些条目是在 UTC+8 记的。**

```
"2026-10-11T20:30:00.000-07:00"  → 次日 03:30 UTC   （更新）
"2026-10-12T10:00:00.000+08:00"  → 次日 02:00 UTC   （更旧，但数字以 T10 开头）
```

**字符串顺序读出来是反的，因为它比较的是 `19` 和 `20` 这些数字，从不看偏移。**

> **⚠️ 两个时刻按"什么时候发生"比较；两个 ISO 字符串按"怎么拼写"比较。**

**⚠️ 而这条 bug 之所以活了这么久**：
**它只在部分输入上出错**——比如 `20:00-07:00` 对 `19:09+08:00` 恰好字符串顺序也是对的。
**一个"只在某些输入上错"的比较，比一个"总是错"的比较更糟**：
**它在任何人试的例子看起来都对，然后在用户的真实账本上坏掉。**

**② 删除：存储层过滤了，而屏幕又把它合并回来了**

**所有者原话**：**"我尝试去删掉 test04。但是在离线删除时，不管是离线还是在线，他都在那儿，好像没什么变化。"**

**原因**：本地删除的条目**故意保留在存储里**（第 3 轮要用它展示"你删了什么"），
`readStoredEntries` 会把它过滤掉——
**但屏幕把设备条目和查询条目合并，而查询里还留着那一条**（服务器还不知道它被删了）。

> **⚠️ "什么都不加"无法"减掉什么"**——**合并没有办法表达"这一条没了"，于是被要求忘掉的那条又原样回来了。**

**修法**：**把"本机已删除"作为一个外部 store 发布出去**（沿用已被真机验证的那套机制），
**并在合并之后应用它**——**只过滤其中一个来源，另一个来源会把它加回来，而那正是这次的现象。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **614 通过**（web **311**，新增 4 条排序测试）
- **已用 grep 核实 `subscribeDeleted` / `for (const id of deleted)` / `Date.parse` 三处都落地**

### 1.08.25 —— **没有任何东西在投递那个队列**（2026-10-11 11:00）

**改了什么**

- **新增 `syncController.ts`**：**四个时机自动投递**——`online` 事件、回到前台、应用启动、每次本地写入后。
- **`drainOutbox` 的"永久失败"与"暂时失败"分开**（`permanent` 字段）。
- 加了**同时只跑一次的守卫**（`online` 和 `visibilitychange` 在手机唤醒时常常一起触发）。

**为什么**

**所有者的那句话直接指出了缺的东西**：

> **"你可以设计一个每次连上网的时候立刻核对一遍所有的账单，然后发现变量为零时，
> 就把它上传到服务器上，然后把它的变量改成一，这样可以吗？"**

**可以——而缺的东西比"一个设计偏好"严重得多**：

| 查到的 | 后果 |
|---|---|
| **`drainOutbox` 从来没被任何地方调用** | 队列里的行**永远不会被投递** |
| **`online` / `visibilitychange` 一个监听都没有** | **网络恢复时没有任何反应** |

**⚠️ 于是**：**一笔离线记账只有在"用户恰好在联网时又记了一笔"时才会被顺手送上去。**

**这解释了之前所有的现象**：
**未同步的行一直堆积、淡红色一直不消失**——
**而"新写一笔、老的也跟着变红"不是标记错了，是那些老记录真的还没送出去，而且永远没人会送。**

**⚠️ 而顺带查出的第二个 bug 会让队列彻底死掉**：
`syncOne` 不记录"这是永久失败"，而 `drainOutbox` 只按"失败 5 次"跳过——
**于是一行只要失败 5 次就永远不再重试，还永远留在队列里（红色永远在）。**

**修法**：**4xx（非 409）标为 `permanent`，永不重试、也不挡住后面的行；
网络错误和 5xx 是可重试的**——
**"一次断网"和"这个请求永远不会成功"必须分开，否则要么无限重试、要么丢掉一个只需要等网络恢复的改动。**

**⚠️ 而"回到前台"比 `online` 更重要**：
**被挂起的页面根本收不到那个事件**，所以只监听 `online` 的实现，
会让一台锁屏过夜的设备一直抱着它的队列。

**怎么验证的**

### 1.08.23 —— 消失的记录、清不掉的红色、以及"这是哪个时区"（2026-10-11 10:39）

### 1.08.21 —— 离线改完要立刻出现，且明细顺序固定（2026-10-11 10:16）

**改了什么**

- **每次本地写入后刷新视图**（`write.ts` 的 `afterWrite`）：先发布 store，再让查询层失效。
- **`clearInFlight()`**：写入后清掉"正在飞行的读取"，否则这次写入会被一次**在它之前开始**的读取回答。
- **明细页固定按时间倒序**（`DetailPage.tsx`）：最新的在最上面，最旧的在最下面；
  **同一天的标题也按日期倒序**。

**为什么**

**所有者报了两个症状，而它们是同一个原因**：

> **"离线状态下，在编辑完成之后，它并不会显示在明细里，而是等到恢复网络之后再突然出现。"**
> **"离线状态跟恢复网络之后的明细顺序好像还被打乱了。"**

**⚠️ 而第一个正是那四个小时教训的同一个形状，只低了一层**：

> **数据改了，而没有人告诉界面。**

写入**确实进了存储**——那一半是对的。**缺的是通知**：
`ledgerSnapshot` 只由 `readLocalTransactions` 填充，
所以跳过它的写入让屏幕继续显示旧副本——**一次编辑看起来被无视，一次删除看起来被拒绝。**

**⚠️ 而教训早就写下来了，却没有用在这里**——这就是为什么现在有一个 `afterWrite`，
而且**每条写入路径都必须调用它**。

**⚠️ 第二个原因更隐蔽**：**明细页在查询有数据时优先用查询数据**
（这是对的——服务器答案是真话，本机那份是副本）。
**所以只刷新 store 不够**：查询缓存里的旧页面挡在前面，屏幕继续显示旧列表，
**直到网络恢复、查询本身变了才"突然出现"。**

**修法**：**先发布 store（屏幕立刻有东西可画），再让查询失效（它才会放掉不再为真的答案）。**
顺序反过来的话，会有一个"查询正在重取、而 store 还是旧列表"的窗口——**屏幕会闪回用户刚改掉的状态。**

**⚠️ 而排序问题的根子在于"顺序取决于数据从哪来"**：

| 来源 | 顺序 |
|---|---|
| 下载的月份 | 服务端的顺序 |
| `upsertEntry` 新建 | **追加到数组末尾** |
| 同步之后 | **又变成服务端的顺序** |

**于是同一条记录会从最下面跳到最上面，而用户看不出任何理由。**

**修法**：**按记录自己的时刻排序**——最新的在最上面，无论来源、无论时机。
**⚠️ 而时刻相同时回退到 id 比较**，否则同一秒记的两笔会在两次渲染之间互换位置——
**一个在读的时候会重排的列表，比一个稍微排错的列表更糟。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **600 通过**
- **待真机确认**

- **`localLedger.ts`：新增 `ledger-marks`**（哪些条目还没同步、哪些是本地删除）。

- **记账页接上离线写入**：服务器拒绝或断网时，**写入仍然落到设备上**，不丢。

**为什么**

**而"浅红底"是所有者直接要求的**：

> **"离线状态下新建出来的记账底色要特殊一些，比如把他们的背景（那一行的背景）换成浅红色之类的，
> 用来提醒用户，现在还没被备份到服务器，只是在本地记账而已。"**

**他是对的，而且理由正是这个项目自己的教训**：

> **"没有反馈"和"没有生效"在用户看来没有区别。**
> **一行和已保存的长得一模一样、而设备根本没把它送出去——用户会认为它是安全的。
> 如果设备在队列排空之前丢了，那个假设就是丢掉这条记账的原因。**

**⚠️ 三条实现上的决定**：

| 决定 | 理由 |
|---|---|
| **标记另存一个键（`ledger-marks`），不写进条目里** | **条目是服务端响应原样存下的**——那正是第 3 轮做冲突对比需要的。**把我们的记账字段混进去，会让服务端每次改 schema 都要考虑它从没发过的字段** |
| **本地删除的条目留在存储里，只是不显示** | **它的副本正是第 3 轮要展示"你删了什么"的材料**。留着几百字节；丢了就没有对比 |
| **用 `--color-danger-soft`** | 它是调色板已有的浅底、且**不随主题变化**（状态色不跟品牌色走）。**如果以后要区分"未同步"和"出错"，加一个琥珀色警告令牌才是诚实的做法——这里用错误色是一个刻意记录下来的选择** |

**⚠️ 而"分类"这一处暴露了一个真问题**：
**创建时的 `categoryId` 可以是空的**（服务端会归入每个账本自己的"暂无分类"）。
**离线时不能猜一个 id**——所以 `localEntry` 会**从设备已有的账本里找那个系统分类，用它的真实 id**。
**账本里连它都没有时，id 留空**（服务端也接受并自行解析），
**最坏情况是一次往返把它纠正过来，而不是一次失败的写入。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **600 通过**
- **未真机验证**——按 `S8-离线写入-设计决定.md` §7 的七条场景

### 1.08.19 —— S8 第 2 轮开工：离线写入的队列（2026-10-11 09:56）

**改了什么**

- **新增 `outbox.ts`**：离线写入的队列——**一行一个实体，存"最终意图"而不是操作流水**。
- **新增 `S8-离线写入-设计决定.md`**：三个基本决定、存储结构、重放协议、验收清单。

- **BACKLOG 新增三条待办**：I8（「浏览器其它」是什么、怎么删）、汇率折算、截图识别来源——
  **后两条按所有者要求标为"不急着做"**。

**为什么**

所有者拍板：**下一步做 S8 第 2 轮（离线记账/改/删）**。

**⚠️ 而这一轮不是从零开始**——服务端的注释就是为它写的：

| 已有 | 原话 |
|---|---|
| `idempotency_key`（`@unique`） | **"makes a retried upload harmless"** |
| `version` + `deleted_at` | **"a tombstone, never a hard delete — let a device that was offline learn what changed without resurrecting data"** |

**三个决定**：

| # | 决定 | 理由 |
|---|---|---|
| 1 | **存"最终意图"而不是操作流水** | 用户在火车上改同一笔三次，**他要的是最后一版**；存流水会让"顺序"变成到处都要操心的事 |
| 2 | **本地立即生效，服务器稍后跟上** | 两条路各自独立——**任何一条失败都不能让另一条不动**，否则一次写入失败会让界面看起来没反应 |
| 3 | **本轮只发现冲突、留住材料，不解决** | 解决在第 3 轮（所有者已定：先自动合并、只问冲突字段、**自动合了哪些必须显示**） |

**⚠️ 而 `baseVersion` 是这一轮的关键字段**：
**它无法事后补出来**——它是"**这台设备离线时看到的那一版**"。
有它，服务端的乐观锁才能回答"这期间别人动过没有"；
没有它，**离线一周的设备会静默覆盖别人一周的修改**——
**而一本会悄悄丢掉一条记录的账，比一本拒绝保存的账更糟。**

**四条队列规则**（都有测试）：

1. **离线新建后再编辑**：仍是 `create`（否则服务端 404 到永远）；
2. **离线新建后再删除**：**整个取消**，不入队（服务端从没见过这个 id）；
3. **`baseVersion` 保留最早的值**（第二次编辑不能用自己的产物当基准，否则两次编辑会塌成一次静默覆盖）；
4. **写队列走 `writeValue`**（按 key 串行化——**这个坑这个项目已经踩过一次**）。

**怎么验证的**

- 类型检查三个包通过；全量测试 **600 通过**（shared 167 / web 297 / api 136）
- **未接界面，未真机验证**——按设计文档 §7 的七条场景验收

### 1.08.17 —— ⚠️ 那个"一秒后自动计算"的逻辑根本不存在（2026-10-11 09:36）

**改了什么**

- **分析页：计算不再等查询**（`queries.ts` 的 `useStats`）。
  挂载后 **1 秒**，若 store 里还没有这次请求的结果、而设备上有账目，
  就自己读取、计算、发布。
- **明细页：本机读取也不再等查询**（`useTransactions`）——
  `readLocalTransactions()` 在挂载时自己发起一次，每个视图一次，**不轮询**。

**为什么**

**所有者的那句话直接指出了我的实现缺口**：

> **"既然数据跑通了，为什么之前的那个卡住一秒自动开始计算的逻辑没有生效呢？"**

**答案：它不存在。**

`analysisStore` 与 `ledgerSnapshot` **只在 `queryFn` 里被写入**——
**所以查询不跑，就永远不计算，store 永远是空的**，
**而屏幕在等的正是那份空 store。**

> **⚠️ 我实现的是"查询跑了就发布"，而不是"过一会儿就算"。**
> **这两件事在查询正常时看不出来，在查询卡住时结果完全相反。**

**这解释了一条一直很别扭的现象**：
**明细页之所以在 1.08.11 之后就成功了，是因为它那条 store 通道由 `useLocalEntries` 自己发起读取；
而分析页的 store 只在 `queryFn` 里写——于是同一个修法只对一半的页面生效。**

**⚠️ 现在的结构**：

| 页面 | 数据通道 | 谁发起 |
|---|---|---|
| 明细页 | `ledgerSnapshot` | **`useTransactions` 的 effect 自己发起** |
| 分析页 | `analysisStore` | **`useStats` 的 effect 自己发起（1 秒后）** |

**两条通道都不再经过查询层**，而查询仍然在跑、服务器答案仍然优先。

**怎么验证的**

- 类型检查三个包通过；全量测试 **594 通过**
- **待真机确认**

### 1.08.16 —— 本机存储在，而这次读取没看到它（2026-10-11 09:31）

**改了什么**

- **读取本机存储时加一次重试**：第一次为空就再读一次，并记 `DIAGNOSTIC:ledger-reread`。
- **`localRead` 报告拆出 `storedEntries`**，与 `diskEntries`（查询缓存）分开计数。
- **横幅、明细页说明、运行记录三处都显示"本机存储 N 条"**。

**为什么**

所有者的诊断里同时出现了两个互相矛盾的数：

```
本机存储：60 个月 / 138 条      ← 诊断页读到了
横幅：磁盘 0 条，内存 138 条     ← 读取那条路没读到（而且没有"本机存储"那几个字）
```

**⚠️ 判断**：**同一个设备、同一个存储，一次读到了、另一次没读到。**

**而"第一次 `get` 返回空、值却确实存在"是 IndexedDB 的已知行为**
（页面恢复或负载下可能无错误地失败，见
[WebKit #251203](https://wiki.webkit.org/show_bug.cgi?id=251203)）。

**⚠️ 一次重试的代价可以忽略，而它区分的是两件在程序其余部分完全无法区分的事**：

| 说法 | 含义 |
|---|---|
| **"设备上没有"** | 需要用户去下载 |
| **"这一次读取没看到"** | 什么都不用做，重读即可 |

**拆开 `storedEntries` 与 `diskEntries` 也是同一个理由**：
**一个"存了"的数和一个"读到"的数，才能把这两件事分开；合并后的总数恰好会掩盖要查的那个分歧。**

**怎么验证的**

- 类型检查三个包通过；全量测试 **594 通过**
- **待真机确认**——判据：横幅/说明里出现 `本机存储 N 条`，以及是否出现 `DIAGNOSTIC:ledger-reread`

**他是对的，而这一版就是那个做法**：**一个只增不减的映射。

**"move away of uSES"（离开 useSyncExternalStore）**——
