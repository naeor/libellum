## 1. 最重要的发现：**一个用户不再等于一本账**

现在的代码**硬假定"一个用户 = 一本账"**：

```ts
// 每一次接口调用都这样开始（24 个接口）
const bookId = await currentBookId(prisma, userId);   // 只给 userId，不给 bookId
```

也就是说：**所有接口都不接受"你要操作哪本账"这个参数**，因为它们认为你只有一本。
而所有者要的是"一个人可以有多本账（私人的、公共的）"，所以：

| # | 要改的地方 | 规模 |
|---|---|---|
| 1 | 每个接口都要接受并校验 `bookId` | 24 个接口入口 + 全部权限判断 |
| 2 | 前端需要"当前账本"状态 | 现在没有这个概念 |
| 3 | **新增"开始页"** | 新页面 + 新路由 |
| 4 | `book_members.role` 真正生效 | 列已存在，**从未被检查** |
| 5 | 共享类型（`ledgerMetaResponseSchema` 等）要带上"账本 + 我的角色" | 共享包 |

## 2. 页面与导航（KQ1、KQ2 已定）

### 2.1 开始页

| 项 | 决定 |
|---|---|
| 什么时候进入 | **首次登录**（注册完成）**或主动点击左上角品牌名** |
| 平时登录进哪 | **上次使用的那本账**（服务器保存），直接进**明细页的展示态** |
| 开始页能看到什么 | 自己的**所有账本**（私人 + 被邀请的共享），可新建、可进入、可归档/退出 |
| 点账本 → | 看到该账本详情 → 点"编辑"进入 → **就是现在这整套界面** |
| 引导 | 要告诉用户"点品牌名可以回开始页"；账户页也加一个入口 |
| **当前账本是哪本** | **所有页面固定一小块显示**：`当前账本：XXX` |

> **为什么这样定很聪明**：绝大多数人只有一本账，于是他**永远不用看见开始页**，
> 记账步数一步都不增加；而需要多本账的人有完整的入口。

### 2.2 账本切换与"当前账本"

- 品牌名（左上角）= 回开始页的入口；
- **所有页面**（除开始页与账户页）固定显示当前账本名；
- 服务器保存"上次使用的账本"，登录时直接进它。

## 3. 账号编号与账本编号（KQ2 已定）

### 3.1 ⚠️ 编号从"随机"改成"连续"——**代价已记录**

原设计是**随机八位数字**，理由是：编号公开、还要被用来搜人，**连续编号会让人能枚举所有账号**。

所有者为了"**能提前把编号写在卡片上**"而改成连续。这个权衡是对的，**代价不隐藏**：

> **现在防枚举靠的是搜索限流，而不是编号本身的不可预测性。**

### 3.2 编号区间（已实现）

| 区间 | 用途 |
|---|---|
| **10000000** | 所有者本人（naeor） |
| **10000001** | 现有第二个账号（mama） |
| **10000002 – 10000099** | **首批 98 个邀请码**（见 `docs/邀请码.md`，不入库），注册后即**管理员** |
| 10000100 | **跳过**（让两段序列一眼可辨） |
| **10000101 起** | 之后任何方式生成的邀请码，注册时由服务器依次分配 |

### 3.3 并发安全：**原子计数器，而不是"提议 + 仲裁"**

所有者原本设想：客户端提一个号 → 服务器比对 → 撞了按到达时间排 → 再撞就随机给一个。
**意图完全正确**（两个同时注册的人绝不能拿到同一个号），但实现上有一个**更简单的等价物**：

```sql
UPDATE "counters" SET "next" = "next" + 1
 WHERE "name" = 'account_number_direct'
RETURNING "next" - 1 AS "taken";     -- 一条语句，两个人不可能拿到同一个值
```

没有重试、没有仲裁、没有随机兜底；`users.account_number` 的**唯一索引**仍是最后一道保险。

### 3.4 ⚠️ 实现中发现的一个真问题：**一个计数器不够**

**如果"发码预留"和"注册分配"共用一个计数器**，那么：
批量发 98 个码会把计数器推到 `10000100`（**越过预留区间**），
之后"没有邀请码"的注册就会落进 `10000100+`——**而那个区间正在被发放**。两个账号、同一个号。

**所以拆成两个**：

| 计数器 | 用途 |
|---|---|
| `account_number` | 发给**邀请码**的预留编号（码把它带走） |
| `account_number_direct` | **注册时直接分配**的编号 |

两个都只增不减，所以预留的号即使码没用也**永不复用**，两段序列也不可能相撞。

### 3.5 账本编号（**待实现**）

所有者要求"每个账本也有全局统一独立编号"。已确定：

- **纯数字**，与账号编号同样的形式；
- **永久跟着账本**，账本被弃置后编号作废、不复用；
- **不能被用来搜索账本**（否则遍历编号就能发现别人的账本），它只用于"报出来对账"；
- 实现方式与账号编号相同：`counters` 表里加一行 `book_number`。

> ❓ **待所有者确认**：账本编号的**起始值**？（账号用了 8 位；账本建议也用 8 位，
> 例如从 `20000001` 起，这样一眼能分出"这是账号还是账本"。）

## 4. 权限（KQ3、KQ4、KQ6 已定）

### 4.1 两种角色，**取消 owner**

所有者决定：**取消 owner，只保留 editor 与 viewer**。

| 角色 | 能做 |
|---|---|
| **editor** | 记账与修改、**邀请他人**、**更改他人权限**；不能把自己降为 viewer（否则没人能改回来） |
| **viewer** | **看到的和 editor 完全一样**（账目、统计、明细），**唯一的区别是不能编辑** |

**服务端必须强制检查权限**——所有者特别强调：

> "即使 viewer 通过某种方式发起了更改，服务器的数据也不会被污染。"

> ⚠️ **一个必须先解决的问题**：`book_members.role` **目前被取出但从未使用**
> （`requireBookAccess` 是死代码）。所以**现在任何成员都能改任何账本**——
> 这不是"将来要修"，而是**现在就是错的**。协作实现时第一件事就是让它生效。

### 4.2 归档 / 退出（KQ4 已定）

| 动作 | 含义 |
|---|---|
| **归档** | 一个人一本账时使用。**服务器保留全部数据**、标记"**弃置**"，**客户端删除数据**，**普通用户再也看不到** |
| **退出** | 曾经多人时使用。**我只失去访问权，账本对其他人照常存在** |
| **编辑** | 账本详情里可改（如改名） |

**两条边界规则（已定）**：

1. **最后一个 editor 不能退出**——否则账本会变成没人能改的"死账"。
   要结束它，只能**由创建者删除整本**，或**先把别人设为 editor**。
2. **管理员能看弃置账本**：所有者要求"把首批 100 个编号内的账户标记为管理员，可以访问所有数据"。
   所以"没人能访问"指的是**普通用户**。实现上用 `users.is_admin`（**存储字段，不是按编号区间判断**——
   区间判断会把权限意外赠给将来落进该区间的人）。

## 5. 邀请体系（KQ4、KQ5 已定）

### 5.1 三种入口

| 机制 | 谁生成 | 限制 | 用途 |
|---|---|---|---|
| **普通邀请码** | 所有者（命令行） | 一次性 | 注册全新账号 |
| **次级邀请码** | 任意用户 | **每个账户终身最多 3 个**；一次性；**用它注册的人没有生成资格** | 把**还没有账号**的家人主动拉进来 |
| **分享链接** | 账本的 editor | **有效期 1–7 天**、**可邀请 1–10 人**、可**提前撤销** | 把**已有账号**的人拉进**这本账** |

**可追溯性**（所有者明确要求）：任何邀请码都要能查出**是哪个账号生成的**、**被哪个账号用了**。
数据库里 `registration_invites.used_by_user_id` 已有前者的一半，实现时要补上"生成者"字段。

### 5.2 分享链接的细节

- 链接**留在协作者界面**，生成时可选**有效天数**与**人数上限**；
- 邀请者能看到**还剩几个名额**；
- 被邀请人点开 → **自动弹窗**（写明账本名、邀请人、我的权限）→ 确认 → **开始页多一本账**；
- **边界情况（已定）**：如果同一个人**同时**被次级码和链接邀请进**同一本账** → **合并成一本**（按账本去重）。

### 5.3 协作者页面 = "**这本账的**协作者"

- 显示这本账的所有协作者；
- **自己置顶且有特殊高光**；
- 是邀请的入口（生成链接、查看名额、撤销）。

## 6. 离线与冲突（KQ 相关，所有者已定）

### 6.1 范围：**"所有理论上能本地计算的都做"**

所有者原话要点：

> "我希望这个软件的**绝大部分功能都可以离线使用**，或者说它**最开始本来就是被设计成离线软件的**；
> 服务器更多的是起到一个**数据备份**的作用。只是后续我发现作为网页端，把很多东西
> ——比如 OCR 识别——**扔进服务器里会比在本地手机计算好太多**……
> 所以**只要不涉及到需要太多算力的内容都尽可能做成本地就能完全实现**。"

| 功能 | 离线 |
|---|---|
| 记账、看历史、改、删 | ✅ **必须** |
| 统计（图表） | ✅ |
| 分类 / 支付方式 / 标签管理 | ✅ |
| **导出文件** | ✅ **做**，但要提醒用户"**导出的是本地记录，不一定靠谱**" |
| OCR 识别 | ❌ 依赖服务器（算力原因，所有者认可） |

### 6.2 冲突：**提示用户选择，逐字段对比**

所有者要求：

> "把服务器里面的记录和用户本地的记录都摆出来，包括修改时间并**高亮冲突的具体内容**。
> 只要发生了冲突就**记下冲突的内容、用户选择、时间等等并且保存到数据库中**。"

补充决定：
- **"高亮"就是把背景颜色换一下**，让它更显眼；
- 冲突记录**只存服务器，不给客户端看**——所有者的判断是"这种东西没必要给客户看，
  但服务器多存点数据总没错：**一天 100 次冲突一年也就 4 万条，可能还没有 1MB**"。

所以需要新表 `sync_conflicts`，记录：设备、流水、两个版本的内容、用户选了哪个、时间。
**没有客户端界面**——这与 PLAN §1.5 的原则一致（审计数据不上客户端界面）。

  ↓

  ↓
S10 可上线（部署 + 备份演练 + 只读演示账号）
  ↓

  ↓
S11 阅读与列表体验
  ↓
S12 磨光（双语 + 主题 + 大键盘 + 图标）          ← 横切：改所有文件，必须最后

## 9. 账本编号（**已实现 2026-10-10**）

### 9.1 设计

| 项 | 决定 |
|---|---|
| **形式** | **8 位纯数字**，与账号编号一致 |
| **区间** | 账号 `10xxxxxx`、账本 `40xxxxxx`——**前两位不同，一眼可分**（所有者选 `40000000` 正是为此） |
| **分配** | 与账号编号**同一张 `counters` 表**、同一个原子计数器函数 |
| **可搜索吗** | ❌ **不能**。账本只能通过邀请加入，编号是**标签不是地址** |
| **永久性** | 跟着账本；账本被弃置后编号作废，**不复用** |

### 9.2 已有账本的编号顺序

按**创建者的账号编号**排序 —— 所有者原话："**最前面的是我的帐本**"。
所以 `naeor`（10000000）的账本拿到 `40000000`，`mama` 的拿到 `40000001`。

> **为什么不用 `created_at` 排序**：今天两者结果相同，但所有者明确说了"我的在最前面"，
> 那就按**账号编号**排——它是所有者陈述过的顺序，而且**可复现**（同一份数据跑两次结果一样）。

### 9.3 界面

- **明细页**：切换条上方一条小字 `当前账本：我的账本 40000000`，**两态都显示**；
- **「我的账本」页**：列出账本编号，并说明"编号用于核对，不能用来搜索"。

> ⚠️ **一个实现上的注意点**：这条小字**没有放进绿色区域**，而是放在切换条那一行的上方，
> 且用绝对定位。原因：绿色区域的高度是**唯一被转场动画驱动的东西**，它的内边距是从真机量出来的；
> 在里面加第二行，就必须同步改 `--hero-tall` / `--hero-short` 并在真机上重量一遍。
> 放在这里则**任何形态下都不改变行高**（绝对定位不占位），因此不影响已调好的转场。

## 11. 局域网先行（所有者的提议，**已确认可行**）

所有者问："我们是否可以用本地的局域网去模拟上线、开发？我自己还有几台设备。"

**可以，而且建议先这样做。** 现状已经支持：API 监听 `0.0.0.0:3000`、
前端监听 `192.168.0.184:5173`（排查"网络连接异常"时已验证过）。

| 用途 | 怎么用 |
|---|---|
| 家人连着家里 WiFi | 手机浏览器打开 `http://192.168.0.184:5173` |
| **多设备测试** | 每台设备各注册一个账号 → 验证"多人同一本账" |
| 调试协作与冲突 | 局域网延迟低、可控，**比公网更适合调试** |

**三个限制必须知道**：

| 限制 | 影响 | 对策 |
|---|---|---|
| **只有同一个 WiFi 能用** | 家人回自己家就断 | 局域网**只用于测试**，长期仍要服务器 |
| **不是 HTTPS** | ⚠️ 浏览器禁用 **Service Worker / PWA**，离线能力**无法完整测试**（`crypto.randomUUID` 也在此列——已踩过） | S8 若要真机测离线，需自签证书或在 `localhost` 上测 |
| IP 会变 | 链接失效 | 测试时记当前 IP |

**结论**：**局域网测功能正确性，服务器测真实环境**（HTTPS、离线、中国大陆速度）。

## 12. 管理员分级（**仅记录，不实现**）

> 所有者 2026-10-10 定。他自己的原话值得原样保留：
>
> > "**你看权利就是这么迷人，八字没一撇的事，我倒是先安排起每个人的权利了。**"

**只有 001–030 号被激活为管理员，其余账号一律**不是**管理员。**（所有者明确要求。）

⚠️ **本节是"计划"，不是"现状"。** 代码里现在只有一个布尔 `users.is_admin`，
含义是"能看全部数据（含弃置账本）"。**下面这些角色与权限一个都还没实现**，
写在这里是因为它决定了后续所有管理功能的形状，而**先想清楚谁该能做什么，比事后补权限便宜得多**。

### 12.1 分级

| 编号 | 角色 | 权限 | 次数 / 配额限制 |
|---|---|---|---|
| **001** | **最高管理员**（所有者本人） | **全部权限**。另包括：**管理其他管理员的角色与权限配置**、**配置全量注册邀请码规则与开关** | 无限制 |
| **002–003** | **紧急恢复管理员** | ① **撤销其他较低级管理员的权限** ② **指定某个账号重新成为最高管理员** | 指定最高管理员**只能用 1 次**，用后自动失去该权限，**需要最高管理员恢复** |
| **004–010** | **平台运维管理员** | 查看各类日志与运营指标、处理异常同步任务、**管理邀请码是否可用**、**管理每个账号的次级邀请码配额** | 次级配额：**一周最多 10 次**，每次最多 **+1** 个配额<br>暂停/恢复账号登录：**一周最多 10 次**，每次最多 **100 个账号**（开与关都算一次） |
| **011–020** | **用户支持管理员** | 查看账号是否存在、是否被锁定、注册时间与状态；**重新发送邀请**或**撤销未使用的邀请**；**发起账号恢复申请** | 未定 |
| **021–030** | **运营管理员** | 管理**演示账号与演示数据**、创建测试样本与测试账号 | 未定 |

### 12.2 为什么"配额"要写进设计

所有者给运维管理员设的限额有一个共同点：**它们都是"防止一次操作影响太多人"的上限**。

| 限额 | 防的是什么 |
|---|---|
| 次级邀请码配额 +1 / 次，10 次 / 周 | 防止一次给某个账号开很大的口子 |
| 暂停登录 ≤ 100 个账号 / 次，10 次 / 周 | 防止一次误操作把所有人挡在门外 |
| **开与关都算一次** | 否则"关掉再打开"可以绕过计数——这是一个容易漏掉的细节，所有者明确指出了 |

> **这组数字与"紧急恢复管理员只能指定一次最高管理员"是同一种设计**：
> 高权限动作**要么次数有限，要么范围有限**，而且**用完需要更高一级来恢复**。
> 这不是不信任，而是"一个账号被盗时，损失有上界"。

### 12.3 与现有代码的差距（实现时要做的事）

| 要做 | 说明 |
|---|---|
| 角色表 | 现在的 `users.is_admin` 布尔不够。需要 `admin_role` 枚举 + 一张**审计表**记录每一次高权限动作（谁、何时、对谁、结果） |
| 配额计数 | 需要按"周"计数的表；周界用什么时区要定（建议 UTC，与其它审计一致） |
| **所有高权限动作都要记审计** | 撤销管理员、指定最高管理员、改配额、暂停账号——这些是**最需要事后追溯**的操作 |
| `001` 的唯一性 | "最高管理员"同时只能有一个，且**转移要留痕**（谁转给谁、何时） |
| 权限检查的位置 | 必须**在服务器**，且与 `book_members` 一样成为**唯一判据**——客户端传来的任何角色都不算数 |

> ⚠️ **一条实现原则（从 `book_members.role` 的教训来）**：
> `book_members.role` **被取出却从未检查**，导致"现在任何成员都能改任何账本"。
> **管理员角色绝不能再犯同一个错**——加字段的同时就要加检查，并且在测试里断言"低权限角色发起的动作被服务器拒绝"。
