## 0. 结论摘要

**已有脚本质量高于预期，可以无人值守运行** —— `deploy/backup.sh` 没有交互、
`set -euo pipefail`、有恢复演练、有轮转、且**从不碰生产库的 drop**。

**四个真问题**（按严重度）：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **异地存储完全不存在** | 服务器或账号丢了 = 数据全丢。这是当前唯一的致命缺口 |
| 2 | **没有任何失败通知渠道** | 备份连续失败只能靠人去 SSH 发现 |
| 3 | **恢复演练的逐表比对清单漏了 3 张表**：`admin_grants`、`admin_allowlist`、`_prisma_migrations` | 备份若缺了权限表或迁移状态，演练**不会发现** |
| 4 | **备份状态没有落盘记录**（只打印到 stdout） | 无法回答"上一次成功是什么时候"；S13 概览也就没有数据 |

**建议**：`systemd timer`（不是 cron），**每天 03:00 Asia/Hong_Kong**，
本地 7 天 + 异地 30 天，**异地桶用"只允许写、不允许删"的独立密钥 + 版本保留**。

**⚠️ 需要所有者确认的 6 件事见 §9。其中"是否开通对象存储"和"告警用什么渠道"必须先答，才能进阶段二。**

## 1. 现有脚本审计（逐条回答所有者列的检查点）

### 1.1 `deploy/backup.sh`

| 检查点 | 结论 |
|---|---|
| **是否依赖交互输入** | ✅ **没有**（`read` 出现 0 次） |
| **失败是否返回非零** | ✅ 有（`set -euo pipefail` + 多处显式 `exit 1`） |
| **备份文件是否完整** | ✅ 三重校验：`PGPASSWORD` 导出 → `pg_restore --list` 解析 → **真恢复到临时库** |
| **是否能验证恢复结果** | ✅ **逐表比对行数**（不是只看"恢复没报错"） |
| **并发运行风险** | ⚠️ **有**：两次同时运行会各自建临时库（名字带时间戳，不会撞），但会**同时吃磁盘/IO**。需要用锁挡 |
| **是否可能误删数据库** | ✅ **不会**：全脚本没有 `dropdb` 生产库，只有 `dropdb --if-exists "$VERIFY_DB"`（临时库） |
| **数据库/磁盘压力** | ✅ 可忽略：库 **9.6 MB**，dump **90 KB**，恢复演练实测 **< 2 秒** |
| **库外需要持久保存的数据** | ⚠️ **见 §1.3** —— 只有 `.env`（密钥）和备份文件本身，没有图片/上传文件（本项目图片从不落盘） |
| **备份是否覆盖所有数据结构** | ✅ **dump 本身覆盖全部 23 张表**（`pg_restore --list` 里有 23 个 `TABLE DATA`） |

**⚠️ 但演练的"逐表比对清单"是硬编码的，只有 20 张表**，漏了：

```
admin_grants          ← 管理员授权（敏感权限）
admin_allowlist       ← 管理员允许名单（敏感权限）
_prisma_migrations    ← 迁移状态（决定"这个备份能不能配这个版本的应用"）
```

**后果**：如果某次备份恰好缺了权限表，**演练会报"通过"**。
→ 阶段二修：清单补上这三张（S13 部署后还要再加 `admin_audit_logs`、`backup_logs`）。
**更好的做法**：不再硬编码清单，而是**从库里的 `information_schema` 取表名再逐表比对** ——
这样以后加表不需要记得改脚本（本项目对"手抄第二份清单"有明确教训）。

### 1.2 `deploy/restore.sh`

| 检查点 | 结论 |
|---|---|
| **是否依赖交互** | ⚠️ **是**（`read -r -p '输入 yes 继续'`），除非加 `--yes` |
| **是否可能误删数据库** | 🔴 **会** —— 它 `dropdb` + `createdb` **重建生产库**（3 处 `dropdb`） |
| **结论** | **绝不能用它做自动演练。** 恢复演练请永远用 `backup.sh` 内建的那条路径（临时库），或 S12-C 新增的只读演练脚本 |

它的用途是"真的需要救命时"手动执行 —— 那时交互确认是对的，不能改掉。

### 1.3 库外需要备份的东西（重要但容易漏）

| 东西 | 在哪 | 要不要备份 | 结论 |
|---|---|---|---|
| 生产库 | Docker volume `db-data` | ✅ 已覆盖 | `pg_dump` 就够了 |
| API 数据卷 | `api-data`（卷名 `deploy_api-data`） | ✅ **已查清：不需要备份** | 实测 **1.2 GB 全是可重新下载的东西**：`.cache` 334 MB + `.local` 896 MB 是 whisper 语音模型；`uploads/` 与 `models/` **都是空的**。**没有任何用户数据** |
| **`deploy/.env`（密钥与数据库口令）** | 服务器文件 | 🔴 **必须异地保存** | **没有它，备份恢复出来也连不上/起不来。加密后单独保存，绝不进仓库** |
| Caddy 证书 | `caddy-data` volume | ❌ 不需要 | 重新申请即可 |
| 用户上传的图片 | —— | ❌ 不存在 | 本项目图片从不落盘（OCR 只在内存里过一遍） |
| 备份文件本身 | 宿主机 `deploy/backups/` | ✅ S12-C 要解决 | 本设计的主体 |

## 2. 调度方案：**systemd timer**（不是 cron）

| 对比项 | cron | systemd timer | 结论 |
|---|---|---|---|
| 关机错过 03:00 | ❌ 不会补跑 | ✅ `Persistent=true` **开机后补跑一次** | **决定性** |
| 时区 | 依赖 `CRON_TZ`，行为随实现而异 | ✅ `OnCalendar=*-*-* 03:00:00 Asia/Hong_Kong` 明确带上时区 | systemd 更清楚 |
| 防重叠 | 要自己 `flock` | ✅ 同一个 service 不会并发启动 + 仍加 `flock` 双保险 | systemd 更好 |
| 日志 | 手工重定向 | ✅ 自动进 journal，`journalctl -u` 查 | systemd 更好 |
| 环境变量 | 精简，PATH 常缺 | 可 `Environment=` 显式给 | systemd 更好 |

**服务器实测**：systemd **255**（支持 `OnCalendar` 带时区，需 ≥235）、`systemctl is-system-running: running`、
`flock` 已安装、`journalctl` 可用、`ubuntu` 在 **docker 组**（`backup.sh` 里的 `docker compose` 不需要 sudo，实测 OK）。

**拟用配置（阶段二才写）**：

```ini
# /etc/systemd/system/libevra-backup.service
[Unit]
Description=Libevra production database backup (dump + verify + offsite)
Wants=network-online.target
After=network-online.target

[Service]
Type=oneshot
User=ubuntu
WorkingDirectory=/srv/libevra/deploy
ExecStart=/usr/bin/flock -n /srv/libevra/deploy/.backup.lock /srv/libevra/deploy/backup-all.sh
TimeoutStartSec=1h
Nice=10
IOSchedulingClass=best-effort
IOSchedulingPriority=7
```

```ini
# /etc/systemd/system/libevra-backup.timer
[Unit]
Description=Daily 03:00 Asia/Hong_Kong backup

[Timer]
OnCalendar=*-*-* 03:00:00 Asia/Hong_Kong
Persistent=true
AccuracySec=1min
RandomizedDelaySec=0
Unit=libevra-backup.service

[Install]
WantedBy=timers.target
```

**⚠️ 不修改操作系统时区**：服务器现在是 `Asia/Shanghai`，**不动它**。
`OnCalendar` 自带时区后缀，所以"03:00 香港时间"与系统时区无关（两者当前都是 UTC+8，但没有依赖这一点）。

**⚠️ `Persistent=true` 的语义**：关机错过的那一次，**开机后补跑一次**（只补一次，不补多次）。
这正是我们要的 —— 但意味着**白天开机时也可能跑一次备份**，这没问题（备份是只读生产库的）。

## 3. 保留、校验、异地

### 3.1 保留策略

| 位置 | 保留 | 谁清理 |
|---|---|---|
| **本地** `deploy/backups/` | **最近 7 天成功备份** | `backup.sh` 现有轮转（`--keep 7`） |
| **异地对象存储** | **≥30 天** | **桶的生命周期规则**（不是脚本） |

**⚠️ 两条硬规则**：

1. **清理只发生在"本次备份已成功"之后** —— 现有脚本靠 `set -euo pipefail` 天然满足：
   导出/校验失败会在轮转之前 `exit 1`，**旧的备份一个都不动**。
2. **永远不删"最新的一份"** —— 现有轮转按 `mtime +7` 删，**没有这个保护**。
   阶段二补一条：保留最新的 N 份，任何情况下不删（见 §8 改进清单）。

### 3.2 校验分级（回答"每天完整演练会不会太重"）

**实测：整轮 dump + 恢复到临时库 + 逐表比对 < 2 秒，库 9.6 MB。**
所以**当前每天做完整演练的代价可以忽略**，不必退化成"每周演练"。

但设计上仍分三级，写进脚本输出，概览页分别显示：

| 级别 | 每天做什么 | 失败含义 |
|---|---|---|
| **L1 本地** | `pg_dump` 成功 + 文件大小合理 + `pg_restore --list` 能解析 | 文件不可用 |
| **L2 恢复演练** | 恢复到临时库 + **逐表行数比对（表名从 `information_schema` 动态取）** | 文件能读但**数据不完整** |
| **L3 异地** | 上传后 **下载回来比对 SHA-256** | 本地的没问题，但异地那份可能坏了/没传上去 |

**⚠️ 三级状态必须分开显示**，不能因为 L1 成功就显示"备份正常"。
这也正是 S13 概览页要的三件事。

**⚠️ 何时改成"每周完整演练"**：当 `dump > 50 MB` 或演练耗时 > 60 秒时。
届时日常只做 L1+L3，每周日做一次 L2。**脚本里留一个开关，不靠人记。**

### 3.3 异地存储方案对比

| 方案 | 成本（估） | 优点 | 风险 |
|---|---|---|---|
| **A. 腾讯云 COS**（推荐） | 存储约 **¥0.01/月**（数据 3 MB 级：90 KB×30 天 ≈ 2.7 MB）；请求费可忽略；**内网上传免流量费** | 同区（香港）→ 快、免流量、文档熟悉 | **与服务器同一个云账号** → 账号被盗则两边都没了。**必须用独立子账号 + 只写不删权限 + 版本保留** |
| B. Cloudflare R2 | 免费额度 10 GB，**无出网费** | 便宜、出网免费、S3 兼容 | 需要境外账号与支付方式；HK→R2 延迟可接受（90 KB 无所谓） |
| C. Backblaze B2 | 约 **$0.005/GB/月** ≈ ¥0.01/月 | 便宜、S3 兼容 | 同样需要境外账号 |
| D. 家里/第二台机器 | 0（已有设备） | 真正异地 | **不可靠**（断电、硬盘坏、没人管），不适合当唯一异地备份 |

**推荐 A（腾讯云 COS）+ 三道结构性防护**：

1. **独立子账号（CAM）**：只有 `PutObject` / `ListBucket` / `GetObject` 权限，**没有 `DeleteObject`**。
   → 即使服务器被入侵、`.env` 被读走，攻击者**也删不掉历史备份**。
2. **桶开"版本保留/多版本"**：同名的覆盖不会毁掉旧版本；再配一条**目标保留 30 天**的策略。
3. **生命周期规则负责过期清理**，不交给脚本的凭据。
4. **上传前用 `gpg --symmetric --cipher-algo AES256` 加密**（服务器上 `gpg` 已装）。
   口令放 `deploy/backup-encryption.key`（600 权限）+ **所有者自己另存一份**。
   → 桶泄露不等于数据泄露；**但口令丢了等于备份全废**，这是这个方案唯一的硬风险，必须写进运维手册。

**⚠️ 成本口径**：以上是**估算**。腾讯云 COS 在香港区的具体单价、是否有最低消费、
是否需要实名/开通，**以控制台为准**。**我不擅自开通任何付费服务。**

### 3.4 凭据怎么放（不泄露、不进仓库）

| 东西 | 位置 | 权限 |
|---|---|---|
| COS 子账号的 `SecretId`/`SecretKey` | `/srv/libevra/deploy/.backup.env` | `600`，属主 ubuntu |
| 加密口令 | `/srv/libevra/deploy/.backup.key` | `600`，**所有者另存一份** |
| 桶名/区域/前缀 | 同上（非秘密） | — |

**⚠️ 三条禁令**：不进 Git（`.gitignore` 已有 `deploy/.env`，需再加 `.backup.env`/`.backup.key`）、
不进日志（`backup.sh` 打印时用 `***` 遮住）、不进聊天。

**工具选择**：服务器**没装 rclone/aws**。两条路：
① `apt install rclone`（简单，生态成熟，支持 COS 的 S3 兼容接口 + 加密）；
② 用 `curl` 手写 COS 的签名请求（**不做**，签名算法自己实现 = 又一个第二份实现）。
**建议 ① `rclone`**，但它是**新增系统包**，需要你同意。

## 4. 与 S13 管理后台的整合

### 4.1 三个状态要分开

S13 里我建的 `backup_logs` 现在只有 `ok` 一个布尔，**表达不了"本地成功、异地失败"**。建议改成：

```sql
-- 修改 20261017160000_admin_console 这个迁移（尚未部署到生产，所以现在改是安全的）
ALTER TABLE "backup_logs" ADD COLUMN "local_ok"   BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE "backup_logs" ADD COLUMN "restore_ok" BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE "backup_logs" ADD COLUMN "offsite_ok" BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE "backup_logs" ADD COLUMN "offsite_ref" VARCHAR(300);
ALTER TABLE "backup_logs" ADD COLUMN "sha256" VARCHAR(64);
-- "ok" 保留为"三项全过"的汇总列，避免读的一方自己组合
```

### 4.2 ⚠️ 关键顺序问题：生产上**还没有**这张表

`backup_logs` 只存在于仓库迁移里，**生产库还没有它**（线上是 `d2c7a67`，S13 未部署）。
所以：

| 顺序 | 结果 |
|---|---|
| **先部署 1.13.01，再启用备份** | `backup.sh` 可以写库，概览页立刻有数据 ✅ |
| 先启用备份，后部署 | 写库会失败 → 备份本身**不能因此失败**，只能降级写文件 |

**设计**：`backup.sh` 写状态**双写**：
1. **永远**写 `/srv/libevra/deploy/backups/last-run.json`（**数据库挂了也能记录**）
2. **表存在时**再写一行 `backup_logs`（`to_regclass('public.backup_logs') is not null` 探测）

**⚠️ 为什么必须有文件那一份**：`backup_logs` 在**生产库自己**里面。
**数据库坏掉时最需要备份状态，而那时恰恰读不到这张表**。文件那份是给"服务器还能登录但库挂了"用的。

### 4.3 概览页要显示什么

| 显示 | 来源 |
|---|---|
| 上次**本地**备份时间 / 结果 | `backup_logs`（或文件，若库不可用则由运维手册教人直接看文件） |
| 上次**恢复演练**时间 / 结果 | 同上（`restore_ok`） |
| 上次**异地**上传时间 / 结果 | 同上（`offsite_ok`） |
| **"未知"状态** | 超过 26 小时没有新记录 → 显示红字"上次备份已超期" |

**过渡方案（阶段二就能有）**：失败时 `systemctl` 记录非零退出 + 写 `last-run.json` +
概览页显示超期红字。**这是"可被发现的失败"，不是"主动通知"。**

## 6. 灾难恢复演练（这轮不执行，写成手册步骤）

**场景**：服务器彻底丢失（磁盘坏 / 云账号问题 / 误删实例）。

```
① 新开一台 Ubuntu 24.04（同区域或任意）+ 装 Docker
② 取回部署代码：GitHub 上的同一个 commit（git archive，不在服务器上放 GitHub 凭据）
③ 取回 deploy/.env —— 这份不在任何备份里，所有者必须另行保存（见 §1.3）
④ 安装 rclone + 加密口令，从 COS 下载最近一份备份并解密
⑤ 起 db 容器（空库）→ ./deploy/restore.sh <dump> --yes（手动确认那条路径）
⑥ 起 api/web → /api/v1/health；登录检查账目条数与管理员
```

**⚠️ 阶段二会把这段写成 `docs/生产环境与运维手册.md` 的一节**，并在**隔离临时库**上真演练一次
