## 1. 所有者已确认的决定（2026-10-17，**尚未实施**）

1. **底部「账户」改名为「我的」**，明确作为用户个人中心。
2. **分类、标签、支付方式属于各自账本**，入口迁入「账本/协作 → **账本设置**」；各账本默认隔离。
3. 现有「账本详情」扩展为更完整的「**账本设置**」；**保留账本/协作双中心结构**。
4. **支付方式与资金账户不强行合并**；资金账户若尚未实现，作为独立功能评估，**不得假装已存在**。
5. **删除已被使用的分类 / 标签 / 支付方式要提供影响提示**：分类可选**同类型现有分类**或默认
   「其他/暂无分类」作为历史记录替换目标；标签删除可**解除关联**；支付方式需**单独定义**替换或未指定规则。
6. **共享账本的破坏性设置修改**要明确提醒**会影响全部协作者**。
7. **删除与历史记录重关联必须在服务端事务中完成**（原子性、并发、权限）。
8. **新方向**：个人账本继续支持现有离线记账；**共享账本考虑改为"离线只读、在线写入"**。
   先审计当前实现与受影响的队列、冲突、缓存逻辑；**不得擅自覆盖旧机制**。

> ⚠️ **第 8 条会改变已上线行为，属于需要单独批准的实施项。** 本文只给影响面与方案，不实施。

### 2.3 两处「账本信息」页需要先合并/扩展成一个「账本设置」

| 现有页面 | 路由 | 能力 | 问题 |
|---|---|---|---|
| `LedgerInfoPage`（当前账本，标题「账本信息」） | `/ledger/info`（`LedgerSubPages.tsx:20-74`） | 只读：名称、编号、所有者、成员数 | 与下一行职责重叠、能力不足 |
| `StartBookInfoPage`（任意账本，标题「账本详情」） | `/start/book/:id`（`StartBookPages.tsx:59-268`） | 改名、弃置、成员/分享入口 | 只从开始页齿轮进入；同样没有分类/标签/支付方式 |

**方案（建议）**：**两个入口、一个组件**——`LedgerSettingsPage({ bookId?: string })`：
- 不传 `bookId` → 编辑**当前账本**（`/ledger/settings`，由 `/ledger` 进入）；
- 传 `bookId` → 编辑**指定账本**（`/start/book/:id/settings`，由开始页齿轮进入，**不改变全局当前账本**，
  沿用 1.10.08 已建立的 `apiFetch` 单次 header 覆盖机制）。
**必须保留「账本/协作」双中心结构**：不把账本页改成"设置页"；设置是账本页里的一个入口。

### 2.4 「我的」页保留什么

| 层 | 内容 |
|---|---|
| **用户级（我的）** | 个人资料、密码、恢复码、账号级邀请码额度、下载管理、软件更新、**默认币种（账号级，Q1 已确认）**、退出登录 |
| **账本级（账本设置）** | 分类 / 标签 / 支付方式、导出 / 导入、成员、分享、留言、编辑历史、账本信息 |
| **应用级** | 系统管理、版本公告、关于、法律条款 |

> 原则不变：**分类、标签、支付方式属于账本；账号属于人；平台属于应用。**
> 入口的父级必须与数据的父级一致——否则用户会以为"换账号才换分类"。

## 3. 删除 / 重关联：现状与目标语义

### 3.1 现状（只读审计）

| 对象 | DELETE 现在的行为 | 数据库约束 | 审计缺口 |
|---|---|---|---|
| 分类 | **归档**（`classification.ts:141`，`is_archived=true`） | `transactions.category_id` **Restrict**（`schema.prisma:900`） | 被引用也能"删"；界面没告诉用户历史记录会怎样 |
| 支付方式 | **归档**（`classification.ts:209`） | `transactions.payment_method_id` **SetNull**（`schema.prisma:901`） | 归档后历史显示成"未指定"？**界面没有说明** |
| 标签 | **真删**（`classification.ts:271`） | `transaction_tags` **Cascade**（`schema.prisma:1000`） | 真删会丢关联，**界面没有影响提示** |

**两个额外事实**：
- `classification.ts` **全文没有 `prisma.$transaction`**；标签的 `count`（`:269`）与 `delete`（`:271`）是两条独立语句。
- 服务端已经算过 `{ affectedEntries }`（`classification.ts:269`/`:273`），mutation 也已声明
  （`queries.ts:1584`），**但界面从未读取**（`ManagePages.tsx:497`）——"影响 N 笔"差最后一步。

### 3.2 目标语义（与所有者决定 5、7 对齐）

| 对象 | 删除时的提示 | 用户选择 | 服务端行为（同一事务） |
|---|---|---|---|
| 分类 | "有 N 笔历史记录使用它" | ① 换成**同类型的现有分类**；② 换成默认「其他/暂无分类」（同类型系统分类） | 校验目标分类属于同一账本、同一 `kind`；`updateMany` 重关联 + 归档原分类；全部在一个事务 |
| 标签 | "有 N 笔账目使用它" | 解除关联（可选：先展示 N） | 事务内删 `transaction_tags`（Cascade 已保证）+ 删标签；`affectedEntries` 在事务内重新计数 |
| 支付方式 | "有 N 笔历史记录使用它" | ① 换成另一个支付方式；② **不选 → 未指定**（Q5 已确认） | 事务内 `updateMany` 重关联或置 NULL + 归档；默认「未指定」 |
| **通用规则（Q5）** | **默认先让用户选择"要不要改成另一个"**；用户不选才落到默认：分类→其他/暂无分类、支付方式→未指定、标签→解除关联 | | |

**⚠️ 批量操作记录（Q4 已确认）**：重关联/删除是**一次批量操作**，只记录**一条**批量记录
（操作者、时间、账本、对象、影响笔数、旧值→新值摘要）；**不为每一笔交易写独立事件**。
具体落点（新表 / 单条 `transaction_events`）在实施时定——会影响是否需要一次迁移。

**⚠️ 权限**：删除/重关联是**写**操作，沿用现有 `requireBookForWrite`（服务端每次查 `book_members`）；
**不新增第二套权限判断**（AGENTS §5.0）。viewer 的界面隐藏**只是界面**，服务端 403 不变。

**⚠️ 历史/事件成本**：若"批量重关联"要进编辑历史，需要新增 `transaction_events` 的事件类型
（`ledger/events.ts:22-36` 的枚举 + DB CHECK 约束，见迁移 `20261013190000_book_changed_event`），
**S13-E 就不再是"零迁移"**。这个取舍要所有者拍板（见 §6 Q4）。

## 4. 共享账本「离线只读、在线写入」：审计与方案

### 4.1 现状（关键事实）

| # | 事实 | 证据 |
|---|---|---|
| 1 | **手动记账/编辑/删除走离线写**（`AddEntryPage` → `write.ts`） | `AddEntryPage.tsx:211`、`write.ts:248/288/396` |
| 2 | **拍照/语音直接走在线 mutation**；离线即失败 | `ScanPage.tsx:344`、`VoiceReviewPage.tsx:282` |
| 3 | **离线写路径完全不判角色** | `write.ts` 全文无 `role` / `viewer` 判断 |
| 4 | 服务端写强度：viewer 写入返回 403 `book_read_only` | `app.ts:278`、`ledger/access.ts:105-107` |
| 5 | 403 被 sync 记为**永久失败**，本次会话不再重试；行永久红印，本地值停在服务器从未接受的状态 | `sync.ts:276`、`:150-158` |
| 6 | "队列"其实是按条目的印记（EntryMark），按 `账号:账本` 分域；**只有当前账本会发送** | `localLedger.ts:364-366`、`sync.ts:62-63` |
| 7 | 冲突链路完整（409 带回 `current`+`conflicts` → `ConflictScreen` → 先本地生效再上报） | `write.ts:453-489`、`transactions.ts:719-733` |
| 8 | `/ledger` 响应**不返回 `myRole`** | `ledger.ts:42-113`（`book: {...book, memberCount}`） |
| 9 | 离线横幅只有两种文案，无法表达"共享账本离线只读" | `SyncBanner.tsx:36-38` |
| 10 | 退出账本**不清本地域**（切换后旧数据/旧印记仍在） | `queries.ts:605-612` |
| 11 | 预下载无条件执行（共享账本也会被下载） | `fill.ts:183` |
| 12 | 疑似既有缺陷（需真机复核）：`localLedger.ts:211` 读**未分域**的 `query-cache`，而持久化写 `scopedKey("query-cache")`（`cache.ts:167,190`） | 审计记录；不在本轮修改 |

> **一句话**：**服务器是安全的（403 对），客户端是不诚实的**——它让 viewer 以为可以离线写，
> 然后把失败藏在"永久红印"里。共享离线只读的真正价值是**把这条谎话去掉**，不是新增权限。

### 4.2 改造方向（待批准，不实施）

**目标**：个人账本保持现状（离线写可用）；共享账本**离线只读、在线写入**。
不是"共享账本不能写"——**在线时可以写**，只是**离线时不排队、不假装成功**。

需要新增/修改的判定点（建议顺序）：

| # | 判定点 | 位置（建议） | 说明 |
|---|---|---|---|
| 1 | 唯一"共享"判定 | `ledgerTabLabel` 的 `memberCount` 已存在于 `/ledger` 查询；建议在 `/ledger` 响应加 `myRole`，避免客户端另算第二份 | `ledger.ts:42-113`、`queries.ts:221,237-248` |
| 2 | 写入前的"是否允许离线写"闸 | `write.ts:248/288/396/421` 四个入口 | 共享账本且离线 → 拒绝并给出"请联网后修改"的可见提示；不产生印记 |
| 3 | 存量印记处置 | `sync.ts` 的 `intents()` / `runSync` | **Q6 已确认：默认保留、不自动丢弃**；恢复网络后尝试同步，或由用户明确决定。**升级瞬间**可能存在共享账本的未同步改动：**不能静默丢弃**，也不要默认"弹窗二选一"；先保留，再让它走同步/冲突流程 |
| 4 | 403 的单独识别 | `sync.ts:276` | 403 不再当成"永久失败的红印"，而是"权限/只读"状态，界面文案区分 |
| 5 | 入口禁用与文案 | `AddEntryPage`、`EntryDetailPage`、`DetailPage` 的编辑/删除入口 | 共享账本离线时禁用写按钮，并说明原因（不是隐藏） |
| 6 | 离线横幅 | `SyncBanner.tsx` | 增加"共享账本离线只读"状态 |
| 7 | 冲突屏 | `ConflictScreen` | 共享账本离线只读后不应产生新冲突；**存量改动恢复网络后是否会进入现有冲突链路，Q6 明确"尚未确认"——必须先写验证用例，不能假设它天然可用**（见 §4.4） |
| 8 | 下载管理/预下载 | `fill.ts`、`downloadManager.ts` | **Q7 已确认：保留现有缓存和下载能力，允许离线只读；不额外扩展预下载范围** |
| 9 | 退出账本/切账本清理 | `queries.ts` | 是否清本地域需与存量处置方案一起定；**在 Q6 的"保留待同步"前提下，不能清掉未同步的共享账本改动** |

### 4.4 Q6 的待验证点（**先验证，再写实现**）

所有者指出：断网设备恢复网络时，系统应把断网期间的改动同步到账本；**理论上冲突提醒会显示，
但不确定现有冲突代码在"共享账本离线只读"下还能不能生效**。因此实施前必须验证：

1. 共享账本里已存在的离线印记（升级前产生）在恢复网络后，是否仍走 `sync.ts` → `409` → `ConflictScreen` 链路；
2. 共享账本离线只读后**新产生**的写被禁用，不再产生新印记——存量印记的 403/冲突分支是否仍然可达；
3. 若冲突屏不可用，需要什么最小修复（只修冲突展示，还是重做该段），**不要为了让方案看起来完整而假设它成立**。

### 4.3 风险（必须先接受）

| # | 风险 | 处置建议 |
|---|---|---|
| R1 | **本地改了、服务器不知道**（离线写被拒绝时若提示不清，用户会以为已保存） | 写入前闸 + 明确提示；绝不"先写本地再说" |
| R2 | 切账本后旧印记变幽灵（已有问题） | 与 R3 一起处理；**默认保留待同步**（Q6），不静默删 |
| R3 | **升级瞬间的存量共享账本未同步改动**无法从代码判断数量 | **默认保留、不自动丢弃**（Q6）；恢复网络后尝试同步；冲突链路是否可用见 §4.4 |
| R4 | 冲突屏仍会出现在只读账本 | 只处理存量；不产生新冲突；**冲突链路可用性待验证** |
| R5 | 离线横幅文案会说谎 | 新增状态文案（受 `copy.test.ts` 语体约束） |
| R6 | 退出账本不清本地域 | 单独修或与 R2/R3 一起；**不能清掉未同步改动** |
| R7 | 预下载范围扩大 | **Q7：不额外扩展预下载范围**；保留现有能力 |
| R8 | 拍照/语音本来就离线不可用 | 保持现状；文案与手动路径统一 |
| R9 | `localLedger` 疑似 `query-cache` 不分域缺陷 | **先真机复核再修**，不混进本轮 |
