## 1. 📌 发版规则（必须遵守）

### 1.1 版本号格式

```
1.10.01
│ │  └── 该阶段里的第几版：**用户看得见的行为变化就 +1**
│ └───── 正在开发的阶段，**与 `开发计划.md` 的阶段号一致**
└─────── 第几次整体开发：**只有"从头再做一遍"才变**
```

**来源**：所有者提出（原话见 `开发日志.md` §1.49.3）。

**⚠️ 中间那段与阶段号一致，是这套方案最有用的一半**：
"这个构建来自哪个阶段"写在屏幕上，而"里面是什么"离 `开发计划.md` 的一节只有一步。
一个 `1.4.2` 这样的版本号需要一次谁也不会去做的查表。

**⚠️ 版本号统一采用两位的段**（`1.10.01`，不是 `1.10.1`）——
这样三段宽度固定，`1.09.72` → `1.10.01` 是同一把尺子上的两个值。

### 1.2 ⚠️ 每次更新都要做两件事

**所有者定的规矩（原话）**：

> **"我需要提醒一下以后你每次更新一次，就把版本号加1。"**
>
> **"在之后也加一条规则：就是每次更改都要做版本更新，并且写清楚这次版本更新做了什么，写入文档。"**

**所以每一次代码改动都必须**：

| # | 动作 | 位置 |
|---|---|---|
| 1 | **把 `APP_VERSION` 的最后一段 +1** | `apps/web/src/lib/version.ts` |
| 2 | **在本文档下面追加一条记录**，写清改了什么、为什么 | `docs/开发过程记录/版本记录（1.10）.md` |

**⚠️ 为什么这条规矩是必要的**：

> **一个不动的版本号，无法用来区分两个构建——而那是它唯一的用途。**
> **这个项目已经在"分不清你在跑哪一版"上花了三轮**（`开发日志.md` §1.48–1.49）。

### 1.3 一条记录要写什么

**最少三件事，缺一不可**：

1. **改了什么**——具体到文件或行为；
2. **为什么**——是哪个报告、哪条证据、哪个判断；
3. **怎么验证的**——测试数量、真机结果，或"待真机确认"。

**⚠️ 并且允许写"这一版没修好"**：

> **一个把"未解决"写成"已解决"的记录，比没有记录更糟——下一个人会从错误的地方开始。**
> （见 `归档/离线与同步-设计决定.md` §4 的做法。）

### 1.10.23 —— **S12-A：管理员允许名单真正独立 + 上线前安全收尾**（2026-10-14）

**所有者指示**：*"S12-A 阶段：生产部署前的安全与发布准备。"*
并明确指出管理员实现的一个核心问题：*"授权记录和允许名单并没有完全分离……
如果未来误将另一个合格账号加入 `admin_grants`，在默认的 first-batch 范围下，
它可能同时通过所谓的两重检查。"*

> **完整记录见 [`S12-A上线前安全与发布准备.md`](S12-A上线前安全与发布准备.md)。**
> 本节只记"改了什么 / 为什么 / 怎么验证"。

#### 一、⚠️ 核实确认：所有者指出的问题属实

1.10.22 的 `isOnAdminAllowList()` 判定是「账号在资格区间内 **且** 持有有效 `admin_grants`」——
**它是从 `admin_grants` 派生的**。于是：

- 两个函数、两个开关、两个调用点，**但只有一个数据来源**；
- **一次授权同时满足两半**，两道检查**永远不可能不一致**；
- 运维只有**一个把手**（`ADMIN_ALLOWLIST_SCOPE` 环境变量）。

**今天不能直接利用**（`admin_grants` 里只有 `naeor`），**但一次打错 UUID 的 `admin:grant`
就会造出一个看起来通过了两道检查的管理员。**

#### 二、改了什么

| # | 改动 | 文件 |
|---|---|---|
| 1 | **新增 `admin_allowlist` 表**（独立授权表；`user_id` 主键、`listed_at/by`、`revoked_at/by`、`note`；外键 `Cascade`）**迁移不插入任何行** | `prisma/migrations/20261014140000_admin_allowlist/` |
| 2 | **`isOnAdminAllowList` 改读该表**，**不再从 `admin_grants` 派生**；**删除 `ADMIN_ALLOWLIST_SCOPE`** | `admin/guard.ts` |
| 3 | **判定顺序调整**：账号层面的三个事实（存在 / 非演示 / 资格）先判，两道独立检查后判——否则既不合格又不在名单的账号会被报成"不在名单"，而下一个读者会以为资格规则不可达 | `admin/guard.ts` |
| 4 | **两个新命令**：`pnpm admin:allow` / `pnpm admin:disallow`（**都不写对方的表**） | `scripts/allow-admin.ts`、`disallow-admin.ts`（新） |

可审计；多实例天然一致；**改名单不需要重启容器**——而"现在就把这个账号去掉"

**`admin:grant` 之后必须再 `admin:allow`。** 本轮加上允许名单表之后，

**这是设计在工作，不是故障。** 补上 `admin:allow` 后实测 `ADMIN OK`。

#### 二、⚠️ 最值得记的一条：**一个 token 干两件相反的事**

所有者正是预判了这一点：*"如该 token 同时用于装饰性元素，请检查是否需要保留单独的低强调颜色."*

.text-section-title {

  font-weight: var(--tw-font-weight, var(--text-section-title--font-weight));
}

### 1.10.08 —— 开始页精简 + 每本账的齿轮面板 + 海浪提示词动画（2026-10-13）

**所有者给的整份规格**，核心三条：

> **"将开始页重新明确为一个简洁、独立、具有品牌特色的「账本选择与管理空间」。"**
> **"点击齿轮不得自动切换当前账本……所有后续操作必须准确携带目标账本 ID。"**
> **"不要改动关于海浪的任何动画机制。关于动画部分，你需要改动的只有向上拉的提示词和箭头。"**

#### 一、⚠️ 海浪提示词的真正原因：**不是淡出，是被容器裁掉**

规格描述的现象是 *"跟着海浪移动，最后被其他图层遮挡或藏到海浪后面"*。读 CSS 后确认这是**字面准确**的：

```css
.space-cue-window { height: calc(20dvh * (1 - var(--p))); overflow: hidden; }
```

**提示词被装在一个"高度随展开进度收缩到 0"并且 `overflow: hidden` 的盒子里——它不是淡出的，是被物理裁掉的。**

**修法（只动提示，不动海浪）**：

| | 之前 | 现在 |
|---|---|---|
| 定位 | 收缩盒里的 flex 兄弟 | **脱离盒子的覆盖层**（`position: absolute; inset: 0`），无高度耦合，**没有被裁的可能** |
| 透明度 | 无（靠盒子裁剪） | **`opacity: clamp(0, calc(var(--p) * 14 - 12), 1)`** |
| 层级 | 在海浪之下 | **`z-index: 3`，高于海浪的 2**——否则它会被它正在提示的那片海盖住 |
| 触摸 | 展开时仍可点 | **不可见时 `pointer-events: none` + `inert`** |

**⚠️ 透明度曲线与要求一一对应**：`--p` 是**同一帧里写进 DOM 的那个数**（`useSpaceTransition` 每帧写），
所以 CSS 插值**在构造上就不可能不同步**——规格里禁止的"与海浪进度无关的固定延迟"根本没被引入。

| `--p` | 0 | 0.5 | **0.85** | 0.93 | 1 |
|---|---|---|---|---|---|
| 透明度 | 0 | **0** | **0**（"海浪先基本完成展开"） | 0.64 | 1 |

**⚠️ 反向拖动就是沿同一条线走回去**，连续、不跳变、无阈值可抖。

#### 二、账户头像：只属于收缩态，同样由 `--p` 驱动

绿色区右上角，`opacity: clamp(0, calc(var(--p) * 5 - 3.6), 1)` —— **完全展开时不可见也不可点**
（`visibility` 跟着透明度走），向收缩态过渡时淡入。**没有新增收缩态海浪高度**（它定位在已有的海洋带内）。

#### 三、开始页：从"管理页"回到"账本空间"

**移除**：原先摆在开始页上的**整个「分享这本账」模块**（权限 / 有效期 / 人数上限 / 生成 / 管理 / 撤销）。
**它没有消失，而是进了齿轮面板后的专门页面**——规格点名要求的位置。

### 1.10.07 —— S11 第一阶段补充：协作页详细布局规范（2026-10-13）

**所有者给的整份补充规格**，核心是一条**容器规则**：

> **"摘要型信息保留卡片；可直接操作的功能区采用'半开放式'设计；浏览型列表保留一个总外框，但内部不再套小卡片。"**
>
> **"当前协作页空间利用率偏低，存在明显的'盒子套盒子'问题。"**

#### 一、⚠️ 先确认问题真的存在：**"框套框"是代码结构，不是观感**

动手前先读实现，确认他看到的不是错觉：

```
SectionFrame（总外框）
  └── HistoryList 自己又画了一个 rounded-card border  ← 第二层框
        └── 才是一条记录
```

`Section` 画一张卡，`HistoryList` 在卡**里面**再画一张卡——**两圈边框包着两行字**。
留言区同样：`Section` 的卡 + 留言列表自己的卡。

**这不是美术问题，是容器层级问题**，所以修法也是结构性的。

#### 二、新增 `SectionFrame`：把三条容器规则写成一个组件

| 内容类型 | 容器 | 组件 |
|---|---|---|
| 摘要对象 / 概览 | **卡片** | `Section`（当前账本、成员、账本信息） |
| 小列表 / 复合功能区 | **一个总外框** | **`SectionFrame`**（编辑记录、留言） |
| 局部操作区、外框内的条目 | **直接排列** | 传进去的子元素**不加边框** |

**`SectionFrame` 的标题与右侧操作在框外**（所有者：*"标题和操作在总外框外部；右侧操作用绿色文字，不做大按钮"*），
并配一个 **`FrameAction`**，让六处次级入口（`查看全部` · `展开完整对话` · `新消息 N 条` · `账本详情` · `切换账本` · `成员管理`）
**不可能有一处又变成实体按钮**。

**⚠️ 去框靠 `embedded` 开关，不是复制一份列表**：`HistoryList` 在完整历史页仍自己画框（那里它**就是**页面），
在协作页里传 `embedded` 就不画——**一个列表，两种外框归属**。复制一份会是"同一个服务端句子有两个渲染器"（`教训.md` §8.12）。

#### 三、留言区：两半 + 中间一条线

按所有者 §5 的结构重做：

| 部分 | 做法 |
|---|---|
| **显示区** | 最近 **2 条**，**每条不再有独立卡片**；行间轻分隔线；`bg-canvas/60` 轻微区分（他允许的"浅灰/浅绿灰"） |
| **中间横线** | **一条真的 `border-t`**——他的原话：*"它负责告诉用户'上面是内容，下面是操作'"* |
| **操作区** | **左输入框 + 右小按钮**，`flex-1` vs `shrink-0` |
| **输入框** | `rows={1}`、浅底、默认细边、聚焦才出绿色细框——*"避免'框中框'的压迫感"*；占位 `写一条留言…` |
| **发送按钮** | `px-3.5 py-2 text-xs`，**明显小于**邀请成员的 `px-4 py-2.5 text-sm`——*"它是'局部操作按钮'，不是一级主操作按钮"* |

**⚠️ 新加了回车发送**（Shift+Enter 换行）。手机上的回车键就是"发送"，一个忽略它的多行框会显得坏掉。

#### 四、"新消息 N 条"

| 规则 | 决定 |
|---|---|
| 含义 | 自**上次查看本账留言**以来新增的条数 |
| 存哪 | `localStorage`，**key 里带账本 id** |
| 首次进入 | **算 0**（否则第一次打开就是"新消息 47 条"——那不是新消息，那是历史） |
| 没有新消息 | **隐藏**（他允许），而 `展开完整对话 ›` **始终显示** |
| 边界 | 严格 `>`：**当时正在看的那条不算新的**，否则每次访问都报最后一条，徽标变成噪音 |

**⚠️ 为什么存在客户端**：服务端的"每人已读"会是**同一件事的第二份记录**（`教训.md` §8.7），
而它只为这一台设备的显示服务。**⚠️ 为什么 key 必须带账本**：一个共用时间戳会让
**B 账本继承 A 账本的已读状态**——在 B 里写的留言会被报成"已读"，**人不会被告知**。

#### 五、⚠️ 一个我自己写出来又测出来的真 bug

第一版用了 **`window.localStorage`**。浏览器里 `window` 与全局是同一个对象，
**但这个项目的 Web 测试故意跑在纯 Node 里、没有 DOM**（`vitest.config.ts`：
*"Components are checked by rendering them to static markup — that needs no DOM, no jsdom."*）。

**`window` 在那个环境里不存在，整个留言板会直接渲染不出来。**
改成**裸全局 + `typeof` 守卫**。**这是测试抓到的，不是 review 抓到的**——
也正是"为什么这条规则值得有测试"的例子。

（同一轮里还有**一次是测试自己错**：我把"跨账本隔离"的断言对象写反了，实现是对的。）

#### 六、单人状态：邀请成员变成页面内操作

所有者把它归入第三类容器（*"一级页面内的局部操作区域……直接开放式结构"*）：
现在是 **`SectionFrame bare`**——一个标题、一句话、**一个输入框 + 一个按钮**，**没有外框**
（输入框自己就有边，再包一层就是框套框）。回车即发。

**⚠️ 完整流程没有消失**：`/ledger/invite` 仍在，负责**选权限**、看已发出的邀请、看成员列表；
页面上留了一行绿字入口说明这件事。**一条省掉谨慎路径的快捷方式，比它省下的那一步更贵。**

**我也提过用 `is_admin` 更简单，但所有者没有选它**。
所以规则就是"**编号区间**"，不是"是不是管理员"——
**这样以后把某人提为管理员，不会顺手把他的通知上限也一起取消。**
`quota.ts` 的注释里写了 **"不要把它简化成 `isAdmin`"**。

### 1.10.03 —— 建了新账本却进不去（2026-10-13）

**所有者报告**：

> **"我用妈妈账户创建新的账本'共享账本'时，不管是点击创建并进入，还是事后在账本空间页面尝试点击
> 都无法进入，还是会进入我的账本。"**

**一句话结论**：**账本建成了、服务端也切对了，是客户端把"当前账本"钉死在第一本上，**
**于是"进入另一本账"变成了一扇单向门。**

**改了什么**

| 文件 | 改动 |
|---|---|
| `apps/web/src/lib/queries.ts` | **`useActivateBook` 增加 `onSuccess`：把新账本写进 `current-book`。** 这是缺的那一步。 |
| `apps/web/src/lib/currentBook.ts` | **`setCurrentBook()` 改为返回写入的 Promise**（原先 `void writeValue(...)` 丢弃了它）。理由见下。 |
| `apps/web/src/lib/currentBook.test.ts` | **再补 2 条回归测试**（共 7 条） |

**为什么**（完整因果链，每一步都实测过）

1. **账本确实建成了**：`40000003 共享账本`，`mama` 是它的 editor，0 笔流水。
2. **服务端每一步都对**：`POST /books/40000003/activate` → **200**；此后带"新账本"的请求头 → `/ledger` 返回 `40000003 共享账本`。
3. **缺口在这一步**：`setCurrentBook()` **只在 `useLedger()` 的查询函数里被调用**，
   **激活账本时从不调用**——于是服务端记住了新账本（`users.lastBookId`），**而客户端没有**。
4. **于是死循环**：
   - `enterLedger` 结尾是 `window.location.assign("/")`（整页刷新，刻意的）；
   - 刷新后启动代码从设备读回 `current-book`，**还是 `40000001`**，并把它作为请求头发出去；
   - `/ledger` 遵守请求头，于是返回**旧账本**的元数据；
   - 而 `useLedger` 顺手 `setCurrentBook(旧账本.id)`——**把它又钉了回去**。
   - 所以**每一次尝试都走同一条路，结果永远一样。**
5. **⚠️ 而且这里还有一个真实的竞态**（顺手一起修了）：
   `setCurrentBook` 原先 `void writeValue(...)`，
   而 `storage.ts` **只在 IndexedDB put 成功之后**才更新同步镜像——
   所以"先写、再 `location.assign`"是一次真的竞速：**输了，刷新就会把刚离开的账本读回来。**
   现在 `onSuccess` 返回这个 Promise，TanStack 会等它，**写入落地之后才跳转**。

### 1.10.02 —— 换账号后看到上一个账号的账本（2026-10-13）

**所有者报告**：

**一句话结论**：**服务端没有问题、数据也没有问题，是客户端在会话失效时没有清掉"当前账本"。**

**改了什么**

| 文件 | 改动 |
|---|---|
| `apps/web/src/auth/AuthProvider.tsx` | 把"离开一个账号时要清掉的本地状态"抽成 **`forgetLocalState()`**：`forgetUser()` → `clearQueryCache()` → `forgetCurrentBook()` → `setOfflineAccount(null)`。<br>**三条路径现在都走它**：`logout()`、**会话失效（401）**、**登录时发现换了账号**。<br>另外改正了一处**过期注释**（它还写着"每个账号只允许一台设备登录"——那条规则早已被所有者删除）。 |
| `apps/web/src/lib/currentBook.test.ts` | **新增 5 条回归测试**（这个模块原先没有测试）。 |

**为什么**（完整因果链，每一步都核实过）

1. **数据是干净的**：`mama` 只属于 `40000001`、`naeor` 只属于 `40000000`；`40000000` 的 152 笔全是 `naeor` 记的、`40000001` 的 118 笔全是 `mama` 记的。**零串账。**

5. **登录路径是第二道防线**：`login()` 现在会比对"之前记住的账号"，**换人就清**；换回自己则保留离线副本（否则会把只是被登出的人的数据一起删掉）。
