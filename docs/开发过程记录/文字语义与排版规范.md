## 0. 一句话结论

**字号本身并不乱——乱的是"同一个职责用了两种写法"，以及"同一个字号配了两种行高"。**

三个最具体的证据：

| 现象 | 实测数据 |
|---|---|
| 同一职责、两种样式 | 功能区标题 `<h2>` **一半是 `14px/500` 深色、一半是 `12px/400` 灰色** |
| 同一字号、两种行高 | `text-xs` 共 **186 处，其中 53 处额外加了 `leading-relaxed`** → 同样的 12px，行高 **16px 或 19.5px** |
| 同一元素名、两种语义 | 后台页标题、二级页标题、用户名**都是 `20px/600`**，但后者缺 `tracking-tight`（字距差 0.5px）|

**所以要做的是"把职责命名下来"，不是"把字号改一遍"。**
本方案的目标是：**迁移完成后视觉几乎不变**（例外见 §9）。

## 1. 当前全站文字样式的实际使用情况

### 1.1 字号类使用次数（静态扫描，84 个 tsx）

| 类 | 实际值 | 次数 | 说明 |
|---|---|---|---|
| `text-xs` | 12px / lh 16px | **186** | 最常用——辅助说明、标签、行内元信息 |
| `text-sm` | 14px / lh 20px | **175** | 最常用——正文、标题、按钮 |
| `text-base` | 16px / lh 24px | 32 | 金额、少量强调 |
| `text-lg` | 18px / lh 28px | 7 | 极少 |
| `text-xl` | 20px / lh 28px | 6 | **三个不同职责都在用** |
| `text-2xl` | 24px / lh 32px | 5 | 余额、少量标题 |
| `text-3xl` | 30px / lh 36px | 3 | 记账金额输入 |
| `text-[11px]` | 11px | **24** | 底部导航、徽标、账号编号 |
| `text-[10px]` | 10px | 5 | 图表刻度、热力图 |
| `text-[15px]` | 15px | 7 | `Button`、对话框 |
| `text-[16px]` | 16px | 5 | **输入框（防 iOS 缩放），见 §5** |

### 1.2 字重

**全站只用两个**：`font-medium`(500) **59** 次、`font-semibold`(600) **20** 次。
没有 `font-normal`、没有 `font-bold`。**这一点是干净的**，不需要新层级。

### 1.3 行高

`leading-relaxed` **88 次**，`leading-none` 2 次，`leading-snug` 0 次。

**⚠️ 问题在于它和字号的关系没有约定**：

| 组合 | 次数 | 实际行高 |
|---|---|---|
| `text-xs` | 186 | 16px |
| `text-xs leading-relaxed` | 53 | **19.5px** |
| `text-sm` | 175 | 20px |
| `text-sm leading-relaxed` | 30 | **22.75px** |

**同一个 12px 的辅助说明，有的行高 16px、有的 19.5px，差别是肉眼可见的。**

### 1.4 颜色类

| 类 | 值 | 次数 |
|---|---|---|
| `text-muted` | `#6b7f76` | **295** |
| `text-ink` | `#24312b` | **165** |
| `text-white` | — | 44 |
| `text-brand-dark` | `#447d63` | **42** |
| `text-danger` | `#b8574f` | 22 |
| `text-brand` | `#55997a` | 14 |
| `text-category-ink` | `#3f7059` | 1 |
| `text-warn` / `text-accent-ink` | — | 0 |

**颜色体系是健康的**：`text-muted` 与 `text-ink` 覆盖了绝大部分，且**全部走 token**。

### 1.5 数字排版

`tabular-nums` **12 处**，分布在 9 个文件（`DetailPage` 6、`SummaryPanel` 3，其余各 1）。
`font-mono` **24 处**——用于账号编号、交易编号、邀请码。

**⚠️ 两者职责不同，但现在没有区分规则**：`tabular-nums` 是"数字要竖向对齐"，`font-mono` 是"这串字符要逐字读"。

## 2. 主要重复与不一致问题

### P1 ⚠️ 功能区标题有两种互不相干的样式（**最该先修**）

| 样式 | 用在哪 |
|---|---|
| `text-sm font-medium text-ink`（14px/500 深色） | `Section.tsx`、`SectionFrame.tsx`、`LedgerInvitePage`、`StartBookPages`、`ProfilePage`、`LedgerSpacePage` |
| `text-xs text-muted`（12px/400 灰色） | `AddEntryPage` ×6、`EntryDetailPage` ×7、`SettingsPage` ×4、`ExportPage` ×3、`DownloadMorePage` ×3、`ManagePages` ×2、`RecordPage`、`ScanPage`、`LedgerMorePage`、`ConflictScreen` ×2 |

**两者都是 `<h2>`。** 也就是说：**机械上同一个标签，视觉上两个层级**——
而所有者明确要求 *"不要通过覆盖大量全局 HTML 标签来强制统一不同语义的文本"*。
**这里的修法不是统一它们，而是承认它们是两个职责并各自命名。**

### P2 ⚠️ 三级标题与用户名共用一个样式，但只有一个带字距

| 位置 | 实测 |
|---|---|
| 一级页标题（`TabPageHeader`） | 20px / 600 / **ls −0.5px** |
| 二级页标题（`InnerPage`） | 20px / 600 / **ls −0.5px** |
| 账户页用户名（`MePage`） | 20px / 600 / **ls 0** |

**⚠️ 第三行不是标题，是用户数据。** 它借用了标题的字号，于是既没有标题的字距，
又有了和标题一样的字号。**这是一个"临时借用"变成"既成事实"的例子。**

### P3 ⚠️ 无样式 `<h2>` 继承父级字号

`AboutPage` ×3、`LegalPage` ×1 写作 `<h2 className="font-medium">`——**没有字号类**。

**实测结果是 `14px / 500 / 22.75px`**，即**继承了父容器的 `text-sm`**。
所以它们**看起来和正文一样大**，层级只靠 500 字重表达。

**⚠️ 这一条不改也是安全的**（Tailwind 4 的 preflight 把标题的 `font-size` 设为 `inherit`，
所以不会有浏览器的 24px 意外）。但它**不能算一个有规格的标题**——
换到另一个父容器里字号就会变。

### P4 ⚠️ 12px 辅助文字两种行高

`text-xs` 无 `leading-relaxed` → **16px**；加了 → **19.5px**。
**两种都在大量使用（133 : 53）**，且分布在同一类内容上（错误提示、说明段落、列表说明）。

### P5 ⚠️ `text-[11px]` 已是事实上的第六个字号（24 处）

底部导航标签、`CurrentBookCaption`、历史编号、成员角色徽标、通知徽标、离线状态、
分享链接状态、下载管理、软件更新……**它承担的是"最小可读文字"这个明确职责**，
但**它不是 token，只是一个任意值**——所以它无法被查到、无法被调整。

### P6 ⚠️ 数字排版有 4 套规格，且没写下来

| 位置 | 实测 |
|---|---|
| 明细页余额 | 24–30px（独立规格，见 §5） |
| 统计汇总金额 | 16px / **500** / tabular-nums |
| 统计图例金额 | 12px / 400 / tabular-nums |
| 图表刻度 | 10px / 400 / 无 tabular-nums |

**⚠️ 前三者该共享"数字排版规则"（等宽数字、字距、对齐），第四者不该**（刻度是静态标签）。

### P7 次级绿色文字操作有 3 种字号

| 实测 | 位置 |
|---|---|
| 12px / 400 / `brand` | `查看全部 ›` |
| 12px / 400 / `brand-dark` | 卡片内的小链接 |
| **14px / 400 / `brand`** | `新建账本` |

**所有者已明确要求统一为绿色文字**（1.10.07：*"请把这些全部做成实体按钮……优先使用绿色文字 + 轻量交互状态"*），
但**字号不统一**：`新建账本` 比 `查看全部` 大 2px。

### P8 常规按钮有两种规格

| 位置 | 实测 |
|---|---|
| `Button.tsx` primary/secondary | **15px / 500** |
| 普通 14px 按钮（`近 30 天`、`人民币`） | 14px / 400 |
| `邀请`、`发送` 等局部按钮 | 14px / **500** |

**⚠️ 14px 的按钮一半是 400、一半是 500**，取决于作者当时写没写 `font-medium`。

## 3. 建议的语义角色

**⚠️ 命名原则：按职责命名，不按外观命名。** `text-xs` 描述外观，`辅助说明` 描述职责——
只有第二种在改了字号之后还成立。

| # | 语义角色 | 建议 token | 字号 | 字重 | 行高 | 颜色 | 现用量 |
|---|---|---|---|---|---|---|---|
| 1 | **页面标题** | `--text-page-title` | 20px | 600 | 28px | 白 / `ink` | 一级页 + 二级页 |
| 2 | **功能区标题** | `--text-section-title` | 14px | 500 | 20px | `ink` | `Section` 等 |
| 3 | **小标签标题** | `--text-label-title` | 12px | 400 | 16px | `muted` | 表单/设置分组 |
| 4 | **卡片标题** | `--text-card-title` | 14px | 500 | 20px | `ink` | 与 #2 同规格，**分开命名** |
| 5 | **正文** | `--text-body` | 14px | 400 | 20px | `ink` | 最大一类 |
| 6 | **正文·宽松** | `--text-body-relaxed` | 14px | 400 | 22.75→**23px** | `muted`/`ink` | 说明段落 |
| 7 | **辅助说明** | `--text-helper` | 12px | 400 | 16px | `muted` | 第二大 |
| 8 | **辅助说明·宽松** | `--text-helper-relaxed` | 12px | 400 | 19.5→**20px** | `muted` | 错误/长说明 |
| 9 | **微文字** | `--text-micro` | 11px | 400 | 16px | `muted`/`brand-dark` | **取代 `text-[11px]`** |
| 10 | **次级文字操作** | `--text-link` | 12px | 400 | 16px | `brand` | `查看全部 ›` 等 |
| 11 | **主按钮文字** | `--text-button-lg` | 15px | 500 | 22.5px | 白 / `brand-dark` | `Button.tsx` |
| 12 | **常规按钮文字** | `--text-button` | 14px | **500** | 20px | 白 / `brand-dark` | 统一到 500 |

### 3.1 📌 与我给的参考值的差异，以及为什么

所有者给的初步参考是「一级页 24px / 二级页 22px / 功能区 17px」。
**建议不采用这三个数字，理由是同一条**：**它们都会显著改变现有外观。**

| 参考值 | 实测现状 | 建议 | 理由 |
|---|---|---|---|
| 一级页标题 24px | **20px** | **保持 20px** | 24px 会让五个一级页的绿色头部全部变高，而头部高度刚刚在 1.10.11 统一过 |
| 二级页标题 22px | **20px** | **保持 20px** | 同上；且一级/二级现在本就同规格，没有非分不可的理由 |
| 功能区标题 17px | **14px 或 12px** | **保持 14px / 12px 两个角色** | 17px 是本次改动里最大的一处视觉变化，违反"避免一次重构改变整个应用的外观" |

**⚠️ 这三条建议是"保持现状并命名"，不是"否定参考值"。**
如果所有者要的是**向上调整层级**，那是一次**有意的视觉重设计**，
应当单独作为一版来做（并接受所有页面头部变高、卡片标题变大），而不是混在"统一"里悄悄发生。

### 3.2 ⚠️ 需要所有者裁决的两点

1. **功能区标题要不要合并成一个？**
   建议**不合并**：`Section`（14px/500）与 `SettingsPage`（12px/400）服务的内容不同——
   前者是**内容区**里的分组，后者是**设置列表**的分组。
   **但如果所有者认为"看起来不一致"，那就是两次设计决定，应当由他定。**
2. **`text-sm`(14px) 与 `text-base`(16px) 的边界**——
   16px 目前用在金额和少量强调上，**边界是模糊的**（32 处）。

## 5. 应当保留的特殊例外

**所有者 §7 列了 9 项不能重做。以下逐项说明"为什么它必须是例外"**：

| # | 例外 | 为什么不能纳入统一 |
|---|---|---|
| 1 | **开始页海浪与提示动画** | 字号是 `calc(2.1rem - 0.7rem * var(--p))`——**它随展开进度连续变化**，不是一个字号。取一个 token 反而会锁死动画 |
| 2 | **明细页动态头部** | 同上，标题与日期的位置/尺寸随 `--p` 插值 |
| 3 | **明细页余额数字** | 30px/600 是为"一眼看清余额"服务的，与列表里的金额不在一个阅读距离上。**共享数字排版规则，不共享字号** |
| 4 | **分析页图表** | 刻度/图例/浮层受 SVG 尺寸与密度约束，10px 是为在 390px 宽内容纳 12 个刻度 |
| 5 | **账本／协作留言区** | 1.10.07 刚定的两半结构，行高与内边距是成套的 |
| 6 | **全屏留言页** | 输入区行高必须与键盘/滚动配合 |
| 7 | **底部导航** | `text-[11px]` 是为 5 个标签在 390px 下不换行选的；**它应成为"微文字"的基准，而不是被改** |
| 8 | **危险操作状态** | `text-danger` 是语义色，已走 token；字号随所在容器 |
| 9 | **登录/注册/恢复流程** | `AuthLayout` 是 `text-lg font-semibold`——**它是独立版式**（居中、无导航），与页面标题不同职责 |

### 5.1 ⚠️ 两条技术例外（必须保留，否则会出 bug）

| 例外 | 原因 |
|---|---|
| **输入框 `font-size: 16px`**（`index.css` L263-267，`input, select, textarea`） | **iOS Safari 在字号 <16px 时会在聚焦时自动放大页面**。这条规则看着像疏漏，**它是防缩放的关键**，绝不能因为"统一成 14px"而删掉 |
| **`font-mono`（25 处）** | 账号编号、交易编号、邀请码要**逐字读**，等宽是功能而非装饰 |
| **`tracking-widest`/`tracking-wider`（邀请码、品牌名）** | 邀请码要抄写，字距是可用性；**开始页品牌名** `letter-spacing: 0.16em` 是品牌 |

**⚠️ 上面那条品牌字距在 2026-10-14（1.10.20，改名 Libellum → Libevra）被核实过一次，结论值得留下**：

| | |
|---|---|
| **规范原来写的** | "`Libellum` 的 `5.376px` 是品牌" |
| **代码里实际是** | `index.css` 的 `.space-brand-name { letter-spacing: 0.16em }`——**相对值，随字号缩放**（`2.1rem` 时 = 33.6px × 0.16 = **5.376px**，与旧数字一致） |
| **所以改名会不会动它** | **不会。** `em` 与字母个数无关，`Libevra` 渲染出来的字距仍是 `0.16em`。**那个 `5.376px` 从来只是 `2.1rem` 下的换算结果，不是为 `Libellum` 这个拼写定的值** |
| **要做的事** | 名字改写，**数值一行不动**；上次核对测得 `2.1rem` 处左右各 0，收缩态左边缘由 `left: var(--space-content-left)` 决定，与名字长短无关 |

**⚠️ 教训**：把一个**相对值**的换算结果记进规范，会被下一次改名读成"这个数字属于那个名字"。规范该记的是 `0.16em`。见 `Libevra品牌迁移记录.md` §8。

## 6. 建议采用的代码组织方式

### 6.1 首选：Tailwind 4 的 `--text-*` 命名空间

Tailwind 4 用 **`@theme` 里的命名空间**生成工具类：`--text-*` → `text-*`，`--leading-*` → `leading-*`。
本项目**已经在用 `@theme`**（颜色、圆角、`--font-sans` 都在里面），
所以这是**在既有体系内加一段，而不是建一套平行体系**——正是所有者要的第 3 条。

建议写成（示意）：

```css
@theme {
  /* 语义字号。名字说职责，不说外观。 */
  --text-page-title: 1.25rem;      /* 20px */
  --text-page-title--line-height: 1.75rem;
  --text-page-title--letter-spacing: -0.025em;

  --text-section-title: 0.875rem;  /* 14px */
  --text-section-title--line-height: 1.25rem;

  --text-body: 0.875rem;
  --text-body--line-height: 1.25rem;

  --text-helper: 0.75rem;
  --text-helper--line-height: 1rem;

  --text-micro: 0.6875rem;         /* 11px —— 取代 text-[11px] */
  --text-micro--line-height: 1rem;
}
```

**这样 `行高` 与 `字号` 绑在同一个 token 上**——P4（同一个 12px 两种行高）在结构上就不可能再发生。
用法是普通的 `text-section-title`，**不是新组件、不是运行时计算**，满足第 4、5、6 条。

### 6.2 ⚠️ 实施前必须先验证的一件事

**`@theme` 只接受自定义属性与 `@keyframes`**，而本项目**已经因此被烧过一次**：

> `index.css` L151-161 明确记录：把一条普通 class 规则放进 `@theme` 会让**整个 CSS 编译失败**，
> Vite 显示错误浮层**代替整个应用**，所有路由包括登录页都打不开（`教训.md` §8.10）。

**所以第一步不是改代码，是在一个临时分支上加一个 `--text-*` token，
跑 `pnpm check:build` 确认它能编译。** 确认之后再谈迁移。
`--text-*` 是 Tailwind 4 的官方命名空间，预期可用，但**预期不等于验证过**。

### 6.3 明确不采用的方案（逐条对应所有者的要求）

| 不采用 | 对应要求 |
|---|---|
| 把全站文案搬进一个 JSON/TS | §2 —— **本方案只集中样式，不集中内容**（§10 详述） |
| 每个文本包一个 `<Text role="body">` 组件 | 第 4 条——"避免每个文本都包装进新的 React 组件" |
| 运行时 JS 算字号 | 第 5 条 |
| 引入 CSS-in-JS / 新 UI 框架 | 第 6 条 |
| 给 `h1`/`h2`/`p` 写全局样式强制统一 | 第 7 条——**P1 恰恰证明同一标签有两个职责** |
| 手写一套 `.type-body { }` 平行于 Tailwind | 第 3 条 |

## 10. ⚠️ 为什么集中管理**样式**，却绝不能集中管理**文案**

这是所有者最强调的一条，值得写清楚理由，而不只是照做。

### 10.1 「字号」是一个设计决定，「文案」是一个业务事实

**字号 14px** 是设计者对所有"正文"的统一回答——**一份，可以放在一处**。

**「我的账本」** 不是设计决定。它是：
- **用户数据**（他给账本起的名字）；
- 或者是**默认值**（`DEFAULT_BOOK_NAME`，服务端常量）；
- 或者是**后端返回的字符串**（错误消息、分类名）。

**这三样都不属于前端样式系统。** 把它们搬进一个 JSON，等于**在前端复制了一份服务端的事实**——
而 `教训.md` §8.7 与 §8.12 讲的正是这件事：**同一件事的第二份记录，迟早会不一致。**

### 10.2 具体的四类危害

| 类别 | 如果集中管理会怎样 |
|---|---|
| **用户数据**（账本名、用户名、备注） | 它们**根本不"存在"于代码里**，只在数据库里。放进 JSON 就要么是空壳，要么是与数据库竞争的第二来源 |
| **服务端消息**（错误提示、`summary` 句子） | 已在服务端组装（`history.ts` 明确写了"句子是服务端的"）。**搬到前端 = 两个地方都能改这句话** |
| **动态状态文字**（今天 16:48、共 N 条、¥6,633.09、新消息 N 条） | 它们是**计算出来的**，不是常量。放进 JSON 只能放模板，于是多了一层间接 |
| **后端返回的分类/标签名** | 用户自己建的，随数据变化。**前端不可能有一份完整列表** |

### 10.3 一句话

> **集中"要对齐的东西"，不集中"要各自正确的东西"。**
>
> 字号错了，是所有页面一起错——**一处定义、一处修**。
> 文案错了，是那一处业务逻辑错——**它必须留在能正确产生它的地方。**

### 10.4 ⚠️ 一个需要说明的前提：目前**没有**国际化机制

我检查了前端：**没有 i18n 框架，没有语言包**。
所以"文案应该由国际化机制负责"这一条**当前是空头承诺**——
现阶段文案就是**内联在组件里**，这是既成事实。

**建议**：本轮**不动文案的管理方式**（符合所有者 §2 的最后一句），
但把"将来要引入 i18n"记为独立事项，**不与文字样式混在一起做**。

## 11. 后续：改一处，全站同步

**迁移完成后，调整"功能区标题"的字号只需要改一行：**

```css
@theme {
```

没有这条检查，token 会在几个月内被新的任意值绕过——**`colors.test.ts` 的存在就是这个道理的先例。**

## 12. 本轮实施记录（2026-10-13，第二轮）

> **本节是实施结果。§0–§11 是第一轮的审计与方案，保留原样以便对照。**

### 12.1 ✅ 首先验证了一件曾被烧过的事

第一轮把「先验证 `@theme` 能否接受 `--text-*`」列为**动手前提**（§6.2），因为本项目曾因
把普通 class 放进 `@theme` 而**整个 CSS 编译失败、所有路由打不开**。

**结论：Tailwind 4.3 的 `@theme` 接受 `--text-*` 命名空间。**

实测（从编译产物中读出，非推测）：

```css
.text-section-title {
  font-size: var(--text-section-title);
  line-height: var(--tw-leading, var(--text-section-title--line-height));
  font-weight: var(--tw-font-weight, var(--text-section-title--font-weight));
}
```

**⚠️ 三个细节值得记下来：**

1. **字号 / 行高 / 字重绑定在同一个 token 上**——这正是本轮要的效果：**"改了字号忘了改行高"在结构上不可能再发生。**
2. **工具类是按需生成的**：没人用 `text-section-title` 时，编译产物里**连变量都没有**。
   所以「查编译产物里有没有这个类」**不能**用来判断 token 是否被接受——那是我一开始的判断错误。
3. **Tailwind 通过 `var(--tw-leading, …)` 读取行高**，那是它用 `@property` 注册的内部变量。
   **手写 class 不该依赖另一个体系的内部变量**，所以本项目的自定义 class 用**字面值 + 语义变量**，不碰 `--tw-*`。

### 12.7 ⚠️ 实施中犯的错，以及它说明的事

**我用正则批量给「所有 `Section` / `SectionFrame`」注入 `titleClassName`，结果：**

1. **破坏了 `MessageBoard.tsx` 与 `LedgerPage.tsx` 的 JSX**——
   正则把属性插进了 `action={...}` 内部，以及 `<FrameAction>` 的属性位置。
   **`typecheck` 立刻报错**（`TS2657 JSX expressions must have one parent element`），已修好。
2. **误伤了 `ChartLabPage.tsx`**——它**有自己的局部 `Section`**，不是共享组件。
   已 `git restore`，`git diff` 为空。

> **⚠️ 教训：这类"给所有调用点加一个 prop"的改动，不能靠正则。**
> **属性在 JSX 里可以出现在嵌套的任意深度**，而正则不知道结构。
> **正确做法是改默认值 + 显式列出例外**（本次最终采用的方式），而不是逐点注入。
> 所幸 `typecheck` 在几秒内就抓到了——**这也是为什么每一步都必须先跑类型检查。**

3. **⚠️ 还有一次判断错误**：我一度用「编译产物里有没有 `--text-section-title`」来判断 token 是否被接受，
   结论是"没被接受"。**那是错的**——Tailwind 按需生成，没人用就没有。
   **真正可靠的验证是"实际用一次再构建"，不是查产物。**

### 13.6 防退化：`typeScale.test.ts`

⚠️ **新增 3 条检查**（参照 `colors.test.ts` 的写法）：

1. **任意字号 `text-[Npx]` 只允许出现在白名单文件里**；
2. **每个白名单条目必须写明理由**——*没写理由的例外是一个洞，不是一个例外*；
3. **检查本身必须真的扫到文件**——*一个悄悄什么都没查的守卫比没有守卫更糟*。

**⚠️ 注释会被剥掉再检查**：本项目把决定写在代码注释里，
所以 *"以前这里是 `text-[11px]`"* 是文档不是用法——**否则守卫会惩罚解释，而正确的修法是删掉解释**。

### 13.7 怎么改一处、全站同步

```css
/* apps/web/src/index.css —— 唯一的地方 */
@theme {
  --text-section-title: 1rem;              /* 改这里 */
  --text-section-title--line-height: 1.5rem;
}
```

**改完这一个值**：所有引用 `text-section-title` 或 `.section-title` 的标题
（`Section`、`SectionFrame`、以及各页面的功能区标题）**同时变化**，
**字号与行高一起动，字重由 token 决定**。

**⚠️ 为什么这样做有效**：`Section` / `SectionFrame` 是**唯一作者**——
页面不自己写标题的字号。而 `typeScale.test.ts` 保证没有新的任意值绕过去。

**⚠️ 唯一的例外是白名单里的文件**（图表、明细页头部、输入框）——**它们被明确列出，而不是被忘记。**
