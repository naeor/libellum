## 3. ⚠️ 部署时发现的 3 个真 bug（这是本轮最有价值的部分）

**三个都不会被类型检查、单元测试或 CI 发现**，因为它们全都只在"真的构建镜像、真的启动容器"时才暴露。
这正是 `check:build` 与 CI 各自覆盖不到的那一段。

### 3.1 `prisma.config.ts` 和 `prisma/` 没进镜像 → 构建直接失败

```
schema.prisma: file not found
prisma/schema.prisma: file not found
[ELIFECYCLE] Command failed with exit code 1
```

**成因**：Prisma 7 从 `prisma.config.ts` 读 schema 位置，而 `Dockerfile.api` 的构建阶段**没有 COPY 这个文件**。
它一直"看起来没问题"，因为开发机上文件就在那里。

**⚠️ 更危险的是它的第二种表现**：迁移目录也没进镜像。`prisma migrate deploy` 找不到迁移时会
**报"没有待应用的迁移"并退出 0** —— 于是 `api` 会在一个**空 schema** 上启动，
表现是"接口全 500"，而不是"迁移失败"。**一个退出码为 0 的假成功，比一个失败更难查。**

**修复**：构建阶段与运行阶段都 COPY `prisma.config.ts` 与 `prisma/`。

### 3.2 `node_modules` 不可写 → 迁移和接口都会挂

```
Error: Can't write to /repo/node_modules/.pnpm/@prisma+engines@7.10.0/...
       please make sure you install "prisma" with the right permissions.
```

**成因**：`COPY --from=build` 出来的 `node_modules` 属于 **root**，而容器以 **uid 10001** 运行。
**Prisma 在首次使用时要把查询引擎写进自己的包目录。**

**修复**：`chown -R 10001:10001 /repo/node_modules`（与 `/data` 同一个用户）。

### 3.3 ⚠️ pnpm 在每次运行脚本前重装依赖 → `migrate` 退出 127

```
Packages: +308
Error: ERR_PNPM_CMD_SHIM_CHMOD  ... Operation not permitted
[WARN] The install that runs before scripts failed, so your node_modules may be out of sync
$ prisma migrate deploy
sh: 1: prisma: not found
[ELIFECYCLE] Command failed with exit code 127.
```

**⚠️ 这个 bug 教了三件事，每一件都值得记住：**

1. **pnpm 11+ 默认在 `pnpm run` / `pnpm exec` 之前检查依赖，发现"不同步"就自己跑一次安装。**
   默认值是 `install`，而且**那句警告说的是"安装失败但我还是继续跑了命令"** ——
   于是 `node_modules` 被它自己搞坏，命令再去找 `prisma` 就找不到了。
   **退出码 127 读起来像"镜像坏了"，完全不像"依赖检查刚把依赖删了"。**

2. **⚠️ 关掉它的开关**只能**写在 `pnpm-workspace.yaml` 里。**
   我按直觉试了两次，**两次都完全无效**：
   * `ENV verifyDepsBeforeRun=false` 在 Dockerfile 里 → 无效
   * 在运行镜像里放一个 `.npmrc` 写 `verify-deps-before-run=false` → 无效，
     而且 `pnpm config get verify-deps-before-run` 仍然回答 `undefined`

   **去查了 pnpm 官方文档才确认**：pnpm 12 **只从 `.npmrc` 读认证与 registry 设置**，
   **其他所有设置都来自 `pnpm-workspace.yaml` 或全局配置文件**。
   正确写法是 `pnpm-workspace.yaml` 里的 `verifyDepsBeforeRun: false`。

   **⚠️ 这一条已经写进 `pnpm-workspace.yaml` 的注释里**，因为下一个遇到"设了但没用"的人会浪费同样的时间。
   **两个无效的尝试都被删除，没有留在仓库里假装有效**——一条不起作用的配置行比没有更糟，因为下一个人会信它。

3. **为什么在生产镜像里必须关掉**：镜像里的 `node_modules` 是 CI 验证过的、锁定的图层，
   运行时的"依赖检查"**不可能改善它，只能让容器偏离那个被验证过的产物**。
   而它偏偏在**运维命令**（`invite:create`、`admin:grant`、`admin:allow`、`db:deploy`）上触发 ——
   也就是出事时最需要它们好用的那些命令。

**修复**：`pnpm-workspace.yaml` 增加 `verifyDepsBeforeRun: false`（不是 `warn`：`warn` 仍会执行检查，
仍会在事故中途告诉运维"你的依赖可疑"，而那正是有害的部分）。

## 4. ⚠️ 部署时发现并修掉的配置问题

### 4.1 `Caddyfile` 的 `email` 空值会让**整个站点起不来**

第一次 `caddy validate` 就失败了：

```
parsing caddyfile tokens for 'email': wrong argument count or unexpected line ending after 'email'
```

**实测确认了 Caddy 的两种行为**（这是关键，因为两者看起来一样）：

| `ACME_EMAIL` | 结果 |
|---|---|
| **未设置** | `{$ACME_EMAIL:默认值}` 的默认值生效 → **配置有效** |
| **设置了但是空字符串** | 展开成**什么都没有** → `email` 没有参数 → **Caddy 拒绝整个配置** |

**⚠️ 而 Docker Compose 传的 `${ACME_EMAIL:-}` 正是"设置了但为空"。**
所以"还没填邮箱"这个最常见的状态，会让**整个站点无法配置** ——
不是"少了到期提醒"，是**账本站不起来**。

**修复**：`deploy/web-entrypoint.sh` 在容器启动时按需生成 `email` 那一行，
**只有真有地址时才写出来**。Caddyfile 格式没有条件语句，所以两行 shell 是表达条件的最小诚实做法。

**⚠️ 这正是 `caddy validate` 存在的理由。** 配置写好后一直"看起来没问题"，
因为从没被真正的 Caddy 解析过。**首次部署前 validate 一步都不能省。**

### 4.2 `web` 容器一直报 unhealthy，而站点其实完全正常

`docker inspect` 显示健康检查每 30 秒失败一次：

```
SSL routines:ssl3_read_bytes:tlsv1 alert internal error ... Connection reset by peer
```

**成因**：健康检查是 `wget --spider http://127.0.0.1:80/healthz`。
Caddy 收到 **Host 不是配置站点**的请求时，会回它自动的 HTTP→HTTPS 跳转，
于是 `127.0.0.1` 拿到 `308 Location: https://127.0.0.1/healthz`；wget 跟过去，
容器递出 `libevra.com` 的证书，握手就死了。

**⚠️ 危险的不是检查失败，而是它传达的信息**："web 不健康"正是会让运维去查一个**并不存在的故障**的信号。

**修复**：健康检查带上真实的 `Host` 头，于是不触发跳转 ——
不依赖 DNS、不需要证书，仍然走浏览器在 TLS 终止后走的同一条路径。**修复后 8 秒内 healthy。**

### 4.3 三个 shell 脚本没有执行权限

`deploy/*.sh` 从 Git 出来时在 Linux 上是 `rw-rw-r--`。已 `chmod +x`。

### 4.4 ⚠️ `www` 的 DNS 有一处拼写错误（**需要你改**）

```
实测：www.libevra.com  CNAME  →  libvera.com
                                 ^^^^^^ 应为 libevra.com
```

**`www` 的 CNAME 指向了 `libvera.com`（把 v 和 e 写反了），那个域名不存在**，
所以 `www.libevra.com` 完全无法解析（`curl` 返回 000）。

**Caddy 侧已经准备好了**：`web-entrypoint.sh` 会探测 `www.$LIBEVRA_DOMAIN` 是否解析，
解析成功才添加 `www → apex` 的跳转块。**⚠️ 探测是有意的**：为一个 DNS 不指向本机的域名申请证书
会失败，而 Let's Encrypt 对失败次数**按注册域名限流**——探一下比撞限流便宜得多。

**你要做的**：在 Namecheap 把 `www` 的 CNAME 目标从 `libvera.com` 改成 **`libevra.com`**，
然后重启一次 web 容器（命令见 §6）。

> ### ⚠️⚠️ 为什么这一节里**没有**邀请码
>
> **这个仓库是公开的。** 邀请码是**唯一**能注册账号的东西，所以**把码写进任何进仓库的文件，
> 就等于把注册开放给所有能读到这个仓库的人**——包括把它抄走的人和搜索引擎。
> 这正是 `.gitignore` 里 `docs/邀请码.md` 那条规则存在的原因。
>
> **⚠️ 本文档的第一版确实写进去了。** 提交前扫描到，已改为不写。
> 记下这件事是因为**同一个错误很容易再犯一次**：这次的形状是"为了让你方便，
> 我把码贴在这里"——而**方便正是这一类泄露的入口**。
>
> **要看当前待用的邀请码**（在服务器上）：
>
> ```bash
> cd /srv/libevra/deploy
> sudo docker compose -f docker-compose.prod.yml exec -T db \
>   psql -U libevra -d libevra_prod -c \
>   "select code, note, account_number from registration_invites where used_at is null;"
> ```
>
> **⚠️ 邀请码发出去之后就把它从对话里删掉**，不要留在聊天记录里。

**⚠️ 为什么邀请码是"预留"而不是"管理员"**：
`--reserved` 让编号落在**第一批区间 `10000000`–`10000099` 内**（这样你**有资格**当管理员），
**且 `grantsAdmin` 保持 false**。
**要成为管理员必须两步都做，缺一不可**：

```bash
docker compose -f docker-compose.prod.yml exec api pnpm admin:grant <你的 UUID> --by "owner"
docker compose -f docker-compose.prod.yml exec api pnpm admin:allow <你的 UUID> --by "owner"
```

**⚠️ 只做第一步，账号还不是管理员**——`admin:list` 会把它显示在「⚠️ 只满足一半（不会通过校验）」一栏，
而它**确实不能通过校验**。**这是设计在工作，不是故障。**

**⚠️ 本机开发库的 `naeor` UUID 没有被带到生产。** 生产管理员必须在这里重新建立。

## 6. 日常使用与维护

### 6.1 你的注册步骤

1. 打开 <https://libevra.com>
2. **用 §5 那条查询命令取出邀请码**（它**不在这份文档里**，因为仓库是公开的），
   然后注册 —— 它会给你账号编号 **10000002**
3. 把注册后的账号告诉我，我给你 UUID 并执行那两步授权

**⚠️ 这个邀请码永不过期，但只能用一次。** 不要发给别人——虽然它不再自动产生管理员，
但它仍然是**唯一**能注册账号的东西。

### 6.2 常用命令（在服务器上，`/srv/libevra/deploy`）

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"

$DC ps                                  # 看容器状态
$DC logs -f api                         # 看 API 日志
$DC logs web --tail 50                  # 看 Caddy 日志（证书信息在这里）
./backup.sh                             # 备份 + 恢复演练（逐表比对行数）
$DC exec api pnpm admin:list            # 看管理员状态
$DC restart web                         # 重启 web（改完 DNS 后需要）
```

### 6.3 ⚠️ 重新加载 Caddyfile 需要重启 web 容器

`Caddyfile` 是**挂载进来再生成**的（`Caddyfile` → 渲染后的 `/etc/caddy/Caddyfile`），
所以改完 `deploy/Caddyfile` 或 `web-entrypoint.sh` 之后：

```bash
$DC up -d --force-recreate web
```

**不能只 reload**——生成步骤在启动脚本里。

### 6.4 发布新版本

```bash
./deploy.sh --version 1.10.24
```

⚠️ `deploy.sh` 会先备份、构建、迁移、健康检查，**不通过就停下并给出回滚路径**。
**CI 不会自动部署**——上线只能由你在服务器上主动执行（这是 S12-A 定下的规则，见 ADR-037）。

**⚠️ 回滚应用不会回滚数据库。** 迁移是只向前的。

### 6.5 备份

```bash
./backup.sh                    # 立即备份 + 演练
```

**⚠️ 本地备份不是备份策略。** 同一台服务器上的备份会和服务器一起消失。
**异地那一份还没做**（见 §7）。建议加 cron：

```bash
crontab -e
17 3 * * * cd /srv/libevra/deploy && ./backup.sh >> backups/cron.log 2>&1
```
