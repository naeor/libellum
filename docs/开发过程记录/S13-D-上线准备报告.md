### 5.1 表现状

|---|---|---|

| **字段** | `id`、`started_at`、`finished_at`、`ok`、`file_ref`、`note`；`started_at` 倒序索引 | 同上 |
| **生产是否已有** | ❌ 没有。该迁移随 S13 一起尚未部署 | 线上仍是旧版本（本轮未连接生产核实，仅依据版本状态） |
| **读取者** | ✅ 概览接口读最新一行 | `apps/api/src/routes/admin.ts:171`；映射见 `:195-202` |
| **写入者** | ❌ **全仓库没有 INSERT** | `backup.sh` 只写宿主机 `deploy/backups/last-local.json`（`:78,93-117`）；`backup-all.sh` 只写 `last-run.json`（`:41,108-146`） |
| **测试** | ⚠️ 只有「重置时清空」与「没有记录时为 null」 | `apps/api/test/support.ts:67`；`apps/api/test/adminConsole.test.ts:445-457`。**没有一条测试写入过一行 `backup_logs`，也没有测过 `ok=false` 的映射** |

### 5.2 宿主机脚本怎么写入（现有 psql 通道）

`backup.sh` 已经在用这条通道做逐表行数比对：

```bash
docker compose -f docker-compose.prod.yml exec -T db \
  env PGPASSWORD="$POSTGRES_PASSWORD" \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -tAc "select count(*) from \"$T\""
```

（`deploy/backup.sh:210-223`）

**结论**：

- ✅ 不需要新增任何高权限 HTTP 接口；备份脚本本来就有数据库的完整访问权（它要 dump 和恢复演练）。
- ✅ 口令来自 `deploy/.env`，通过 `set -a; . ./.env` 载入，再以 `PGPASSWORD` **环境变量**传入，
  **不出现在命令行参数、不写日志、不进仓库**。
- ✅ 插入语句只需 `gen_random_uuid()`（PostgreSQL 13+ 内置，生产是 17），
  `started_at` 走默认值。**不要**把 `id` 留给数据库默认值——该列没有默认值，Prisma 是在客户端生成 UUID 的。
- ⚠️ 必须在**表已存在**时写；S13 迁移部署前，任何 INSERT 都会失败。

### 5.3 写库失败是否影响退出码

**当前实现没有写入者，所以现在不存在这个问题。** 将来接入时必须遵守：

- `backup-all.sh` 是 `set -euo pipefail`：**裸写一条会因 SQL 失败而中止整条备份流程**，
  把"状态写不进去"升级成"备份失败"。
- 正确写法是 `if ! psql ...; then echo "⚠️ backup_logs 写入失败（不影响备份结论）" >&2; fi`
  或 `|| true`；**绝不能走 `fail_stage`**。
- 如果放在 `cleanup` trap 里，同样必须 `|| true`，否则会覆盖真实退出码。
- 结论：**写库失败不应改变脚本退出码，也不应改变心跳结果**——数据库不可用时，
  备份本身通常已经失败，心跳会报警；此时没有记录是"未知"，不是"成功"。

### 5.4 与 Healthchecks 心跳的一致性

| 事实 | 证据 |
|---|---|
| 成功心跳**只在整条流程成功后**发送 | `backup-all.sh:365-369`，位于本地备份、恢复演练、加密、上传、远端元数据校验全部通过之后 |
| 任何阶段失败都发 `--fail` 并退出非零 | `fail_stage`：`:176-183`；异地未配置也发 fail 心跳：`:233-240` |
| 心跳发送失败**不影响备份退出码** | `heartbeat.sh:70-97` 失败只返回 1；`backup-all.sh:165-173` 调用后不改变退出码 |
| `--skip-heartbeat`、`--skip-offsite` 是显式调试开关 | `backup-all.sh:49-59,224-230` |

**结论**：`backup_logs` 的"成功"必须与心跳的"成功"在同一决策点产生。

- ❌ **不要在 `backup.sh` 里写 `ok=true`**：`backup.sh` 只覆盖本地导出 + 恢复演练；
  之后加密、上传、远端校验仍可能失败，而心跳不会发成功。那样会出现「数据库说成功、外部监控说失败」。
- ✅ **应在 `backup-all.sh` 全流程成功后写 `ok=true`**；失败路径（`fail_stage`）可选地
  best-effort 写 `ok=false` + 阶段说明。
- ⚠️ 心跳发送失败但备份成功时，脚本退出 0、`last-run.json` 的 `heartbeat.ok=false`；
  如果此时 `backup_logs.ok=true`，后台显示"成功"，而 Healthchecks 会在宽限期后报警。
  这不是数据错误，但要在文档里说清：**"备份成功"与"监控收到信号"是两件事**。

### 5.5 管理后台如何区分「失败 / 未知 / 正常成功」

**当前实现**（`AdminPages.tsx:214-233`）：

| 数据库状态 | 界面 |
|---|---|
| 没有任何行 | 「还没有备份记录。备份脚本尚未接入……」 |
| 最新行 `ok=true` | 「上次备份 <时间>」「成功（含恢复演练）」 |
| 最新行 `ok=false` | 「上次备份 <时间>」「失败」 |

**缺口**：

1. **没有"过期"判断**。一行三个月前的 `ok=true` 仍显示「成功」，只是时间很旧；
   读者要自己看日期才知道它早已不再代表现在。
2. **失败行目前没有写入者**，所以"失败"这一态实际上永远不会出现；只有"无记录"。
3. 无记录时，无法区分「从未接入」「数据库不可用所以没写成」「备份脚本根本没跑」。

**建议的最小改动**（本轮**未实施**）：

- **只读三态**：后台根据 `now - startedAt` 计算，超过阈值（建议 36 小时，覆盖每日 03:00 + 宽限）
  即显示「未知（记录已过期）」；
- **写入**：`backup-all.sh` 成功路径写 `ok=true`；`fail_stage` best-effort 写 `ok=false` + `note` 阶段；
  `note` 截断 500 字符，不含口令、路径以外无敏感信息；
- **测试**：补一条 API 测试，分别 seed `ok=true`（新鲜）、`ok=false`、`ok=true`（过期）三行，
  断言概览映射正确；
- **不改 schema**：三态可以由 `ok` + `started_at` + `note` 表达。S12-C 提过的
  `local_ok/restore_ok/offsite_ok` 列属于更细的改进，等真有"本地成功、异地失败"的展示需求再加。

### 5.6 最小改动建议（伪代码，未写入仓库）

```bash
# 仅在 backup-all.sh 的“整条流程成功”分支、exit 0 之前执行
docker compose -f docker-compose.prod.yml exec -T db \
  env PGPASSWORD="$POSTGRES_PASSWORD" \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -q -v ON_ERROR_STOP=1 -c "
    insert into backup_logs (id, started_at, finished_at, ok, file_ref, note)
    values (gen_random_uuid(), '$STARTED_AT', now(), true, '$DUMP',
            'backup-all: local+restore+encrypt+upload+remote-meta ok')
  " || echo "⚠️ backup_logs 写入失败（不影响备份结论）" >&2
```

**为什么本轮不动它**：

- 所有者明确要求"优先不改备份脚本"，且 S12-C 已上线；
- 写库会让备份链路多一个失败点，必须在隔离目录试跑、并确认生产迁移已应用；
- 目前后台如实显示"还没有记录"，**不会把未知伪装成成功**，可以安全等待。

## 6. 生产数据库迁移清单（`admin_console`）

迁移文件：`prisma/migrations/20261017160000_admin_console/migration.sql`（73 行，**纯加法**）。

| # | 变更 | 内容 | 风险 |
|---|---|---|---|
| 1 | 新表 `admin_audit_logs` | `id uuid pk`、`admin_user_id uuid`、`admin_username varchar(64)`、`action varchar(48)`、`target varchar(200)`、`outcome varchar(16)`、`detail jsonb`、`request_id varchar(64)`、`at timestamptz default now()`；索引 `at desc`。**无外键**（审计要活得比账号久） | 低 |
| 2 | `users` 加两列 | `disabled_at timestamptz null`、`disabled_by varchar(200) null` | 低（可空，既有行默认 NULL） |
| 3 | 新表 `backup_logs` | `id uuid pk`、`started_at timestamptz default now()`、`finished_at timestamptz null`、`ok boolean default false`、`file_ref varchar(300)`、`note varchar(500)`；索引 `started_at desc` | 低（暂无写入者） |

**没有**：数据回填、列删除、类型修改、外键、触发器。
因此**应用回滚不需要回滚这个迁移**——旧代码不认识这三样东西，也不会因为它们存在而出错。

### 生产执行前检查（只读）

1. 确认当前线上 commit 与版本（`/srv/libevra/.deployed-commit`、浏览器「软件更新」）。
2. 确认迁移表状态：`_prisma_migrations` 最新一条应为 `20261014140000_admin_allowlist`，
   且 `admin_console` 尚未出现。
3. 确认三张对象尚不存在：`admin_audit_logs`、`backup_logs`、`users.disabled_at`。
4. 确认磁盘余量足够（新表为空，空间需求可忽略；但要给备份文件留空间）。
5. **先跑 `./backup.sh`**（`deploy.sh` 也会自动再跑一次，失败即停止发布）。

### 执行后检查（只读）

1. `_prisma_migrations` 出现 `20261017160000_admin_console`，`finished_at` 非空。
2. `admin_audit_logs`、`backup_logs` 存在；`users` 有 `disabled_at`/`disabled_by`。
3. `/api/v1/health` 返回 `version: "1.13.02"`、`database: "up"`。

## 8. 回滚方案

| 情形 | 动作 |
|---|---|
| 发布后应用异常、健康检查失败 | `deploy.sh` 已停止并要求人工判断；按输出提示切回上一个 commit，再 `./deploy.sh --version <上一版>` |
| 新版本已上线但业务异常 | 应用回滚即可：切回上一个 commit 重新构建发布。**本次迁移是纯加法，旧代码可在新 schema 上运行** |
| 数据被写坏（非迁移导致） | 用发布前 `backup.sh` 的 dump 走 `./restore.sh <文件>`，**整库恢复**；这是所有者操作 |
| 迁移本身失败 | 迁移在事务中，失败不会留下半张表；修好原因后重新 `deploy.sh`。**不要** `migrate reset` |

**绝对禁止**：`docker compose down -v`、`prisma migrate reset`、`docker volume rm deploy_*`、
手工 `DROP`/`DELETE` 生产表。

**回滚后要接受的事实**：`admin_console` 的三张对象会留在库里（纯加法，无副作用），
下一次发布不会重复创建（迁移表已记录）。

## 10. 剩余风险（Top 3 与补充）

1. **S13 仍未部署，线上没有管理后台。**
   线上是旧版本（`1.10.23`）；本轮所有验收都在本地测试库。发布需要所有者确认，
   且发布后若未完成两步授权，管理员入口不会出现（这是安全设计，不是故障）。
2. **`backup_logs` 没有写入者，备份状态仍是"未知"。**
   管理概览会一直显示「还没有备份记录」；它不会被误读成成功，但也无法区分
   「从未备份」「备份失败」「数据库不可用」。接入方案已在 §5 给出，**本轮按指示未改备份脚本**。
3. **没有真机与生产浏览器验收。**
   桌面 Edge 与 390×844 设备模拟不能替代 iPhone/iPad/Safari；`ConfirmDialog` 的焦点环改动
   尤其值得在真机上走一遍（作废、停用、恢复三个弹窗）。

**补充风险**：

- 生产管理员仍需要 `admin:grant` + `admin:allow` 两步人工操作；漏一步会表现为"入口消失"。
- 迁移在发布时自动执行；若磁盘满或数据库连接异常，`migrate` 会失败并阻止 API 启动（`deploy.sh` 会停止）。
- 本轮没有验证二次验证失败限流、预留编号邀请码作废、心跳/邮件/异地备份。
