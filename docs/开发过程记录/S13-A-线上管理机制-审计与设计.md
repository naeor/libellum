## 0. 一句话结论

**管理员身份那套机制是完整的**（五道校验、两张表、四个 CLI）。
**缺的不是权限系统，是"用得上它的入口"** —— 生产上**没有任何管理员 API、没有任何管理界面，
前端甚至不知道谁是管理员**（登录返回的字段里没有 `isAdmin`）。

所以 S13 的工程量主要在**接口 + 页面 + 审计**三件事上，
**不需要重做权限判定**，也**不应该**重做。

三个最刺眼的现状：

| # | 现状 | 为什么刺眼 |
|---|---|---|
| 1 | **作废一个邀请码要手写 SQL**（`update registration_invites set revoked_at=now()`） | 这是最常用、最需要谨慎的操作，却没有任何工具保护 |
| 2 | **前端拿不到 `isAdmin`** | 做任何管理入口，第一步都得先让前端**知道**自己是不是管理员 |
| 3 | **`/api/v1/health` 报的版本是 `0.1.0`**（api 包自己的 `package.json` 版本），不是 `APP_VERSION` | 「线上到底跑的是哪一版」这个问题，**只能 SSH 上去看文件** |

## 4. 结论：**需要**新增管理页面，但要做小

**要。** 理由不是"后台看起来专业"，而是三条实际约束：

1. **邀请码的创建/查看/作废是你最常用的操作**，现在两条里有一条只能手写 SQL。
   **手写 SQL 作废邀请码是这件事里最危险的形状** —— 没有校验、没有审计、一个 `where` 写错就改错行。
2. **"我现在管不了"的根因是没有入口，不是没有权限。** 权限系统已经在了，只是只有 SSH 能碰到。
3. **AI 协作需要一条不靠聊天的规则**。页面 + API + 审计是**可执行**的边界；
   写进文档的规矩，换个 AI 就未必读。

**但要克制**（你也明确说了"避免过度工程化"）：

| 做 | 不做 |
|---|---|
| 一个 `/admin` 入口 + 4 个子页 | 不做完整 CMS 式后台 |
| 只读为主，写操作限「邀请码创建/作废」与「管理员授权/撤销」 | **不做** SSH／防火墙／任意 shell／改密钥／直连 SQL／部署／恢复数据库 |
| 复用 `createRequireAdmin` 与现有视觉组件 | **不重构**应用、不改导航结构、不动记账主链路 |
| 新增一张审计表 | 不做实时监控大屏、不做图表报表 |

**⚠️ 一条硬边界（你的原话，我完全同意，写进设计里）**：
> **"管理员可以管理系统，不应因此默认拥有查看所有私人账本的权限。"**

所以：**管理界面永远不显示任何一笔记账内容**，连"某用户本月花了多少"都不显示。
唯一例外是**数量**级别（用户数、账本数、邀请码数），**不出现金额、备注、分类**。

## 5. 页面结构与导航入口

### 5.1 入口位置：**设置 → 系统管理**

**理由（对比另外两个候选）**：

| 候选 | 评价 |
|---|---|
| 「我的」页面的链接列表 | **不选**。那是高频日常操作（资料、分类、标签），把低频且危险的管理入口混进去，等于每天给你看一个不该随手点的东西 |
| 底部 Tab 新增一项 | **不选**。会改主导航，违背"不重构应用"，而且对 99% 用户是噪音 |
| **设置页新增一组「系统管理」** ⭐ | **选这个**。设置页已经是"低频、需要想一下再点"的地方；且已有「账号安全」这种同性质的组，加一组不改变结构 |

**⚠️ 只在 `isAdmin === true` 时显示这一行。**
**⚠️ 但"隐藏这一行"只是界面礼貌，不是安全**：`/admin` 路由与所有管理接口
**必须在后端独立校验**，未授权时**页面本身也不可得**（前端 `RequireAdmin` 拿到 403 就跳回 `/me`）。

### 5.2 页面结构

```
设置 → 系统管理
   /admin                  概览
   /admin/invites          邀请码（列表 + 新建 + 作废）
   /admin/admins           管理员（状态 + 授权 + 撤销）
   /admin/users            用户（搜索 + 有限信息）
   /admin/audit            操作记录（只读）
```

| 页面 | 内容 | 风险 |
|---|---|---|
| **概览** | 用户数、账本数、邀请码可用/已用数、管理员数、**上一次备份时间与是否通过演练**、最近 10 条管理操作 | 只读 |
| **邀请码** | 可按状态筛选；显示备注、预留编号、创建时间、过期时间、使用情况；**创建**（三选一形态 + 备注）；**作废**（二次确认 + 必填原因） | **中**（写） |
| **管理员** | 每行显示：`已授权/未授权` × `在名单/不在名单`（**四种组合都要显示**，包括"只满足一半"）；授权/撤销各两步 | **高**（提权） |
| **用户** | 按账号编号或用户名精确搜索；返回**最小字段**（见 §6.3）；不做列表全量翻页 | 低（只读） |
| **操作记录** | 最近 N 条审计，可按操作类型筛选；**只读，不可编辑、不可删除** | 低 |

### 5.3 视觉与移动端

**全部复用现有积木**：`InnerPage`（带返回）、`rounded-card`、`text-helper`/`text-muted` 分组标题、
`components/` 里已有的按钮与确认弹窗。**不引入任何新的视觉概念、不加新的颜色令牌。**
**手机可用**：单列布局，宽表格在窄屏改为分行卡片；管理页面**不做横滑表格**。

## 6. 后端 API 与数据模型方案

### 6.1 统一入口：一个 `requireAdmin`，不分叉

```ts
// 每个管理路由都走这一句，没有任何例外
app.get("/api/v1/admin/…", { preHandler: requireAdmin }, handler);
```

**⚠️ handler 里只读 `request.adminActor`，不重新查用户、不从请求里取身份。**
（设计决定 §8.1 已经定死这条。）

**⚠️ 所有路由注册在 `routes/admin.ts` 一个文件里**，并在 `app.ts` 里**无条件注册** ——
因为**权限由 guard 判定，不是由"路由存不存在"判定**。
（这与 1.10.22 那条"测试专用路由在生产构建里不存在"不冲突：那是**测试用的假接口**，
这里是真的产品接口，它必须存在并且必须被正确拒绝。）

### 6.2 接口清单

| # | 方法 | 路径 | 做什么 | 阶段 |
|---|---|---|---|---|
| 1 | `GET` | `/api/v1/admin/self` | **我是不是管理员**（前端判断入口用）；返回 `accountNumber`、`username` | **B** |
| 2 | `GET` | `/api/v1/admin/overview` | 数量级概览 + 备份状态 + 最近操作 | **B** |
| 3 | `GET` | `/api/v1/admin/invites` | 邀请码列表（**默认打码**，见 §6.5） | **B** |
| 4 | `POST` | `/api/v1/admin/invites` | 创建邀请码（形态 + 备注）；**明文只在这一响应里返回一次** | **B** |
| 5 | `POST` | `/api/v1/admin/invites/:id/revoke` | 作废（必填 `reason`） | **B** |
| 6 | `GET` | `/api/v1/admin/admins` | 管理员状态（四种组合） | **B** |
| 7 | `GET` | `/api/v1/admin/users?q=` | 精确搜索用户（最小字段） | **C** |
| 8 | `GET` | `/api/v1/admin/audit` | 审计记录（只读，分页） | **C** |
| 9 | `POST` | `/api/v1/admin/reauth` | 敏感操作的二次验证（见 §7.2） | **C** |

**⚠️ 没有的东西（这一轮明确不做）**：
- ❌ 没有任何"读取账本内容"的接口（连管理员也不行）
- ❌ 没有"删除用户"接口
- ❌ 没有"批量导出邀请码"接口
- ❌ 没有"任意 SQL / shell / 部署"接口

### 6.3 最小数据披露

| 接口 | 返回什么 | **绝不返回** |
|---|---|---|
| `users` 搜索 | `accountNumber`、`username`、`displayName`、`createdAt`、`isDemo`、`status`（若做）、`isAdmin` 两个标记的**状态** | 密码哈希、恢复码哈希、会话、`lastBookId`、账本 id、任何交易数据 |
| `overview` | 计数（用户/账本/邀请码/管理员）、备份时间与结果、最近 10 条审计 | 任何金额、任何备注、任何用户明细 |
| `invites` | 备注、预留编号、时间戳、使用状态（**谁用的只给 username，不给 UUID**） | **邀请码明文（默认）** |
| `audit` | 时间、管理员 username、action、目标（username/邀请码备注）、结果 | 请求体原文、IP 之外的隐私、任何账本内容 |

### 6.4 新增数据模型：`admin_audit_logs`

**字段直接采用设计决定 §9.4 已经定好的那六项**（那条设计现在该落地了）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` | 主键 |
| `admin_user_id` | `uuid` NOT NULL | **管理员 UUID，不是名字**（名字会变） |
| `admin_username` | `varchar(64)` | **快照**：账号被删后记录仍可读（与 `transaction_events.actor_name` 同一个理由） |
| `action` | `varchar(48)` NOT NULL | **稳定标识符**，如 `invite.create` / `invite.revoke` / `admin.grant` / `admin.revoke` / `admin.allow` / `admin.disallow` / `account.disable` |
| `target` | `varchar(200)` | 操作对象（`username` 或邀请码备注）；**不存邀请码全文** |
| `outcome` | `varchar(16)` NOT NULL | `success` / `failed` |
| `detail` | `jsonb` | **最小补充**（如"形态=预留编号"、"编号=10000104"）；**禁止写凭据** |
| `request_id` | `varchar(64)` | Fastify `request.id`，用于把日志和访问日志对上 |
| `at` | `timestamptz` NOT NULL DEFAULT now() | 操作时间 |

**索引**：`(at DESC)` 一条，够用。
**写入方式**：**在业务事务里写**（成功也写、失败也写），写失败**不阻断操作**但打 `error` 日志——
审计表坏掉不应该让管理功能不可用，但**必须吵**。

**⚠️ 明确不记**：密码、会话 cookie、恢复码、任何账本内容、邀请码全文。

### 6.5 邀请码的展示规则（你特别强调的一项）

| 时机 | 展示 |
|---|---|
| **创建成功** | **明文显示一次**，带「复制」按钮，并明确提示"离开此页后无法再查看" |
| **列表** | 只显示打码形式（如 `7K2M-••••-••••`）与备注 |
| 日志与审计 | **永不出现在任何日志、任何审计 detail 里** |
| 批量导出 | **不做** |

**⚠️ 为什么"创建时可以看、之后看不到"是对的**：这个码的用途是**递给一个人**，
递出去之后你自己再看到它的价值接近于零，而**一次不必要的展示就是一次泄露机会**。
**⚠️ 但对于你手里那一张"永不过期"的码，这与"我随时要能查"冲突** —— 见 §10 第 5 条，需要你定。

### 6.6 环境隔离（你的第五节）

**三套环境，必须能被认出来**：

| 环境 | 数据库 | 谁在读 | 规则的落点 |
|---|---|---|---|
| **本地开发** | `ledger_dev` | 你 + AI | 默认目标，**不需要确认** |
| **GitHub 仓库** | — | 公开 | **永不含真实数据、`.env`、邀请码** |
| **生产** | `libevra_prod` | 只有你 | **AI 默认禁止直连**；写操作必须由你在场 |

**建议的落地机制（S13-C 做）**：

1. **所有 CLI 脚本启动时打印目标库**：`目标数据库：ledger_prod @ db:5432` ——
   现在只有 `check-db-parity` 会明确报库名，其他脚本静默连 `DATABASE_URL`。
2. **生产必须显式确认**：新增脚本统一要求 `--env production`，

3. **`deploy/.env` 里的库名保持 `libevra_prod`** —— 名字本身就是最后一道人眼防线。
4. **AI 规则写进 `AGENTS.md`**（第六节）：见 §12。

**⚠️ 不做**：不做"自动识别环境然后静默切换"。自动识别会在识别错的时候**静默地做错事**；
**显式要比聪明安全。**

## 7. 管理员安全边界

### 7.1 五道校验 —— **全部保留，一个都不能简化**

会话 → `admin_grants` → `admin_allowlist` → 前 100 资格 → 账户可用。
**不接受任何形式的"前端判断"、"用户名白名单"、"只看 `isAdmin` 字段"。**

### 7.2 二次验证：**建议做"重新输密码"，不做 TOTP**

| 方案 | 评价 |
|---|---|
| **重新输入密码**（换取一个 5 分钟的 step-up 凭证） ⭐ | **选这个**。复用已验证的 `verifyPassword`，不引入新依赖，不引入新丢失风险（TOTP 的种子丢了就是永久锁死） |
| TOTP / 短信验证码 | **不选**。项目没有邮件/短信通道，TOTP 又增加一个"丢了怎么办"的问题 |
| 不做 | 可接受但偏弱：管理员会话被盗时，攻击者可以立刻自我提权 |

**适用操作**：`admin.grant` / `admin.revoke` / `admin.allow` / `admin.disallow` /
`account.disable`。**邀请码创建与作废不需要**（影响面小、频率高，二次验证会让它变难用）。

### 7.3 管理员授权／撤销：**建议留在服务器终端，不进网页**

**这是整套设计里我最想让你拍板的一条。**

| 方案 | 好处 | 坏处 |
|---|---|---|
| 网页里能 grant/allow | 方便 | **管理员会话一旦被盗，攻击者可以给自己再开一个管理员** —— 第二道锁被从内部打开 |
| **网页只看，改仍走 SSH CLI** ⭐ | **提权永远需要服务器终端**，那是比应用管理员更高的一层 | 你要 SSH，但这件事**一年发生一两次** |

**我的建议**：**S13-B 只做"'看管理员状态'"，不做"在网页里授权"。**
理由和 `docs/开发过程记录/教训.md` 的一贯立场一致：**方便要换来的安全性，得配得上**。
这里换来的"不用 SSH"，价值远小于"应用层漏洞直接变成平台提权"的代价。

**⚠️ 但如果你的判断是"我就是要能在页面上点"，这也完全可以做** ——
那我会把二次验证设为**强制**，并让审计把每一次提权记得更细（§6.4 的 `detail` 写清楚
"从 `{未授权,未列入}` 变成 `{已授权,已列入}`"）。**由你定。**

### 7.4 邀请码创建的速率限制

新增**按管理员账号**的限流（不是按 IP）：如 **10 个/小时**。
理由：正常使用一周也就几个；失控的循环脚本会在几秒内造出几百个永不过期的码。

### 7.5 审计留痕 —— 每条管理操作一行（§6.4）

### 7.6 **管理员不可见私人账本** —— 硬边界，三层保证

| 层 | 保证 |
|---|---|
| **接口层** | 管理 API 的查询里**根本不 join `transactions`/`books`**（除了计数） |
| **测试层** | 一条测试：`/admin/*` 的任何响应体里**不出现任何已知交易 id 或金额** |
| **文档层** | 设计决定 §6 与本文都写明"管理 ≠ 数据访问" |
