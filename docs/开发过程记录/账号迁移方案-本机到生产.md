## 3. 能否沿用原来的用户名和密码？

### 3.1 密码：**能，而且哈希本身可以直接搬**

`apps/api/src/auth/password.ts` 用的是 **Argon2id**（`@node-rs/argon2`，
`memoryCost 19456 / timeCost 2 / parallelism 1`）。

**两个环境跑的是同一份代码、同一套参数**，而 Argon2 的输出是**自描述的 PHC 字符串**：

```
$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>
```

算法、参数、**盐**、摘要**全都在这一个字符串里**。
所以 `password_hash` 是**可移植的**——生产端用同样的参数 `verify` 就能通过，
**所有者继续用原来的密码登录，不需要知道、也不需要重设密码**。

**⚠️ 这一点与"能不能反过来从哈希推出密码"无关**：我们搬的是哈希，不是密码。
**⚠️ 前提**：生产必须跑同一个 `hashPassword`/`verifyPassword` 实现（本方案成立，两侧同为 1.10.23）。

### 3.2 会话：**不能沿用，也不该沿用**

| 事实 | 说明 |
|---|---|
| 会话令牌是 `randomBytes(32)` 的**原始值放 Cookie**，数据库里只有 **SHA-256 哈希** | 见 `auth/session.ts` |
| Cookie 名 `libellum_session`，`SameSite=Lax`，`Secure` 由 `NODE_ENV==="production"` 决定 | 开发机经 Vite 代理时 `NODE_ENV=development`，**Cookie 没有 Secure 标志** |
| ⚠️ **`SESSION_SECRET` 在代码里根本没被读取** | 全项目 `grep SESSION_SECRET` 在源码里 **0 命中**；`env.ts` 的 `Env` 接口里也没有它。它存在于 `deploy/.env`，但**当前没有任何代码用它** |

**结论**：会话是"随机令牌 + 哈希"的机制，**"迁移会话"在技术上只是搬一行 `sessions`**，
但那**没有意义**：Cookie 绑在 `localhost` 上，换到 `libevra.com` 域名浏览器根本不会带过去。

**⚠️ 所以：迁移后需要重新登录一次。** 这不是缺陷——**登录本来就该在新设备/新域名上重新做一次**。

**⚠️ 顺带一个发现，建议单独处理**：`SESSION_SECRET` 这个名字暗示它在给 Cookie 签名，
**但代码从没读过它**。它现在是**一个没有使用者的配置项**——
本项目对"没有使用者的东西会腐烂"有过记录（`颜色清单.md` 的 `--color-focus-ring`）。
**建议**：要么把会话真正签名（引入它的本来目的），要么从模板和文档里删掉它。
**⚠️ 本轮不动**——那是一个独立的安全决定，不是迁移的一部分。

### 3.3 恢复码

`recovery_code_hash` 也是 Argon2id，**同样可移植**。
把它一起迁移，**原来的恢复码继续有效**（哈希未使用过）。
**⚠️ 也可以选择不迁移**，让所有者登录后在设置里重新生成一个。

## 4. 编号与 UUID 冲突

| 项 | 会不会冲突 | 说明 |
|---|---|---|
| **用户名 `naeor`** | ❌ 不会 | 生产 `users` 为 0 行 |
| **UUID `bc82bf91-…`** | ❌ 不会 | 生产没有任何行 |
| **编号 `10000000`** | ❌ **不会，而且空闲** | 生产计数器是 `10000003`，`10000000` 从未被分配 |
| **账本编号 `40000000`** | ⚠️ **计数器需要前移** | 见 §2.1 第 2 条，**不改会撞号** |

**⚠️ 关于"优先保留 10000000"**：**可以直接保留，不需要动计数器。**
因为生产计数器当前值是 `10000003`，**已经大于** `10000000`，所以：
- 迁入 `10000000` 不冲突；
- 之后注册的新账号从 `10000003` 开始，**也不会撞**。

**⚠️ 唯一需要动计数器的地方是 `book_number`**，而且那是**为了正确性**（防撞号），
不是为了让编号好看。**这就是要求里说的"不要直接修改生产数据库计数器"要防的事** ——
我会把这个改动**单独列出来给你确认**，而不是藏在迁移脚本里。

## 6. 两个方案的对比

### 方案 A：把 `naeor` 的数据直接迁移进生产库 ⭐ **推荐**

| 维度 | 评价 |
|---|---|
| **复杂度** | 中。需要写一个按外键顺序插入的脚本（§6.2） |
| **风险** | **低**——生产库**是空的**，没有可被覆盖或冲突的数据 |
| **能保留什么** | **全部**：用户名、**密码**、**UUID**、**编号 10000000**、昵称、`last_book_id`、恢复码、**152 条有效流水 + 8 条软删墓碑**、全部分类/支付方式/标签、6 条冲突解决记录、导入导出的可追溯引用 |
| **对以后的影响** | 与"一直就在生产上"**没有区别**。UUID 稳定，离线设备认得的 id 不变 |
| **不可逆性** | ⚠️ 写入后想撤销只能**从迁移前的备份恢复**（§8.3） |

### 方案 B：在生产注册一个新账号，只搬数据

| 维度 | 评价 |
|---|---|
| **复杂度** | **高**。"保留编号 10000000"需要 `invite:create --reserved`，而它**从计数器取号** → 生产会给出 `10000003`，**不是 10000000**。要拿到 `10000000` **就得改计数器**，而那正是要求里说要避免的 |
| **风险** | 中——多一步注册、多一次哈希生成，且要额外处理"新 UUID"带来的引用改写 |
| **能保留什么** | 用户名 + 密码（**注册时你自己输，服务器重新哈希**）、昵称；**数据要靠第二个脚本搬**，而且**所有行的 `user_id` / `book_id` 都要改写**（新 UUID） |
| **⚠️ 关键代价** | **UUID 变了**。对服务器无影响，但**离线设备本地缓存的行 id 与新账号的引用关系需要重新建立**——而离线优先的设计里，客户端生成的 id 就是主键 |
| **编号** | ⚠️ **拿不到 10000000**，除非改计数器（不推荐）；实际会拿到 `10000003` |
| **管理员资格** | `10000003` **仍在第一批区间（10000000–10000099）内**，所以**资格没问题** |

### 6.1 结论

> **推荐方案 A。**
>
> 理由是**生产库完全是空的**——方案 B 的复杂度（改编号、改 UUID、改引用）
> 在这里**买不到任何东西**。方案 A 更简单、保留更多、且与"账号一直在生产上"无法区分。
>
> **⚠️ 方案 B 唯一真正的优势是"整个流程走的是应用自己的注册路径"**，
> 也就是说它不会引入任何绕过应用逻辑的数据写入。
> 如果你更看重这一点，方案 B 也完全可行，只是**要接受编号变成 `10000003` 且 UUID 会变**。

## 7. 管理员：必须重新建立，不能复制

**要求里点名的这一条，我完全遵守，并且要说明为什么它是必要的：**

| | 开发库现在 | 生产环境 |
|---|---|---|
| `admin_grants` | 1 行（`naeor`，`--by owner-laptop`） | **0 行** |
| `admin_allowlist` | 1 行（`naeor`，`--by owner-laptop`） | **0 行** |

**⚠️ 迁移后 `naeor` 在生产上不会是管理员**，尽管它的 `users.is_admin = true` 会被搬过去。
因为 `admin/guard.ts` 要求**两道独立检查都通过**：

```
有效会话 AND admin_grants 有效授权 AND admin_allowlist 在名单 AND 前 100 资格 AND 账户可用
```

**所以迁移完成后必须执行这两条命令（在生产服务器上）：**

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"
$DC exec -T api pnpm admin:grant bc82bf91-c0d9-4f88-9e34-6558fcd66ee8 --by "owner"
$DC exec -T api pnpm admin:allow bc82bf91-c0d9-4f88-9e34-6558fcd66ee8 --by "owner"
```

**⚠️ 只做第一条，`naeor` 还不是管理员** —— `admin:list` 会把它显示在
「⚠️ 只满足一半（不会通过校验）」一栏，而它**确实不能通过校验**。

**⚠️ 这恰恰是"不能复制开发授权"的技术理由**：那两条命令是**在生产环境里重新做一次决定**，
并把"谁在什么时候决定的"记为 `owner`。复制开发库的行**会让生产继承一次本机上的决定**，
而那个决定是在开发机上、为了让本机测试能跑而做的。**授权应该在生产上重新发生。**

## 8. 如果执行：完整的安全流程

### 8.1 加密传输（**不经 GitHub**）

**⚠️ 明确不走 GitHub**：不建私有分支、不提交 dump、不传 PR 附件。
GitHub 只留**数据库结构与迁移脚本**（本来就在仓库里）。

**传输方式：SSH 管道 + 端到端加密，落盘即加密**

1. 在本机用 `pg_dump --data-only -Fc` 导出**只包含 naeor 范围的表**（不是整库）
2. **本地加密**：`age`（或 `openssl enc -aes-256-gcm`）用一个**一次性口令**加密
3. **经 SSH 管道**把密文送到服务器（**不落明文**）
4. 服务器上解密到 `/srv/libevra/deploy/_migrate/`（`chmod 600`，**用完立即 `shred -u`**）
5. 导入完成后删除中间文件

**⚠️ 一次性口令不在对话里传**：由你在服务器上输入，或由我在本机生成后**只写在服务器的临时文件里**。
**⚠️ 更简单的替代**：因为数据量很小（约 242 行），
可以**直接走 `ssh` 标准输入传 SQL**，不落任何中间文件。

### 8.3 事务一致性与失败回滚

**整个插入在**一个 `BEGIN … COMMIT`**里完成**：

```sql

SET CONSTRAINTS ALL DEFERRED;   -- 让 last_book_id 的回填可以在最后做

  -- 最后做自检，不通过就 RAISE EXCEPTION → 整个事务回滚

```

**事务内自检（任一不通过就整体回滚）**：

| 检查 | 期望 |
|---|---|
| `users` 里 naeor 恰好 1 行 | 1 |
| 迁移进来的流水数 | 160 |
| 未删流水数 | 152 |
| **孤儿检查**：`transactions` 里 `category_id` 不在 `categories` | 0 |
| **孤儿检查**：`book_members` / `transactions` 的 `book_id` 不在 `books` | 0 |
| `last_book_id` 指向的账本存在 | 是 |
| `counters.book_number` **大于** `books` 里的最大编号 | 是 |

**⚠️ 任何一步失败 → 整个事务回滚 → 生产回到迁移前的空状态**（因为原本就是空的，

**⚠️ 但计数器那一行也在同一个事务里**，所以它同样会被回滚，不会留下半改状态。

## 10. 如果不迁移：如何安全地建一个正式账号

**结论先说：即使不迁移，你也不"必须从零开始"——按下面的做法可以保留编号与密码。**

### 做法

1. **在生产上创建一个预留给 `10000000` 的邀请码**
   ⚠️ 现有 `invite:create --reserved` 是**从计数器取号**的，会给出 `10000003`。
   **要拿到 `10000000` 需要一个只做一次的小脚本**（或在确认后把计数器临时设为 `10000000`，
   注册后它会自增到 `10000001`）。
   **⚠️ 我会把那一步单独列出给你确认，不藏在脚本里。**

2. **用那个邀请码注册**，用户名填 `naeor`，**密码填你原来的密码**
   —— 服务器会用同一套 Argon2id 重新哈希。**你继续用原来的密码登录。**

3. **手动搬数据**：`naeor` 的账本 + 152 条流水 + 分类/支付方式/标签
   —— 这需要**改写所有 `user_id` / `book_id`**（因为新账号是新 UUID），
   **是方案 B 的主要工作量**。

4. **重新建立管理员**：`admin:grant` + `admin:allow` 两条（同 §7）。

### 代价对照

| | 方案 A | 不迁移 / 方案 B |
|---|---|---|
| 用户名 | ✅ `naeor` | ✅ `naeor` |
| **密码** | ✅ 原密码（哈希直接搬） | ✅ 原密码（**你注册时自己输**） |
| **编号 10000000** | ✅ 直接保留 | ⚠️ 需要**一次性的计数器处理**才能拿到 |
| **UUID** | ✅ 原 UUID | ❌ **新 UUID** |
| **152 条流水** | ✅ 自动 | ⚠️ 需要**改写引用的搬运脚本** |
| 冲突解决 / 编辑历史 | ✅ | ⚠️ 需要一起搬并改写引用 |
| 复杂度 | 中 | **高**（改写引用比按顺序插入更容易出错） |

**⚠️ 我的建议仍然是方案 A**：它**保留得更多、出错面更小**，
而且因为生产库是空的，它**没有"污染已有数据"这个风险**。

## 12. `www.libevra.com` 的 DNS：**仍然是错的**

**实测（2026-10-16）**：

```
www.libevra.com  CNAME → libvera.com     ← ✗ 拼写错误：libvera（v 和 e 颠倒了）
Google DNS:  status = 3 (NXDOMAIN)
curl https://www.libevra.com/  →  000（连不上）
对比：libevra.com  A → 43.161.227.152  ✅ 正常
```

### 你要在 Namecheap 改哪一条

| 项 | 现在的值 | **应改为** |
|---|---|---|
| Type | `CNAME Record` | 保持 |
| Host | `www` | 保持 |
| **Target** | **`libvera.com`** ❌ | **`libevra.com`** ✅ |
| TTL | 任意（Automatic 即可） | 保持 |

**⚠️ 注意看仔细**：错的是 **`libvera`**（v、e 颠倒），正确的是 **`libevra`**。
这个字形差别很小，**改完请逐字再看一遍**。

### 改完怎么验证

```powershell
# 1. 本机解析（改完可能要等 DNS 生效，通常几分钟）
Resolve-DnsName www.libevra.com

# 期望看到：CNAME → libevra.com，并且解析出 A 记录 43.161.227.152
```

```powershell
# 2. 用公共 DNS 复核（绕过本机缓存）
(Invoke-RestMethod "https://dns.google/resolve?name=www.libevra.com&type=CNAME").Answer
# 期望：libevra.com.
```

```bash
# 3. 站点真的能打开（这一步要等 Caddy 拿到 www 的证书）
curl -s -o /dev/null -w "%{http_code} -> %{redirect_url}\n" https://www.libevra.com/
# 期望：308 或 301，Location: https://libevra.com/...
```

**⚠️ 第 3 步需要先重启一次 web 容器**，因为 `www` 的跳转是
`web-entrypoint.sh` 在**启动时探测 DNS** 之后才生成的
（探测是有意的：给一个 DNS 不指向本机的域名申请证书会失败，而 Let's Encrypt 按注册域名限流）：

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml --env-file .env"
$DC up -d --force-recreate web
$DC logs web --tail 10        # 期望看到 "www.libevra.com resolves - added a redirect"
```

**⚠️ 我没有改动任何 DNS 配置**，也不会改——那需要你在 Namecheap 操作。
