# Libevra 品牌迁移记录（原名 Libellum）

> **本文是这次改名的唯一权威记录。** 2026-10-14，版本 **1.10.20**。
>
> **给三种读者**：
>
> | 你关心什么 | 直接看 |
> |---|---|
> | 改名做完了吗、还能不能继续开发 | **§1**、**§4**、**§11** |
> | **我能不能把某个 `libellum` 字符串改掉** | **§5（保留清单）** 与 **§6（数据兼容）**——**改之前必须读** |
> | 我（所有者）还要手动做什么 | **§10（人工操作清单）** |
>
> ⚠️ **一句话结论**：**用户可见的品牌已全部改为 `Libevra`；功能、视觉、数据一律未动；
> 内部技术标识有意保留旧名；域名与 GitHub 仓库改名是人工操作，尚未执行。**

## 1. 更名背景与结论

| 项 | 内容 |
|---|---|
| **原因** | **域名**。`libellum.app`（2026-10-08 定名时选定、当时核实未注册）这条路线不再可行 |
| **旧名** | `Libellum` |
| **新名** | **`Libevra`** |
| **触发时间** | 2026-10-14 |
| **落地版本** | **1.10.20**（`apps/web/src/lib/version.ts`） |
| **性质** | **只改品牌名称**。**不是**产品定位、功能或视觉风格的重新设计 |
| **未动的** | 海浪（形状／四层颜色／几何／动画／手势）、文字与颜色语义 token、布局间距圆角、明细页两形态、全部业务逻辑、数据库、离线存储、同步协议、API |

**四条执行原则**（所有者给定，逐条落实）：

1. **用户看得见的品牌，尽可能完整改为 `Libevra`** —— ✅ 见 §3；
2. **内部技术标识不要求全部改名** —— ✅ 见 §5；
3. **历史记录不应被篡改** —— ✅ 见 §3 末与 §5 末；
4. **不能靠全仓库字符串替换** —— ✅ **全程逐处判断**；本项目自己就有两次"脚本替换改坏源码"的事故记录（`交接.md` §5 第 5 条、`开发日志.md` §9.1）。

**拼写纪律**：新名一律写作 `Libevra`——**不是 `Libevra`、不是 `Libevera`、不是 `Libevrra`**，大小写只有 `Libevra`（品牌）与 `libevra`（标识符／文件名）两种形态。

## 2. 旧品牌命中位置分类总览

对全仓库（排除 `node_modules`、`.git`、`dist`、`_backups`、`.certs`、`apps/ocr/.venv`、`apps/api/src/generated`）**逐行**检索 `libellum` 的**全部大小写变体**——`Libellum` / `libellum` / `LIBELLUM` **分开检索**（交替式正则会漏报，本项目实测过）。

**⚠️ 先说清一件事：总命中数在改名之后变多了，而这恰恰是对的。**

| | 命中总数 | `.md` | 源码/配置 | `.json` |
|---|---|---|---|---|
| **改名之后**（含本文档） | **581** | 315 | 229 | 37 |

原因有二，都与"没改干净"无关：

1. **历史文档一个字节都没改**（`开发日志.md` 时间线、`版本记录（1.08-1.09）.md` 全文、`归档/**`、5 份阅读报告），**而本文档本身**就是一份**通篇在讨论 `libellum` 该不该改**的新文档——它必然带来大量命中；
2. 不该人为改动的产物（`.docx` / `.pdf`、一次布局审计留下的渲染快照 `tools/layout-audit-2026-10-14.json`）**保持原样**。

**所以验收标准从来不是"计数归零"**（所有者本人明确过这一点）。真正的判据是下面这张分类表——**每一处命中都必须能归入 A / B / C / D，且 A 类为 0**：

| 类 | 含义 | 处置 | 现状 |
|---|---|---|---|
| **A** | **用户可见品牌** | **必须改为 `Libevra`** | ✅ **只剩 1 处，且是有意保留**（关于页的仓库地址，等 GitHub 改名，见 §3.3） |
| **B** | **当前仍有效的产品文档／工程说明** | 改为 `Libevra` | ✅ 已改，见 §3.2 |
| **C** | **内部技术标识**（数据、协议、构建、环境变量、包名） | **有意保留旧名** | ✅ 见 §5，**每一类都写了"改了会怎样"** |
| **D** | **历史记录与生成产物**（开发日志、历史版本、归档、过程稿、审计快照、`.docx`/`.pdf`） | **有意保留旧名** | ✅ 见 §3.4 |

不是为了现在做，而是为了让下一个人知道"这是有代价的"：

| 想改的东西 | 需要什么 |
|---|---|
| IndexedDB 库名 | 一次**打开旧库→拷贝全部键→写新库→验证→才删旧库**的迁移；并且要能处理"迁移中途失败"（**用户唯一副本**）。**不建议做** |

## 12. 一条值得传下去的教训

**规范里不要记"相对值的换算结果"，要记相对值本身。**

`文字语义与排版规范.md` 曾经这样写品牌字距：**「`Libellum` 的 `5.376px` 是品牌」**。
于是改名时它读起来像"这个数字属于那个名字"——**而代码里其实一直写着 `letter-spacing: 0.16em`**，
`5.376px` 只是 `2.1rem` 下的换算结果，**与拼写毫无关系**。

**这类记录的危险不在于它错，而在于它在改名时会被当成"必须重算的数"**——然后有人去调一个本来就正确的值。
**已经按此更正**（§3.2 的《文字语义与排版规范》一行），并写明了该记的是 `0.16em`。

**同类要警惕的写法**：
- 把"某常量在当前字号下的像素值"写进规范，而不写那个常量；
- 把"某说明里提到几次品牌名"当验收（历史上真有过一次这样的产物核对）——
  **改名后它必然变化，而它测量的是文案重复，不是品牌正确性**；
- 把"字符串计数为零"当成功标准（所有者本人已经指出过这一点）。
