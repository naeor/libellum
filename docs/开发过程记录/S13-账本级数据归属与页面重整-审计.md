## 0. 一句话结论

**分类、标签、支付方式在数据模型、API、离线缓存三层里都已经是"账本级"**——
`bookId` 非空、唯一键带 `bookId`、每个查询都按 `request.book.bookId` 过滤、
每本新账本自动生成自己的一套预设、离线副本按 `账号:账本` 分域。

所以 **S13-E 不需要数据迁移，也不需要新的数据模型**。真正缺的是三件事：

1. **入口位置错了**：分类／标签／支付方式的管理页挂在**账户页（我的）**下，
   路由是根级的 `/categories`、`/payment-methods`、`/tags`——**界面在暗示它们是账号级的**；
2. **"支付方式"不是"资金账户"**：全仓库没有任何余额 / 账户 / 转账概念，
   支付方式只是一个名字 + 排序 + 归档标记；
3. **账本级没有自己的偏好**：默认币种存在 `users` 上（账号级），但"导出／导入"是账本级，
   两件事被并排放在设置页同一组里。

**因此 S13-E 的主体是「界面归位 + 文案 + 一层明确的三层划分」，不是数据模型重构。**
真要做"资金账户（余额 / 转账 / 对账）"，那是**新增模型**，应单独成阶段，不应塞进 S13-E。

## 2. 逐条详述

### 2.1 分类属于账本（已验证事实）

**模型**

- `Category.bookId String @map("book_id") @db.Uuid` —— **必填**：`prisma/schema.prisma:729`。
- 反向关系 `Book.categories Category[]`：`prisma/schema.prisma:625`。
- 外键声明与级联：`book Book @relation(fields: [bookId], …, onDelete: Cascade)`：`:752`。
- **唯一键是 `(bookId, kind, name)`**：`:755`；查询索引 `(bookId, kind, isArchived)`：`:756`。
- 分类分收支两套（`kind`），所以"餐饮"只属于支出：`:722-723,731`。
- 注释写明"分类只归档、永不删除，历史账目要继续指向它"：`:725-726`。

**没有任何用户级分类**：`User` 模型的关系列表 `:117-144` 里没有 category / tag / paymentMethod。

**API**

- 创建：`bookId` 取自 `request.book!.bookId`（**不读客户端传入的 bookId**），
  排序值按 `where: { bookId, kind }` 聚合：`apps/api/src/routes/classification.ts:60-89`（`:62,66,71-77`）。
- 改名/归档：先 `findFirst({ where: { id, bookId } })`，不存在即 404：`:91-101`。
- 归档而非删除：`update({ …, data: { isArchived: true } })`：`:129-145`（`:141`）。
- 一次性取回：`GET /api/v1/ledger` 用 `prisma.category.findMany({ where: { bookId } })`：`apps/api/src/routes/ledger.ts:57-69`。

**"客户端传 bookId"这条路不存在**：`createCategorySchema` 只有 `name / kind / sortOrder`，
没有 `bookId`：`packages/shared/src/ledger.ts:165-169`。

### 2.2 标签属于账本（已验证事实）

- `Tag.bookId` 必填：`prisma/schema.prisma:783`；唯一键 `(bookId, name)`：`:791`；
  反查关系 `Book.tags Tag[]`：`:626`；外键 `onDelete: Cascade`：`:788`。
- **没有 `isArchived`**：`Tag` 只有 `id / bookId / name / color / createdAt`：`:781-793`。
  所以标签是**真删除**，与分类、支付方式不同：`classification.ts:256-274`。
- 创建/改名/删除都先按 `bookId` 校验归属：`classification.ts:218-234,236-254,262-267`。
- 删除前统计受影响条目数（供界面提示）：
  `prisma.transactionTag.count({ where: { tagId: id } })`：`:269`。**这里没带 bookId，但不会越界**——
  `tagId` 本身已经属于某一本账，`transaction_tags` 也只可能连到该账的交易（见 §2.9）。
- 标签是账本内的跨分类标记（"出差 / 可报销"）：`prisma/schema.prisma:780-781`。

### 2.3 支付方式 ≠ 资金账户（已验证事实 + 设计建议）

**事实**

- 只有 `PaymentMethod` 一个模型：`prisma/schema.prisma:762-778`。
- 字段只有 `id / bookId / name / icon / sortOrder / isArchived / createdAt / updatedAt`：`:763-770`。
- 注释直接写明**"v1 记录支付方式但不跟踪余额——余额会牵出转账与对账"**：`:760-761`。
- 对外契约 `paymentMethodSchema` 只有 `id / name / isArchived / sortOrder`：
  `packages/shared/src/ledger.ts:98-104`——**没有余额、没有币种、没有账户类型**。
- 归属：`bookId` 必填，唯一键 `(bookId, name)`：`prisma/schema.prisma:764,775`。
- 预设只有五个名字（微信 / 支付宝 / 银行卡 / 现金 / 其他）：`apps/api/src/ledger/presets.ts:39-45`。
- 全仓库检索 `资金账户`、`账户余额`、`balance`：**没有任何账户模型**；
  唯一的 `balanceCents` 是**统计口径**（收入减支出），不是账户余额：
  `apps/api/src/routes/transactions.ts:567`；`apps/web/src/lib/offline/localStats.ts:62,99`。

**结论**：产品语言里如果要用"资金账户"，它是**一个新模型**（余额、币种、账户类型、转账、对账），
不是给 `PaymentMethod` 改个名。**S13-E 不应把它塞进来**（见 §5.3）。

### 2.4 不同账本能独立配置（已验证事实）

- 每本账本**在创建时**生成自己的一套分类（收入/支出各一组 + 隐藏的"暂无分类"）：`apps/api/src/ledger/bootstrap.ts:57-73`；
  支付方式同样按 `book.id` 建：`:75-81`。
- 注释是本项目写下的明确原则：**"Nothing is copied between ledgers. A new book gets its own presets,
  so customising one does not leak into the other."** `bootstrap.ts:21-22`。
- 建第二本账走同一个函数：`apps/api/src/routes/books.ts:146-177`（`:159-160` 调 `createDefaultLedger`）。
- 预设清单是**同一份常量**（不是每账本复制一份代码）：`apps/api/src/ledger/presets.ts:18-49`。
- 因此"在 A 账本改名 / 归档 / 新建分类"**不会**影响 B 账本——它们是不同的行，唯一键都带 `bookId`。

**唯一一处"跨账本共享"的东西**是预设的**名字表**（常量），这是设计意图：
新账本要有可用的一组默认值，而不是空列表。

### 2.5 共享账本的协作者共享同一套配置（已验证事实）

- 读：`GET /api/v1/ledger` 的三条查询都是 `where: { bookId }`，**不含 `userId`**：`apps/api/src/routes/ledger.ts:57-79`。
  同一个 `bookId` 的成员拿到完全相同的分类 / 支付方式 / 标签。
- 写：`POST /categories` 用 `request.book!.bookId`：`classification.ts:62`；
  改名 / 归档先 `findFirst({ where: { id, bookId } })`：`:96-99,133-137,184,206,241,266`。
- **没有"个人私有分类"**：模型里没有 `createdBy`，也没有任何 `userId` 过滤；
  editor A 新建的分类，editor B 下一次请求就能看到。
- viewer **能读**（`GET /ledger` 是读强度，见 §2.6），改不了。

### 2.6 editor / viewer 的读写权限（已验证事实 + 一处文档不一致）

**权限校验位置（唯一来源 `book_members`）**

| 步骤 | 位置 |
|---|---|
| 建两个强度的守卫 | `apps/api/src/app.ts:248-249` |
| 守卫实现（先认证、再判账本） | `apps/api/src/auth/guard.ts:85-95` |
| 成员/角色判定 | `apps/api/src/ledger/access.ts:66-89`（`leftAt` 必须为 null：`:84`） |
| 写强度判定 | `access.ts:98-110`；`WRITE_ROLES = ["editor", "owner"]`：`:64` |
| 分类三模块的注册强度 | **写**：`app.ts:278` `registerClassificationRoutes(…, requireAuth: requireBookWrite)` |
| 交易写 / 统计读 / 导出写 / 导入写 | `app.ts:276,277,281,282` |
| `GET /ledger` 的强度 | **读**：`app.ts:265-275`（传的是 `requireBookRead`） |

**结论**：viewer 可以打开分类页并看到列表（因为列表来自 `GET /ledger` 的读接口），
但**任何写操作都会在服务端被拒**（403 `book_read_only`），这正是所有者要求的
"即使 viewer 通过某种方式发起了更改，服务器的数据也不会被污染"：`app.ts:239-246`。

**已验证的两处瑕疵（不是权限漏洞，是界面/文档）**

1. **界面没有按角色隐藏**：`ManagePages.tsx` 里三个页面对 `useCategoryMutations` 等**没有任何角色判断**
   （`apps/web/src/pages/ManagePages.tsx:158-161,271-274,386-389`），
   而角色在客户端**是拿得到的**——账本齿轮面板就用了 `canWrite = role === "owner" || role === "editor"`
   （`apps/web/src/components/BookManageSheet.tsx:178`）。
   结果：viewer 能点开、能点按钮，点了才 403。**服务端安全，体验差。**
2. **注释与注册强度不一致**：`apps/api/src/routes/ledger.ts:10-14` 仍写"`/ledger` 用的是写强度守卫"，
   而 `app.ts:265-275` 实际传的是读强度。**以代码为准**，注释该改（属 S13-E 的顺手项）。

### 2.7 交易如何引用分类 / 标签 / 支付方式（已验证事实）

**字段与外键**（`prisma/schema.prisma`）

| 引用 | 列 | 约束 | 行号 |
|---|---|---|---|
| 分类 | `categoryId`（**必填**） | FK `onDelete: Restrict` | `:855,900` |

`kind` 与分类**分开存**（`transactions.kind`），这样"分类以后被重新归类"也不影响统计口径：
`schema.prisma:858-860`。

**服务端解析与校验**（都带 `bookId`）

- 更新：`:773-781`。

**前端与离线**

### 2.8 若"改成账本级"需要哪些迁移 / API / 前端 / 离线改动（结论：不需要；下面是核对表）

**必须先说清楚**：当前实现**已经是账本级**，所以这一问的前提不成立。为了让"不改"这个结论可复核，
下面列出**假如今天才从账号级改成账本级**需要付出的东西，并标注现状：

| 改造项 | 假如要改 | 现状 |
|---|---|---|
| 表结构 | 给 `categories/tags/payment_methods` 加 `book_id` 非空列 + 回填 + 重建唯一键 | ✅ **已经是** `book_id NOT NULL`，唯一键含 `book_id`（`:729,755,764,775,783,791`） |
| 迁移脚本 | 需要一次数据回填迁移（把用户级行复制到其账本） | ✅ **不需要**；历史迁移已完成（`prisma/migrations/`） |
| API 契约 | 每个写接口都要新增"目标账本"参数并校验 | ✅ 账本来自 `x-libellum-book` 头，服务端用 `book_members` 判定（`access.ts:119-127`） |
| 预设 | 新账本要自动生成一套 | ✅ `bootstrap.ts:57-81` |
| 前端 | 账本切换后必须整页重载，否则旧缓存的分类会串账 | ✅ 已按重载设计：`useActivateBook` → `setCurrentBook` → `location` 重载（`apps/web/src/lib/queries.ts:264-307`） |
| 离线 | 缓存的分类要按 `账号:账本` 分域 | ✅ `offline/scope.ts:41-50,121-123`；`queries.ts:891` |
| 历史数据 | 旧记账的 `category_id` 必须仍可解析 | ✅ 分类只归档不删（`classification.ts:141`），FK `Restrict`（`:900`） |

**如果 S13-E 之后要引入"账本级偏好"（例如默认币种下放到账本），那才需要真改动**：

- 迁移：`users.default_currency` 保留为账号级默认值，新增 `books.default_currency`（或 `book_preferences`），
  旧值作为"未设置时的回退"——**不能直接把列的语义换掉**（那会让老用户静默改掉偏好）。
- API：`PATCH /api/v1/auth/me` 保持账号级（`apps/api/src/routes/auth.ts:373-385`），
  另加账本级写入口；读时"账本有值用账本、无值用账号"。
- 前端：`user.defaultCurrency` 的 4 个读取点要改成分层解析
  （`SettingsPage.tsx:70`、`StatsPage.tsx:58,83-90`、`DetailPage.tsx:190`、`ExportPage.tsx:378`）。
- 离线：偏好随 `["ledger"]` 缓存即可，无需新存储键。
- **⚠️ 这是"改语义"，需要所有者明确指令**（`AGENTS.md` §5.0 对既有判断的保护同样适用于这类默认值来源）。

### 2.9 历史数据、引用完整性与跨账本泄露风险（已验证事实 + 设计建议）

**引用完整性（事实，机制是"不硬删"）**

| 对象 | 删除方式 | 对历史的影响 | 证据 |
|---|---|---|---|
| 分类 | 只置 `isArchived` | 旧账目仍能解析名字与统计 | `classification.ts:125-145`；`schema.prisma:725-726` |
| 支付方式 | 只置 `isArchived` | 同上 | `classification.ts:202-213` |
| 标签 | **真删除** | 只丢标签链接，**金额不受影响**；界面先报受影响条目数 | `classification.ts:256-274`（`:269`） |
| 分类外键 | `Restrict` | 有账目引用时，数据库层面也不允许删 | `schema.prisma:900` |
| 支付方式外键 | `SetNull` | 即使被删，交易还在 | `schema.prisma:901` |
| 标签外键 | `Cascade` | 删标签只删关联行 | `schema.prisma:1000` |

**跨账本泄露：SQL 层没有发现缺口（事实）**

- 每条分类/标签/支付方式查询都带 `bookId`（见 §2.1/2.2/2.5 的行号）。
- 交易的三个解析函数都带 `bookId`（`access.ts:203-206,248-251,268-271`）。
- 导入、统计、导出、`GET /ledger` 都以 `request.book.bookId` 为唯一账本来源
  （`import.ts:228-241`、`stats.ts:38`、`ledger.ts:48`）。
- 管理接口**完全不碰**分类与交易：`apps/api/src/routes/admin.ts:48`（注释）与全文检索，
  只有 `users / books 计数 / invites / audit / backup_logs`。

**跨账本泄露：真正值得记的结构性风险（事实 + 建议）**

1. **`queryKeys.ledger` 不带 `bookId`**：`apps/web/src/lib/queries.ts:121`，而 `useLedger` 的查询键就是它（`:862-863`）。
   现在**靠"切换账本即整页重载"兜住**（`:264-307`），所以不会串；
   **但只要将来出现"不重载的账本切换"，A 账的分类列表就会喂给 B 账的界面**。
   → **建议**：给该键加上账本（或在 `onSuccess` 里断言 `ledger.book.id === currentBookId()`），
   让"错账本"变成一次显式失败而不是一份看起来正确的界面。
2. **`ManagePages` 的角色判断缺失**（§2.6）：不会泄露数据，但会让 viewer 看到不属于自己的操作入口。
3. **离线缓存里分类是"随响应整包"的**（`storage.ts:36-42` 单键值库 + 按作用域前缀，`scope.ts:121-123`）：
   只要作用域带 `bookId` 就安全；**游客场景下作用域会退化**（见 §2.11），那才是真正的风险点。

### 2.10 入口散落位置与归位建议

**已验证事实：这些入口现在分散在四处**

| 位置 | 内容 | 证据 |
|---|---|---|
| 账户页「我的」 | 分类管理 / 支付方式 / 标签 三个链接 | `apps/web/src/pages/MePage.tsx:36-38` |
| 根级路由 | `/categories`、`/payment-methods`、`/tags`（**不带 `/ledger` 前缀**） | `apps/web/src/App.tsx:246-248` |
| 页面注释 | "三者都从账户（`MePage`）打开，所以声明的父级是它" | `apps/web/src/pages/ManagePages.tsx:32` |
| 设置页「显示与数据」 | 导出数据 / 导入历史账（**作用于当前账本**） | `apps/web/src/pages/SettingsPage.tsx:144-151` |
| 设置页「记账偏好」 | 默认币种（**账号级**，存在 `users` 上） | `SettingsPage.tsx:87-123`；`schema.prisma:102-106` |
| 账本空间齿轮面板 | 账本信息 / 成员 / 分享（**账号页里没有**） | `apps/web/src/components/BookManageSheet.tsx`；`App.tsx:255-277` |

**设计建议：三层划分（S13-E 的核心产出）**

| 层 | 装什么 | 放哪 | 现在 |
|---|---|---|---|
| **用户级** | 个人资料、密码、恢复码、**账号级**邀请码额度、下载管理、软件更新、默认币种（若决定保留账号级） | 账户页 | 一半对（分类被错放进来） |
| **账本级** | **分类 / 标签 / 支付方式**、导出 / 导入、成员、分享、留言、编辑历史、账本信息 | **当前账本 → 账本设置** | 分类三项在账户页；导出导入在设置页 |
| **应用级** | 系统管理（管理员）、版本公告、关于、法律条款 | 设置 / 关于 | 基本正确 |

**原则一句话**：**分类、标签、支付账户属于账本；账号属于人；平台属于应用。**
入口的父级要跟数据的父级一致——**否则用户会以为换账号就换分类，实际是换账本就换分类。**

### 2.11 对 S14 游客本地账本与迁移的兼容影响

**已验证事实：当前离线作用域是 `账号:账本`**

- `scope = account !== "" && ledger !== "" ? account + ":" + ledger : ""`：`apps/web/src/lib/offline/scope.ts:41-50`。
- 只有一半时**故意不设作用域**（宁可不分域也不要看起来正确的错误域）：`scope.ts:92-103`。
- 键由作用域前缀拼出：`scopedKey(base)`：`scope.ts:121-123`。
- 由 `useLedger` 在拿到账本后设置：`queries.ts:877,891`。

**影响一：游客没有账号 → 作用域为空 → 多本游客账本会撞在一起**

游客模式（S14-B）要求"**多本地账本**"（`docs/开发过程记录/S14-游客模式与准入系统-设计要点.md` §1.2），
但没有 `accountId`。按现在的实现，`scope` 会是空串，于是**所有游客账本共用未分域的键**，
与"游客的本地账本不能与账号的离线副本混在一起"（同文档 §1.2 第 4 条）冲突。
→ **建议**：游客作用域用 `guest:<localBookId>`（或引入不依赖账号的本地身份 id），
并在迁移到正式账号时**换域**（复制而非移动，沿用 `migrateUnscopedKeys` 的做法：`scope.ts:125-163`）。

**影响二：分类/标签/支付方式随 `["ledger"]` 响应整包进缓存**

- 服务端一次返回三套元数据：`apps/api/src/routes/ledger.ts:42-113`；契约在 `packages/shared/src/ledger.ts:147-149`。
- 游客模式下没有这个接口（未登录），**必须自带一份本地预设**，否则记账页没有分类可选。
  S14 设计要点已把这条列为开工前必须先解决的项（"本地分类 / 支付方式 / 标签的默认值"）。

**影响三：迁移时不能搬 UUID，只能按名字重建**

- 服务端每本新账本都会**自动生成预设**：`bootstrap.ts:57-81`。
  所以"游客本地分类 A（UUID x）"迁移后在新账本里是**另一行**（UUID y，可能同名、也可能用户改过名）。
- 已有先例可复用：导入按名字在该账本内匹配，找不到就报错让人先建：`import.ts:281-295`。
- **建议规则**：迁移时"按名字匹配 → 命中即复用 → 未命中则新建 → 系统分类（暂无分类）按 `isSystem` 对齐"，
  并要求**幂等**（同一份游客数据重试不产生第二套分类）。

**影响四：权限与隔离不受影响**

迁移完成后，读写仍由 `book_members` 决定（`access.ts:66-89`），
游客数据进入的是一本普通的账本，**不会带来新的权限路径**。

## 3. 已验证事实 vs 设计建议

### 3.1 已验证事实（本轮从代码读出）

1. 分类、标签、支付方式的 `bookId` **必填**，唯一键都含 `bookId`（`schema.prisma:729,755,764,775,783,791`）。
2. 三个模块的写接口**注册的是写强度守卫**，viewer 写入会被服务端拒绝（`app.ts:248-249,278`；`access.ts:98-110`）。
3. `GET /ledger` 是**读强度**，viewer 能读分类（`app.ts:265-275`）。
4. 新建账本**自动生成自己的一套预设**，`bootstrap.ts:21-22` 明写"账本之间不复制"。
5. 交易以 `categoryId`（必填，`Restrict`）/ `paymentMethodId`（可空，`SetNull`）/ `transaction_tags`（`Cascade`）引用（`schema.prisma:855-856,900-901,995-1005`）。
6. **不存在**资金账户 / 余额 / 转账模型；`balanceCents` 只是收支差（`transactions.ts:567`）。
7. 默认币种在 `users` 上（`schema.prisma:102-106`；`auth.ts:373-385`），是**账号级**。
8. 三个管理页挂在账户页，路由是根级 `/categories` 等（`MePage.tsx:36-38`；`App.tsx:246-248`）。
9. 离线作用域是 `账号:账本`，缺一半就为空（`scope.ts:41-50,92-103`）。
10. 管理接口不读分类/交易（`routes/admin.ts:48` 与全文）。

### 3.2 设计建议（**尚未实施，需所有者批准**）

1. **S13-E 只做界面归位**：分类/标签/支付方式进"账本设置"，账户页只留账号项；
   导出/导入标注"当前账本"并归到账本级组。
2. **三层划分**（用户级 / 账本级 / 应用级）写进 `开发计划.md` 与设计规范，作为后续新入口的归属判据。
3. **分类页按 `role` 隐藏写入口**（复用 `BookManageSheet.tsx:178` 的 `canWrite` 判法），
   服务端保持不变（**只新增界面判断，不动任何既有权限判断**——`AGENTS.md` §5.0）。
4. **资金账户另立阶段**：先做"要不要做余额"的产品决定，再谈模型；不要用改名冒充。
5. **游客作用域显式化**：`guest:<localBookId>`，迁移时换域且复制不移动（S14-B/C 的设计输入）。
6. **`queryKeys.ledger` 加账本维度或加断言**，把"换账本不重载"的假设变成显式失败点。
7. 顺手修 `ledger.ts:10-14` 的注释与 `app.ts:265-275` 不一致。
