## 0. 一句话结论（原始审计）

**Libevra 的布局已经相当统一——比预期的更整齐。真正缺少的不是数值统一，而是"名字"。**

| 核实项 | 结果 |
|---|---|
| 页面左右边距 | ✅ **全站统一 24px**，8 个页面无例外，320/390/768 三个视口都成立 |
| 横向溢出 | ✅ **0 处**（27 次测量，三个视口） |
| 圆角 | ⚠️ **源码里只有 7 种写法**，但其中 **`rounded-t-3xl` 与 `rounded-t-card` 是同一个用途的两个值** |
| 间距语义 | ❌ **没有 spacing token**——`@theme` 里只有 `--radius-card` 与 `--radius-field` |
| 列表行内边距 | ⚠️ **三种体系并存**（20px / 21px / 16px），同一个"设置项"职责 |

**⚠️ 所以本轮的结论是"补名字 + 收掉少数真实冲突"，而不是"统一间距"。**
按所有者的话：*"不要因为代码更整洁，就把一个原本舒服的界面改得更松、更厚重."*

## 1. 现有布局系统总体评价

**结论：这是一套"凭直觉但很有纪律"的布局。**

它**没有** spacing token，`@theme` 里只有两个圆角变量；
但它**在行为上**已经收敛到一组稳定的数值——页面边距 24、卡片内边距 20、控件内边距 14、
列表行 20×12、区块间距 16 或 10。

**⚠️ 这有两面**：

- **好的一面**：视觉是统一的，因为它出自少数几个共享组件（`Section`、`SectionFrame`、`Card`、`Button`、`TextField`）。
  **约束来自组件，不是来自 token。**
- **风险的一面**：纪律**没有被写下来**，所以它靠的是"大家都照着上一个页面抄"。
  **本轮审计找到的三处冲突，全部出现在"没人抄"的地方**——新写的页面组件、局部的行、独立的浮层。

> **⚠️ 这与前两轮的结论完全一致**：问题不在数值本身，在**同一职责被写了两次**。

## 3. 全站圆角统计（浏览器实测 + 编译产物核对）

### 3.1 实测分布（390 视口，9 页合计）

| 次数 | 圆角 | 说明 |
|---|---|---|
| **36** | `4px` | 图表日历格（`rounded-sm`）、小 chip |
| **35** | **`14px`** | **`--radius-field`**：输入框、按钮、列表行 |
| **22** | **`20px`** | **`--radius-card`**：卡片 |
| 16 | `18px（50%）` | **正圆**（头像、分类圆标）——**不是 18px 圆角** |
| 9 | `16px` | 记账入口按钮（`rounded-2xl`） |
| 4 | `16px（50%）` | 正圆 |
| 3 | `32px（50%）` | 正圆（大） |
| 2 | `4px（50%）` | 正圆（小） |
| 1 | `20px（50%）` | 正圆 |
| 1 | `10px（50%）` | 正圆 |
| 1 | `9999px` | `rounded-full` 的解析值 |

**⚠️ 关键读法：带「（50%）」的是圆形元素，不是"另一种圆角"。**
把圆形算进去会得出"全站 11 种圆角"的错误结论。**真实圆角只有 5 种：4 / 14 / 16 / 20 / 24。**

### 3.2 ⚠️ 编译产物核对（Tailwind 4 默认值）

| 类 | 实际值 | 等于 |
|---|---|---|
| `rounded-sm` | `0.25rem` | 4px |
| `rounded-2xl` | `1rem` | 16px |
| `rounded-3xl` | `1.5rem` | **24px** |
| `rounded-card` | `var(--radius-card)` | **20px** |
| `rounded-field` | `var(--radius-field)` | **14px** |
| `rounded-t-card` | 上两角 = 20px | |
| `rounded-t-3xl` | 上两角 = **24px** | |

### 3.3 ✅ 已经形成语义等级的部分

**⚠️ 好消息：卡片与控件两层已经是语义化的**——
`--radius-card` 与 `--radius-field` 存在于 `@theme`，**源码里没有一处写死 `rounded-[20px]`**。

| 角色 | token | 值 |
|---|---|---|
| 普通信息卡片 | `--radius-card` | **20px** |
| 按钮 / 输入框 / 列表行 | `--radius-field` | **14px** |
| 圆形元素 | `rounded-full` | 50% |

**⚠️ 所以圆角这一块，本轮不需要"建立体系"，只需要补上**大型容器**这一层（见 §3.4）。**

### 3.4 ⚠️ 发现的真实冲突：底部面板有两种圆角

| 组件 | 写法 | 实测 |
|---|---|---|
| `BookManageSheet.tsx:257` | **`rounded-t-3xl`** | **24px** |
| `MonthPicker.tsx:66` | **`rounded-t-card`** | **20px** |

**两者都是「从底部升起的面板」，是同一个职责，却差 4px。**

**⚠️ 而且这里还有一个更隐蔽的后果**（实测 `className` 与编译产物确认）：
`.rounded-t-card` 的定义是 `border-top-*-radius: var(--radius-card)`，
**而全站唯一使用 `rounded-t-card` 的地方就是 `MonthPicker`**。
所以 **`--radius-card` 这个 token 当前只控制 MonthPicker 的两个上角**——
卡片用的是 `rounded-card`（同一个变量，但走的是另一条规则）。

**⚠️ 这本身没错，但它意味着：改 `--radius-card` 会同时改卡片圆角和 MonthPicker 的上圆角，
而 `BookManageSheet` 不受影响。** 两个面板从此**永远不会一起变**。

> **⚠️ 这是本轮唯一一处"同职责两个值"，建议归并（但不在本轮改）。**
> **保守建议：统一到 `--radius-card`（20px）**——因为 `.rounded-t-card` 已经是为面板准备的写法。
> **⚠️ 需所有者确认**：24px 也可能是**有意**让面板比卡片更圆，那属于"设计目的"而非遗留。

**⚠️ 另注**：另一个会话正在改 `BookManageSheet`（1.10.18 记录提到"气泡内边距与圆角"）。
**实施前需与它协调，避免冲突。**

## 5. 浏览器实测的对齐结果

### 5.1 ✅ 对齐正确的部分

| 检查项 | 实测 |
|---|---|
| 页面标题与内容容器左对齐 | ✅ 绿头 `px-6`（24）与区块 `px-6`（24）一致 |
| 同级卡片左右边缘 | ✅ 同一页内卡片左边缘全部 24px |
| 区块标题起始位置 | ✅ 均由 `Section` / `SectionFrame` 的 `px-6` 决定 |
| 图标与文字垂直居中 | ✅ 由 `items-center` 保证，无实测偏差 |
| 底部与导航栏距离 | ✅ 全部页面一致（见 §5.3） |

### 5.2 ⚠️ 行内文字偏置：三种体系

**卡片左边缘 = 24px 是统一的。但"卡片内文字从卡片边缘缩进多少"有三种值：**

| 页面 | 卡片左 | 行内文字左 | **偏置** | 来源 |
|---|---|---|---|---|
| `/settings` 设置 | 24 | **45** | **21** | 行 `px-5`（20）+ 卡片边框 1 |
| `/categories` 分类 | 24 | **45** | **21** | 同上 |
| `/profile` 个人资料 | 24 | **49** | **25** | 卡 `p-6`（24）+ 边框 1 |
| `/me` 账户 | 24 | **49** | **25** | 行内元素自带 24 + 1 |
| `/export` 导出 | 24 | **40** | **16** | 行 `px-4`（16） |
| `/ledger` 账本（历史/卡片） | 24 | **41** | **17** | 卡 `p-4`（16）+ 1 |
| `/stats` 分析 | 24 | 41 / 57 / 61 | 17 / 33 / 37 | 图表内部布局，**专用** |

**⚠️ 分析这 4px 的真实原因**（按所有者要求，不只报数字）：

- **21 vs 25 的差别不在"行"上**，而在**外层卡片的 padding**：
  `/settings` 的列表卡是 `p-0` + 行自带 `px-5`（20）；
  `/profile` 的卡是 `p-6`（24）——**两者都是"卡片给内边距"，只是给在了不同层**。
- **所以这不是对齐错误，是两种容器结构**：
  **A. 卡无内边距 + 行自带**（设置、分类）；**B. 卡有内边距 + 行无**（个人资料）。
- **⚠️ 两者视觉上都成立，但混用会让"同一页里两种行"看起来差 4px。**
  **建议归并的是"用哪一种"，而不是"把 21 改成 25"。**

**✅ 正确的做法（本轮不做）**：确定**列表型卡片一律走 A**（卡 `p-0`，行 `px-5`），
因为它还能让分隔线通到卡片边缘（现在设置页正是如此，视觉更好）。

### 5.3 ✅ 底部安全区与导航

| 检查项 | 实测 |
|---|---|
| 底部导航 | 固定，`rounded-2xl`（16px）——**浮起式，不是贴底栏** |
| 页面底部留白 | `0/24/26/24`：**26px 是避让浮起导航的计算值** |
| 当前账本提示 | 位于导航上方，与标签同级（1.10.11 已定） |
| 安全区 | `env(safe-area-inset-bottom)` 已用于底部面板 |

**✅ 无遮挡。⚠️ 26px 这个非整数值是"避让"算出来的，属于 §10 的技术性例外，不应被间距体系覆盖。**

## 7. 建议的间距语义等级（**4 个 token，不是 20 个**）

**⚠️ 所有者的原则**：*"只有真正经常复用、具有明确职责的布局数值才值得语义化."*

按 §2 的实测，**只有下面 4 个既高频又职责明确**：

| token | 值 | 现有类 | 实测用量 | 职责 |
|---|---|---|---|---|
| `--spacing-page-x` | **24px** | `px-6` | 9 页全部 | **页面左右边距（唯一基准）** |
| `--spacing-card` | **16px** | `p-4` | 7+ | **普通卡片内边距** |
| `--spacing-row-x` | **20px** | `px-5` | 14+ | **列表行水平内边距** |
| `--spacing-control-x` | **14px** | `px-3.5` | — | **输入框水平内边距** |

**⚠️ 明确不 token 化的**：区块间距（`pt-7`/`pt-8`/`pt-6`）、`gap` 的 2/4/8/12、
以及所有只出现一两次的值。**它们继续用 Tailwind 默认 scale**——
**在 `@theme` 里加 `--spacing-*` 会覆盖 Tailwind 的整套 scale，是重复竞争的系统**（违反所有者第八条）。

**⚠️ 实现方式建议**：这 4 个**不必是 CSS 变量**，可以是
**共享组件里的一个常量**（如 `Section` 的 `px-6` 已天然承担了 `spacing-page-x`）。
**⚠️ 更诚实的做法是先只写文档、不动代码**——因为**它们已经一致了**，
token 化只是让"一致"变得可查询。

### ⚠️ 7.1 实测：加 `--spacing-*` 会覆盖 Tailwind 的整套 scale（**已用构建验证，不是推测**）

为确认风险，我**临时**在 `@theme` 里注入了一行 `--spacing-4: 99px` 并重新构建
（**随后已移除，`index.css` 无残留，构建通过**）。结果：

| 类 | 注入前 | 注入后 |
|---|---|---|
| `.p-4` | `padding: calc(var(--spacing) * 4)` = 16px | **`padding: var(--spacing-4)` = 99px** |
| `.gap-4` | 同上 | **`gap: var(--spacing-4)` = 99px** |
| `.px-6` | `calc(var(--spacing) * 6)` | 不变（未定义 `--spacing-6`） |
| `.pt-7` | `calc(var(--spacing) * 7)` | 不变 |

**⚠️ 结论：Tailwind 对**四的倍数档**（`p-4`、`gap-4`…）会优先读 `--spacing-4`；
没定义的档位才回落到 `--spacing × N`。**

**⚠️ 这意味着：在 `@theme` 里加一个 `--spacing-4`，会同时改变全站所有 `p-4`/`gap-4`/`mt-4`——
包括图表日历格那 36 个 `4px` 圆角所在的地方，以及所有卡片内边距。**

**⚠️ 所以这正是所有者禁止的"与现有系统平行而冲突的新体系"**：
Tailwind 的 spacing scale **已经是**那套系统，再加一层只会互相覆盖。
**→ 建议：这一轮不要新增任何 `--spacing-*`。**

> **⚠️ 与所有者的候选表对照**：他提的 4/8/12/16/24/32 **基本就是项目现状**。
> **实测多出来的是 2、6、10、14、20**——其中 **14 与 20 是控件与行的基准，值得保留**；
> **2 和 6 是"半档微调"，10 是图表内部值**。**不建议为了凑整把它们改掉。**

### 15.4 ⚠️ 为什么底部面板的圆角与卡片**分开**

所有者裁决：*"底部面板属于大型浮起式交互容器，与普通卡片不是同一种组件……
未来修改底部面板圆角时，不应该连普通信息卡片的圆角一起改变."*

**⚠️ 关键不在那 4px，而在"改一个不会连带改另一个"。**
`--radius-card` 同时画着**所有信息卡片**，所以如果把面板绑在它上面，
**"让面板更圆"和"让卡片更圆"就会永远变成同一次编辑**。

**⚠️ 另一个具体理由**：`.rounded-t-card` 的定义是 `border-top-*-radius: var(--radius-card)`，
**改 `--radius-card` 会同时改卡片和它的消费者**——面板与卡片从此无法分别演进。

### 15.5 ⚠️ Bottom Sheet 的判定标准（避免以后误判）

**本轮只把 2 个组件认定为 Bottom Sheet**，判定依据是**「从视口底边升起、覆盖在内容之上的浮层」**：

| 是 Bottom Sheet ✅ | 不是 ❌ |
|---|---|
| `BookManageSheet`（`fixed inset-x-0 bottom-0`） | 普通 `Dialog`（居中，四角都圆） |
| `MonthPicker`（底部升起的选择面板） | 弹出菜单（锚定在触发元素旁） |
| | 卡片（在文档流里，四角都圆） |

**⚠️ 判据不是"圆角大不大"，而是"它是不是从底边长出来的"。**
**⚠️ 因此 `rounded-t-sheet` 只设上两角；普通 Dialog 与卡片继续用 `rounded-card`（四角）。**

### 15.6 ✅ 不新增全局 spacing token（**已否决，不要再提**）

所有者的决定：*"不新增全局 `--spacing-*` 变量，不建立新的间距配置体系."*

**§7.1 的实测数据支持这个决定**：注入 `--spacing-4: 99px` 后，`.p-4` 与 `.gap-4`
立刻从 `calc(var(--spacing) * 4)` 变成 `var(--spacing-4)`——
**Tailwind 对 4 的倍数档会优先读 `--spacing-N`**，所以加一个变量会全站连动。

> **⚠️ 一条应当长期保留的原则（所有者原话）：**
> **"并不是所有设计规则都必须成为 CSS token。共享组件本身也可以是规则的唯一来源。"**
>
> **本项目的页面横向基准（24px）就属于这一类**：它由 `Section` / `SectionFrame` / `TabPageHeader`
> 的 `px-6` 共同保证，**没有 token，但有一个来源**。

**⚠️ 因此 §7 里"建议的 4 个间距 token"与 §11 的 P2-3 均已作废。**
文档保留它们是为了记录"考虑过并否决"，**不是待办事项。**

### 15.7 最终圆角语义等级

| 角色 | 实现 | 值 | 用在哪 |
|---|---|---|---|
| 小型控件 / 图表格 | Tailwind `rounded-sm` | **4px** | 图表日历格 |
| **控件 / 列表行 / 输入框** | **`--radius-field`** | **14px** | 按钮、输入框、列表行、chip |

### ⚠️ 测量过程中的两个陷阱（已修正，记录以免重犯）

**① 开发服务器当时没在运行，而探针指向 HTTPS。**
第一次 27 次测量**全部返回同一份数据**——那是 Chrome 的"无法访问此网站"错误页。
**"每个页面都一致"看起来像结论，其实是没有数据。**

**② 修好之后仍全部相同：cookie 域与 scheme 不匹配。**
Vite 默认只监听 **HTTP `127.0.0.1:5173`**（HTTPS 仅在 `LAN=1` 时启用）；
`secure: true` 的 cookie 在 HTTP 下被丢弃，域写成 `localhost` 又送不到 `127.0.0.1`——
**结果每次都被重定向到 `/login`。**

**⚠️ 所以探针现在会先核对 `location.pathname`，不等于目标路径就直接报错。**
**拒绝测量错误页，比发表一张"看起来很像数据"的表更重要。**
