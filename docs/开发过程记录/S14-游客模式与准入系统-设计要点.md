## 0. 一句话结论

**S14 要先回答四个问题：谁能进来（入口与名额）、没有账号能不能先用（游客本地）、
游客怎么参与共享账本（受限云端）、邀请码怎么发而不被滥用（额度与风控）。**

这四个问题互相牵连：名额决定"公开注册"是否可用，邀请额度决定"熟人网络"是否可扩张，
游客决定"第一次接触"是否需要账号，云端协作决定"游客"是不是一个真正的服务端身份。
**所以必须先做可行性与规则拍板，再写第一行代码。**

## 1. 范围（六块）

> **只写方向与可行性。** 每一块都列出"必须满足什么"和"本文不决定什么"。

### 1.1 统一登录 / 注册 / 游客入口

**目标**：一个入口页，四条路径并列——

| 路径 | 需要的凭据 | 现在有没有 |
|---|---|---|
| **账号登录** | 用户名 + 密码 | ✅ 已有（`/login`） |
| **公开注册** | 无邀请码，但受**每日名额**约束 | ❌ 不存在 |
| **邀请码注册** | 邀请码 + 用户名 + 密码 | ✅ 已有（`/register`，但注册页只接受邀请码） |
| **游客模式** | 无账号 | ❌ 不存在 |

**必须满足**

- **公开注册名额耗尽时，其余三条路径仍然可用**——名额只约束"公开注册"这一条，
  不能把登录页或邀请码注册一起关掉。
- **复用现有登录 / 注册页的视觉与组件**，**不造第二套认证系统**、不新增第二套账号模型。
- 四条路径的**告知**要清楚：哪些数据在服务器、哪些只在本机、游客数据什么时候会丢。

**本文不决定**

- 入口怎么摆、按钮文案、先展示哪一条（UI 设计阶段再定）。
- 公开注册要不要与邀请码注册共用一个表单（实现细节）。

### 1.2 游客本地记账

**目标**：**免账号**也能先记账；**多本地账本**；基础记账 / 分类 / 账户 / 分析 / 导出。

**必须满足**

- **数据默认只留本机、不上传。**
- **必须明确提示**：清缓存、换设备、设备损坏会丢数据。
- 转正式账号时做**安全迁移**：**防重复记账、防归属错误、迁移失败不删本地**。
- 游客的本地账本**不能与账号的离线副本混在一起**（否则同一台设备换账号会串数据）。

**本文不决定**

- 游客最多能建几本本地账本。
- 游客是否拥有完整的"账户 / 分类 / 标签"管理，还是只给一组默认值。
- 游客导出先做 CSV 还是同时做 XLSX（见 §2.3）。

### 1.3 受限云端游客协作（方案 B）

> **先可行性分析，不实施。** 这一块最贵、风险最高，**不排进 S14 的必须交付**。

**目标**：用户**明确同意**后获得**受限游客身份**；通过**邀请链接 / 二维码 / 短时配对码**
**加入或创建共享账本**；**服务端保存与同步，不要求创建者在线**。

**必须满足（设计时）**

- **游客不参与全站搜索**；权限受限（能读 / 能写 / 能否邀请，待定）。
- **设备丢失处理**：游客没有密码/恢复码时，换机或丢机怎么办？
  创建者能否移除该游客？旧设备的会话如何作废？
- **滥用限制与配额**：一个游客能加入几本账、每天能创建几本、能发多少邀请。
- **共享权限**：游客在共享账本里是 viewer 还是 editor？能不能邀请别人？
- **升级迁移**：游客转正式账号后，原有共享关系、账本归属、历史记录怎么处理。

**本文不决定**

- 游客的服务端身份是"受限 `User`"还是"独立的 guest 主体"（见 §2.5，这是硬分叉）。
- 短时配对码的有效期、次数、是否一次性。
- 是否允许游客创建共享账本，还是只能加入别人创建的。

### 1.4 动态公开注册名额

**目标**：**每日有限名额**（例如首日 20，视需求与风险逐步增加）；**分批释放 + 随机偏移**；
当天未用可**有限累计**，**不可无限结转**；服务端**原子扣减**，**防并发超额**；
**不能仅凭名额耗尽判断需求**（要排除机器人抢注）；异常时**自动收紧**。

**必须满足**

- 名额判定**只在服务端**；客户端显示的数字不是权限。
- **原子扣减**：并发请求不能超过当日剩余名额。
- 名额耗尽的**时间、速度、请求来源**要能被观察，否则无法区分"需求大"与"被刷"。
- 异常时**只收紧名额 / 转人工审核**，**不自动封禁账号**。

**本文不决定（全部待所有者拍板）**

- 首日多少、每天多少、上限多少、按什么节奏增加。
- 分批释放的时间点、随机偏移的范围、时区。
- 未用名额结转几天、累计上限多少。
- 异常阈值、自动收紧的幅度、恢复方式。

> ⚠️ **不得把示例数字当成决定**：本文出现的"20"只是所有者举的例子。

### 1.5 新版邀请码制度

**目标规则（所有者 2026-10-17 给出，尚未实施）**：

| 规则 | 内容 |
|---|---|
| **成熟期** | 注册未满 **7 天**无生成额度 |
| **首次额度** | 满 **7 天**得 **1 次** |
| **月度额度** | 满 **14 天**后，**每月 1 日**再得 1 次 |
| **累计上限** | **未用额度最多累计 2 次** |
| **已生成的码** | **仍 7 天有效** |
| **被邀请用户** | **同样适用成熟规则，不再永久禁邀** |

**必须区分两个东西**

| 概念 | 含义 | 例子 |
|---|---|---|
| **生成额度** | "现在还能发几次" | 满 7 天 +1；这个月还没用 |
| **已生成邀请码** | "已经发出去的码" | 7 天后过期；用一次就消耗掉 |

**⚠️ 它们不是同一个计数。** 把"还能发几次"和"已经发了几个"混成一个数字，
会出现"码过期了额度却没回来"或"额度用完了但码还能发"的两种错误。

**本文不决定**

- 月度发放按哪个时区（服务器 UTC？香港？所有者所在地？）。
- "满 7 天 / 满 14 天"的边界：当天算不算、按自然日还是 24 小时。
- 额度消耗顺序、能否透支、同一天重复生成的保护。
- 老账号怎么处理（已经用掉终身 3 个的，是否按新规补发；生效日）。
- 邀请链滥用的上限（一个账号最多能带来多少层/多少人）。

**⚠️ 边界**：**本轮不改生产规则、不影响 S13 的邀请码管理**。
S13 管的是**管理员发出的注册邀请码**（`RegistrationInvite` 的一类），
这里说的是**账号级邀请码（次级码）**——**两者不是同一件事**，不要合并。

### 1.6 异常注册检测与邮件告警

**目标**：监测**异常注册、配额快速消耗、异常兑换、无正常使用行为的批量账号**。

**必须满足**

- **优先用注册时间 / 邀请关系 / 速率 / 汇总指标**，**不读私人账本内容**（金额、备注、分类一律不读）。
- 可疑情况**优先人工审核，不自动封禁**。
- **复用已有 Resend 告警通道**，但必须**去重、汇总、限频**，**防止邮件轰炸**。
- 告警要能回答"发生了什么、多少、什么时候、要不要现在处理"，而不是只发一句"有异常"。

**本文不决定**

- 具体指标与阈值（例如"1 小时内同一 IP 注册 5 个"）。
- 是否允许读"账本数量 / 记账笔数"这类**汇总计数**（不读内容）。
- 告警收件人、汇总频率（每小时 / 每天）、保留期。
- 自动收紧是"降名额"还是"暂停公开注册"。

## 2. 可行性要点（基于当前代码）

> **这一节是本文最重要的部分。** 结论都尽量指到文件/行为；**没验证的地方写"未验证"**。

### 2.1 认证与注册现状

| 事实 | 证据 / 位置 |
|---|---|
| 注册**必须**带邀请码；请求体是 `inviteCode + username + displayName + password` | `packages/shared/src/auth.ts` 的 `registerRequestSchema` |
| 邀请码**一次性**：注册事务里用 `updateMany where usedAt: null, revokedAt: null` 抢占 | `apps/api/src/routes/auth.ts`（注册事务） |
| 普通邀请码 **7 天**、预留编号码**不过期** | `docs/开发计划.md` S2 / `docs/生产环境日常掌控速查.md` §4 |
| 注册会**创建默认账本**（分类 / 支付方式） | `apps/api/src/routes/auth.ts` 调 `createDefaultLedger`；`apps/api/src/ledger/bootstrap.ts` |
| 会话是 httpOnly Cookie；每个请求用 `Session → User` 校验 | `apps/api/src/auth/guard.ts` 的 `createRequireAuth` |
| 账号可被管理员停用；停用会删全部会话 | `apps/api/src/admin/accounts.ts`；`auth/guard.ts` |
| **没有**"游客"概念、没有公开注册、没有每日名额 | 代码与 schema 中均未找到 |

**结论**：公开注册不是"把邀请码校验去掉"这么简单——它要新增一条**不带邀请码**的注册路径，
以及一个**与邀请码无关**的名额闸门。邀请码路径必须保持原样（S13 的邀请码管理依赖它）。

### 2.2 离线层：哪些能复用、哪些绑定账号

| 能力 | 现状 | 游客可复用？ |
|---|---|---|
| 键值存储 | IndexedDB 数据库 `libellum`，一个 object store `kv`（`apps/web/src/lib/offline/storage.ts`） | ✅ **可复用**（通用 KV） |
| 本地账目 / 印记 | `ledger-months` / `ledger-marks`，键由 `scopedKey()` 生成 | 🟡 **键设计可复用**，但 scope 需要游客命名空间 |
| 离线作用域 | `账号:账本`（`scope.ts` 的 `setOfflineAccount` + `setOfflineBook`；两半缺一不可） | ❌ **绑定账号**：游客没有 `userId` |
| 本地统计 / 筛选 | `localStats.ts` / `filterLocally` 等纯函数 | ✅ **大概率可复用**（只要账目形状一致） |
| 本地账目合并 / 视图 | `ledgerView.ts`、`localLedger.ts` 的外部 store | 🟡 可复用，但要保证**不与账号 scope 混读** |
| 同步 / 写入队列 | `sync.ts` / `write.ts` 全部走 `apiFetch`，需要登录态与服务端账本 | ❌ **不可复用**（游客没有服务器） |
| 下载管理 | 按月从 API 下载 | ❌ 不适用 |
| 持久化查询缓存 | 按 scope 持久化 | 🟡 可复用，需新增游客 scope |
| 持久化存储申请 | `navigator.storage.persist()` | ✅ 可复用（但**不能把它当成"不会丢"的保证**） |

**结论**：**"本地读写"这一层大部分能复用，"同步与权限"这一层全部绑定账号。**
游客模式不是"给现有应用加一个开关"，而是要新增一条**本地-only 的写入与数据源路径**，
并让它在界面上与账号路径**互不串数据**。

### 2.3 游客本地账本缺什么

| 缺的东西 | 为什么现在没有 | 影响 |
|---|---|---|
| **本地账本元数据** | 账本列表来自 `GET /books`，本地只按 `bookId` 存账目 | 游客要多本地账本，必须新增一份本地账本注册表（名称、币种、创建时间、当前账本） |
| **分类 / 支付方式默认值** | 由服务端 `createDefaultLedger` 写入；默认清单在 `apps/api/src/ledger/presets.ts` | 游客要么本地复制一份（会形成**第二份清单**），要么把清单移到 `shared` 供两端共用 |
| **本地导出** | `GET /api/v1/export` 需要登录 + 账本；XLSX 生成器在 `apps/api/src/export/xlsx.ts` | CSV 可用 `shared/spreadsheet` 的 `csvRowEscaped` 在浏览器生成；**XLSX 需要把生成器移到 `shared` 或先不做** |
| **游客身份** | 离线 scope 的第一半是 `userId` | 需要一个新的游客标识（例如设备级 guest id），且**不能冒充真实 userId** |
| **游客数据边界** | 现有 key 都是 `账号:账本` | 游客 key 必须用独立前缀（如 `guest:<deviceId>:<bookId>`），否则换账号会读出游客数据 |

**⚠️ 一个必须提前定的取舍**：默认分类清单只有一份，还是两份？
**两份清单迟早会漂移**（`教训.md` §8.7）。建议**把默认清单放到 `shared`**，
但这属于代码改动，**不在本轮**。

### 2.4 游客 → 正式账号的安全迁移

**可复用的地基（好消息）**

- 账目主键由**客户端生成 UUID v7**，服务端接受客户端 id（`prisma/schema.prisma` 的 `Transaction.id`）。
- **幂等键** `idempotency_key` 全局唯一（`Transaction.idempotencyKey @unique`）；
  同一笔重发不会产生第二笔。
- 迁移可以复用**现有创建账目接口**（而不是直接写库），这样校验、幂等、权限都是同一条路径。

**必须解决**

| 风险 | 做法（方向，不是实现） |
|---|---|
| **重复记账** | 迁移时保留原 id / 幂等键；重试只重发同一批；迁移前先查目标账本是否已有同 id |
| **归属错误** | 迁移必须显式选择目标账号与目标账本；**不能默认"当前账本"**；服务端用 `book_members` 判定 |
| **迁移失败不删本地** | 只有服务端**确认全部成功**后才标记本地为"已迁移"；失败保留原数据并可重试 |
| **分类 / 支付方式映射** | 游客的本地分类可能是自建的；迁移时要么按名称匹配，要么让用户选映射；**不静默丢弃** |
| **半迁移** | 记录迁移批次与进度；重复进入迁移页能继续，不会从头发一遍 |
| **换设备** | 游客数据在旧设备上；新设备登录正式账号看不到，除非先迁移 |

**⚠️ 迁移不是一个"按钮"，是一组可重入的步骤。** 验收时必须测"重复点、断网、中途刷新"三种情况。

### 2.5 云端游客的身份问题（方案 B 的硬分叉）

**现状**

- 所有账本接口都要求 `requireAuth`；它每次都查 `Session → User`（`auth/guard.ts`）。
- 分享链接加入（`POST /api/v1/share/:token/join`）同样要求登录（`routes/share.ts`）。
- 账本权限唯一判据是 `book_members`（`ledger/access.ts`），**不看任何管理员字段**。
- `User` 模型要求 `username` 唯一、`passwordHash` 非空；没有"游客"字段。

**两种可选身份模型（未拍板）**

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 受限 `User`** | 给游客创建一条 `User`（随机用户名、随机密码哈希或不可登录标记），发一个受限会话 | 复用现有 `requireAuth` / `book_members`，**不新增鉴权路径** | 污染用户表；`username`/编号要占位；**全站搜索必须显式排除**；会话/恢复/停用规则要重新想 |
| **B. 独立 guest 主体** | 新表 + 新 guard，账本成员表要能同时指向 user 与 guest | 语义干净，不污染用户表 | **必须新增一层鉴权**；`book_members` 的外键/唯一约束要改；**不能改既有敏感判断**（AGENTS §5.0），只能在旁边新增 |

**⚠️ 一条硬约束**：**不能为了游客去改写 `requireAuth`、`book_members` 判定或管理员五道校验。**
`AGENTS.md` §5.0 明确：敏感权限**只许新增，不许改动既有判断**。
所以无论选 A 还是 B，都必须是**新增一层**，并在测试里钉住旧行为不变。

**⚠️ 还有一条**：如果走 A，"游客不参与全站搜索"不能只在界面上隐藏——
`directory/lookup` 的查询必须显式排除游客（这是一条**新增**过滤，不是改旧判断）。

### 2.6 名额的原子性与数据模型（方向）

**可复用的模式**：邀请码注册已经有一个**一次性原子占用**的写法——
`updateMany where usedAt: null, revokedAt: null`，只有一个请求能成功。
每日名额可以用同样的思路，但**不要直接复用邀请码表**：邀请码是**凭据**，名额是**配额**，
两者的生命周期、展示规则、审计含义都不同。

**可能的实现方向（未拍板）**

1. **一行一天的配额表**：`day` 主键 + `granted` + `used` + `released_at`；
   扣减用一条 `UPDATE ... SET used = used + 1 WHERE day = $1 AND used < granted RETURNING used`
   （Postgres 行锁保证原子），或 `SELECT ... FOR UPDATE`。
2. **预生成"名额槽"**：像邀请码一样预生成单次槽位，注册时抢占。
   好处是复用"抢占"模式；坏处是**又造一套一次性凭据**，还要清理过期槽。
3. **惰性计算**：按日期 + 配置 + 当日随机种子算出"应该放出多少"，
   注册时在事务里扣减。**可以避免新增调度器**，但算法要非常小心（可测试、可复现）。

**⚠️ 不新增第二份计数**：如果既有 `granted` 又有"已注册人数"能推导，
就不要同时存两个会漂移的数字（`教训.md` §8.7）。

**现状**：API **没有常驻调度器**（未找到 `setInterval`/cron）。
分批释放要么依赖宿主机 timer（现有 timer 只服务备份，**不要顺手改**），
要么做**惰性计算**。这一点必须在 S14-A 里定。

### 2.7 邀请额度的现状与改动面

| 现状 | 值 / 位置 |
|---|---|
| 邀请码有效期 | **7 天**（`REFERRAL_REMINDER_TTL_MS = 7 * 24 * 60 * 60 * 1000`） |
| 终身上限 | **3 个**（`REFERRAL_CODE_LIFETIME_LIMIT = 3`） |
| 计数口径 | 该账号**生成过的所有码**都算（含已撤销 / 已过期），从 `createdByUserId` 数 |
| **被邀请者** | **不能生成**（`referredByUserId !== null` → `referral_not_allowed`） |
| 计数存储 | **没有单独的额度表/列**，完全由 `registration_invites` 行推导 |

**新规则与现状的差异**

- "终身 3 个" → **按成熟度发放**（7 天 1 次、14 天后每月 1 日、累计上限 2）。
- "被邀请者永久禁邀" → **被邀请者也按成熟规则发放**。
- "7 天有效" → **保持**。

**⚠️ 改动面**：这不只是改两个常量。
`mintReferralCode` 现在的判断顺序是"是否被邀请 → 是否 demo → 是否超过 3 个"，
新规则要引入**时间窗口**与**额度账本**；而"被邀请者禁邀"是一条**敏感判断**，
改动它必须得到所有者明确指令 + 补测试（AGENTS §5.0）。

**⚠️ 老账号**：已经用掉 3 个的账号，新规下还能不能发？生效日怎么算？
**这是所有者的事，不是实现者能定的。**

### 2.8 告警通道的现状

| 事实 | 说明 |
|---|---|
| 已有 Resend 告警 | `deploy/alert-mail.sh`，通过 Resend HTTPS API 发信 |
| 配置 | `deploy/.backup-mail.env`（600，不进仓库）：`MAIL_API_KEY` / `MAIL_TO` / `MAIL_FROM` |
| 多收件人 | `MAIL_TO` 支持逗号分隔 |
| 现状用途 | **备份失败 / 恢复失败 / 失联告警**，是**宿主机 shell 脚本**，不是 API 模块 |
| 已验证 | 2026-10-17 邮件与失联告警真实收件通过（`S12-C-最终验收记录.md`） |

**结论**：**通道可以复用，代码不一定能直接复用。**
异常注册检测在 API 侧（要读注册数据），要么：
① 新增 API 侧的发信模块，复用同一套 Resend Key 与发件域；
② 定时把汇总结果交给宿主机脚本发信。
**两条路都要评估**，不要假设"已经有 Resend 了所以直接调一下就行"。

**⚠️ 告警纪律**：去重键 + 汇总窗口 + 冷却时间；同一异常不在一天内反复发；
邮件里**不出现账本内容、不出现邀请码明文、不出现密码/会话**。

## 附录 A · R1 局域网用户发现（候选研究 · **暂缓**）

**结论：暂缓，不排期，不作为上线硬阻塞。**

### A.1 为什么暂缓

| 理由 | 具体 |
|---|---|
| **Web/PWA 没有可靠统一的发现能力** | 浏览器不暴露 mDNS/Bonjour；网页不能主动扫描局域网；WebRTC 需要信令与权限，且它不是"发现" |
| **权限限制** | 设备可见性、网络权限、企业/校园网隔离、AP 隔离，都会让"能看到"变成偶然 |
| **可见 ≠ 可信** | 同网段出现一个设备，不等于它是谁的、能不能共享账本；信任仍要一次明确邀请 |
| **复杂度高** | 发现、配对、信任、撤销、跨平台差异，每一层都是新面 |
| **S14 范围已经够大** | 游客 / 公开注册 / 邀请额度已经占满准入这一层 |

### A.2 当前替代

- **二维码**（已有分享链接二维码）
- **邀请链接**（已有，1–7 天 / 1–10 人）
- **短时配对码**（游客云端协作可能用，未做）

它们都是**显式、可撤销、可审计**的，比"自动看到"更符合"共享账本要对方同意"的规则。

### A.3 未来方向

如果 R2 的结论是"需要原生能力"，再研究原生 **mDNS/Bonjour**：

- iOS：`NSLocalNetworkUsageDescription` + Bonjour 服务声明 + `NWBrowser`。
- Android：`NsdManager`。
- **它是原生客户端的能力，不是 Web 的**；没有 R2 就不做 R1 的实现。

### A.4 明确不做

**本轮不实现、不建表、不加权限、不改分享链接。**

## 附录 B · R2 移动客户端与本地数据可靠性评估（研究 · **只评估**）

**初步结论**：**A 继续 Web/PWA 仍是基线**；B Capacitor 是"要应用商店 / 本地通知 /
更强文件能力"时**成本最低的增量**；C/D 只在"必须原生且愿意承担双端维护"时才考虑。
**不要求原生客户端完成才能上线。**

### B.1 四种方案

| 方案 | 是什么 | 代码复用 | 初判 |
|---|---|---|---|
| **A 继续 Web/PWA** | 现状：React SPA + Service Worker + IndexedDB | 100% | 零迁移；**iOS 通知 / 后台受限是真实短板** |
| **B Capacitor 打包** | 现有 Web 代码套原生壳 + 插件 | 大部分 | **改动最小**；**仍是 WebView，不等于完整原生能力** |
| **C React Native** | 重写 UI 与数据层（可复用 shared 逻辑 / API） | 部分（逻辑/接口） | 成本高；**离线 / 同步逻辑要重做一遍** |
| **D 原生双端** | Swift / Kotlin 各写一套 | 少 | 成本最高；双端长期维护；与"一个人维护"冲突 |

### B.2 12 个维度对照（初步）

> 评分是**方向性判断**，不是最终结论；详细评估报告在 S14-A 之后另出。

| # | 维度 | A Web/PWA | B Capacitor | C React Native | D 原生双端 |
|---|---|---|---|---|---|
| 1 | **代码复用与要改的模块** | 全部 | 大部分；壳 + 插件 + 构建配置 | UI/数据层重写；shared/API 可复用 | 全部重写 |
| 2 | **本地持久化** | IndexedDB（**不是临时缓存**，但可能被浏览器回收） | 同一套 IndexedDB（WebView）+ 可选择 SQLite/私有目录插件 | SQLite / 文件系统（更可控） | SQLite / 私有目录（最可控） |
| 3 | **离线与恢复同步** | 已实现（印记 + 幂等 + 冲突） | 可沿用 | 需重做同步/冲突 | 需重做 |
| 4 | **后台限制与后台同步** | iOS 最弱；Android 也受限 | 原生后台任务插件可改善 | 较好 | 最好 |
| 5 | **设备能力**（文件/图片/OCR/语音/相机/通知） | 相机/文件/语音基本可用；通知弱；OCR/语音仍走服务器 | 插件补齐文件/通知/相机；OCR/语音仍可走服务器 | 全面 | 全面 |
| 6 | **iOS Safari/PWA 与 Android/打包差异** | iOS 存储回收、通知/安装限制 | WKWebView 仍受 iOS 限制 | 原生控件，差异小 | 原生，差异最小 |
| 7 | **多设备协作与游客迁移** | 已有账号/共享账本；游客迁移要新做 | 可沿用 | 需重做 | 需重做 |
| 8 | **安全与设备密钥/备份/隐私** | Cookie/HTTPS/IndexedDB；设备密钥要新设计 | 可用 Keychain/Keystore 插件 | 原生密钥库 | 原生密钥库 |
| 9 | **开发测试维护成本与长期债** | 最低 | 中（构建/签名/插件升级） | 高（双端/生态） | 最高 |
| 10 | **APK 分发更新与 iOS 签名/TestFlight/App Store** | 无 | 需要（Android 侧载/商店；iOS 签名/审核） | 同 B | 同 B |
| 11 | **是否先 Android 再 iOS** | N/A | 可以（Android 侧载成本低） | 可以 | 可以 |
| 12 | **Web 真无法解决 vs 实现不足** | 通知/后台/局域网发现是"真做不到"；相机/文件/语音/离线读写大多"做得到或已做" | 仍受 WebView 限制 | 真原生能力 | 真原生能力 |

### B.3 成本差异（方向性）

| 方案 | 一次性成本 | 长期成本 | 换来的 |
|---|---|---|---|
| **A** | 0 | 最低 | 现状 |
| **B** | 小–中（壳、插件、签名、构建） | 中（每次 Capacitor/系统升级要跟） | 图标、应用商店、本地通知、部分文件能力 |
| **C** | 大（UI + 数据层重写） | 高（双端 + 生态） | 更原生的体验与能力 |
| **D** | 最大（两套原生） | 最高 | 完整原生能力 |

**⚠️ 三条必须写进结论的**：

1. **WebView 不等于完整原生能力**（Capacitor 也受 WKWebView/Chromium 限制）。
2. **不承诺"原生绝不会丢数据"**——任何本地存储都可能因卸载、系统清理、设备损坏而丢。
3. **先分清"Web 真做不到"与"我们没做好"**：通知/后台执行/局域网发现是前者；
   相机、文件、语音、离线读写大多属于后者或已有可用方案。

### B.4 明确不做

**本轮不迁移框架、不出 APK、不买 Apple Developer、不改存储层、不做双端原生。**

## 附录 C · D1 版本公告与更新日志机制（上线前设计项）

### C.1 先分清四件事

| 层 | 是什么 | 要不要公告 |
|---|---|---|
| **代码提交** | 每次 `git commit` / PR | ❌ 不公告 |
| **开发版本** | 本地 / 测试构建、内部试用 | ❌ 不公告 |
| **生产部署** | `deploy.sh --version X.Y.Z` | ⚠️ 只在面向用户的发布时公告 |
| **正式发布** | 用户能感知的新功能 / 规则变化 | ✅ 写更新日志；重要改动一次性提示 |

### C.2 机制：优先静态公告文件

**推荐（初稿）**

```
GitHub 技术版本记录（开发者）
        ↓ 人工整理（不自动解析，避免泄露内部细节）
用户可读更新日志（静态文件，随 Web 构建发布）
        ↓
关于 / 软件更新 → 更新日志（历史可查）
        ↓
按风险分级：只写日志 / 一次性提示 / 必须确认
```

**为什么优先静态文件**

| 方案 | 评价 |
|---|---|
| **静态文件随构建发布** ⭐ | **零 DB、零后台、零部署复杂度**；版本与构建天然绑定 |
| 服务端 API + DB | 多一套表、接口、缓存与发布流程；**为几行公告不值得** |
| 远端静态文件（CDN / GitHub raw） | 需要网络、缓存、CSP 与可用性；离线时读不到 |

### C.3 展示与提示分级

| 级别 | 触发 | 表现 |
|---|---|---|
| **信息级** | 普通修复、小 UI | 只写更新日志，不打扰 |
| **通知级** | 重要功能 / 影响使用的改动 | 应用内**一次性**提示（按发布版本记一次，**不每次打开都弹**） |
| **强提示级** | 登录 / 注册 / 隐私 / 账号恢复 / 数据迁移规则的重要变化 | **必须清晰告知**；必要时要求确认后继续 |

**⚠️ 不滥用强提示**：强提示一多，用户就会学会无脑点掉，真正重要的那次也会被点掉。

### C.4 规则

- **普通修复与小 UI 可合并**成一条。
- **不写内部路线图 / 内部代号 / 未发布功能**。
- 面向用户的措辞遵守既有产品语气纪律（ADR-020：严谨、礼貌、中性，不夹带项目内部语境）。
- **历史日志从「关于」或「软件更新」入口随时可查**。

### C.5 待定

- 谁写、谁批、发布前谁核对。
- "已读"按设备还是按账号记（按设备简单，但换设备会再弹一次）。
- 强提示是否要跨设备一致。
- 历史日志保留多久。

### C.6 明确不做

**本轮不建表、不做后台发布系统、不把 `版本记录` 直接当用户公告**（它含内部细节与命令）。
