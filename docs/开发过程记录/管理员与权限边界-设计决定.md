## 0. 先说清楚：这一轮之前，项目**没有**管理员机制

这句话需要说得准确，因为它不是"做得不够好"，而是"并不存在"。核实结果：

| 事实 | 证据 |
|---|---|
| `users.is_admin` **被写**入过 | 迁移 `20261010200000` 里有一句 `UPDATE users SET is_admin = true WHERE account_number = '10000000'` |
| `users.is_admin` **被读**取过 | ⚠️ **全项目没有任何一处用它做权限判断**——没有 guard、没有路由、没有查询。`grep isAdmin` 的结果只有：schema 注释、一次赋值（`routes/auth.ts`）、以及 `collab/quota.ts` 里一段**明确说不要用它**的注释 |
| 唯一能产生管理员的路径 | 注册时 `isAdmin: invite.grantsAdmin`——**邀请码说了算** |
| 那条路径当时的状态 | ⚠️ **库里有 98 个未使用、永不过期、`grants_admin = true` 的邀请码**（编号 `10000002`–`10000099`） |

**所以真实情况是**：管理员**不是一个权限，而是一个存储标记**——写着 `true`，却没有任何东西读它。
而同时存在一条**任何人都能触发的提权路径**：拿到那 98 张卡里的任意一张，注册，就成为"管理员"。

**这一轮把两件事一起修了**：让管理员真正成为一个被校验的权限，并把那条路径关掉。

## 1. 唯一管理员：`naeor`

| 项 | 值 |
|---|---|
| **用户名** | `naeor` |
| **数据库主键 UUID** | **`bc82bf91-c0d9-4f88-9e34-6558fcd66ee8`** |
| 公开账号编号 | `10000000` |
| 注册时间 | 2026-10-09 20:56:17 UTC |
| 是否符合前 100 资格 | ✅ 是（编号 `10000000`，区间下界本身） |
| 账户是否正常 | ✅ 未禁用、非演示账号 |
| 授权时间 | 2026-10-14 12:19:12（本机时间） |
| 授权人（记录） | `owner-laptop` |

**核实过程**（不是"用户名等于 `naeor` 就授权"）：

1. `select ... from users where username = 'naeor'` → **恰好 1 行**；
2. 按 `username` 与 `account_number` 分组查重 → **没有任何重复**；
3. `is_demo` = false；
4. **授权绑定的是 UUID**，不是用户名——用户名可以改，UUID 是主键。

**⚠️ 一条设计纪律**：**代码里没有任何地方写着 `naeor` 或那个 UUID。**
授权是**数据库里的一行**，不是源码里的一个常量。判断"谁是管理员"要查库，不是读代码。
唯一的例外是历史迁移 `20261010200000` 里那句 `WHERE account_number = '10000000'`——
**那是当时的事实，本文不改写历史迁移**。

## 2. 前 100 个账号：资格是什么，以及它**不是**什么

### 2.1 规则

> **只有前 100 个账号具有被授权的资格。有资格 ≠ 是管理员。**

- 第 1 个账号：有资格，**不自动**成为管理员；
- 第 50 个账号：有资格，**不自动**成为管理员；
- 第 101 个账号：**没有资格**，正常情况下不能成为管理员。

今天的实际状态：**`naeor` 是唯一管理员；`mama`（`10000001`）有资格但未授权。**

### 2.2 ⚠️ 资格是怎么确定的——一个不能靠猜的问题

**不能用的依据**（这些都是"看起来像顺序、其实不是"的东西）：

| 想当然的依据 | 为什么不行 |
|---|---|
| `created_at` 排序 | 时间是插入顺序，**不是编号分配顺序**；同毫秒更是任意 |
| UUID 字典序 | UUID 是随机的，**与注册顺序毫无关系** |
| 账号编号"就是注册顺序" | ⚠️ **恰恰不是**——见下 |
| 用户名 | 可以改，且是用户选的 |

**⚠️ 关键事实：账号编号不是注册顺序，而是「预留编号段」。**

`auth/recovery-code.ts` 里有三个计数器，它们的**起始值由迁移种下**：

| 计数器 | 起始值 | 谁在用 |
|---|---|---|
| `account_number` | `10000002` | **邀请码预留编号**（生成码时就分配好） |
| `account_number_direct` | `10000101` | 没有预留编号的注册（即"直接注册"） |
| `book_number` | `40000000` | 账本编号 |

也就是说：`10000000`–`10000099` 是所有者**为第一批邀请码预留的编号段**，
而"直接注册"从 `10000101` 起算——**高于该段，故意不侵入它**。

**所以真正的依据是**：**编号区间 `10000000`–`10000099`，就是本项目自己对"前 100 个账号"的定义**，
而且这个定义**先于任何账号存在**（迁移种下了计数器）。

**⚠️ 而且它与项目已有的一处定义完全一致**：`collab/quota.ts` 里"头一百个账号不受通知配额限制"
用的就是同一个区间，并且注释里明确写着**不要把它简化成 `users.is_admin`**。两处必须是同一个区间。

### 2.3 为什么资格可以放心用区间判断

**⚠️ 这条很重要，因为它看起来像"用区间推权限"——那正是本项目犯过的错。**

区别在于**区间是门槛，不是授权**：

| | 过去的错（迁移 `20261010200000` 修的） | 现在的做法 |
|---|---|---|
| 规则 | "编号预留了 → **成为管理员**" | "编号在区间内 → **可以被授权**" |
| 后果 | 任何生成预留码的命令都会**造出管理员** | 不会造出任何东西；要授权必须**显式写一行** |

**⚠️ 而"资格"本身也不由编号段以外的任何东西决定**：编号一旦分配就**不再变化**
（`users.account_number` 是 `@unique`、`NOT NULL`，应用在注册之后从不写它），
所以**删账号、改昵称、改用户名都不会让人进出这个区间**。

**✅ 结论：不需要"一次性资格名单冻结方案"。**
资格不是从历史里**重建**出来的排名，而是**计数器起始值本来就说好的区间**——
这是可以严格证明的，不是猜的。（本节即对该问题的回答：**存在可靠依据，且已依据它实现**。）

### 2.4 实现

`apps/api/src/admin/rules.ts`：

```ts
export const FIRST_BATCH_ACCOUNT_FIRST = "10000000";
export const FIRST_BATCH_ACCOUNT_LAST  = "10000099";

export function isFirstBatchAccountNumber(accountNumber: string): boolean
```

**⚠️ 三个刻意的细节**：

1. **字符串比较**，不是数字。编号补零到 8 位，两种顺序一致；用字符串避免了对着数据库来的值做 `Number()`。
2. **格式不合法一律"不合格"**（不是抛异常）。这是一道门，门对着看不懂的东西，答案只能是"不"——
   抛异常会把数据问题变成 500，而**权限检查上的 500 是一次带额外步骤的拒绝服务**。
3. **这个函数只回答"有没有资格"，不回答"是不是管理员"。**

## 3. 管理员身份的证据：两道锁，两个不同的东西

管理员**授权**由两部分组成，**两者必须同时成立**：

| # | 事实 | 存在哪 | 它回答的问题 |
|---|---|---|---|
| **A** | **管理员角色标记** | `users.is_admin`（布尔） | "这个账号被授予过管理员角色吗" |
| **B** | **管理员授权记录** | `admin_grants` 表（可撤销、带日期与授权人） | "这个授权是谁在什么时候给的，现在还有效吗" |

**⚠️ 为什么不是只有一个。** 一个布尔说"某人是管理员"，别的什么都不说：没有谁决定的记录、
没有日期、也没有一种与"授权"本身可区分的撤销方式。**授权是一件事，应该留下痕迹。**

**⚠️ 但 guard 真正依赖的是 B，不是 A。** 这一点必须说清楚，否则下一个人会以为改 `is_admin` 就能提权：

- guard 读 **`admin_grants`**（存在、且未撤销）；
- `is_admin` 是**标记**，由授权脚本在同一事务里写入/清除，**让数据库描述的状态与被校验的状态一致**；
- **只把 `is_admin` 改成 true 不会让人成为管理员**——第 9 组测试与"不合格账号带授权"那条都在钉这一点。

### 3.1 数据模型

```
admin_grants
  user_id     UUID  PRIMARY KEY  → users(id) ON DELETE CASCADE
  granted_at  TIMESTAMPTZ NOT NULL DEFAULT now()
  granted_by  VARCHAR(200) NOT NULL      -- 自由文本，不是外键
  revoked_at  TIMESTAMPTZ                -- NULL = 当前持有
  revoked_by  VARCHAR(200)
  note        VARCHAR(500)
```

**⚠️ 四个刻意的选择**：

| 选择 | 理由 |
|---|---|
| **`user_id` 就是主键**（一个账号一行） | "这个账号被授权了吗"只有一个答案；两行活授权就是两个答案。撤销后重新授权是 **upsert 同一行**，历史留在一条线上 |
| **`revoked_at` 而不是删除行** | 撤销是**关于过去的事实**；删行会抹掉"这个账号曾经持有该角色"，而那正是审计要问的 |
| **`granted_by` 是自由文本，不是外键** | 跑授权脚本的是**终端前的人**，他可能根本没有应用账号。外键会逼出一行不存在的用户，或者逼出一次伪造 |
| **`ON DELETE CASCADE`** | 账号没了，授权跟着没。留一行指向空 UUID 的授权，是**等一个 UUID 被再次使用**——这种事不能靠运气 |

## 4. 双重校验：两道**独立**检查

> **必须同时满足**：
> **有效登录会话 AND 有效管理员授权 AND UUID 属于有效管理员允许名单 AND 符合前 100 资格 AND 账户可用**

### 4.1 五步，缺一不可

| # | 检查 | 数据来源 | 失败原因（内部） |
|---|---|---|---|
| 1 | **有效登录会话** | `sessions` 表（cookie → token 哈希） | `not_authenticated` / 401 |
| 2 | **有效管理员授权** | `admin_grants`（存在且 `revoked_at IS NULL`） | `no_grant` |
| 3 | **在管理员允许名单内** | **`admin_allowlist` 表**（独立表，见 §4.2） | `not_allowlisted` |
| 4 | **前 100 资格** | `users.account_number` 区间 | `not_first_batch` |
| 5 | **账户可用** | 存在且非演示账号 | `account_unavailable` |

**⚠️ 身份从"已经过验证的会话"取，绝不从请求里取。** 明确不信任：
请求头、请求体、查询参数里的 `isAdmin` / `role` / `username` / 账号编号 / 自定义管理员头——
测试第 7 组专门拿这些值去撞 guard。

### 4.2 ⚠️ 第 2 与第 3 是**两张表**，而不是一个判断读两遍

**这是本轮最容易被做错的一点，所以单独说。**

最诱人的写法是：

```ts
// ❌ 这不是双重校验，这是同一句话说两遍
if (!user.isAdmin || !user.isAdmin) return deny;
```

它**能通过全部功能测试**，却只给了运维**一个把手**。而要求是：

> *"不要简单地在一个 `if` 判断中重复读取同一个 `isAdmin` 字段两次，就声称实现了双重验证。"*

**两个问题确实不同**：

| 检查 | 问的问题 | 两者可以不一致的情形 |
|---|---|---|
| **2 授权** | "这个账号被授予过管理员角色吗？" | 有人在出事时**只撤角色**、还没动名单 |
| **3 允许名单** | "这个账号是**当前允许**行使管理员身份的那几个之一吗？" | 名单上有它、但角色已被撤；或者角色在、名单被收窄了 |

**两种不一致都必须拒绝。** 实现上它们是两个函数、两次读取、**两个独立的失效开关**：

```ts
hasActiveAdminGrant(prisma, userId)   // 读 admin_grants；ADMIN_GRANT_CHECK_DISABLED=1 时一律拒绝
isOnAdminAllowList(prisma, userId)    // 读 admin_allowlist；ADMIN_ALLOWLIST_CHECK_DISABLED=1 时一律拒绝
```

**⚠️ 开关关掉等于拒绝，不等于放行**——"少做一次检查"不是"检查通过"。
测试 **"denies when either half of the check is disabled"** 逐个关掉再打开，
三次请求的期望分别是 **200 → 403 → 403 → 200**。

#### ⚠️⚠️ 4.2.1 **已被取代的旧规则**（1.10.22 → 1.10.23）

> **这一小节保留下来，是因为它记录的正是本轮修掉的那个错误。**
> **不要照着它实现。**

**1.10.22 的写法**：`isOnAdminAllowList` 的判定是
**「该账号在资格区间内 **且** 持有有效 `admin_grants`」**——
也就是**允许名单由 `admin_grants` 派生**。

**当时的理由（现在看是错的）**：存第二张表会多出"第二个存放『谁是管理员』的地方"，
而本项目为这个形状付过代价（`教训.md` §8.7）。

**⚠️ 为什么那个理由不成立**：

- 派生出来的第二道检查**与第一道共享同一个数据来源**，所以 `isAdmin && isAdmin` 的批评
  **依然成立**，只是从"同一个字段读两遍"变成了"同一张表查两遍"；
- **一次授权会同时满足两半**——两道检查**永远不可能不一致**，
  而"能不一致"正是要求问两次的理由；
- 运维只有**一个把手**（`ADMIN_ALLOWLIST_SCOPE` 环境变量），而不是两个。

**所有者发现了它：**

> *"授权记录和允许名单并没有完全分离……如果未来误将另一个合格账号加入 `admin_grants`，
> 在默认的 first-batch 范围下，它可能同时通过所谓的两重检查。"*

**⚠️ 修正后的做法（现行）**：

| | 第一重 | 第二重 |
|---|---|---|
| 表 | `admin_grants` | **`admin_allowlist`（独立表）** |
| 写入 | `pnpm admin:grant` | **`pnpm admin:allow`** |
| 撤销 | `pnpm admin:revoke` | **`pnpm admin:disallow`** |
| 能单独存在吗 | ✅ 能 → **拒绝** | ✅ 能 → **拒绝** |

**⚠️ 两个命令都不写对方的表**，所以运维必须两次都表态。
**`ADMIN_ALLOWLIST_SCOPE` 已随派生实现一起删除**——没有派生的名单可以"收窄"了。

**⚠️ 那条回归测试**：*"误加第二个合格授权、名单不变 → 仍拒绝"*。
在旧的派生设计下它会**失败**，而在整套测试里它是**唯一**能区分两种设计的一条。

**允许名单表本身的设计**（`user_id` 主键、`revoked_at` 而非删除、`Cascade`、
迁移**不插入任何行**）与 `admin_grants` 同形，理由也相同——详见 `prisma/schema.prisma` 里
`AdminAllowEntry` 的注释。

**⚠️ 为什么是表而不是环境变量**：本项目所有状态都在 PostgreSQL（不引入第二套配置机制）；
可审计；多实例天然一致；**改名单不需要重启容器**——而"现在就把这个账号去掉"
恰恰是需要它立刻生效的那个场景。环境变量方案的优势是"API 根本碰不到"，
代价是每改一次要重启、多实例要同步、Windows 开发与 Linux 生产两套格式容易漂。

### 4.3 ⚠️ 不缓存

**每个请求都重新读这两张表，进程里不保留任何管理员判定结果。**

这既是要求（*"避免使用长期缓存的管理员权限结果"*），也是对"撤销"这个词的诚实读法：
**一个被缓存的管理员判定，就是一个开不掉的管理员。**

代价是罕见路由上两次带索引的查询；换来的是**撤销在下一次请求就生效**，而不是在某个未说明的将来。
测试第 9、10 组在**不重新登录**的前提下钉住这一点——**以后谁为了性能加缓存，这两条会红。**

### 4.4 ⚠️ 拒绝时说什么

**所有拒绝都是同一个 403、同一句话**：「没有权限执行这个操作。」

**不告诉调用者他卡在哪一关。** "没有授权"和"不在名单上"是两个不同的事实，
而告诉对方是哪一个，就回答了他真正在问的那个问题——*"我离成功还有多远？"*

**真实原因（`AdminRefusal`）留给测试与服务器日志，永远不进响应体。**
测试里有一条专门断言响应体**不包含** `grant` / `allowlist` / `first_batch` / `uuid` 这些词。

**⚠️ 未登录是 401（"你是谁"），已登录但无权是 403（"不是你"）。**
把两者合成一个会让登录 bug 看起来像权限 bug。

## 5. ⚠️ 历史管理员邀请码：已失效（这一轮的安全修复）

### 5.1 问题

迁移 `20261010200000` 建立了"邀请码可以授予管理员"的机制，理由是**显式优于推断**——
它修的是更早的 bug（"预留了编号就等于管理员"）。**当时那个修法是对的。**

**但它留下了一个没有预料到的后果**：所有者按计划生成了 **98 个管理员邀请码**（编号 `10000002`–`10000099`），
**永不过期**，并且设计意图是**印在卡片上、几个月内陆续发出去**。

于是 `grants_admin = true` 变成了**一条自动提权路径**：

> 拿到那 98 张卡里任意一张的人 → 注册 → **自动成为管理员**，
> **而那一刻没有任何人做过决定**——而"某一刻有人决定过"是特权唯一应该要求的东西。

**一张纸不应该是决定权限的东西，而且一张躺在抽屉里的纸没法被追问。**

### 5.2 处置（已执行）

| # | 动作 | 结果 |
|---|---|---|
| 1 | **注册流程不再读 `grants_admin`** —— `isAdmin: false`，永远 | 测试：拿管理员码注册 → 编号照给（`10000060`），**`is_admin = false`**，`admin_grants` 0 行 |
| 2 | **迁移清掉未使用的 `grants_admin`** | 98 行 → 0 行 |
| 3 | **编号预留保留** | `reserved = 98` **未变**——那从来不是特权 |
| 4 | **已使用的码保留其值** | 那是"发生过什么"的记录 |

**⚠️ 为什么保留那个列而不是删掉它。** 删列要改表，而它现在**没有任何读取者**；
更重要的是，**留着它 + 一段说明，比删掉它更能解释这里发生过什么**。
schema 里的注释、迁移里的注释、以及本节，共同构成那份说明。

**⚠️ 而且现在连"手工把标志设回 true"也无效**——测试第 14 组最后一条：
新建一个 `grants_admin = true` 的码并注册，**依然不是管理员**。
**关掉的是路径，不只是把数据收拾干净。**

### 5.3 其他自动提权路径：全部封死

| 路径 | 结果 |
|---|---|
| 普通注册 | ❌ 无效（`is_admin = false`，无授权行） |
| 普通邀请码 | ❌ 无效 |
| 预留编号 | ❌ 无效（编号不是特权） |
| 填写特殊账号编号 | ❌ 无效（编号只是资格） |
| 伪造请求参数 / 前端状态 | ❌ 无效（服务端不读） |
| 改昵称 / 用户名 | ❌ 无效（没有这个接口；即使直接改库，guard 也不看名字） |

## 6. ⚠️ 管理员**不等于**能看别人的账本

> **账本权限只来自 `book_members`，不来自任何其他东西。**

这是本轮最重要的边界，也是所有者明确要求的：

> *"管理员身份不自动意味着拥有所有用户私人账目的读取和修改权限。"*

**已实现的证明**：测试第 13 组让一个**真正的管理员**（通过校验、返回 200）去读一本**他没有成员关系的账本**，
`/ledger`、`/transactions`、`/summary`、`/stats` 四个入口**全部 403**，写操作也 403；
而账本主人读自己的账本 200。**这条测试如果变绿变红，说明管理员角色悄悄变成了一把万能钥匙。**

**⚠️ 这一轮没有开放任何跨账户的数据读取能力。**
`decideAdmin` 只回答"这个人能不能做管理员操作"，它**不提供任何数据访问**；
未来的管理员功能必须**各自定义自己的适用范围**。

### 6.1 三套权限相互独立

| 权限系统 | 由谁决定 | 与管理员的关系 |
|---|---|---|
| **应用内管理员** | 本文所述机制（服务端校验 + UUID 名单） | — |
| **账本 Owner / Editor / Viewer** | `book_members` 表 | **完全独立**：管理员不因为身份获得成员权 |
| **服务器与数据库** | SSH、操作系统权限、PostgreSQL 超级用户 | **完全独立**：应用管理员**不自动**获得 SSH / root / 数据库权限 |

**⚠️ 反过来同样成立**：知道数据库连接口令**不是**软件内的管理员认证方式。
两者是不同层面的东西，不能互相顶替。

## 7. 授权与撤销

> **⚠️ 管理员需要两步，而不是一步。** 1.10.23 起，「授权」与「列入允许名单」是两个
> **独立的表、独立的命令、独立的撤销**。**只做其中一步，账号不是管理员。**
> 这是 §4.2.1 那个错误修正之后的直接结果。

### 7.1 授权（第一重）：`pnpm admin:grant`

```bash
pnpm admin:list                                             # 先看：谁有资格、谁已是管理员
pnpm admin:grant <用户 UUID> --by "<操作者>"                 # 第一重：授权
pnpm admin:allow <用户 UUID> --by "<操作者>"                 # 第二重：列入允许名单
```

**⚠️ 这两条命令都不可省。** 只执行第一条时，`admin:list` 会把这个账号列在
**「⚠️ 只满足一半（不会通过校验）」** 一栏里——它**确实不能通过校验**，而那正是设计。

**⚠️ 这是**唯一**创建管理员的路径。**没有路由、没有请求体字段、没有邀请码标志能做到它——
**一个能靠发请求获得的特权，迟早会被靠发请求获得。**

**两个脚本共同的保证**：

| 保证 | 实现 |
|---|---|
| 拒绝不存在的用户 | 先 `findUnique`，查不到就退出，**不写任何东西** |
| 拒绝不合格的账号 | `isFirstBatchAccountNumber` 不过就退出 |
| 拒绝演示账号 | `is_demo` 为真就退出 |
| 拒绝重复写入 | 已有活记录 → 打印现状并退出（**幂等**） |
| 事务一致性 | `admin:grant` 在同一个 `$transaction` 里写 `admin_grants` 与 `users.is_admin` |
| 可安全重复运行 | 见上；撤销后重跑是 **upsert 同一行**（不产生第二行） |
| 不输出敏感凭据 | 只打印用户名、编号、UUID、操作者、时间 |
| 普通用户无法从网页调用 | **它们是 CLI 脚本，不在路由表里** |
| **不写对方的表** | `admin:grant` 不碰 `admin_allowlist`；`admin:allow` 不碰 `admin_grants` |

**⚠️ `--by` 是必填的**，不是仪式：一条没写作者的记录，对"这是谁干的"这个问题只能耸肩，
而那是关于特权第一个会被问到的问题。

### 7.2 撤销（同样是两步）：`pnpm admin:revoke` / `pnpm admin:disallow`

```bash
pnpm admin:revoke <用户 UUID> --by "<操作者>" --why "<原因>"     # 撤授权
pnpm admin:disallow <用户 UUID> --by "<操作者>" --why "<原因>"   # 移出允许名单
```

**⚠️ 撤哪一个？** 两者都足以让管理员操作立刻失败，但含义不同：

- **撤授权**（`admin:revoke`）＝"这个账号不再持有管理员角色"——**常规做法**；
- **移出名单**（`admin:disallow`）＝"这个账号**不论持有什么**都不许行使管理员身份"——
  **出事时的第一反应**，因为它与被撤的那个权限无关。

**两者的共同保证**：

| 保证 | 说明 |
|---|---|
| **立即生效** | guard 不缓存，**下一次管理员请求就失败**——**不需要让人重新登录，也不需要重启服务** |
| 会话本身不动 | 这是**权限撤销**，不是登出；测试里撤销后 `/auth/me` 仍然 200 |
| 写时间戳，不删行 | 记录仍然说明"曾经持有、何时停止" |
| 幂等 | 已撤销 → 打印现状，不重复写 |
| **不碰另一张表** | 撤授权不动名单；移出名单不动授权——**两件事本来就可能不一致，那正是能分别问的理由** |
| **⚠️ 拒绝清空最后一个** | 除非显式加 `--allow-empty`。**系统不会自动补一个替补管理员** |

### 7.3 ⚠️ 唯一管理员登不进去怎么办

**不走公开接口。没有"找回超级管理员"。**
一条绕过正常认证的恢复路径，就是一条绕过正常认证的攻击路径。

**正确做法**（按顺序）：

1. **SSH 上服务器**（这是操作系统权限，与本文的应用内管理员无关）；
2. **从备份恢复**，或**在终端前重新授权**（pnpm admin:grant **并且** pnpm admin:allow，两步都要）——该脚本需要数据库访问权，
   而数据库访问权**本来就是比应用管理员更高的权限**；
3. 如果数据库本身不可用，走 `tools/backup-verify.mjs` 验证过的备份恢复流程
   （**它不接受"只备份"**——见 `版本记录` 里那次演练：21 张表、约 603 行一致）。

**⚠️ 注意这条推理的方向**：恢复管理员**不需要**管理员权限，它需要**服务器权限**——
因为那才是真正更高的那一层。这也是 §6.1 三套权限相互独立的实际用处。

## 8. 未来管理员功能如何复用这套机制

### 8.1 统一入口

```ts
import { createRequireAdmin } from "../admin/guard.js";

app.post("/api/v1/admin/<something>", { preHandler: requireAdmin }, async (request) => {
  const actor = request.adminActor;   // 已由 guard 解析并校验
  ...
});
```

**五件事一次做完**：会话 → 授权(`admin_grants`) → 允许名单(`admin_allowlist`) → 资格 → 账户状态。

**⚠️ handler 里必须读 `request.adminActor`，不要重新查一遍用户、更不要从请求里读 id。**
guard 已经把身份从**已验证的会话**里解析出来了；再查一次就是"同一件事的第二份实现"，
而那正是本项目反复记录成"洞是怎么出现的"的那个形状。

### 8.2 ⚠️ 不要每个功能自己写一套判断

这是硬要求（对应所有者原话：*"不要让每个管理员功能自己复制一套判断代码"*）。
一条授权规则的第二份、略有不同的副本，就是洞出现的方式——`auth/guard.ts` 的注释里写着同样的话。

### 8.3 本轮**没有**暴露任何管理员 API

**没有管理员后台、没有用户数据管理、没有全站账目查看、没有封禁面板、没有全局统计。**

给 guard 做端到端测试用的那条路由是**测试专用**的：

- 由 `buildApp({ enableTestAdminRoute: true })` 注册，**默认关闭**；
- **`src/server.ts` 不传这个选项，也没有任何环境变量能打开它**；
- 唯一调用者是 `test/admin.test.ts`；
- 它**只报告 guard 的判定结果**，不读账本、不碰用户数据、没有副作用。

**⚠️ 这就是"不为测试而长期暴露一个没有实际需求的管理员 API"的实现方式**：
在正常构建里，那条路由**不存在**，而不是"存在但藏起来了"。

### 8.4 每新增一种管理员操作，仍要单独定义

| 必须定义 | 为什么 |
|---|---|
| **操作权限** | "管理员"不是一个可以整体授予的数据访问权 |
| **适用范围** | 能看什么、能改什么，逐项写清楚 |
| **审计规则** | 见 §9.4 |

### 9.4 审计记录：接口已定，**本轮不建空表**

**所有者要求"预留安全审计机制"，同时说"没有实际管理员操作就不必为预留而增加复杂的空表和后台页面"。**
两者都遵守，做法是**先把要记的字段定下来**，等第一个真实操作出现时再建表：

| 字段 | 用途 |
|---|---|
| `admin_user_id` | **管理员用户 UUID**（不是名字——名字会变） |
| `action` | 操作类型（稳定标识符，不是人类句子） |
| `at` | 操作时间（`timestamptz`） |
| `target` | 操作对象标识 |
| `outcome` | 成功 / 失败 |
| `request_id` | 请求追踪信息 |

**⚠️ 明确不记**：密码、会话 Cookie、恢复码、完整私人账目、不必要的敏感个人信息。

**⚠️ 为什么值得等。** 现在建一张没有写入者的表，它会**看起来像"审计已就位"**，
而实际是一张空表——本项目对"没有使用者的东西会腐烂"已经有记录（颜色系统那次的
`--color-focus-ring`：*"一个没有使用者的 token 会腐烂"*）。
**先定字段、后建表，比先建一张空表更诚实。**

### 10.1 ⚠️ 测试库曾经落后 9 个迁移（本轮已补，但**没有自动检查**）

**发现**：`ledger_test` 停在 `20261011140000`，而 `ledger_dev` 已经在 `20261013190000`。
本轮**一并补齐**了（不补的话新的 admin 测试根本跑不起来）。

而测试库需要**手动单独跑一次**（`交接.md` §2.1 写过这件事）。
没有任何东西会提醒你"两边进度不一样了"。

**⚠️ 影响**：在那之前，跑在测试库上的集成测试**可能一直在测一个旧 schema**。
本次没有发现因此产生的错误结论，但**这属于运气好，不属于设计好**。

**建议的修复方案**（按价值排序，都还没有做）：

| # | 方案 | 说明 |
|---|---|---|
| 1 | **加一条检查**：比较 `_prisma_migrations` 在开发库与测试库上的已应用集合，不一致就报错 | 最小、最直接。可以并进 `pnpm check:docs` 那种"常驻检查器"的模式，或单列 `pnpm check:db` |
| 2 | **让 CI 覆盖它**：CI 已经在干净库上跑 `db:deploy`（`.github/workflows/ci.yml`），所以**新迁移一定能在空库上通过**；缺的只是"本地两个库彼此一致"这一条 | 本地检查即可 |
| 3 | 更彻底：测试库由脚本从零重建（`migrate reset` 等价物） | ⚠️ 破坏性，**需要所有者同意**，且会拖慢测试启动 |

**⚠️ 本轮没有实施任何一条**——它们都不在"管理员身份"这个任务的范围内，
而本项目对"顺手改无关的东西"有明确纪律（`教训.md` §8.13）。

### 10.2 管理员相关的遗留事项

## 11. 一句话总结

> **管理员身份是：一行可撤销的数据库授权 + 一次独立的允许名单校验 + 前 100 编号的资格门槛 + 一个可用的账户，
> 全部由服务端从已验证会话出发、每请求实时判定、不缓存、不信任客户端、且在拒绝时不透露卡在哪一关。**
>
> **现阶段唯一管理员是 `naeor`。前 100 个账号只是有资格，不自动获得任何权限。**
> **管理员不代表能看别人的账本。**
