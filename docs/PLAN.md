## 1. 项目定义

### 1.1 已确认功能（v1 范围）

**账号与安全**

| 功能 | 说明 |
|---|---|
| 用户名 + 密码登录 | argon2id 哈希；服务端会话 + httpOnly Cookie；支持"退出所有设备" |
| 邀请码注册 | 开源但不开注册；注册必须带邀请码 |
| **一次性恢复码** | 注册时生成、让用户自行保存；忘记密码用它重置（**不依赖邮件服务**） |
| 登录限流 | 防暴力破解 |
| 会话策略 | **同时只允许一个账号登录，且必须在线才能登录**（见 3.3；这条决定消掉了多设备离线冲突） |
| 公开只读演示账号 | 预置示例数据，供招聘方与路人体验 |

**账本、货币与支付方式**

| 功能 | 说明 |
|---|---|
| 每账号一本独立账本 | 注册即自动创建，可改账本名；账号间数据完全隔离 |
| **多币种混记** | 同一账本内可分别记人民币 / 美元等；**v1 各币种独立统计，不做汇率折算** |
| 汇率折算开关 | 设置中预留开关，可按汇率把所有币种折算成指定币种统计（**v2 实现**） |
| **支付方式** | 这笔从"微信 / 支付宝 / 现金 / 其他"支出（可自定义、可排序）；**v1 不追踪余额** |

**记账**

| 功能 | 说明 |
|---|---|
| 记一笔 | 金额、收/支、分类、支付方式、币种、**记账时刻**、备注 |
| **收入也记（入账）** | 收支并重。明细页直接呈现"这个月花了多少、分了多少笔、赚了多少、结余多少" |
| 截图识别记账 | 上传付款截图，自动识别金额与时间，核对后入账（**S5 实现**，图片不落盘） |
| **记账时刻与时区** | 默认读取手机当前时间（**精确到秒**）；同时记录手机所在时区。**统计一律按"记账时的本地日期"**，服务器只负责存数据 |
| **连续记账** | 记完一笔可接着记下一笔，**分类 / 支付方式 / 币种 / 日期全部沿用上一笔**，金额与备注清空 |
| 常用金额快捷键 | **不足 10 条记录时**用默认值 10 / 20 / 100；**达到 10 条后**自动取最近 30 天出现最多的 **5 个金额** |
| 复制上一笔 | 一键复制**全局最近一笔**的分类、金额、备注等结构 |
| 备注自动补全 | 输入备注时联想历史用过的写法（**S12 实现**） |

**分类与标签**

| 功能 | 说明 |
|---|---|
| **预设分类（注册即生成）** | **支出 9 类 + 收入 6 类**，清单见下方。**纯文字，不用图标**（v1 不做图标） |
| 收支各一套 | `categories.kind` 区分；切换到"收入"时只看到收入分类 |
| 分类是否必填 | 界面**永远有值**：首次记账默认**"无分类"**，之后默认**沿用上一笔的分类**（见下方说明） |
| 自定义分类 | 可增删改、调排序 |
| **归档而非删除** | 归档后 ① 选择器里不再出现 ② 历史流水的分类名照常显示（颜色淡一点）③ **随时可恢复** |
| **标签** | 一笔账**最多 10 个标签**；列表页只显示**前 5 个**，进入该笔详情可看到全部。**v1 不做二级分类** |

**预设分类清单（2026-10-09 定稿，由项目所有者确认）**

| 支出（9 类） | 面向用户的说明 |
|---|---|
| 餐饮 | 日常用餐与饮品支出 |
| 娱乐 | 游戏、影音与休闲消费 |
| 服务 | 通信、会员及其他服务费用 |
| 购物 | 日用品与商品采购 |
| 教育 | 学费、课程与培训支出 |
| 转账 | 转给他人的款项 |
| 生活缴费 | 房租、水电、物业等固定支出 |
| 交通 | 通勤、加油与出行费用 |
| 其他 | 未归入以上类别的支出 |

| 收入（6 类） | 面向用户的说明 |
|---|---|
| 转账 | 他人转入的款项 |
| 工资 | 薪资与劳务报酬 |
| 奖金 | 年终奖及各类奖励 |
| 理财 | 投资、利息与分红收益 |
| 退款 | 退货及费用返还 |
| 其他 | 未归入以上类别的收入 |

> **"无分类"怎么表示**：`transactions.category_id` **可为空**，为空即在界面上显示为"无分类"，统计里单列一栏。这样既满足"分类永远有值"（用户眼里不会看到空），又不会强迫用户为了保存一笔账先去选分类。

**查看与统计**

| 功能 | 说明 |
|---|---|
| **明细页（登录后的主页）** | 顶部：主题色底 + 白字，显示**该月支出 / 入账 / 结余**（**按币种分组，每个币种一行**）；中部：支出 / 收入 两个切换按钮（**默认支出**）；下部：白底流水预览，**最新在最上面**，向下滚动加载更早 |
| 多币种展示规则 | 按**记账总数额**（支出与收入的绝对值之和，不折算汇率）从大到小排序；**只显示前 2 种**，其余收进"其它币种（N）"一行可展开——**不静默隐藏，避免用户以为钱不见了** |
| 流水筛选 | 按分类 / 支付方式 / 标签 / 币种筛选，关键字搜索，按日分组 |
| 默认月份 | **当月；若当月没有任何记录，自动跳到最近有记录的那个月** |
| 删除 | 软删除；删除后底部出现"已删除 · 撤销"提示条，**5 秒内可撤回** |
| **统计（全部要做）** | 月度收支趋势折线 · 分类占比饼图 · 环比 / 同比对比 · 年度总览 · 每日花销日历热力图 · 另加若干专业向分析（**S4 实现**） |
| 统计布局 | 常用的放前面，其余可折叠；优先级后期再调 |

**数据与体验**

| 功能 | 说明 |
|---|---|
| 导出 CSV / XLSX | 按时间范围导出 |
| **CSV 导入历史账** | 提供模板；导入时逐行校验并给出错误报告 |
| **中英双语可切换** | 界面文案全量国际化 |
| 浅色主题 | 白色底 + 单一主题色，主按钮用主题色，简约风；后期支持主题色自选 |
| 手机优先 | 响应式，可"添加到主屏幕" |
| **离线可用** | 见 3.3：v1 先交付在线版，但**架构从第一天就按离线优先设计**；离线写入界面在第二批交付 |

> **账本模型的取舍（重要）**：v1 做成"一个账号 → 一本自己的账本"，先把单人记账打磨到好用。**多人共享账本（邀请家人共记一本账）放到 v2**——共享会牵出成员管理、权限矩阵、邀请码、并发冲突一整套界面与接口，不适合塞进第一版。
>
> **但数据库从第一天就按「可共享」设计**：`books`（账本）+ `book_members`（成员与角色）两张表照建，v1 每个账本只有一行 owner 记录。这样 v2 做共享时**只写界面和接口，不用改表结构、不用数据迁移**——这是本方案里最关键的一处"为未来留门"。

### 1.2 明确不做（v1）

| 不做 | 原因 |
|---|---|
| 记账提醒通知 | 你的选择；这是唯一让 APK 成为刚需的功能，去掉后网页方案完全够用 |
| 多账户与余额（现金/微信/支付宝） | v1 只记"**这笔从哪付的**"（支付方式），**不追踪各账户余额**——余额要牵出转账、对账、期初余额，不适合第一版 |
| **离线写入界面** | 推迟到第二批交付。但**架构在第一批就按离线优先设计**（见 3.3），否则后补要改表、迁数据 |
| **按汇率折算统计** | 设置中预留开关，**v2 实现**。v1 各币种独立统计，不做折算（折算需要汇率来源与按日汇率快照） |
| **二级分类** | 你未勾选；扁平分类 + 标签已能覆盖大部分场景，二级分类留到有明确需求再加 |
| **预算与超支提醒** | v2；先把记账与统计做扎实 |
| **多设备同时离线编辑** | 由"**同时只允许一个账号登录**"这条策略规避掉，不做冲突合并 |
| **多人共享账本（邀请他人共记一本账）** | 你的决定：v1 每个账号一本独立账本。表结构已预留（见 1.1 注），v2 只需加界面与接口 |
| 上架应用商店 | 个人开发者需软著等材料，成本远超收益 |
| 面向陌生人的开放注册 | **开源 ≠ 开放注册**。v1 采用邀请码制：家人由你发码加入；对外只提供**只读演示账号**。理由见 8.6 |
| 付费/增值/广告 | 定位是"免费开源"，一旦加商业化就要面对备案、税务、支付合规，与简历目标不符 |

### 1.3 非功能约束

| 约束 | 具体要求 |
|---|---|
| 终端 | 安卓手机浏览器为主（Chrome / 国产厂商浏览器 / 微信内置浏览器可看）。布局从 360px 宽度起自适应 |
| **大陆可访问性** | **硬要求**：家人日常使用必须稳定。服务器选香港，不用 Cloudflare/Vercel 默认域名；延迟目标 < 100ms（详见 10.1） |
| 性能 | 首屏在 4G 下 3 秒内可用；列表分页加载，单页 20–50 条 |
| 安全 | 密码不可逆存储、全程 HTTPS、账号间数据严格隔离（详见第 8 章） |
| 成本 | 月支出 ≤ ¥100 |
| 开发条件 | 你无安卓真机、有基础编程能力；**主要编码由 AI 协作完成，你负责验收、提问与决策**（协作方式见 ROADMAP） |

### 1.4 「开源 + 简历」双重目标带来的硬性要求

这两条目标会直接否决几个"最省事"的方案，务必先看：

| 要求 | 对选型的影响 |
|---|---|
| 代码公开托管在 GitHub | 仓库要干净、有 README、有 LICENSE；**服务器密钥、数据库密码绝不能进仓库**；用 `.env.example` 说明需要哪些变量 |
| 招聘方点开就能试 | 需要稳定可达的公网域名 + **只读演示账号**（招聘方不会注册） |
| 要能讲出技术深度 | 因此**不推荐纯 BaaS（如 Supabase 一栈到底）**——那样后端是别人写的，面试没什么可讲 |
| 要能体现工程规范 | 需要：数据库迁移、类型安全、CI 自动检查、测试、备份策略、错误处理 |
| 开源项目要有可读性 | 需要：英文 README（你在美国读书，招聘方更可能看英文）、提交信息规范、目录结构清晰、注释适量 |
| 免费 = 可信 | 不接第三方统计/广告 SDK；README 里写明"不收集数据、不出售数据" |

> 结论：**自建后端 + 认真做开源规范**。相比最省事的做法多花约 2 个工作日，换来的是一个能在面试里讲 20 分钟、且真实有人在用的项目。

## 2. 形态选型：为什么是「Web，APK 备用」

### 2.1 四种形态对比

| 维度 | 原生安卓（Kotlin） | **Web / PWA（选定）** | 微信小程序 | 混合（Capacitor 套壳） |
|---|---|---|---|---|
| 你无安卓真机时的开发体验 | 极差（每次改动都要打包装机） | **极好**（改完刷新即见） | 好 | 一般（要过 Gradle） |
| 多用户账号 | 需自己做 | **天然支持** | 需自己做 | 天然支持 |
| 家人加人/换手机的成本 | 每人重装 APK | **发个链接，各自开账号** | 需扫码+授权 | 每人重装 APK |
| 迭代速度 | 慢 | **最快** | 中（要过审核） | 中 |
| 截图识别记账 | 好 | **好**（浏览器选图/拍照都可用） | 好 | 一般（需常驻 OCR 进程） |
| 断网通知提醒 | **最好** | 弱（依赖推送，国内浏览器支持参差） | 弱（订阅消息限制多） | **最好**（本地通知） |
| 桌面小组件 | 支持 | 不支持 | 不支持 | 支持 |
| 导出 Excel/CSV | 一般 | **最容易** | 一般 | 容易 |
| 简历可讲度 | 高（但你没安卓基础） | **高（现代前端 + 自建后端，可讲一整条链路）** | 中 | 高 |
| 分发阻力 | 要开"未知来源" | **零阻力** | 零阻力（但有审核门槛） | 要开"未知来源" |
| 开源友好度 | 一般（贡献者要装 Android 环境） | **最好**（clone + 两条命令就能跑） | 差（要开发者账号） | 一般 |

### 2.2 定案与理由

**做网页。** 四条决定性理由：

1. **账号系统已经决定了必须要有服务端**，所以"APK 不用服务器、数据存本机"的优势根本不存在——那正是 APK 唯一省钱省事的地方。
2. **你没有安卓真机**。纯 APK 路线下，一个界面 bug 的成本是"改代码 → Gradle 打包 → 签名 → 导出 → 传文件 → 家人卸载重装"，且你无法在他们手机上调试；网页是"我改完，他们下拉刷新"。
3. **家人分居两地（你在大陆之外、家人在大陆）**：网页天然跨设备、跨系统，换手机、加人都只是发个链接。
4. **开源项目要让陌生人能跑起来**：网页方案是 `git clone` + 两条命令；安卓方案要求贡献者装 Android SDK。

**APK 的定位：v2 可选项。** 如果家人真的需要"断网也准时提醒"或"桌面小组件"，用 Capacitor 把现有网页代码原样打进一个安卓壳，加一个本地通知插件即可，**前端代码零重写**。这不是"二选一"，而是"先把本体做好，外壳随时能加"。

> 版本参考（2026-10 核实）：Capacitor 稳定版 **8.5**，官方本地通知插件 `@capacitor/local-notifications` **8.3.1** 仍在维护。8.5 是 breaking minor（改了 iOS UIScene 生命周期），真要套壳时直接上 8.5 并跑一次 `npx cap migrate`。

### 3.3 离线优先（local-first）架构

> 这是你提出并共同定下的关键决策：**不做"纯离线"，做"离线优先 + 服务器权威"**。

**为什么不能做纯离线（数据只在浏览器里）**

| 方案 | 数据存在哪 | 清缓存 / 换手机 / 手机丢失 | 跨设备 | 演示站 |
|---|---|---|---|---|
| 纯离线 | 只在这一个浏览器的 IndexedDB | **数据全没，无法找回** | ❌ | ❌ |
| **离线优先 + 服务器（选定）** | 本地一份 + 服务器权威一份 | 服务器还在，重新登录即恢复 | ✅ | ✅ |

记账数据**不可再生**——家人记了三个月的账，清一次浏览器缓存就全丢，这个风险不能接受。

**数据流**

```
        界面操作
           │  ① 立即写入本地（IndexedDB）→ 界面立刻响应，不等网络
           ▼
     本地数据库（本机）──② 变更进入同步队列（带幂等键）
           │
           │  ③ 联网时按顺序上传
           ▼
   服务器（权威副本 + 每日备份）──④ 回执确认后标记本地记录为"已同步"
```

**四条关键设计（必须在第一批就写进表结构与接口，后补代价很大）**

| # | 设计 | 解决什么问题 |
|---|---|---|
| 1 | **客户端生成 ID**（UUID v7） | 离线记账不必等服务器分配 ID，同步天然幂等 |
| 2 | **幂等键**（每次变更一个唯一 ID，服务端记录已处理集合） | 网络重试 **不会重复记账** |
| 3 | **软删除**（删除是打标记，不是真删） | 否则离线设备会把已删除的账"复活" |
| 4 | **`updated_at` + 版本号** | 判断新旧；必要时"最后写入者获胜"并保留冲突副本 |

**会话策略（你定的，很关键）**：**同时只允许一个账号登录，且必须在线才能登录。**
这一条直接把"两台设备同时离线改同一笔账"这个最难的问题消掉了——不需要做复杂的冲突合并。

**离线时的界面提示（必须显眼）**

> 🟡 **离线模式** — 数据暂存本机，尚未同步（待同步 3 笔）。**请勿清除浏览器数据**，离线期间的数据无法备份。

顶部横幅常驻显示；同步成功后短暂显示"已同步"再收起。

**关于"本地计算是否安全"**

- **统计与金额计算放在本地完全没问题**，而且更快：金额用整数"分"，是纯函数，不会算错。
- 真正要防的是两件事：①**数据只存一份会丢**（上面的架构解决）；②**只靠前端判断权限会被绕过**（服务端仍然对每一次读写做鉴权与校验）。
- 一句话：**前端负责快，服务端负责对和安全。**

**分批交付**

| 批次 | 交付内容 |
|---|---|
| 第一批（v1 在线版） | 表结构与接口按上面的四条设计落地；网络可用时直接读写服务器；本地缓存只做"读"的加速 |
| 第二批（离线写入） | IndexedDB 本地库 + 同步队列 + 幂等重放 + 离线状态横幅 + 待同步计数 |

这样既不影响"家人尽快能用上"的时间点，也不用回头改表。

### 3.4 协作与共同记账（第三批 · 设计已定稿，尚未开发）

> **状态：定稿于 2026-10-09 08:05。** 五个关键问题已由项目所有者确认。**本节只描述设计，不写任何代码。**

**目标**

让两个人能**互相找到**，然后**一起记账**（共享同一个账本），后续还可能扩展出别的协作动作。

**为什么它能成立**

账号有了一个**可公开的纯数字编号**（8 位，如 `86818383`）。编号可以随便告诉别人，于是"找到某个人"就变成"输入这串数字"——这就是整个功能的入口。

**已定下来的五个问题**

| # | 问题 | **结论** | 理由 |
|---|---|---|---|
| 1 | 登录用什么标识 | **用户名（保持唯一）**，编号只作社交标识 | 唯一登录名 + 可重复显示名是通行做法（微信、Telegram、GitHub）；用户名好记好输，对长辈更友好；已完成的登录逻辑不动 |
| 2 | 用户名能否重复 | **不能** | 由第 1 题决定：用户名是登录凭据，必须唯一 |
| 3 | 模块叫什么 | **协作**；其中每个人叫**协作者** | 中性、正式、不暗示社交关系；比"好友"更贴合"一起记账"的语义 |
| 4 | 如何添加 | **搜索编号 → 发送申请 → 对方同意** | 看别人的账目是敏感操作，必须对方点头；代价是需要申请表与待处理提示 |
| 5 | 能否互相看见账目 | **必须加入同一账本才可见** | 分享的最小单位是**账本**而非账号；"协作者"身份本身不授予任何账目权限 |

**术语表**

| 词 | 含义 | 谁能看到 |
|---|---|---|
| **用户名** | 登录凭据，**全站唯一**，作用等同于"微信号"；也可以被搜索到 | 任何人（公开） |
| **昵称** | 应用内显示的名字，**可以重复**（等同于"微信昵称"） | 任何人 |
| 账号编号 | 8 位纯数字，随机生成，公开可分享 | 任何人 |
| 协作 | 第三批的整个功能模块 | — |
| 协作者 | 与我**互相添加成功**的人（单向申请不算） | 双方可见彼此的昵称、用户名与编号 |
| 账本成员 | 协作者中被授权访问**某一个具体账本**的人 | 该账本范围内的数据 |
| 恢复码 / 密码 | 凭据 | **永不对外** |

**搜索用什么（2026-10-09 补充决定）**

类比微信：**用户名 = 微信号**（唯一、可被搜索），**昵称 = 微信昵称**（可重复、只用于显示）。

由此决定：**搜索框同时接受「用户名」与「账号编号」**。

| 标识 | 优点 | 缺点 |
|---|---|---|
| 用户名 | 好记、好念、好分享 | **可以被猜测**（字典枚举） |
| 账号编号 | **不可枚举**（8 位随机，1 亿空间） | 需要记或存下来 |

- 想给对方什么就给什么，实现上只是一次 `OR` 查询
- 不想公开用户名时，只给编号即可
- **对策**：搜索接口必须**限流**（否则用户名枚举与编号遍历都会变得廉价）；登录本身仍由 argon2id 与失败锁定兜底

**不会变的边界**

- **编号公开，密码与恢复码保密**——编号只是"找到你"的入口，不是凭据
- **不用协作功能也能记账**；协作是可选功能，不影响单人使用
- **看见账目 ≠ 看见账号**：分享的最小单位是账本，协作者身份本身不给任何账目权限
- **任何单向动作都可撤销**：能拒绝申请、能删除协作者、能退出账本
- **编号搜索必须限流**，否则可被用来枚举账号

**技术预判（开发时细化）**

- 新表：`collaborations`（状态：待同意 / 已接受 / 已屏蔽），由申请方一侧发起
- 复用已有的 `books` / `book_members`：**共同记账 = 往同一个账本里加成员**，表结构在第一批就按可共享建好了，**不需要迁移数据**
- 服务端仍需对每次读写做鉴权：账本成员关系是唯一判据

**明确暂缓（项目所有者已确认"很后期再做"）**

- **二维码扫码添加**：把账号编号编码成二维码，扫码即发起申请，省去手输 8 位数字。方向记录在此，**当前不做**。
- 协作相关的**消息通知**（站内提醒）暂不做，先用"待处理申请"列表代替。

### 5.2 五个关键设计决策（面试会被问）

1. **金额用整数"分"存（bigint），不用 float/double。**
   浮点数无法精确表示 0.1，累加会漂移（`0.1+0.2≠0.3`）。记账软件出现 0.01 元误差就是致命 bug。所有加减在整数域完成，只在展示层格式化成 `12.34`。
2. **权限只在 `book_members` 判断，业务表全部带 `book_id`。**
   任何一次查询都必须先通过"当前用户是不是这个账本的成员"这一步，杜绝"改一下 URL 里的 id 就能看别人账本"的越权漏洞。
3. **记账日期用 `date`、系统时间用 `timestamptz`，两者分开。**
   "这笔钱是 10 月 3 日花的"和"这行记录是 10 月 5 日 14:22 创建的"是两件事，混用会导致跨时区/补记账时数据错乱。
4. **主键由客户端生成（UUID v7），并配一个幂等键。**
   离线记账不能等服务器分配 ID，所以客户端先本地生成。同步时带上 `idempotency_key`，服务端见过就跳过——**"请求超时后重试"不会变成两笔账**。这是离线优先架构能成立的前提（见 3.3）。
5. **删除一律是软删除（tombstone），永不做物理删除。**
   硬删除会让离线设备下次同步时把已删数据"复活"。软删除 + 墓碑标记才能让删除正确传播到所有副本。

### 5.3 索引与约束

- `transactions`：`(book_id, occurred_on DESC)`、`(book_id, category_id)`、`(book_id, payment_method_id)`、`(book_id, currency, occurred_on)`；`idempotency_key` 唯一索引
- `transaction_tags`：`(tag_id)`（按标签反查流水）
- `tags`：`(book_id, name)` 唯一
- `book_members`：`(user_id)`（首页要列"我参与的所有账本"）
- 约束：`amount_cents > 0`；`book_members` 主键防重复加入；外键均设级联策略
- 所有列表查询强制带 `book_id` 且分页，禁止全表扫描式查询

### 5.4 预留扩展（v2 及以后）

多账户与余额、预算与超支提醒、按汇率折算统计、定期账单（房租/订阅）、AA 结算、二级分类。这些都能通过**新增表 + 一次 Prisma 迁移**加上，不需要改动现有表结构——这正是选关系型数据库 + ORM 迁移的原因。

> **标签（tags）已从本清单移出**：按你的决定，它进入 v1。

### 6.5 鉴权与防护要点

- 会话 Cookie：`HttpOnly` + `Secure` + `SameSite=Lax`；写操作校验 CSRF 令牌（双提交）
- 登录失败：同一用户名 / IP 递增延迟 + 限流，防暴力破解
- 所有写接口限流（Fastify rate-limit）
- 上传：只允许 jpg/png/webp，做**真实内容嗅探**（不信任扩展名），大小上限 10MB，**图片只在内存中存在，识别后立即释放**

## 8. 安全与隐私

| # | 风险 | 措施 |
|---|---|---|
| 8.1 | 密码泄露 | argon2id 哈希 + 每用户独立盐；数据库泄露也无法还原明文；日志绝不打印密码 |
| 8.2 | 会话被盗 | httpOnly Cookie 存 token，且库里只存 token 的哈希；支持"退出所有设备" |
| 8.3 | 中间人窃听 | Caddy 自动 HTTPS，强制跳转；开启 HSTS 与安全响应头 |
| 8.4 | **越权访问他人账本** | 每个读/写接口先校验 `book_members`；前端传的 `user_id` 一律忽略，以会话为准 |
| 8.5 | 恶意上传 | 白名单类型 + 内容嗅探 + 大小限制 + **不落盘**（没有文件就没有可执行、可遍历、可泄露的文件） |
| 8.6 | **陌生人注册滥用** | 开源不等于开放注册：注册**必须邀请码**；对外只放**只读演示账号**（`is_demo=true`，写操作被服务端拦截，数据每日重置） |
| 8.7 | 暴力破解 | 登录限流 + 失败递增延迟 |
| 8.8 | 数据丢失 | 每日自动备份，本地 7 天 + 异地 30 天；上线前做一次**恢复演练** |
| 8.9 | 隐私 | 账目属敏感数据：不接入任何第三方统计/广告 SDK；日志不记录金额、备注、图片路径；README 写明隐私立场 |
| 8.10 | 服务器被入侵 | 只开放 22/80/443；SSH 密钥登录并禁用密码；系统与镜像定期更新；数据库不对公网暴露端口 |
| 8.11 | **密钥入库（开源项目高发事故）** | `.gitignore` 从一开始就排除 `.env`；仓库只放 `.env.example`；上线前用 `git log -p` 复查一次历史里没有密钥 |

> 一句话总结给面试官：**"钱的数据，宁可少一个功能，也不能多一个越权。"**

### 10.4 备案问题：我们走了哪条路（已核实）

**结论：不申报 ICP 备案，改为办一次「公安联网备案」。**

| 问题 | 核实结论 |
|---|---|
| 个人能做 ICP 备案吗？ | 能做（需满 16 周岁、证件住所在本省、域名持有人 = 主办人）。但官方文档明确：因国务院取消"互联网电子公告服务专项审批"，BBS 前置审批已停止办理，**"论坛网站已无法办理 ICP 备案"**——交互式站点在审核中很容易被驳回 |
| 备案的前提 | 必须有**中国内地服务器**；域名顶级域须已批复、注册商为已批复的境内机构、已实名、持有人与备案主体一致。**香港服务器不能也不需 ICP 备案** |
| 那香港就"什么都不用办"？ | ❌ **不是**。依据《计算机信息网络国际联网安全保护管理办法》，**服务器在境外但为中国内地提供服务**的，须在开通起 **30 日内**到[全国互联网安全管理服务平台](https://beian.mps.gov.cn)办理**公安联网备案**；个人可选"个人用户登录" + APP 扫码实名，主体审核约 2–3 个工作日；备案号须展示在网页底部 |
| 还有别的风险吗？ | ⚠️ 有公开案例称：**未备案域名可能被腾讯网址安全判为风险域名，在微信内被拦截**（可申诉）。这条**没有官方明文规则**，但值得预防 |

来源：[阿里云 · 公安联网备案及注销](https://help.aliyun.com/zh/icp-filing/basic-icp-service/the-public-security-network-for-record-and-cancellation)、[阿里云 · 通用网站 ICP 备案要求](https://help.aliyun.com/zh/icp-filing/basic-icp-service/product-overview/icp-filing-requirements-for-a-regular-website)

**因此本项目要落实三件事：**

1. **S7 上线后 30 天内完成公安联网备案**，并把备案号放到网站底部（页面会预留位置）。
2. **不要把链接在微信群/朋友圈传播**。给家人的正确做法：发链接时附一句"**用手机浏览器打开**"，或让家人复制到 Chrome / 系统浏览器打开。微信内置浏览器能打开网页，但存在被提示风险的可能。
3. **域名注册信息用你本人真实信息**（本来就该如此），日后真要备案时不用返工。

### 11.2 开源协议：已定为 AGPL-3.0

| 协议 | 含义 | 适用判断 |
|---|---|---|
| **AGPL-3.0（已选定）** | 别人可以自由使用、修改、分发；但只要**把它作为网络服务提供给他人使用**，就必须公开其修改版源码 | 与"开源、免费、防止被拿去做闭源生意"的定位完全一致——选了它，就没人能把 Libellum 改一改做成闭源记账服务 |
| MIT（备选） | 别人可任意使用、修改、甚至闭源商用，只需保留版权声明 | 最省心、贡献门槛最低、招聘方最熟悉；代价是放弃"防止闭源"这一层 |

**选 AGPL 需要知道的三件事（我如实说，不改你的决定）：**

1. **部分公司对 AGPL 有政策限制**：一些企业禁止在产品中集成 AGPL 代码。不过你是**独立项目作者**，招聘方看的是工程能力，这条影响很小。
2. **贡献门槛略高一点**：少数开发者会因为 AGPL 而不愿贡献代码。
3. **它反而是个能讲的故事**：面试时可以说"我选 AGPL 而不是 MIT，是因为这个工具要免费给家人和陌生人长期用，我不想有人拿它改造成闭源服务再卖——这是产品判断，不只是技术选择"。

> 如果以后想换成 MIT：只需替换仓库根目录的 `LICENSE` 并更新 README 徽章，**代码一行都不用动**。协议决定是可逆的。

### 11.5 面试高频追问（提前准备）

## 13. 项目命名

### 13.1 筛选标准（先说一个我踩过的坑）

我一开始把"GitHub 用户名是否空闲"当成硬指标，结果发现：**所有短且可发音的英文单词，GitHub 用户名几乎 100% 被占用**（GitHub 有上亿用户，短名早被抢光）。用随机字符串做对照后确认检测方法没问题——是这个标准本身不适用。

**真正要紧的只有三条：**

| 标准 | 为什么 |
|---|---|
| **域名可用**（.app / .dev / .com） | 演示站要有个好地址，家人也要好记 |
| **没有同名产品或公司** | 避免侵权与被误认 |
| npm 包名空闲 | 次要；以后若发布共享包，图个干净 |

GitHub 仓库挂在你自己的账号下（`你的用户名/项目名`），**不需要抢同名用户名**；但 **GitHub 组织名**（`github.com/orgs/xxx`）值得占，干净、免费、以后能当项目门面。

### 13.2 英文自造词方向：实测结果

（2026-10-08，两套独立 RDAP 通道交叉验证）

|---|---|---|---|---|---|---|---|
| **Naelo** | 2 音节 / 5 字母 | 自造词，柔和、国际范，像 Linear / Monzo | 空闲 | 空闲 | 已注册 | **未注册** | **未注册** |
| **Yinda** | 2 音节 / 5 字母 | 谐音"银达 / 赢达"，对中文用户最亲切 | 空闲 | 空闲 | 已注册 | **未注册** | **未注册** |
| Cendo | 2 音节 / 5 字母 | -o 结尾，金融科技味最像 Monzo | 空闲 | 空闲 | 已注册 | 已注册 | 已注册 |

### 13.3 拉丁语方向：你的想法验证结果

你提的 `liber rationum` / `liberum` 方向我做了专项核实（词典 + 同名产品 + 域名），**思路很漂亮，但 `liberum` 必须放弃**。

| 你的想法 | 核实结果 |
|---|---|
| `liber rationum` 是"账本"吗？ | **成立**。Lewis & Short 中 `ratio` 首义即"清算、账目"，复数 `rationes` 指"账目"；`liber` 亦有"登记簿、名录"义项 |
| 能说"古罗马人就这么说"吗？ | ❌ **不建议**。这个确切短语的用例主要来自 **16–17 世纪罗马法/教会法文献**，未找到古典拉丁原文用例。古罗马人实际说 `codex accepti et expensi`、`tabulae`、`adversaria`（草账）。写进 README 容易露怯 |
| `liber` 既"书"又"自由"，双关成立？ | **成立，但要说清**：这是**同形异音**——"书"是短 i（`lĭber`），"自由"是长 i（`līber`），还有第三个义项"孩子（liberi）"。属**拼写双关**而非读音双关 |
| `liberum` 做名字？ | ❌ **两条硬伤**：① 语法上它是形容词"自由"的**变格形式**（中性主格/宾格），不是词典形，单独做品牌别扭；② **五个域名后缀全被注册**，且 **Panmure Liberum 是英国受监管的投资银行**（原 Liberum Capital），另有 Liberum Wealth 等，金融领域直接撞名 |

顺带排掉的另外几个拉丁候选（都是我原本看中、核实后否掉的）：

| 候选 | 含义 | 否掉的原因 |
|---|---|---|
| **Libri** | 拉丁"书"的复数 | ⚠️ 德国 **Libri GmbH** 持有含"计算机软件"类别的英国商标，另有同名 iOS App |
| **Rationum** | 拉丁"账目"的属格复数 | ⚠️ **应用商店里已有记账 App 叫 Rationum**（EAS ERP），同类目直接撞名 |
| **Libero** | 意大利语"自由" | ⚠️ Microchip **Libero SoC** FPGA 工具链知名度高 |
| **Ratio** | 拉丁"账目、计算" | ⚠️ 已有记账 App "Ratio Money – Finance Tracker" |

**拉丁方向里唯一活下来的：Libellus / Libellum**（`liber` 的指小词，意为"小簿子、备忘账、日记账"）——检索下来**没有任何金融 / 记账类撞名**，只有一个小众开源项目与一家法国小公司。

| 名字 | 域名可用情况 | npm | GitHub 组织 | 备注 |
|---|---|---|---|---|
| **Libellum** | **`libellum.app` 未注册**（`.dev` / `.io` 也空） | 已被占 | 已被占 | 语法上是变格形式，但读音顺、域名最好 |
| Libellus | 仅 `libellus.dev` | 空闲 | 已被占 | 词典形更正统，但 `.app` 已被占 |

> ⚠️ 一个需要你知道的英语联想：英语 **libel**（诽谤）正是从拉丁 `libellus` 演变而来（小册子 → 诉状 → 诽谤文书）。美国招聘方不一定会联想，但这是这个词的阴影面。

### 13.4 定名结论：Libellum（已定）

| 方案 | 名字 | 域名 | 优点 | 缺点 |
|---|---|---|---|---|
| **✅ 选定** | **Libellum** | **`libellum.app`**（已核实未注册） | 拉丁"小簿子 / 备忘账"，与记账语义最贴；无金融类撞名；有可讲的故事（liber = 书 / 自由） | npm 与 GitHub 组织名已被占（不影响用你自己账号建仓库）；libel 的英语联想 |
| 备选 | Naelo | `naelo.app` | 短、国际范、npm + GitHub 组织 + `.app` + `.dev` 全空闲、零争议 | 自造词，无含义 |
| 备选 | Yinda | `yinda.app` | 家人一眼记住，"银 / 赢"联想 | 国际观感弱，撞一家新加坡 IT 公司 |

**定名理由（面试可以直接讲）**：拉丁语 `liber` 同时是"书"和"自由"，指小词 `libellus / libellum` 意为"小簿子、日记账"——**一个免费的、开源的小账簿，名字本身就把项目说完了**。而在 Liberum / Libri / Rationum 之间做取舍时，是**商标与同名产品排查**淘汰了另外三个。

**品牌用法**
- 正式名：**Libellum**
- 副标题（双关放这里，品牌名不必自己扛）：`Libellum — the free, open ledger`
- 域名：`libellum.app`；仓库：`github.com/<你的用户名>/libellum`

### 13.5 核实的边界（务必知道）

- `npm 404` 只代表**包名当前未被占用**，不代表一定能注册；域名实际能否购买以注册商结账页为准（本表只核实了"注册局是否已有记录"）。
- 同名产品排查基于公开检索，**不构成商标检索**。作为开源免费项目当前风险可接受；若日后商业化，需另做商标查询（可用 TMview 查英国/欧盟商标）。
- 拉丁语词义与用法核对自 Lewis & Short（Perseus 数字版）；`liber rationum` 的语料证据来自 16–17 世纪法律文献，**不是古典拉丁的常用表达**。
- GitHub 组织名 404 结果已用随机字符串对照验证检测有效。
- **正式定名前建议再复查三处**：GitHub、App Store / Google Play、TMview（商标）。

## 附录 A：术语速查（给你自己看）

| 术语 | 通俗解释 |
|---|---|
| SPA | 单页应用：打开一个网页，切换页面不刷新，像 App 一样 |
| PWA | 渐进式网页应用：网页可以"添加到主屏幕"，有图标、能离线缓存 |
| API | 后端提供的接口，前端通过这些接口读写数据 |
| ORM / Prisma | 用代码操作数据库的工具，还能生成"数据库变更记录"进仓库 |
| 迁移（migration） | 数据库结构的版本记录，换台机器能一键还原出同样的表 |
| Session | 登录凭证：服务器记住"这台浏览器是谁"，用 Cookie 携带 |
| 哈希 | 单向加密，只能验证不能还原，用来存密码 |
| CI/CD | 自动检查代码 + 自动部署，提交后不用手动发版 |
| 容器 / Docker | 把程序连同运行环境一起打包，换服务器不会"在我这儿能跑" |
| 邀请码制 | 注册需要一串一次性代码，防止陌生人白嫖你的服务器 |
| ICP 备案 | 中国大陆对境内网站的经营许可登记；服务器在香港则不需要 |
